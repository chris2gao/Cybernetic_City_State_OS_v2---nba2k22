# 决定 · 谁执行（原 D2）

**结论：沿用现有后端执行角色（Codex / Antigravity），但由工作流收窄交给它的上下文。**

裁决人：Claude Code Desktop，依人类授权。2026-07-27。

---

## 为什么不新造一个角色

现有角色**已经在生产使用且边界行为经过验证**：不推 master、不吸收他方提交、
信号里点名的产物不存在时明写"没有伪造或冒充独立审核"。
配套的任务包契约（intent / definition of done / allowed scope / stop rules / return contract）
也已实测可用。

**新造一个的收益是什么？** 只有一个：新设计要求执行者
**只看到实现方案与只读的测试，看不到测试是怎么推导出来的**。
而旧角色的上下文模型是"读该读的一切"。

## 但这个差别不需要靠换角色来解决

**角色由协议定义，交给它什么由我们定。**

工作流的阶段六派单只放：步骤拆分、冻结的测试、以及实现所需的最小信息。
**不放证据集、不放 B 的推导过程。**

这样既拿到了上下文收窄，又没有重建一个已经能用的东西。
与实现方案的原则一致：**按需移植，不重建能用的**。

## 它没解决什么

**上下文分区仍然是加载纪律，不是访问边界。**

有 shell 的执行者能读我们没给它的文件。**收窄派单消除的是污染和动机，不是能力。**

要变成真边界，得用每角色一个工作树——本仓库已有 32 个已注册工作树，
Codex 与 Antigravity 的子代理本来就各跑各的，**机制现成，只是没启用**。

这一项**单独列为待办**，不因 D2 已决而消失。

## 对下游的影响

`06_execution/` 的加载器是**加载一个外部代理**，不是驱动内部角色——
比另一条路简单，且可以直接复用现有的派单与握手格式。

## 解除的阻塞

schema 自测里 `谁执行` 标为高影响、阻塞阶段六与七。**本决定解除该阻塞。**

`run-002/A_需求建模.yml` 的未解歧义应相应更新。
