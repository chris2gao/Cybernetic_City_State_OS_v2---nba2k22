# 第二代系统 · 实现方案 v0.2

取代 v0.1。v0.1 按"依赖顺序"排，先建注册表、再建上下文、再移植机制——那是**从细节出发**。
本版改为**从骨架出发**：每个阶段实现它的核心机制，八个做完，工作流就能在测试环境跑；
之后补环境机制，即可在正常环境跑。

**原则：先立骨架，再长血肉。** 不一上来就解决一大堆细节。

---

## 一、结构

```
阶段 → 核心机制 → 实现它 → 该阶段可在测试环境跑
                                    ↓
                          八个阶段全部可跑
                                    ↓
                     补环境机制（上下文、角色分工）
                                    ↓
                             正常环境可跑
```

**每个阶段只认一件事：它的核心机制。** 实现了，那个阶段基本就能跑；
没实现，别的细节做得再全也跑不起来。

## 二、八个阶段与各自的核心机制

| # | 阶段 | 核心机制 | 现成可拿 |
| :-- | :--- | :--- | :--- |
| 1 | 需求建模 | **追问机制**——把几句话追问成立体建模 | GitHub 已有多套连续追问，挑一套改造 |
| 2 | 证据信息库 | **信息挖掘与提炼方法论** | deep research、NotebookLM、专业库 |
| 3 | 结果建模 | **解题机制**——在 问题→信息→答案 之间建立关联 | 最强模型出手；方法论后续沉淀 |
| 4 | 测试生成 | **映射→测试的生成机制** | 强模型 |
| 5 | 步骤拆分 | **拆分 + loop 停止条件** | 停止条件即阶段 4 的测试 |
| 6 | 执行 | **判断/执行分离**：判断给模型，执行给确定性 skill 与工具 | 现有 skill 与工具体系 |
| 7 | 测试执行 | **测试环境与执行机制** | 同上 |
| 8 | 完成 | 无机制——全部步骤完成且测试通过即终止 | — |

机制的操作规格在 `MECHANISM_LIST_v0.1.md`，逐条写了做什么、产出什么、现在什么状态。

## 三、实现顺序

**按阶段顺序做，1 到 7。** 理由不是形式对称，是每个机制的输入来自前一个的产出——
没有 A 就没得挖信息，没有证据就建不出 B，没有 B 和证据就生成不了测试。

**每个机制的完成标准**：该阶段能在测试环境上跑出产物。不是"设计完了"，是"跑出来了"。

**允许的粗糙**：第一版可以慢、可以手工触发、可以只覆盖主路径。
骨架的要求是**接得上**，不是好看。

## 四、环境机制：从实现过程中提取，不预先设计

上下文管理、角色分工、加载与重载——这些**不在阶段序列里预先建**。
做八个机制的过程中会不断浮现"这里需要限定上下文""这里得换个角色"，
**把浮现的问题提取出来，才是环境机制的真实需求**。

预先设计环境等于猜测需求；从实现中提取等于测量需求。

提取物落 `02_boot/`（环境与上下文）与 `06_execution/`（加载与重载）。

## 七、风险

**在跑起来之前继续设计。** 设计深度已经超过任何试过的东西，**每多设计一轮，
第一步的价值就低一分**。机制 1 能跑出一份真的需求建模，比再补三份方案有用。

**为了正确性堆细节。** 细节的成本每次执行都要付，理由的成本只在人类读时付一次。
写规格时把两者分开。

**顺手移植。** 旧系统的机制看着就想搬。旧仓库三分之一最后被发现是某一个领域的材料，
正是因为东西在没人要它的时候到达了。**按需移植，一次一个。**
