# 任务分派 v0.1

分派依据：**每个模型能看到什么别人看不到的东西。** 不按"谁更强"分，按视野分。

| 模型 | 独占视野 |
| :--- | :--- |
| Claude Code Desktop（本实例） | 设计上下文、本仓库全部改动史、今天累积的失败案例 |
| ChatGPT web | 公网 + 从 GitHub 独立读取本仓库（与本实例的读取路径不同） |
| Gemini 3.1 Pro web | 公网，deep research |
| NotebookLM | 对**给定语料**的扎根分析——它的结论只能来自你喂给它的东西 |
| Codex desktop | 本地仓库 + 执行能力，已验证的发布通道 |
| Antigravity / Gemini 3.1 Pro | 本地仓库 + 执行能力，独立工作树 |
| Opus 4.6 | 任意任务，用于需要一次强推理的地方 |

## 当前分派

### T1 · 机制 1 调研：连续追问机制

**派给：ChatGPT web 与 Gemini 3.1 Pro web，两个并行，互不知情。**

理由：这是公网检索任务，而**检索的失败模式是漏而不是错**。今天已经实测过一次代价——
一次被截断的搜索让"没有任何文档写过这个流程"成为结论，而那份文档就在仓库里。
两个独立检索无法保证完备，但**它们的差集会暴露各自的边界**，这是单次检索给不出的。

不派给我：我没有公网检索的独立视野，做这件事只是多一个同类样本。

**产出**：各自一份候选清单——项目、机制形状、可改造程度、许可证。
**合并**：由我做，重点看两份的**差集**而不是交集。

### T2 · 信息挖掘方法论 deep research

**派给：Gemini 3.1 Pro web 做检索，NotebookLM 做综合。**

理由：这两步性质不同。检索要广，Gemini 的 deep research 擅长；
综合要**扎根于给定语料而不发挥**，这正是 NotebookLM 的独特之处——
它的结论只能来自喂给它的东西，天然不会补一段听起来合理的推论。

这个顺序不能反：先有语料，才有可综合的对象。

理由之二：机制 2 在链条上的位置决定它的权重——**证据同时是 B 的依据和测试的依据**，
一处出错两处跟着错。这是唯一一个错了会同时污染答案和验收标准的环节，值得单独投入。

**产出**：信息挖掘与提炼的方法论初稿。

### T3 · D1 决策：阶段契约

**我提方案，ChatGPT 挑刺。**

理由：D1 要判断"现有的 `CODEX_TASK_INPUT_CONTRACT.md` 是否适配我设计的工作流"。
**我设计了工作流，由我判断它适配什么，是在评自己的推导。**
今天这个形状已经出现过三次，每次都是靠另一方抓住的。

所以我给判断和理由，ChatGPT 从 GitHub 独立读那份契约再驳。它今天驳对过两次
（required_refs 不存在、根因表述过松），这个配合是有记录的。

### T4 · D2 决策：谁执行

**我决定，不外派。**

理由：这是关于**我们自己这套模型班子**的架构判断——谁有执行通道、谁有发布权限、
哪些已验证过。这些事实我手上最全，外部模型没有独立视野可加。

### T5 · 机制 1 实现

**待 T1 合并后再派。** 候选定了才知道是"改造现成"还是"自建"，
两者派给的对象不同——前者偏执行（Codex 或 Antigravity），后者偏设计（Opus 4.6）。

## 我不派给自己的三类

1. **公网检索**——没有独占视野，只是多一个同类样本。
2. **对我自己设计的评审**——今天三次都靠他方抓住。
3. **需要独立发布通道的执行**——Codex 的通道已验证，我的刚开通且未经检验。

## 我保留的

**架构决策、任务分派、跨轮次的一致性核对、以及合并他方产出时看差集。**
最后一项是我的独占价值所在——我手上有今天全部的失败案例，
知道哪一类差异是信号、哪一类是噪音。
