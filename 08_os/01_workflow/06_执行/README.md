# 06 · 执行

按步骤实现，逐步验证。

## 核心机制

**判断 / 执行分离。**

> **判断交给模型，具体开发与执行交给确定性的 skill 和工具。**

数值计算、调用外部工具产生确定性结果——这类事不由模型自己做。

**这是"确定性"问题的真答案，比任何流程约束都有效。**
流程约束是要求模型不要出错；判断/执行分离是让模型不必在那些地方正确。

## 输入 / 输出

- 输入：步骤拆分、冻结的测试
- 输出：实现

## 上下文约束

执行实例（角色 e）拿到的是：**实现方案，以及只读的测试**。
它**看不到测试是如何推导出来的**。

执行实例的活动加载面不包含测试推导过程；测试只读是角色契约的一部分。

**加载纪律不是访问边界。** clone/worktree 只构成 `workspace_partition`；
有 shell 的实例仍可能读取兄弟目录。需要技术拒绝时必须使用经过正负例验证的
`enforced_access_boundary`。完整规则引用
`../../03_mechanisms/context_management/文件隔离与产物生命周期_v1.md`。
活动 D2 裁决见 `../../_dev/决定_谁执行_v0.2.md`。

## 分区盖不住的

**对测试过拟合。** 不碰测试，也能只满足测试的字面而非意图。
这不是篡改，是测试作为不完备规格的固有性质。

对策在阶段七：**审核核的是实现对 B 与证据，不只是套件绿不绿。**

## 已决

**谁执行（D2）**——沿用现有后端执行角色（Codex / Antigravity），由工作流收窄派单
与加载面。收窄派单和 worktree/clone 只提供 `workspace_partition`；技术拒绝只能由
经正负例验证的 ACL、容器、受限 tool root 或网关提供。

## 最小运行状态

`实现/最小运行schema_v1.yml` 与统一 runner 已实现执行者身份、精确写入 allowlist、实际写入集合、
冻结测试摘要、逐步骤尝试记录和未授权写入拒绝。每个步骤必须有完整且连续的尝试记录，最终以
`pass` 结束；预算耗尽或 `invalidate_upstream` 不能伪装成完成。

执行内容仍由后端模型与确定性工具产生；当前最小控制面不构成 ACL、容器或受限 tool root，
也不把声明的 allowlist 冒充技术访问边界。
