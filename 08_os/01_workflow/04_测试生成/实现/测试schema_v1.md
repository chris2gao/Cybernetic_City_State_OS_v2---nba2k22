# 测试程序 · schema v1

与 A、B 同构：结构化对象 + 程序校验。**校验不过就不是合法测试。**

---

## 结构

```yaml
凭证选择记录:
  # 从描述性证据到规定性测试那一步的人类判断。整份测试程序共一条
  # 没有这条，整份测试非法——这一步不可省略，见方法论第二节
  type: object
  必填: true
  裁定人: string          # 谁做的判断
  时间: date
  依据证据: array         # 基于哪些证据做的这次选择
  选定属性: array         # 判定哪些属性重要
  为何是这些: string      # 而不是别的
  度量选择: string        # 怎么衡量
  容差: string            # 误差容忍多少，以及为什么是这个数

测试:
  type: array
  最少条目: 1
  每条:
    描述: string

    被测主体: string      # 指向 B 的某条 `实现方法` ID。**非空**
    # 测什么——来自 B

    判据来源: array       # 证据 ID。**非空，且不得指向 B 的任何内容**
    # 什么算通过——来自证据

    测量方法: string      # **非空**。具体怎么测
    通过判据: string      # 什么结果算通过
    可失败: bool          # 必须为 true

    对应成功判据: string   # A 里的哪条成功判据。**非空**
    类型: "事实核对 | 行为验证 | 边界检查 | 一致性检查"

方法资格:
  # Daubert 五要素，筛的是测试生成方法不是单条测试
  type: object
  可测试性: string
  同行评审: string
  已知错误率: string      # v1 允许 "未量化"，v2 用变异测试给数
  操作标准: string
  普遍接受度: string

实现前检查:
  type: object
  约束可满足: "是 | 否 | 未检查"     # v1 允许"未检查"，靠人工推演
  边界僭越: array                  # B 是否假定能控制边界外的东西。空数组 = 无
```

## 跨字段校验

1. **`凭证选择记录` 必须存在且完整** —— 缺则整份测试非法
2. **每条测试的 `被测主体` 必须能在 B 的 `实现方法` 中找到** ——
   测了 B 没主张要做的东西，测的是别处
3. **每条测试的 `判据来源` 非空，且不得指向 B 的任何内容** ——
   **这一条是整套设计的关键校验**，理由见下
4. **每条测试的 `测量方法` 非空** —— "测一下"不是测量方法
4. **每条测试的 `可失败` 必须为 true** —— 见下
5. **每条测试的 `对应成功判据` 必须能在 A 中找到** ——
   测了却不对应任何成功判据的测试，测的是别的东西
6. **`实现前检查.边界僭越` 非空时，必须逐条说明如何处置**

## 被测主体来自 B，判据来源来自证据

这是"测试由证据推导"的**精确形式**。原来的说法不够准：

一个测试当然要测 B 里的东西——脚本、prompt、配置都在 B 里。
**自我循环的风险从来不在"测 B 里的东西"**，
而在**用 B 自己的说法当通过判据**——那才是同一套推理既出题又判卷。

| | 来自 |
| :--- | :--- |
| **测什么**（被测主体） | **B** 的实现方法 |
| **什么算通过**（判据来源） | **证据** |

**例：**

- B 说"用 Python 脚本算 X" → 被测主体 = 那个脚本；
  判据来源 = 证据里"正确公式是什么"或"已知输入 Y 应得 Z"
- B 说"写一个 prompt 做 Z" → 被测主体 = 那个 prompt；
  判据来源 = 证据里对该行为的记载或规定

**校验第 3 条拦的就是这个**：判据来源一旦指向 B，测试就退化成自证。

## 按类型决定怎么测

B 的每条实现方法带 `类型`，类型决定测法：

| 类型 | 怎么测 |
| :--- | :--- |
| 脚本 / 代码 | 已知输入输出的用例，输出对照证据里的正确值 |
| prompt / skill | 加载后实际运行，输出对照证据里规定的行为 |
| 配置 | 加载后检查生效状态对照证据里的预期 |
| 文档 / 流程 | 按文档执行一遍，结果对照证据里的预期产出 |

**v1 只要求写明测法，不要求自动化。**
`prompt / skill` 那一行的具体做法（LLM 评测）属活跃领域，
**值得单独调研**，归入机制 6/7 的工具选型。

## 为什么强制 `可失败: true`

**一条不可能失败的测试，不携带任何信息。**

它形式上满足所有溯源要求——有证据 ID、有测量方法、挂在成功判据上——
却在任何实现下都通过。这类测试在压力下会大量出现，
因为它们**让套件变绿而不需要实现做对任何事**。

写这一栏时要能回答：**什么样的实现会让这条测试失败？** 答不出就是不合格。

## 为什么 `对应成功判据` 必填

它把测试锚回 A，而不是锚在 B 上。

**测试的合法性有两个锚点**：来源锚在证据（`证据ID`），目的锚在需求（`对应成功判据`）。
两个锚点都不经过 B——这是"测试由证据推导"在结构上的落实，
不是文档里的一句规定。

## v1 不做的

- `已知错误率` 允许 `未量化`（v2 用变异测试）
- `约束可满足` 允许 `未检查`（v2 接 SMT）
- FactScore 支撑密度不进本 schema，只作参考
