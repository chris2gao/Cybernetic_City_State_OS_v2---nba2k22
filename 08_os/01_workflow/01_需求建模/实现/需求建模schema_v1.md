# 需求建模 A · schema v1

**槽位按下游需要什么来定，不按需求属于哪个领域来定。**

`spec-kit` 的九类分类法是为软件规格设计的（数据模型、UX 流、可观测性……），
而本工作流的需求可以是任何东西。照搬会得到一堆对非软件需求永远为空的槽位——
**而永远为空的必填槽位会让停止条件永远不满足。**

---

## 八个槽位

| 槽位 | 必填 | 下游谁要它 |
| :--- | :--- | :--- |
| `目标` | ✓ | 全部 |
| `成功判据` | ✓ | **阶段四**——测试最终要追溯到这里 |
| `边界` | ✓ | 阶段三——B 不能超出边界 |
| `约束` | ✓ | 阶段三、五 |
| `术语` | ✓ | **本阶段自己**——"双方指同一件事"靠它 |
| `关联领域` | ✓ | **阶段二**——直接就是它的步骤 1 |
| `假设` | ✓ | 阶段二——每条假设都是一个待验证项 |
| `未解歧义` | ✓（可为空数组） | 阶段二、三 |

**每个槽位都有下游消费者。** 没有消费者的槽位不要加——
它只会增加追问轮数而不改变任何后续判断。

## 定义

```yaml
目标:
  # 一句话：要达成的可观察结果。不是"做一个X"，是"使得Y成立"
  type: string
  非空: true

成功判据:
  # 什么情况下我们认为目标达成了。阶段四的测试全部要能追溯到这里
  type: array
  最少条目: 1
  每条:
    描述: string
    可观察: bool     # 必须为 true。不可观察的判据无法生成测试

边界:
  # 明确不做什么。空数组不合法——"什么都做"不是边界
  type: array
  最少条目: 1

约束:
  # 技术、资源、时间、政策等硬限制
  type: array
  允许为空: true    # 确实可能没有硬约束

术语:
  # 本需求中含义需要固定的词。双方所指相同，靠这一项承载
  type: array
  每条:
    词: string
    含义: string
    别名: array      # 出现过但应统一掉的说法

关联领域:
  # 这个需求牵涉哪些领域。直接作为阶段二步骤1的输入
  type: array
  最少条目: 1
  每条:
    领域: string
    为什么相关: string

假设:
  # 当前推理依赖但尚未验证的东西。阶段二逐条验证
  type: array
  允许为空: true
  每条:
    假设: string
    如果不成立会怎样: string    # 必填。不写这条，假设就只是一句话

未解歧义:
  # 追问结束时仍未解决的。允许非空——
  # 强行清零会逼出编造的答案，那比留着歧义更糟
  type: array
  允许为空: true
  每条:
    歧义: string
    为何未解: string
    影响: string
```

## 跨字段校验

停止条件不只是"必填项都有值"，还要过这几条：

1. **每条 `成功判据` 的 `可观察` 必须为 true**
   ——不可观察的判据到阶段四生成不出测试
2. **`未解歧义` 里 `影响` 为"高"的条目，不允许存在**
   ——高影响歧义未解，说明还没问完
3. **`目标` 中出现的关键词，应在 `术语` 中有定义**
   ——这是"双方指同一件事"最直接的机械近似
4. **`假设` 每条必须有 `如果不成立会怎样`**

**这四条就是提问生成器的来源。** 校验失败时，
`ValidationError` 指出的是哪条不满足，直接转成下一个问题。

## 为什么允许 `未解歧义` 非空

**强行清零会逼出编造的答案。**

一个诚实标注的"这里还不清楚，影响中等"，比一个模型为了通过校验而编的答案有用得多——
后者会一路流到证据收集和结果建模，而且**没有任何东西会标记它是编的**。

所以校验只拦"高影响"歧义，不拦全部。

## v1 不做的

- 不做嵌套 schema、不做条件必填（`if 领域=X then 必填 Y`）
- 不做 schema 版本迁移
- 术语的"关键词提取"用最朴素的做法，不做语义匹配

**先能跑。这些留给 v2。**
