# 需求建模 · 方法论 v0.1

把几句话的需求，通过追问变成结构化建模 A。

**完成条件不是"问够了"，是 schema 填满且人类确认双方所指相同。**

设计依据全部来自 run-001 的实测调研，出处见文末。

---

## 一、核心结构：schema 一物三用

```
Pydantic / JSON Schema
   ├── 是产物         ——  A 本身就是这个对象
   ├── 是停止条件     ——  必填槽位齐全且跨字段校验通过 = 停
   └── 是提问生成器   ——  ValidationError 解析出缺什么，直接转成下一个问题
```

这是本机制的承重设计。**它把"何时停"和"该问什么"合成了一件事**——
不是先判断该不该继续，再另想问什么，而是**校验失败本身携带了下一个问题**。

## 二、循环

```
用户输入
   ↓
模型解析 → 更新 schema 对象
   ↓
程序校验（不是模型判断）
   ↓
校验通过？──是──→ 人类确认 ──是──→ 完成
   │否                        │否
   ↓                          ↓
ValidationError 解析      指出哪里不对 → 回到解析
   ↓
按 Impact × Uncertainty 排序
   ↓
一次问一个问题
   ↑___________________________|
```

### 三条硬规则

**一、程序校验，不是模型判断。**
调研实测出一个现象，Gemini 称之为**懒惰延迟（Lazy Deferral）**：
大模型会**单方面把关键模糊点推迟**，在非标准路径下甚至不提问直接生成。

所以**"要不要继续问"这个判定权不交给模型**。
每轮之后由程序检查必填槽位与校验约束，**不管模型说了什么**。
模型不能结束循环。

**二、一次问一个。** 不批量抛问题。
多选题给 2–5 个互斥选项，或限定"5 词以内"的短答。

**三、答案立刻回写结构化对象，不留在对话里。**
`spec-kit` 的做法是每接受一个答案就原子化写回文件——
这一条要保留，但**把 markdown 锚点覆写换成 JSON 对象更新**（见第四节）。

## 三、提问优先级

缺失槽位不是按顺序问，按 **Impact × Uncertainty** 排。

- **Impact**：这个槽位空着，会不会实质影响下游的证据收集、结果建模或测试生成
- **Uncertainty**：当前已知信息对它的约束有多弱

不影响下游的模糊点**不问**——它属于后续阶段，或根本不重要。

## 四、schema 的形状

见 `实现/需求建模schema_v1.md`。

**关键选择：不照搬 `spec-kit` 的九类分类法。** 那套是为软件规格设计的
（数据模型、UX 流、可观测性……），而本工作流的需求可以是任何东西。

我们的槽位按**下游需要什么**来定，不按需求的领域来定。

## 五、评估

借用 ReqElicitBench 的**指标**，不跑它的完整基准——
完整环境需要 101 个场景 + LLM 模拟甲方 + LLM 裁判，API 成本很高。

离线取两个指标：

- **IRE 隐性需求发掘率**——追问挖出了多少用户没主动说的东西
- **TKQR 关键问题回合效率**——问到关键点用了几轮

## 六、v1 明确不做的

- **不追求"认识论意义上的停止判据"。** 全世界目前都只有启发式，
  我们用 schema 填满这个机械判据，**它是武断的，但它是可判定的**。
  真判据与阶段二的"何时停止收集信息"是同一个问题，合并研究，不在本机制内解决。
- 不做本体树、不做信念状态机。

## 七、继承与淘汰（来自对话系统时代）

| 继承 | 淘汰 |
| :--- | :--- |
| 状态机 + 必填槽位 | 僵化本体模型 |
| **收集状态与下游执行严格解耦——不填满不放行** | 硬编码 NER 字段映射 |
| | 逐个提问的话术模板 |

被淘汰的三项是被大模型的零样本语义理解取代的；
**保留的控制流设计在 LLM 时代依然有效，而且正是"程序校验不交给模型"的来源。**
