两份深度调研报告（ChatGPT 与 Gemini）在对需求追问机制、底层架构设计以及学术评测工具的分析上，得出了高度一致的结论。以下是这两份报告中共同确认的核心结论：

### 1. 关于 github/spec-kit 中 `/clarify` 命令的评估与剥离
* **核心机制极具价值，但无法直接作为独立组件“开箱即用”**：两份报告都指出 `/clarify` 的提问逻辑（基于分类树的覆盖率扫描、启发式优先级排序、一次只问一个问题、即时原子化覆写更新）是非常优秀的。但它在工程上与 Spec Kit 自身的运行时环境（如 `check-prerequisites` 脚本解析的文件路径）、项目宪章（Constitution）以及特定的 Markdown 模板锚点深度耦合。
* **剥离复用的正确路径是“替换为结构化 JSON”**：如果要将其提取为纯代码后端服务，两者均认为必须抛弃基于 Markdown 文本锚点的文件覆写机制，将其替换为对标准化 JSON 对象或数据模型的更新。
* **不能完全将“是否需要追问”的判定权交给大模型**：ChatGPT 报告中提到在非标准路径下模型会出现未提问直接生成动作等乱象，而 Gemini 报告详细指出了这一现象为“懒惰延迟（Lazy Deferral）”，即大模型容易单方面将关键模糊点推迟，因此必须引入外部强制的规则拦截。

### 2. 关于“何时算填完”的机械化停止条件
* **拒绝依赖大模型的主观判定，必须使用 JSON Schema / Pydantic 进行确定性校验**：两份报告得出一致结论，解决“何时结束追问”最稳健的方案是引入机械化的验证器。将 Pydantic 或 JSON Schema 作为唯一事实来源，只有当所有必填字段（Required Slots）存在且校验（包括跨字段依赖）完全通过时，才算满足停止条件。
* **由验证错误（Validation Errors）直接驱动下一轮发问**：两者都推崇一种“校验 - 失败 - 追问”的闭环系统架构。系统应收集 Pydantic 抛出的 `ValidationError`（或 jsonschema 的错误树），通过程序解析具体是哪个字段缺失或类型错误，将其转化为高优先级的提示词，强制大模型围绕这些具体缺陷向用户提问。

### 3. 古典对话系统（Rasa / Dialogflow）的遗产继承
* **状态机与“必填槽位”思想依然是现代架构的核心**：两份报告都考察了 Rasa 的 Forms/required_slots 以及 Dialogflow 的必填参数和状态机（如 `$page.params.status = "FINAL"`），并得出一致结论：这种将“需求收集状态”与“下游任务执行”严格解耦、不填满必填项就不放行的控制流设计，在 LLM 时代依然极其有效且必须保留。
* **僵化的本体模型和硬编码实体提取已被淘汰**：传统的意图分类、强依赖 NER（命名实体识别）的字段映射以及硬编码的逐个提问话术模板，已经被大模型的零样本语义理解和上下文归一化能力彻底淘汰，不应再被继承。

### 4. 针对 ReqElicitGym / ReqElicitBench 评测基准的借用策略
* **基础设施较重，模拟甲方的 Oracle User 成本高昂**：两者都注意到该基准包含了 101 个应用场景，并且强依赖于大模型驱动的“模拟客户（Oracle User）”与“任务裁判（Task Evaluator）”，完整运行会导致极高的 API 调用成本。
* **推荐“降维解耦借用”的评测策略**：两份报告都建议，对于内部系统研发，不需要运行完整的自动化评测环境。只需借用该项目的核心数据集（初始需求与对应的“黄金隐藏需求集”）以及核心评分指标（如隐性需求发掘率 IRE、关键问题回合效率 TKQR），结合自有对话日志或人工测试进行离线效果评估即可。
