# 阶段二本机默认分区运行试验 v1

## 1. 结论

任务 `context-stage2-local-partition-001` 已在 Windows 本机、非管理员进程中完成。
本轮证明的是当前正常工具路径上的机械可行性，不是生产级隔离或模型质量提升。

| 实验 | 状态 | 结论 |
|---|---|---|
| ENV-01 | `passed` | 环境能力已记录；当前 shell 和文件工具路径不受限，进程未提升。 |
| PART-01 | `failed` | 三个独立 clone 能完成角色工作流，但 executor shell 成功读取 planner 兄弟目录 sentinel，因此 clone 不是访问边界。 |
| BOUND-01 | `passed` | 临时目录上的 Windows DACL 能让授权读取成功、越界读取失败；最终运行能无提权移除 deny 并清理。 |
| RESTORE-01 | `passed` | 新 executor 进程只读取固定入口列出的 3 个授权引用，完成确定性求和步骤。 |
| HANDOFF-01 | `passed` | planner → executor → reviewer 闭环完成；上游内容哈希变化后，旧 executor 和 reviewer 入口均确定性变为 stale。 |
| SIZE-01 | `passed` | 三类输入包均完成文件数、UTF-8 字节数和字符数统计；本机无现成 tokenizer，未伪造 token 数。 |

`PART-01=failed` 是本任务要求暴露的真实负例，不是脚本故障。它否定“clone/worktree
能够构成同一不受限 shell 的访问隔离”，但不否定其作为默认加载与工作区组织分区的价值。

## 4. PART-01 · 任务与角色工作区分区

### 4.1 可运行部分

脚本在系统临时目录中：

1. 建立一个本地 bare Git 源和 seed repository；
2. 建立 planner、executor、reviewer 三个独立 clone；
3. 每个角色写入自己的未跟踪 `private/sentinel.txt`；
4. 每个角色只显式暂存 `published/` 下的 handoff 或正式产物；
5. planner、executor、reviewer 依次提交、拉取和发布。

角色 clone 耗时：

- planner：183.108 ms；
- executor：169.793 ms；
- reviewer：234.241 ms。

关键 Git 操作全部退出 0。planner handoff push、executor handoff push 和 reviewer
verdict push 分别约为 208.699 ms、352.557 ms 和 269.615 ms。

### 4.2 必须保留的失败结论

从 executor clone 作为当前工作目录启动同一不受限 Python shell，直接给出 planner
兄弟 clone 的精确 sentinel 路径。读取退出码为 0，耗时 73.334 ms。

因此：

- `workspace_workflow_status: passed`；
- `access_boundary_status: failed`；
- PART-01 总状态按访问边界目标记为 `failed`。

clone/worktree 只能提供目录、Git 状态和默认加载面的组织分离。若同一模型仍持有不受限
shell 或文件工具，它可以主动读取兄弟角色目录；不能把这一结构包装成“角色不能直接读取
其他角色私有区”已经技术实现。

原始记录：`results/partition.json`。

## 5. BOUND-01 · 可用边界原语抽查

当前进程非管理员，Windows 已有 `icacls.exe`，所以选择临时目录 DACL 作为成本最低的
现成原语。最终运行只拒绝当前 SID 的 `RD`（read data/list directory），不拒绝 DACL
管理权限。

| 检查 | 退出码 | 结果 |
|---|---:|---|
| 授权目录读取 | 0 | passed |
| 安装临时 read-data deny | 0 | passed |
| 越界目录文件读取 | 1 | passed（按预期被拒绝） |
| 移除 deny | 0 | passed |
| 权限恢复后再次读取 | 0 | passed |

这说明 DACL 可以约束正常读取路径，但边界有限：

- 目录所有者仍可主动改变 DACL；
- 它不抵御宿主机管理员或恶意自修改；
- 它不等于容器、受限工具网关或零信任沙箱；
- 当前结果只适用于本机、当前主体和受测文件操作。

### 5.1 早期失败运行的残留

早期版本错误地使用复合 `R` deny，其中包含会妨碍 ACL 恢复的控制权限。三种非提升恢复
方法均被 Windows 拒绝，已按三次失败规则记录到 `~/.codex/FAILURE_LOG.md`。

截至报告生成时有两个合成实验目录残留，均位于系统临时根：

1. `<SYSTEM_TEMP>/context-stage2-local-partition-cpyg8rmj`：复合 `R` deny 的目录壳；
   `Set-Acl`、`SetNamedSecurityInfoW` 和按已知子项删除后移除目录三种方法均返回 access denied。
2. `<SYSTEM_TEMP>/context-stage2-local-partition-o8yfoa81`：较早中断运行的普通实验树；
   批量清理在前一锁定项处停止，后续精确递归删除被当前宿主命令策略拒绝执行。

两项只含脚本生成的合成 Git 数据，不含仓库私有内容、凭证或用户资料。后续成功运行使用
可逆的 `RD` deny，自己的临时树已完整清理；脚本不会继续制造同类残留。

原始最终运行记录：`results/boundary.json`、`results/run_summary.json`。

## 6. RESTORE-01 · 固定角色入口恢复

executor 固定入口至少记录：

- `task_id`、`role`、`current_step`、`status`；
- `todo`、`blockers`、`input_version`；
- 每个授权引用的相对路径与精确 SHA-256；
- dependency、结果输出路径和 stale 输出路径。

写入入口后，编排脚本清空入口和 planner handoff 的进程内对象并执行垃圾回收。随后用
Python `-I` 启动新 executor 进程，只继承 `SYSTEMROOT/WINDIR/TEMP/TMP` 和 Python
编码变量，不继承自定义任务环境。

新进程只读取：

1. `published/planner_to_executor.json`；
2. `fixtures/authorized_input_v1.json`；
3. `fixtures/test_spec_v1.json`。

它未读取 planner/reviewer 私有文件，完成 `3 + 4 + 5 = 12` 的确定性步骤，结果与 test
spec 一致。新进程退出码 0，耗时 98.506 ms。

这里“只读取”由受测 worker 的显式 allowlist 和 read-path 记录证明；由于 PART-01 已证明
OS shell 不受限，它不是不可逃逸的安全保证。

原始记录：`results/restore.json`。

## 7. HANDOFF-01 · 结构化交接闭环与 stale

### 7.1 最小闭环

1. planner 发布 v1 handoff，绑定输入与 test spec 的精确哈希；
2. executor 拉取 handoff，通过固定入口恢复，发布 implementation、test result 和
   executor-to-reviewer handoff；
3. reviewer 新进程只读取 executor handoff、test spec 和 implementation，给出
   `accept` verdict；
4. reviewer 不读取 executor 私有日志、planner 私有 sentinel 或完整执行过程。

reviewer 新进程退出码 0，耗时 106.533 ms。三个发布步骤和消费步骤均退出 0。

### 7.2 确定性失效

planner handoff 从 v1 修改为 v2：

- v1 SHA-256：
  `d6fe8cf563117fc7dab207476f0b4d24f2ee57efba4188a15ac44343faaf9661`
- v2 SHA-256：
  `c33098b5ce368192a0c5aba1972bd20296c1acb598f69b27b25a22b9b20ba290`

executor 和 reviewer 保留的旧入口依赖 v1 哈希。更新工作区后，确定性 checker 比较实际
内容哈希：

- executor entry：`stale: true`，退出码 0；
- reviewer entry：`stale: true`，退出码 0。

stale checker 是系统确定性依赖检查，不把 planner handoff 正文注入 reviewer 的审核
上下文。规划角色仍需决定从哪个阶段重跑；哈希检查本身不做语义重跑裁决。

原始记录：`results/handoff_and_stale.json`。

## 9. 修复记录与适用边界

第一次脚本运行暴露角色发布 helper 使用 `git add --all`，会把 planner 私有 sentinel
发布并覆盖其他 clone 的同名私有文件。实现已改为每个角色只显式暂存正式 handoff/产物，
随后闭环通过。这个失败说明“目录名叫 private”没有任何发布保护，显式 publish allowlist
是必要机制。

ACL 最终实现从复合 `R` deny 收窄到 `RD` deny，最终运行安装、拒绝读取、移除和恢复读取
均通过。早期残留如第 5.1 节记录，不把清理失败隐藏在最终成功运行之后。

本报告不支持以下外推：

- clone/worktree 已实现访问隔离；
- 当前 DACL 方案可抵御有意绕过；
- 体积缩减等于模型表现改善；
- 本地结果证明 Web 模型远程仓库生命周期成本可接受；
- 该试验已完成生产机制设计或部署。

## 10. 对阶段二和机制 3 的交接

当前本机证据支持下列 B 建模边界：

1. 用独立任务/角色工作区组织默认加载面是可行的，但必须与 enforced access boundary
   分开命名和验收。
2. 正常路径若需要技术读取约束，可叠加可逆 DACL 或受限工具接口；本试验不足以选择生产
   边界方案。
3. 每个角色入口应固定、结构化、原子更新，并绑定授权引用与精确内容哈希。
4. 私有区必须在 Git 发布层使用显式 allowlist；不能依赖目录命名或模型承诺。
5. handoff、implementation、test spec 和 reviewer input 可以形成小型、可恢复、可失效的
   闭环。
6. context-volume proxy 支持继续验证最小包，但模型质量和补充成本仍是未证命题。

任务状态为 `completed_with_blockers`：核心实验与耐久产物完成；剩余 blocker 仅为一个
ACL 锁定的早期合成目录壳及一个被宿主命令策略阻止删除的普通早期临时树。它们不改变最终
运行结论，但若要求物理清零，需要新的宿主权限或 Human 清理决定。
