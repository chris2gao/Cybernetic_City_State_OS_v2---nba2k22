## A. 发给 Gemini 3.1 Pro web · Deep Research

下面整段发送。Gemini 不读取 ChatGPT 的结果，两条路线互不知情。

### 请求正文

我们正在为一套新的多模型协作 OS 研究“上下文管理机制”。

需求目标不是建设抵御恶意攻击的零信任沙箱，而是：

- 一个完整需求从开始到结束能够被耐久追踪，不依赖模型持续保留聊天记忆；
- 规划、执行、审核等独立角色默认只获得完成自己职责所需的上下文；
- 不同任务、不同角色的私有工作信息默认不混合；
- 角色之间只通过结构化交接产物通信；
- 信息不足时可以提交结构化申请，批准后获得最小补充；
- 新模型实例能从固定入口恢复本角色有效状态；
- 上游产物版本变化后，依赖旧版本的下游上下文失效；
- 任务完成后保留系统事实，删除无长期价值的私有过程；
- 第一版只支持当前本地开发环境，并以一个真实小型 OS 开发任务闭环验证。

请做一次独立 deep research。不要推荐“最好的方案”，我们需要可供下一阶段建模的证据与候选机制空间。

### 研究问题

#### 定向核实题

1. 无关信息、过长上下文或相关信息位置变化，是否会显著降低大模型任务表现？适用边界是什么？
2. GitHub 的权限粒度是否支持按任务、按角色建立受限交接空间？个人仓库与组织仓库有什么关键差异？
3. 当前主流 agent 框架是否支持跨会话状态持久化、结构化 handoff 和输入历史过滤？默认行为是否会暴露完整历史？

定向核实题看独立来源是否一致，不计算捕获-再捕获覆盖率。

#### 开放发现题

4. 现有 agent 系统有哪些机制模式用于：角色专用上下文、结构化交接、跨会话记忆、固定恢复入口、上下文压缩与按需检索？
   - 捕获单位：**机制模式**，不是论文数或产品数。
5. 在本地代码协作环境中，有哪些低成本机制可实现任务与角色的默认工作区分区，并限制正常工具读取路径？
   - 至少考虑 Git worktree/clone、目录权限、容器或沙箱、受限工具网关、临时仓库/交接包。
   - 捕获单位：**隔离机制**。
6. 现有工作流或 agent 系统有哪些模式用于：产物版本依赖、checkpoint、上游变更后的下游失效、恢复与 retention？
   - 捕获单位：**版本与失效模式**。

### 证据目标

请主动寻找会推翻或限制该需求的材料，例如：

- 最小上下文导致信息不足和反复补充，成本高于收益；
- 多代理 handoff 丢失关键语义或默认共享全部历史；
- 角色入口无法替代完整事件日志；
- 工作区分区无法限制模型的 shell 或工具；
- 每任务、每角色仓库的创建授权清理成本过高；
- checkpoint 与长期记忆无限增长；
- 版本失效传播需要过重的依赖图。

只报成功案例的答案不合格。

### 信源优先级

1. 同行评议论文、作者论文页；
2. 官方框架文档与官方仓库；
3. 官方工程复盘；
4. 真实 issue、失败报告和维护记录；
5. 二手综述仅作线索，不作为关键结论的唯一依据。

软件能力优先 2024–2026 的当前资料；基础研究可使用更早的一手论文。

### 每条证据必须给出

- 证据 ID；
- 支持或推翻的具体主张；
- 一手来源与日期；
- 信源可靠性；
- 本条信息可信度；
- 适用边界；
- 对结果建模 B 可能产生的约束；
- 是读到的事实还是你的推断。

### 必须报告检索边界

- 你使用了哪些查询与检索路径；
- 哪些方向返回为空；
- 哪些结果被截断或受付费墙限制；
- 哪些重要来源无法访问；
- 给出**完整机制清单**，不要自行裁剪成“最值得关注”的几项。

不要读取或猜测另一条 ChatGPT 检索路线的结论。
