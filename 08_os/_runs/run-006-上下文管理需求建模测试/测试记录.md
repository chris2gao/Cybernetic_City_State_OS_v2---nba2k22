# run-006 · 上下文管理机制需求建模测试

## 目的

用一个将继续贯穿第二代 OS 后续阶段的真实需求，验证机制 1 是否能把初始自然语言需求转化为可被阶段二直接消费的结构化需求模型 A。

本次真实需求：开发第二代 OS 的上下文管理机制，使不同独立工作角色默认获得不同上下文，并能跨会话追踪任务。

## 耐久产物

- A：`../../01_workflow/context-management-mechanism/requirement/A_需求建模_v1.yml`
- 人类确认：`../../01_workflow/context-management-mechanism/requirement/人类确认_v1.yml`

这两个文件共同组成阶段一的 `requirement/` 产物包。

## 结果

- schema 八类内容均形成可消费信息：目标、成功判据、边界、约束、术语、关联领域、假设、未解歧义。
- 人类明确确认：A 准确表达了真实需求。
- 阶段二可以直接从 `关联领域` 与 `假设` 开始收集证据。
- 具体隔离技术、角色最终名单和 Web 交接成本被诚实留作未解歧义，没有提前伪装成已定方案。

结论：**机制 1 的核心建模方向有效，本实例阶段一完成。**

## 本次测试发现的问题

### 1. “一次一问”造成交互轮次过多

原方法将“一次一问”作为硬规则。本次真实需求涉及多个相互关联的槽位，单问题轮次产生了明显的交互成本与 token 消耗。

问题不在于问题数量本身，而在于：

- 每个低耦合选择都单独占一轮；
- 用户必须反复等待并回复单个选项；
- 大量状态回显重复消耗 token；
- 机制容易从需求建模逐渐滑向方案设计，却没有阶段性批量检查点。

### 2. 术语需要允许在追问中被纠正

初始对话把目标称为“强访问隔离”。继续追问后确认，真实目标是降低无意上下文污染、误读和注意力漂移，并允许经过审批的有意越界；不是建设抵抗恶意模型的零信任沙箱。

这证明术语槽位不仅用于补定义，还必须允许覆盖此前错误理解，并把旧说法保留为别名，而不是继续沿错误词义向下设计。

### 3. 人类确认必须成为耐久产物

工作流机制规定阶段一完成需要人类确认，但原 schema 只描述 A，没有定义确认如何落盘。如果确认只存在于聊天里，阶段状态不能由磁盘产物推导。

本次采用 `requirement/` 产物包：

```text
requirement/
├─ A_需求建模_v1.yml
└─ 人类确认_v1.yml
```

目录整体是阶段一的单一耐久产物；确认文件只确认双方所指相同，不确认具体 B。

### 4. 追问必须防止过早进入 B

本次部分问题开始涉及独立仓库、版本哈希、入口文件等候选实现形状。它们有助于暴露需求，但不应未经证据直接固化成最终方案。

处理方式：

- 用户明确要求的行为写入 A 的目标、判据或约束；
- 具体技术选型移入假设或未解歧义；
- 一旦八个槽位足够支撑阶段二，停止继续追问实现技术。

## 已裁决的机制改进

### 批量提问规则

默认不再机械执行“一次一问”，改为：

1. 每轮提出 **2–4 个**同一层级、彼此低依赖的问题；
2. 每个问题仍必须可独立回答，并分别写回 schema；
3. 每题给出建议与理由，但不得把建议写成用户已确认事实；
4. 出现高影响术语冲突、前提变化或答案之间相互依赖时，下一轮退回单问题澄清；
5. 一轮回答后统一校验，再根据 ValidationError 生成下一批问题；
6. 不在每轮完整回显整个 A，只回显本轮写入的关键变化，减少 token 消耗；
7. 达到可交给下游的充分程度后停止，不为填充实现细节继续追问。

### 阶段一产物规则

阶段一的产物不是孤立 A 文件，而是 `requirement/` 产物包。第一版至少包含：

- 结构化 A；
- 与 A 版本绑定的人类同义确认。

A 被修订时创建新版本；旧确认不能自动继承，必须重新确认。

## 后续用途

`context-management-mechanism` 将继续作为同一 workflow 实例，依次测试：

1. 信息收集与提炼；
2. 结果建模 B；
3. 测试生成；
4. 步骤拆分；
5. 执行；
6. 测试执行与审核。

每个阶段发现的机制问题都应先记录实测证据，再修改对应机制，不因单次偏好预先扩大全局系统。
