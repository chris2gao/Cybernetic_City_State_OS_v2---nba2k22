# schema v1 自测结论

用 `需求建模schema_v1.md` 给"建第二代城邦系统"这个需求建模，
验三件事：**槽位够不够、校验拦不拦得住、产出能不能喂给阶段二。**

---

## 一、校验结果：**不通过**

逐条跑四个跨字段校验：

| # | 校验 | 结果 |
| :-- | :--- | :--- |
| 1 | 每条成功判据 `可观察` 为 true | ✅ 通过（3/3） |
| 2 | **不允许存在 `影响: 高` 的未解歧义** | ❌ **失败** |
| 3 | 目标中的关键词在术语中有定义 | ✅ 通过 |
| 4 | 每条假设有"如果不成立会怎样" | ✅ 通过（4/4） |

**失败项**：`谁执行` 影响为高，未解。

## 二、这是 schema 在正确工作，但它暴露了一个真缺陷

**它拦对了**：`谁执行` 确实未决，确实高影响——它决定加载器的形态。
按规则，这个需求不该进入阶段二。

**但我们事实上已经在往下做了**，而且做得没错——机制 1、机制 2 都实现了 v1，
**`谁执行` 一点没挡到它们**。它挡的是机制 6 和 7。

所以真正的缺陷不是"太严"，是：

> **schema 把需求当成原子的，而一个大需求的不同部分，被不同的歧义阻塞。**

`谁执行` 阻塞阶段六、七，不阻塞阶段一、二。
schema 没有地方表达"这个歧义只影响哪一部分"，只能整体判死。

## 三、修法：给未解歧义加作用域

```yaml
未解歧义:
  - 歧义: 谁执行
    影响: 高
    阻塞范围: [06_执行, 07_测试执行]     # ← 新增
```

校验规则 2 随之改成：

> 高影响歧义**阻塞它作用域内的阶段**，不阻塞全部。
> 作用域为空或写"全部"时，才整体阻塞。

**这条改动是自测挣来的，不是设计时想出来的。** 只填一次表就出现了，
说明这类缺陷靠推演找不到——**得真填。**

## 四、另外两个发现

### 术语槽位比预想的重要

填的时候发现，`A`、`B`、`证据`、`机制` 这四个词**我们一直在用，但从没定义过**。
写下来才发现"证据"这个词我们同时用它指两件事：**挖到的原始材料**、
以及**交叉验证后可用的依据**。

这是"双方指同一件事"要防的东西，而它**在自己身上就出现了**。
本次填表把它统一为后者（原始材料叫"信源材料"）。

### 假设槽位的"如果不成立会怎样"是最有价值的一栏

四条假设里，写完后果才看清第一条的分量：**"八个机制接口稳定"若不成立，
"先做第一版再升级"这个开发方式失去前提**——那不是一个技术问题，是整个开发方式要换。

**只写假设不写后果，这一条读起来平平无奇。**

## 五、三件事的验证结论

| 验什么 | 结论 |
| :--- | :--- |
| 槽位够不够 | **够，八个都用上了，无一为空**。但未解歧义缺"作用域"子字段 |
| 校验拦不拦得住 | **拦得住，而且拦对了**。但粒度太粗——整体阻塞而非按范围阻塞 |
| 能不能喂给阶段二 | **能**。`关联领域` 四条直接就是阶段二步骤 1 的输入；`假设` 四条直接就是待验证清单 |

第三条是最重要的验证：**两个机制的接缝是通的**，
A 的两个槽位无需转译就是阶段二的输入。
