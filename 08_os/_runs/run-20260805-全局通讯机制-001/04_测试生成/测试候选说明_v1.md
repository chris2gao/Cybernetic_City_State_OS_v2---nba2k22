## 生成原则

测试判定依据来自阶段二证据，而不是从 B v3 反向复制。B v3 只用于标识实现对象和路径。
每项测试都绑定 `E-01` 至 `E-10` 中至少一个证据 claim，并映射到 A 的成功判据。

- 测试总数：50；
- 阻断测试：50；

- A 成功判据覆盖：AC-01 至 AC-09 全覆盖。

## 五组测试

1. `GC-T001–GC-T010`：canonical message、requested_action、YAML 安全子集、禁止投递状态、消息 ID 与路径一致性。
2. `GC-T011–GC-T020`：task 内 sender 序号、sender 独占写入、角色匹配、权限不从消息产生、required refs 精确集合。
3. `GC-T021–GC-T030`：按需上下文、长文档外置、front matter、隐私分类、默认本地发布、Web/Human GitHub 触发。
4. `GC-T031–GC-T040`：Git 收敛、同路径冲突、发布顺序、Human 改路由、sent 语义、无自动轮询、整体归档与 private runtime 删除。
5. `GC-T041–GC-T050`：历史任务不默认加载、discovery、Human/current、sender index、不可变纠正、Git 内容身份、跨端 canonical 等价、私有推理边界、跨模型精确语义恢复。

## 关键失败形状

以下情况必须失败，而不是被“整体上合理”的输出掩盖：

- required refs 少一个或多一个；
- authorization ref 未进入必读集合；
- sender role 与 endpoint card 不一致；
- sender 写入其他 sender 区域；
- YAML 重复键、多文档、alias、merge key 或 custom tag；
- 同一路径 Git 冲突或 non-fast-forward 被静默覆盖；
- local_only 或 forbidden 内容进入 GitHub；
- 公开 task 归档时把 private runtime 一并归档；
- 自然语言解释合理但精确字段错误；
- sent 被错误解释为已送达、已读、理解或接受。
