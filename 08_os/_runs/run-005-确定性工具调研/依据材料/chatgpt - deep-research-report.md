I found method papers, academic or historical software pages, investigative platforms, news databases, and generic deduplication components, but not a maintained open-source tool that cleanly takes your exact input-output contract and does the job end-to-end. ## Detailed checklist for all 17 operations

**Schema validation and missing-required-field detection** — **Yes.** The cleanest off-the-shelf boundary is `python-jsonschema/check-jsonschema` for schema-first validation and `pydantic/pydantic` for typed-object validation in Python. Agent-drive is excellent: CLI for `check-jsonschema`, Python API for both. Integration cost is **low**: no resident service is required, both run offline, and `check-jsonschema` can sit in pre-commit or CI. License and activity are healthy: `check-jsonschema` is Apache-2.0 and active in 2026 issues/docs, while Pydantic is MIT and actively maintained. Known pitfalls: JSON Schema `format` checks are not enforced by default unless configured, and Pydantic does **not** natively validate arbitrary JSON instances against arbitrary JSON Schema; it validates Python models and can emit JSON Schema. **Read:** both projects directly support programmatic validation. **Inference:** for an agent workflow with explicit input/output contracts, schema-first validation is usually the cleaner boundary than model-first validation. citeturn33search1turn33search5turn33search8turn31view1

**Turn validation errors into sorted follow-up questions** — **Partial, not turnkey.** The closest ready-made tool I found is `reuters-graphics/ask-json`, which turns JSON Schema failures into interactive CLI questions and can also be used as a JS module. `guardrails-ai/guardrails` can validate structured outputs, surface field-level failures, and be run from Python or as a standalone server. Integration cost is **low to medium**: both are callable from code, but `ask-json` is inherently interactive by design and Guardrails pulls in a broader validator ecosystem. Known pitfalls: `ask-json` supports only a subset of JSON Schema keywords and only asks for fields that are marked `required`; Guardrails is in active API transition, with 2026 roadmap issues about removing re-ask behavior and narrowing first-class model support. **Read:** existing tools can turn some validation failures into prompts. **Inference:** I did **not** find a maintained OSS tool that takes arbitrary validation errors and returns a machine-readable, impact-sorted question queue for agents without custom policy logic on top. citeturn32view0turn32view1turn13search4turn13search6

**Overlap and total-size estimation for two lists** — **Yes.** If entity matching is already solved or exact IDs exist, overlap is trivial; if not, `moj-analytical-services/splink` and `J535D165/recordlinkage` are the relevant open-source linkage layers. For the actual capture-recapture estimate, the classic package is `Rcapture`. Agent-drive is good: Python for Splink and RecordLinkage, R for Rcapture; no GUI is required. Integration cost is **medium**: exact-ID overlap is negligible, but fuzzy linkage configuration and model tuning are nontrivial, and Rcapture introduces an R runtime. Known pitfalls: RecordLinkage’s own docs emphasize experimentation and note scaling pressure from quadratic pair generation; Rcapture focuses on loglinear/closed-population capture-recapture and has seen limited feature evolution in some areas. **Read:** OSS exists for both the matching and estimation pieces. **Inference:** if your upstream pipeline can hand this step exact or high-confidence identity resolution, this operation is already “solved enough” with existing software. citeturn15search0turn15search1turn15search8turn15search17turn39search0turn39search16turn39search18

**Loop-reporting stripping** — **No turnkey general OSS found.** The closest reusable components are `mediacloud/backend`, which is an open-source media research platform for collecting and querying news data, plus generic text deduplication or clustering components. But I did **not** find a maintained open-source tool whose documented contract is: “take a batch of articles/citations, trace to the earliest original source, and collapse circular reporting chains.” Agent-drive for the components is fine, mostly Python/database/HTTP, but the end-to-end workflow is missing. Integration cost is therefore **high** because you would be assembling a pipeline yourself: URL normalization, content dedup, quote/link extraction, timestamp arbitration, and provenance heuristics. Known pitfalls: text deduplication is easy compared with true origin tracing; repost chains, syndication, silent edits, and missing canonical links make “first source” a provenance problem, not just a similarity problem. **Read:** Media Cloud is real and open-source; the searches surfaced aggregators and dedup systems. **Inference:** there is no convincing ready-made open-source solver for this exact operation in the current ecosystem. citeturn26search0turn26search8turn21search4turn21search5turn26search7

**Morphological cross-consistency pruning** — **No good modern turnkey OSS found.** I found the method literature and the historical Macarma/Carma software page from the Swedish Morphological Society, but not a maintained open-source repo I would recommend as an agent-callable dependency for this operation. The best programmable substitutes are generic constraint solvers such as `google/or-tools` or `Z3Prover/z3`, where each mutually exclusive combination becomes a constraint and the valid candidate set becomes the model space. Agent-drive is excellent for OR-Tools and Z3 through Python and other language bindings. Integration cost is **medium** if your constraints are already formalized, **high** if your compatibility rules still live in prose. Known pitfalls: the modeling burden is yours, and full candidate enumeration can explode combinatorially. **Read:** I found the method description and non-repo software pages, but not modern OSS matching your I/O. **Inference:** treat this as a constraint-modeling problem, not as a tool-selection problem. citeturn20search1turn20search2turn31view3turn38view0

**ACH matrix computation** — **Weak yes, but the dedicated-tool ecosystem is poor.** The old dedicated OSS option is `Burton/Analysis-of-Competing-Hypotheses`, a GPL-3.0 PHP/MySQL web app with only 10 commits visible and clearly older design assumptions. The modern-looking option is `mantisfury/ArkhamMirror`, a much broader local investigative platform that includes a full ACH implementation among many other shards and services. Agent-drive is mixed: Burton is deployable and scriptable only indirectly through HTTP/database automation, while ArkhamMirror is programmatic at platform level but much heavier than a single-purpose library. Integration cost is **medium-high** for Burton and **high** for ArkhamMirror. Known pitfalls: Burton is stale and web-first; ArkhamMirror is large, with Docker/PostgreSQL and a whole platform architecture behind the ACH feature. **Read:** both products expose ACH functionality. **Inference:** there is still no obvious small, modern, agent-friendly ACH compute library that I would call a clean drop-in. citeturn27view0turn35view0

**Sensitivity analysis on the matrix** — **Yes, with generic rather than ACH-specific tools.** `SALib/SALib` is a mature MIT-licensed Python library with many standard sensitivity methods and both Python and CLI-friendly workflows. For your exact use case, the simplest mapping is probably leave-one-evidence-out recomputation or perturbation of evidence weights, wrapped as a model function and passed to SALib-like analyses. Integration cost is **low to medium**. Known pitfalls: SALib is a general sensitivity library, not an ACH-native package, so you still need to formalize the score computation as a callable model. **Read:** SALib supplies the sensitivity-analysis machinery. **Inference:** for matrix-based reasoning, a custom leave-one-out wrapper will often be more interpretable than sophisticated global methods. citeturn37view0

**Detect isolated claims in a claim-evidence structure** — **Partial.** `argdown/argdown` is an actively maintained MIT-licensed argumentation syntax and toolchain, while `recap-utr/arguebuf-python` and `johnlawrence/AIFdb` provide machine-manipulable argument graph representations and stores. Agent-drive is good: Argdown has a CLI and JS ecosystem, Arguebuf has a Python library, and AIFdb is a database-backed system. Integration cost is **medium**. Known pitfalls: I did **not** find a standalone OSS tool whose whole job is “flag claims with no supporting evidence edge”; this is usually a graph query on top of an argument representation rather than a separate packaged product. **Read:** the graph tooling exists. **Inference:** once your claims and evidence are in Argdown, Arguebuf, or AIF form, orphan detection is straightforward to implement. citeturn28view0turn24search14turn17search0turn17search20

**RDF graph shape-constraint validation** — **Yes, strongly.** `RDFLib/pySHACL` is the easiest agent-driven option in Python, and Apache Jena’s `jena-shacl` is the strongest Java-side option. Both expose CLI/API boundaries. Integration cost is **low** for pySHACL and **medium** for Jena. License and activity are strong: pySHACL is Apache-2.0 and was updated July 28, 2026 in the RDFlib org view; Jena is Apache-2.0 and actively tracking SHACL 1.2 work in 2026. Known pitfalls: RDFLib documentation warns about file/network access considerations when processing untrusted RDF inputs; Jena is heavier JVM infrastructure. **Read:** this space is well served. **Inference:** unless you already run a Java semantic stack, pySHACL is the lowest-friction default. citeturn31view0turn12search4turn12search7turn11search13turn11search16

**Test traceability validation** — **Yes, if you can express trace links explicitly.** `itsallcode/openfasttrace` is the clearest open-source traceability suite I found; it traces requirements/specification items into source and other tagged artifacts, and it ships CLI plus Gradle/Maven integration. The Rust follow-on `jFiedler24/open-very-fast-trace` is promising but still early. Agent-drive is good for OFT through CLI/build tooling. Integration cost is **medium**. Known pitfalls: OFT is requirement-tracing software, not a generic provenance validator; if you want each test case to be traced both to a tested object and to a criterion source, you will need to define those as tractable item types or tags in your repo conventions. **Read:** OFT is real, actively developed in 2026, and explicitly about coverage tracing. **Inference:** this operation is feasible with OFT, but only if you standardize artifact IDs and trace tags across your test corpus. citeturn25view0turn23search8turn23search12turn23search1turn23search9

**Mutation testing** — **Yes, strongly.** For Python, `boxed/mutmut` and `sixty-north/cosmic-ray` remain the relevant OSS options; for other ecosystems, Stryker is strong. Agent-drive is solid: these are CLI-first tools designed for CI and automation. Integration cost is **medium to high** because the real price is runtime, not packaging. Known pitfalls: mutmut requires a system with `fork` support and on Windows effectively means WSL; mutation testing is still compute-heavy, though mutmut 3 improved performance and incremental behavior. **Read:** there are mature toolchains and active docs/community. **Inference:** for your workflow principle, mutation testing is one of the easiest “deterministic steps” to externalize completely. citeturn31view2turn9search19turn9search20turn9search13

**Constraint satisfiability solving** — **Yes, strongly.** `Z3Prover/z3`, `google/or-tools`, and `PySAT` are the main programmable workhorses. Agent-drive is excellent: CLI and APIs in Python and many other languages. Integration cost is **low to medium** depending on how formalized the constraints already are. Known pitfalls: solver behavior around unsat cores can be surprising, unsat cores are not necessarily minimal, and some Optimize-plus-unsat-core interactions have caveats in bindings and issue discussions. **Read:** these solvers are mature and actively maintained. **Inference:** if you need explanations for contradictions, start with Z3 or PySAT because they make “why unsat?” style diagnostics easier than trying to repurpose a general workflow engine. citeturn38view0turn10search2turn36search1turn36search4turn36search10turn36search14turn36search17

**Atomic fact support measurement** — **Closest fit exists, but with caveats.** `shmsw25/FActScore` is the best open-source match I found for “decompose claims into atomic facts and score what fraction are supported.” Agent-drive is good through CLI and Python API. Integration cost is **medium** because the repo expects data downloads and, in default modes, external models or API calls. It is MIT licensed. Known pitfalls are significant: the standard workflow can require large knowledge assets, optional access to Llama weights or OpenAI APIs, explicit handling of API cost, and even manual download fallback when rate limits hit. **Read:** FActScore provides the atomic-fact evaluation machinery. **Inference:** it is the best available base, but it is not a purely deterministic validator in the sense you use for schemas or SAT solvers. citeturn29view0

**Coverage relation checking** — **Yes, but usually through generic data tooling rather than a dedicated product.** For JSON-like or record-like data, `jqlang/jq`, `JMESPath`, and `Miller` are agent-friendly ways to compute unmapped or uncovered elements. If the relation is requirements-style coverage, `OpenFastTrace` is the stronger purpose-built option. Agent-drive is excellent: CLI and libraries, fully offline. Integration cost is **low** for jq/JMESPath, **medium** for OFT. Known pitfalls: these generic tools do not know your coverage semantics; you must define the mapping relation explicitly. **Read:** generic filtering/join tools are mature and lightweight. **Inference:** unless your coverage graph is already a requirements-tracing system, you probably do not need a special-purpose product here. citeturn18search0turn18search1turn18search3turn18search4turn18search9turn25view0

**Filter multiple sampled outputs by predicates** — **Yes.** This is one of the least tool-constrained operations. `jq`, `JMESPath`, and `Miller` are sufficient if outputs are structured; if outputs are embedded in an eval or test harness, `promptfoo` or `pytest` can mark pass/fail cases directly. Agent-drive is excellent. Integration cost is **low**. Known pitfalls: the challenge is defining stable predicates, not getting a tool to execute them. **Read:** these tools already support declarative filtering and test-like selection. **Inference:** you do not need a special “multi-sample filter” product unless your predicates themselves are learned or probabilistic. citeturn18search0turn18search1turn18search3turn30view0turn22search0

**Prompt or skill behavior evaluation** — **Yes, strongly.** `promptfoo/promptfoo`, `UKGovernmentBEIS/inspect_ai`, and `confident-ai/deepeval` are the three strongest mainstream OSS options I found, with `qualixar/agentassay` as a newer research-forward entry. Agent-drive is exactly what you want: CLI, Python, CI integration, and in some cases adapters for agent frameworks. Integration cost is **low to medium**. Licenses are favorable overall: Promptfoo is MIT and remains open-source after joining OpenAI; Inspect is MIT; DeepEval is Apache-2.0; AgentAssay is AGPL-3.0. Known pitfalls: many “behavior” metrics are still LLM-as-a-judge or model-based rather than purely deterministic, and AgentAssay’s strongest claims are newer and less battle-tested than Promptfoo or Inspect. **Read:** this ecosystem is active and practical. **Inference:** this is one of the healthiest areas for agent-driven tooling in 2026. citeturn30view0turn30view1turn30view2turn30view3

**Test execution and reproducibility verification** — **Yes.** The practical Python stack is `pytest` plus `pytest-repeat`, `pytest-randomly`, `pytest-replay`, and increasingly `pytest-loop`; for build-level reproducibility, `reprotest` is the classic external check. Agent-drive is strong through CLI and CI. Integration cost is **low to medium**. Known pitfalls: these tools can expose flakiness and environment sensitivity, but they do not magically make a nondeterministic system deterministic; you still need controlled seeds, pinned dependencies, stable clocks, isolated FS/network assumptions, and explicit environment management. **Read:** the plugins all target the exact reproducibility pain points you described. **Inference:** for agent systems, this operation should be split into “repeatability under identical seed/env” and “robustness under randomized order/env perturbation,” because different tools help with different failure classes. citeturn22search0turn22search1turn22search2turn22search10turn22search11turn22search9

## The six hardest operations

For **loop-reporting stripping**, the most important result is the negative one: I found **components**, not a usable end product. Media Cloud is useful upstream because it gives you a programmable open-media corpus and query surface, and generic dedup/clustering tools can collapse near-duplicates, but those do not solve the provenance question. In practice, “who originated this claim?” usually requires canonical-link extraction, quote-matching, syndication detection, and timestamp arbitration under missing or conflicting metadata. **Read:** Media Cloud is an open-source media analysis platform. **Inference:** you should budget for building this yourselves if this step matters strategically. citeturn26search0turn26search8turn21search5turn26search7

For **morphological cross-consistency pruning**, the search result quality was itself a signal. Queries around “cross-consistency assessment” surfaced the method paper, a proprietary or historical software page, and even irrelevant results like the TV series *Cross* before surfacing anything like a modern repo. That is what a weak software ecosystem looks like. **Read:** the method is documented and Macarma/Carma exists as software history. **Inference:** the operationally correct move is to compile your parameters and incompatibilities into SAT/CP constraints and let OR-Tools or Z3 do the pruning. citeturn20search0turn20search1turn20search2turn31view3turn38view0

For **ACH**, the dedicated OSS options are more real than for cross-consistency assessment, but still not comfortable. Burton’s ACH implementation is recognizably dedicated software, but it is old, small, PHP/MySQL, and not shaped like a modern library. ArkhamMirror is current and ambitious, but it is an entire local investigative platform, not a tiny reusable scoring engine. **Read:** both exist and expose ACH capability. **Inference:** if all you need is matrix computation, a custom matrix scorer in Python may be less risky operationally than embedding either of these whole products. citeturn27view0turn35view0

For **mutation testing**, the surprising conclusion is that one of the six “hardest” items is actually well covered. The tools are real, agent-driven, and easy to automate. The cost is compute, not ecosystem immaturity. If you only care about “test suite defect capture rate,” mutation tools are already a strong externalization candidate. **Read:** mutmut, Cosmic Ray, and Stryker all do this. **Inference:** the main design choice is language/runtime fit and CI budget, not whether the ecosystem exists. citeturn31view2turn9search20turn9search13

For **atomic fact support measurement**, FActScore is genuinely valuable because it matches the conceptual unit you care about: atomic facts, not whole-answer scores. But it sits in a gray zone between deterministic tooling and model-driven evaluation. Its README explicitly discusses knowledge-source downloads, optional Llama reconstruction, OpenAI API cost, and fallback workflows when downloads fail. **Read:** it is the closest available open-source solution. **Inference:** treat it more like an evaluation subsystem than a deterministic validator. citeturn29view0

For **prompt or skill evaluation**, the ecosystem is now broad enough that you do not need to overfit to one framework. Promptfoo is the most deployment-friendly CLI/CI choice, Inspect is the most “evaluation framework” feeling option with a large built-in eval catalog, DeepEval has a pytest-like posture for LLM apps, and AgentAssay is interesting if you want statistical efficiency for stochastic agent testing. **Read:** all four are programmatically callable and actively documented. **Inference:** unless you need one framework’s special scoring model, you can pick primarily on license, language, and CI/CD ergonomics. citeturn30view0turn30view1turn30view2turn30view3

## Searches that failed and what that means

I explicitly ran searches that were expected to fail, because you asked for the failure map. The query family around **cross-consistency assessment** produced the method literature and Swemorph software pages, but not a living OSS repo; the result set even contained irrelevant “Cross” TV results, which is a sign of low software discoverability for the exact term. The query family around **news provenance/original source tracing** mostly surfaced Media Cloud, generic aggregators, and citation-graph tools for academic literature rather than a maintained solution for stripping circular reporting in journalism. The query for **SHACL MCP server** mostly surfaced generic MCP indexes and SDKs, not an obviously maintained dedicated server. citeturn20search0turn20search1turn20search2turn21search4turn21search5turn26search0turn12search1turn12search3

A second failure mode was GitHub partial rendering. Several repo pages loaded with GitHub’s “Uh oh!” partial UI, but still exposed the README, license, stars, and enough repository metadata to assess viability. Where a page did **not** surface enough metadata cleanly, I relied on official docs or search snippets instead of guessing. citeturn25view0turn28view0turn37view0

The strongest final pattern is this: if you want **agent-drivable deterministic services**, today’s open-source sweet spot is still **CLI + Python/Java/JS library APIs**, with MCP used mainly as a wrapper pattern rather than as the native distribution format for domain tools. So the selection question is often not “is there an MCP server?” but “is the underlying tool mature enough that wrapping it as an MCP skill is cheap?” For operations like SHACL, SAT/CP, mutation testing, schema validation, and prompt eval, the answer is yes.
