# run-004 · 挖掘目标与领域分析

**需求 A**：机制 4 第一版——由证据推导出测试程序，用以验证 B 的实现是否满足需求。

---

## 步骤 0 · 挖掘目标

### 什么样的信息会让我们相信它可以实现

1. 存在"**从证据生成测试**"的既有做法——不限于软件领域
2. 有办法让**每条测试可溯至一条证据**成为结构约束，而非纪律
3. 存在判断"一条测试够不够格当验收依据"的标准
4. 有办法在**实现之前**用测试验证 B 的可行性（不只是实现之后验证正确性）

### 什么样的信息会让我们相信它不能实现

1. **测试生成的既有做法全部是"从规格生成"**，而规格就是 B——
   那"测试由证据推导"这条规则**无法落地**，只是一句口号
2. 证据是描述性的（世界是这样），测试是规定性的（应当如此），
   **两者之间没有可操作的转换**
3. "实现之前就能验证可行性"在逻辑上不成立——
   没有实现物，测试无物可测
4. Daubert 那套判"证据可采性"的标准**无法类比到判"测试可采性"**

**第 1 条是本轮的核心风险。** 与 run-003 的"ACH 只评估不生成"同构：
现成方法可能全部解决的是另一个问题。

### 停止判据

EIG：能否判定"由证据推导测试"可行/不可行。能判定就停。

### 捕获单位

可实现性结论。**本轮为定向核实题，预期高重合，不算捕获-再捕获。**

---

## 步骤 1 · 领域分析

| 领域 | 为什么相关 |
| :--- | :--- |
| **软件测试生成** | 属性测试、规格驱动测试、变异测试——测试生成的主战场，但多为"从规格生成" |
| **验收测试驱动开发 / BDD** | ATDD、Cucumber 一脉的核心就是"先写验收标准再实现"，与我们"测试先于步骤"同构 |
| **科学方法论 / 可证伪性** | "什么样的观察会推翻这个结论"——**这正是从证据推测试的原始形态** |
| **计量与评估方法论** | 指标效度、构念效度：一个测试到底测没测到它声称测的东西 |
| **司法证据与鉴定标准** | Daubert / Mohan / Kelly-Frye 判的是"证据够不够格被采信"，借来判"测试够不够格当验收依据" |
| **事实核查自动化** | FactScore 之类的原子级事实精确度度量，可能是"证据支撑度"的现成量法 |

**第三个领域是本轮的赌注。** 前两个是软件领域的常规答案，
但它们几乎必然是"从规格生成"——而科学方法论里，
**"什么观察会推翻它"本来就是从证据出发的**。

如果第 1 条风险成立（现成做法全是从规格生成），
**出路大概率在这个领域，不在软件测试领域。**

**若你认为其中某个领域不相关，请说明**——那也是有用信息。
