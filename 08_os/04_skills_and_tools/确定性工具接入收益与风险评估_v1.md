> 核验日期：2026-07-29
>
> 性质：安装前 Human 决策材料
>
> 当前状态：`research_supported` + `environment_observed`；候选工具均
> `not_yet_tested`。本次没有安装、激活、暴露、加载或调用任何候选工具。

## 1. 一页 Human 决策摘要

### 1.1 建议

现在不应“一次性装齐” run-005 的候选。先批准四个小型、可撤回的验证批次：

1. 把一份真实 Markdown schema 编码成 JSON Schema，再用
   `check-jsonschema` 做正、负、边界校准；
2. 先自建很薄的集合、Chapman 估计和引用图检查，不引入大型框架；
3. Human 提供隔离的 WSL 环境后，对 mutmut 与 Cosmic Ray 做同一段已知缺陷、
   含装饰器代码的对照校准；
4. 只以 CLI、离线假 provider 验证 promptfoo；在数据外发和模型费用获得明确
   授权前，不启用真实 provider，也不接 MCP。

其余候选等机制真正活跃、出现可复现失败后再测试。确定性工具的价值不在于
“工具更多”，而在于把可编码的结构错误从模型判断中拿出来，形成稳定退出码、
错误位置和可重复 receipt。

### 1.2 当前裁决

| 路线 | 建议状态 | 现在为什么这样处理 |
|---|---|---|
| Python 集合差、Chapman 小公式、错误转问题、引用图 | `self_build` / `adopt_now_candidate` | 逻辑短、边界清楚、无需常驻服务 |
| `check-jsonschema` | `test_before_decision` | 价值高，但当前三份 schema 不是机器 JSON Schema，必须先编码契约 |
| mutmut / Cosmic Ray | `human_environment_remediation_then_test` | mutation 收益高；Windows 上需 WSL/隔离环境并先校准装饰器与 mutant 明细 |
| promptfoo CLI | `test_before_decision` | Node 已观测到，但真实 provider 会引入网络、数据和模型调用成本 |
| OpenFastTrace / `cargo-ovft` | `test_before_decision` | 可能支持追踪，但 Java/Rust 本机未在 PATH，且需证明能表达本仓库引用规则 |
| Zwicky、EMR-ACH、PyArg、pySHACL、Z3 | `defer_until_mechanism_active` | 当前机制尚未给出足够失败样本；框架成本大于已证明收益 |
| `pytest-json-report` | `test_before_decision` | 只有下游确实消费 JSON 时才有价值；先测 Python 3.14 兼容与报告稳定性 |
| 模型型评估器（原操作 13） | `exclude_from_deterministic_layer` | 仍可用于评估，但调用模型/权重，不属于确定性层 |
| `recapturedocs` | `exclude_from_deterministic_layer` | 官方包是 RecaptureDocs.com 客户端库，不是 capture-recapture/Chapman 工具 |

### 1.3 Human 现在需要决定

- 是否批准下一 run 只创建一份机器 schema，并临时测试 `check-jsonschema`；
- 是否批准准备独立 WSL Python 环境校准 mutation 工具；
- promptfoo 是否只准离线 provider，及何时允许外部模型/数据外发；
- 追踪检查先自建小 validator，还是修复 Java/Rust 环境比较现成工具；
- 是否将机制 3 相关框架继续延后，直到出现真实输入与失败样本。

未获批准前，registry 只注册本评估文档，不注册候选包，不修改 boot/loader。

## 2. 五种状态不是一回事

| 状态 | 含义 | 本次是否发生 |
|---|---|---|
| 调研 research | 阅读本仓库证据与官方资料，形成假设 | 是 |
| 安装 install | 包或 runtime 落到机器/隔离环境 | 否 |
| 暴露 expose | 名称、说明或 schema 对模型可见 | 否 |
| 加载 load | 某一任务把具体 skill/wrapper/server 纳入上下文 | 否 |
| 调用 invoke | 真实输入进入工具并产生输出/副作用 | 否 |

“安装但未暴露”通常没有模型 token 成本，却仍占磁盘并带来供应链维护责任；
“MCP 已连接但未调用”也可能因工具 schema 可见而消耗上下文。不能用“没调用”
推导“零 token”，也不能用“装好了”推导“模型会正确使用”。

证据标签统一为：

- `research_supported`：仓库材料或官方资料支持；
- `environment_observed`：本次只读命令在当前 Codex Windows 环境观测；
- `locally_measured`：本次对真实候选做过可复现测量；本任务没有此类结果；
- `not_yet_tested`：尚未安装/调用候选；
- `human_decision_required`：涉及环境、外发、费用或激活边界。

## 3. 为什么需要确定性外挂

模型擅长解释、归纳和提出候选，却不应独占以下判定：

- 必填字段是否存在、枚举是否拼错、ID 是否能解析；
- 两个集合的差集是否为空；
- 引用图是否有孤儿、环或指向错误命名空间；
- 一个计算公式在同一输入上是否产生相同结果；
- 测试套件是否能抓住受控代码错误；
- 命令是否成功、输出是否满足固定契约。

这些问题可编码、可重复、可产生退出码。工具的收益是阻止“结构已经坏了，但模型
继续写出流畅解释”的假健康。边界也同样重要：工具只能证明已编码规则成立，不能
证明目标正确、证据可信、语义充分或 Human 愿意承担后果。

## 4. schema 校验：具体作用、真实缺口与限制

### 4.1 它能校验什么

真正的 JSON Schema 可以校验必填字段、类型、枚举、格式、数组形状、条件分支和
引用形状。`check-jsonschema` 可把这种校验放进 CLI/pre-commit，并给出稳定退出码。
格式检查是否执行取决于 schema 和 validator 配置，不能默认所有 `format` 都已验证。

### 4.2 本仓库当前不能直接交给它的内容

以下文件是 Markdown 中的 YAML 风格规范与人工/程序规则，不是 JSON Schema：

- `08_os/01_workflow/01_需求建模/实现/需求建模schema_v1.md`
- `08_os/01_workflow/03_结果建模/实现/B_schema_v1.md`
- `08_os/01_workflow/04_测试生成/实现/测试schema_v1.md`

因此，run-005 的“schema 已写好，只缺 checker”过于乐观。接入前至少要：

1. 选择一个最小契约并编码成实际 JSON Schema；
2. 明确输入是 YAML 还是 JSON，以及 YAML 解析后的类型规则；
3. 把集合成员、跨文件引用、文件存在性等规则放到自建 validator；
4. 建立正例、负例、边界 fixture，并固定 tool/schema 版本。

### 4.3 两个真实错误例

**例一：需求对象缺少成功判据。**

```yaml
goal: "建立可审计的测试生成"
boundary:
  included: ["结构测试"]
```

机器 schema 应报告 `success_criteria is a required property` 并以非零退出。
没有这个门，后续阶段仍可能根据自然语言补出一套看似合理的测试，却没有任何
可追溯的成功定义。schema 能阻止缺字段，不能判断已有成功判据是否真的可观测。

**例二：测试把 B claim 当成 criterion source。**

```yaml
test_id: T-017
subject_ref: B-implementation-4
criterion_source: B-claim-1
fail_able: true
```

字段类型和非空检查可能全部通过；但本仓库规则要求 criterion source 指回 A 的
成功判据或证据，而不是 B 自己的主张。这需要自建跨命名空间/跨文件 validator。
它阻止“实现自己证明自己”，但仍不能证明来源本身真实。

**边界例：枚举写成近义词。**

```yaml
impact: 严重
```

如果机器契约只允许 `high | medium | low`，JSON Schema 应拒绝它。若团队想接受
中文值，应修改版本化契约，而不是让模型临场猜测。

### 4.4 结论

`check-jsonschema` 的高收益成立，但前提是先有机器契约。它证明 well-formed，
不证明 correct；仍需语义审核、来源验证、运行测试和 Human 决策。

官方资料：
[check-jsonschema 文档](https://check-jsonschema.readthedocs.io/en/latest/)、
[python-jsonschema](https://github.com/python-jsonschema/jsonschema)。

## 5. mutmut / 变异测试

普通测试全绿只说明现有断言没有失败。mutation 工具会主动把条件、运算符、返回值
等改坏，然后重跑测试：

- 被测试杀死的 mutant 说明断言能感知该类错误；
- survived mutant 暴露“执行到了但没有验证”、空断言、错误边界或遗漏分支；
- skipped/未生成对象可能意味着工具限制，不能被总分掩盖。

### 5.1 当前资料纠偏

截至 2026-07-29，mutmut 的 PyPI 元数据已声明支持 Python 3.14，旧的
“Python 3.14 必然不兼容”不能继续当现状。官方文档仍说明需要 `fork`，Windows
应通过 WSL；装饰器相关的开放问题还要求实测，而不是根据版本号宣告兼容。

本机只读观测为 Python 3.14.6，WSL 可执行文件存在；没有验证某个 WSL
distribution、其 Python 或 mutation 工具能运行。因此状态是
`human_environment_remediation_then_test`，不是淘汰，也不是已可用。

官方资料：
[mutmut PyPI](https://pypi.org/project/mutmut/)、
[mutmut 文档](https://mutmut.readthedocs.io/)、
[装饰器开放问题 #387](https://github.com/boxed/mutmut/issues/387)、
[Cosmic Ray 文档](https://cosmic-ray.readthedocs.io/)。

### 5.2 必须通过的校准门

1. Human 批准独立 WSL/venv，固定 Python、工具版本和依赖 hash；
2. 用一段已知有缺陷、包含普通函数和装饰器的最小代码；
3. 对 mutmut 和 Cosmic Ray 使用相同测试与超时；
4. 记录 discovered/generated/skipped/killed/survived/error/timeout 明细；
5. 人工核对至少一个 killed、一个 survived、一个装饰器对象；
6. 总分不能替代对象清单；工具崩溃不能记为测试质量差；
7. 只有结果可重复、装饰器行为可解释、资源可接受时才申请接入。

## 6. token 与机器资源成本模型

### 6.1 token 账本

| 情形 | 模型 token 假设 |
|---|---|
| 只安装，未暴露 | 0；机器成本另算 |
| registry 记录，未进入 boot | 默认上下文 0；Human 定向打开文档时按实际文本计 |
| skill 名称/摘要被发现 | `unknown_pending_measurement`，取决于宿主注入格式 |
| skill 详细说明被加载 | 说明文本 + 输入输出，`unknown_pending_measurement` |
| MCP 连接但未调用 | 工具 schema/metadata 可能占上下文，`unknown_pending_measurement` |
| MCP 调用 | schema + 参数 + 返回内容；若 provider 调模型，另加 provider token |
| CLI wrapper 调用 | 没有常驻 schema 时主要是命令提示和回传输出 |
| 大报告回传模型 | 输出内容直接成为 token 成本；应落 artifact，只回摘要和路径 |

外部“约 100 token”“超过 20 工具会退化”等只可作为研究线索，不能写成本机测量。
下一 run 应在同一宿主上测 baseline、连接未调用、只激活一个工具三种上下文差值。

### 6.2 机器账本

机器成本独立记录：下载与磁盘、依赖树、启动进程、CPU、峰值内存、运行时间、
网络连接、缓存和清理结果。模型调用型工具还要单列 API 费用与数据外发。

每次 enable/load/invoke receipt 至少记录：任务、工具版本/hash、加载形态、
暴露 schema 数量和字节数、宿主可提供时的 token 实测、输入/输出 hash、退出码、
校验结果、网络目的地、清理与“已消失”证明。

## 7. 按需加载目标架构

这是一项目标设计，不是当前已实现能力：

```text
boot
  -> 只加载类别摘要与 registry 入口
  -> task policy 授权一个候选
  -> loader 暴露一个 skill / CLI wrapper / MCP server
  -> 写 enable receipt
  -> 调用并把长输出落 artifact
  -> 写 invoke receipt
  -> unload / 终止进程 / 清缓存
  -> 验证工具 schema、进程与临时数据均已消失
```

默认优先级：

1. 纯 Python/PowerShell 内联检查；
2. 单命令 CLI wrapper；
3. Agent Skill，用于渐进披露长说明；
4. MCP，仅在需要进程生命周期、隔离或少量稳定 server tools 时使用。

promptfoo 即使提供 MCP，也应先走 CLI；check-jsonschema、mutation 和集合检查没有
常驻 server 的必要。网络默认关闭，凭据不进入 fixture、日志或模型上下文。

- `supply_chain_and_license`: PyPI 元数据 MIT；发布较旧，需锁定并审维护性。
- `maintenance_risk`: 中高；pytest hook/API 变化。
- `false_confidence_risk`: 中；JSON 只让结果可读，不提升断言质量。
- `positive_test`: 通过/失败/跳过计数与 pytest 控制台一致。
- `negative_test`: failing test 仍产生可解析报告且进程非零退出。
- `boundary_test`: Unicode 路径、长异常和敏感参数按策略截断/脱敏。
- `fallback`: pytest 原生退出码 + 自建最小 receipt。
- `proposed_status`: `test_before_decision`。
- `human_action_required`: 先确认哪个 loader 消费 JSON。
- `evidence_refs`: run-005 OP-15；
  [pytest-json-report PyPI](https://pypi.org/project/pytest-json-report/)。

## 10. 第一批建议验证对象

| 顺序 | 对象 | 理由 | 退出门 |
|---|---|---|---|
| 1 | 一份机器 schema + check-jsonschema | 前端阻断价值最高，也能暴露契约转换工作量 | 真实三类 fixture 通过，跨文件边界不虚报 |
| 2 | Python set + trace validator + Chapman | 依赖最少、可建立自建基线 | 手算一致、错误精确、Unicode/重复 ID 有策略 |
| 3 | mutmut vs Cosmic Ray | 能检验“绿测是否有感知力” | 明细完整、装饰器可解释、资源预算可接受 |
| 4 | promptfoo 离线 CLI | 先验证配置执行和外发边界 | 无网络、无 secret 泄露、输出可控 |
| 5 | OFT/cargo-ovft 对照 | 只有自建基线后才知道框架是否省工 | Human 决定是否为对照修复 runtime |

每批独立授权、独立环境、独立 receipt；前一批通过不自动授权后一批。

## 11. 测试矩阵与准入标准

每个主要候选的 `positive_test`、`negative_test`、`boundary_test` 已在第 9 节给出。
共同准入标准如下：

1. 正例可重复通过，负例必须非零退出且指向具体对象；
2. 边界不得静默截断、联网、回退或把 incomplete 写成 pass；
3. 输出 schema、排序与截断稳定，可生成短摘要和完整 artifact；
4. 锁定版本/hash，列出依赖、许可、网络和卸载办法；
5. 记录 CPU、内存、耗时、磁盘、网络与上下文/token；
6. 清理后工具不再暴露、相关进程终止、临时数据按策略删除；
7. 工具不得把“结构通过”提升为“内容正确”；
8. 任一条件不满足，回到 fallback，不进入正式 boot/loader。

## 15. 供应链、数据与维护底线

- 固定版本与 hash；安装前核验官方来源、许可证和维护状态；
- 先隔离环境，后局部 wrapper；不修改全局 PATH；
- 默认禁网，不把凭据、私有输入、完整异常或 URL query 写入日志；
- CLI 优先，只有可证明的生命周期/隔离收益才接 MCP；
- 第三方 config/script/transform 按代码执行面审查；
- 远端 schema、graph、provider、telemetry 均需显式批准；
- 候选停止维护、许可不兼容或不能 fail closed 时，回退自建小检查；
- 当前 registry 只注册文档，不注册任何尚未准入的 package/server/skill。

## 16. 结论

最先值得做的不是安装，而是把可验证对象变成机器契约，并用最小自建检查建立
基线。schema checker、mutation、prompt regression 和 traceability 各有明确收益，
但只有在正例、负例、边界、资源、外发和卸载都被实测后，才能从
`research_supported` 进入“可用”。截至本文件版本，所有候选仍
`not_yet_tested`，所有安装/激活决策仍为 `human_decision_required`。
