# 协作伙伴

全局环境信息。派活的依据是**每个模型能看到什么别人看不到的东西**，
不是"谁更强"——这个班子能力差距不大，**视野差距很大**。

---

## 名册

| 伙伴 | 独占视野 | 擅长 |
| :--- | :--- | :--- |
| **Claude Code Desktop**（本实例） | 设计上下文、本仓库全部改动史、累积的失败案例 | 架构、分派、跨轮一致性核对、合并他方产出时看差集 |
| **ChatGPT web** | 公网 + **从 GitHub 独立读取本仓库**（读取路径与本实例不同） | 审核、deep research、源范围可控的检索 |
| **Gemini 3.1 Pro web** | 公网 | deep research，广度与长尾；另有 Deep Research Max（延长计算、迭代精炼） |
| **NotebookLM** | 对**给定语料**的扎根分析 | 找矛盾、找单一来源、找缺口；Discover Sources 可自行搜索填充语料 |
| **Codex desktop** | 本地仓库 + 执行；**已验证的发布通道** | 执行、发布到评审分支 |
| **Antigravity / Gemini 3.1 Pro** | 本地仓库 + 执行；独立工作树 | 执行 |
| **Opus 4.6** | 任意 | 需要一次强推理的地方 |

**NotebookLM 的独特价值不是更聪明，是更不肯发挥。** 源里没有它就拒答，
不会补一段听起来合理但没来源的推论。这个性质在"需要知道语料边界在哪"时无可替代。

配额（NotebookLM 免费版）：每笔记本 50 源、每天 50 次对话。Pro 版限额更高。

## 分派原则

### 一、按视野分，不按强弱分

需要公网 → web 模型；需要执行与发布 → Codex / Antigravity；
需要对给定语料扎根 → NotebookLM；需要设计与合并 → 本实例。

### 二、并行是测量，不是保险

**同一任务派给两方、互不知情**，目的是**测量覆盖率**，不是双保险。

实测两次，**两次都发现单次检索必然分层，且从单次内部看不出来**：
T1 分成学术与产品两层（16 个候选只重合 1 个），
T2 分成分析方法论与取证/新闻两层。

因此并行时必须要求双方：

1. **报告各自的检索路径**——分层一旦发生要能被看见
2. **同时报告"新增了什么"和"重合了什么"**——只问新增就拿不到重合数，
   而重合数是所有覆盖率估计的必需输入

第 2 条是本项目实测的设计缺陷，第一次并行漏了，补问一次才拿到。

### 三、发现用 Deep Research，收敛用 NotebookLM

反过来用两边都浪费：让源锚定工具去探索新领域，它只会说"材料里没有"；
让 agent 检索去找矛盾，它会**综合出一个通顺的、把分歧磨平了的答案**。

### 四、不要让同一方既产出又评审

**作者不应设计对自己工作的验证。** 本项目今天三次踩到这个形状，每次都靠另一方抓住。

具体到本实例：**公网检索**（没有独占视野，只是多一个同类样本）、
**对自己设计的评审**、**需要已验证发布通道的执行**——这三类不派给自己。

## 已验证的配合记录

- **ChatGPT 的审核抓对过多次**：`required_refs` 在声明的 source head 上不存在
  （按协议是无效输入，应当直接 blocked）；根因表述过松；
  以及一份派单里"read any file"与它自己报告的私钥风险相冲突。
- **Codex 的边界行为可靠**：不推 master、不吸收他方提交、
  信号里点名的评审产物不存在时**明写"没有伪造或冒充独立审核"**。
- **本实例犯过的错**：把被截断的搜索结果当成"不存在"；
  删除了一份驱动了已完成任务的派单（唯一副本，未入库）；
  并行时只问新增没问重合。**三次都是他方或人类发现的。**

这份记录不是自谦，是分派依据：**知道谁在哪种情况下会错，比知道谁更强有用。**
