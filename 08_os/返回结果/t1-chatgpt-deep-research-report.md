# Landscape of Interactive Requirement-Modeling Workflows

## What this category actually is

The workflow you described is closer to a **grounding system** than to a normal intake form: the point is not merely to collect missing facts, but to build enough shared context that both sides are now referring to the same thing. In the classic dialogue literature, this is the problem of building and updating **common ground**—shared knowledge, beliefs, and assumptions sufficient for coordinated action. That framing matters, because many current “AI planning” tools optimize for getting to an implementation plan quickly, while your target optimizes for **mutual alignment before downstream evidence collection and result modeling begin**. citeturn32search0turn40view0

Across the landscape I found, the most relevant implementations cluster into a few distinct shapes: **spec clarifiers** that patch ambiguity inside a draft spec, **coached-discovery systems** that turn a vague idea into a brief/PRD, **plan-mode products** that ask questions before code is written, **question-asking primitives** for embedding structured clarifications into agents, and **research artifacts** that benchmark or improve question quality. What I did **not** find in abundance was a turnkey open-source system whose primary artifact is an explicit, machine-checkable model of “what both parties now jointly mean,” separate from PRDs/specs/tasks. Most existing systems stop at Markdown artifacts or planning docs. citeturn9view3turn13view0turn27view0turn27view2turn25view0turn19view0

## GitHub implementations and reusable open-source methods

**`github/spec-kit`** — GitHub’s open-source Spec Kit is one of the clearest direct fits for a clarification phase. Its `/clarify` flow is explicitly designed to inspect a spec draft, identify the most important underspecified areas, and ask **at most five** clarification questions, one at a time, in dependency order. It stops when there are no more high-impact ambiguities, the question budget is exhausted, the user says they are done, or full coverage is reached. Afterward, it integrates the accepted answers back into the spec under a dedicated clarifications section rather than leaving them as detached chat history. The shape here is strongly **dynamic clarification over an existing structured artifact**, not a fixed checklist. It is a full open-source toolkit and process, but its clarify method is portable on its own. License is MIT; the repository showed about 124k stars and 1,574 commits in the surfaced snapshot. citeturn9view3turn10view0turn11view0turn5view3

**`bmad-code-org/BMAD-METHOD`** — BMAD is the broadest open-source ecosystem I found in this space. It contains multiple relevant shapes under one roof rather than a single mechanism. The **Product Brief** is a guided discovery session that produces a concise executive summary of the product concept; **PRFAQ** is an interactive challenge that forces a customer-first defense of the idea; **`bmad-prd`** creates a new PRD “via coached discovery”; **Forge Idea** runs adversarial questioning one branch at a time; and **Party Mode** creates a multi-persona room where PM/Architect/Dev/UX voices debate tradeoffs with the user in the loop. Forge Idea has the clearest stop condition: it continues until the idea is **hardened, killed, or simply clearer**, and either the user or the system can call the exit. Output varies by skill: a 1–2 page brief, `prd.md` plus `addendum.md` and `.memlog.md`, or `forge-report.html` plus sometimes `forged-idea.md`. BMAD is a full framework, but its methods are separable and reusable. License is MIT; the surfaced repo snapshot showed about 51.2k stars and 1,983 commits. citeturn9view1turn10view1turn11view1turn13view0turn13view1turn13view2turn13view3turn13view4turn36view0

**`nurettincoban/ai-prd-workflow`** — This repository is a prompt-pipeline rather than an agent runtime, but it is unusually explicit about how the clarification phase should work. The `interactive-prd-creation-prompt.md` instructs the model to classify the product type early, make skipped checks visible and auditable, ask questions in **batches of three to five**, proceed from broad foundations to specifics, and only ask follow-ups when they are truly needed for critical information. The stop rule is heuristic but clear: when enough information has been gathered to write a complete PRD, the flow switches to document production. The output is a structured PRD, then downstream prompts transform it into features, rules, and sequenced RFCs. This is highly reusable if you want to lift the method without adopting someone else’s runtime. License is MIT; the repository snapshot showed 276 stars and 36 commits. citeturn9view2turn10view2turn11view2turn31view0

**`snarktank/ai-dev-tasks`** and derivative PRD prompt repos such as **`christerjohansson/ai-product-requirement-document`** — These are simpler, prompt-only implementations of the same basic idea. The core PRD prompt tells the AI to ask only the **three to five most essential clarifying questions**, preferably as enumerated options for easy reply, with priority on the “what” and “why” rather than implementation detail. It also says not to ask questions whose answers are reasonably inferable, which is a form of lightweight stopping logic. After the gap-closing round, it produces a markdown PRD and then a task list. This family is the most directly reusable if you want a **minimal prompt scheme** rather than a framework. For `snarktank/ai-dev-tasks`, the surfaced repo snapshot showed Apache-2.0, about 7.8k stars, and 65 commits. The `christerjohansson` variant is smaller and functionally similar in the returned snippets. citeturn18view2turn18view3turn38view0

**GitHub Copilot custom-agent stack** — This is not one ready-made requirements product, but it is a very relevant substrate. GitHub’s custom agents let you define agent profiles with behavior instructions, tools, and MCP integrations. In parallel, the `askQuestions` tool in Copilot Chat can present a **series of inline questions** in a carousel UI with text input, radio, and checkbox question types; users submit answers and the chat participant receives them as structured input. On top of that substrate, the open repository `github/awesome-copilot` includes a `breakdown-feature-prd` skill that explicitly says: if the feature request is not well defined, **ask clarifying questions before generating the PRD**, and then save the PRD as markdown in the repo. So the “mechanism shape” here is: platform for structured questioning plus an installable skill pack that encodes one PRD-oriented clarification method. GitHub’s platform pieces are proprietary/hosted, while `github/awesome-copilot` is MIT-licensed and highly active; the surfaced snapshot showed about 37.1k stars and 2,111 commits. citeturn26view0turn26view1turn26view3turn18view0turn18view1turn35view0turn35view2

**`NousResearch/hermes-agent`** — Hermes exposes a dedicated **`clarify` toolset** rather than a whole requirement-modeling methodology. That tool lets an agent block and ask the user for clarification, feedback, or a decision, either as open text or as multiple choice with up to four options plus an “Other” free-text path. Hermes’s own docs and migration skills make clear that when a required user decision exists, the agent should use `clarify` rather than free-form prose, and should keep collecting required decisions before proceeding. This is therefore a strong **building block** if you want to construct your own requirement-modeling workflow with explicit user-turn checkpoints. Its stop condition is local rather than global: each clarification blocks until answered, timed out, or retried after payload correction. Output is the user’s validated answer, not a canonical spec artifact. License is MIT; the repo snapshot showed about 221k stars and 18,231 commits. citeturn9view4turn10view3turn11view3turn25view0turn25view1

**`crumplecup/elicitation`** — This Rust library is not requirements-engineering software in the usual sense, but conceptually it is one of the strongest substrates for the structured end of your problem. Its idea is that types “pull” values from the agent through a verified round-trip: `#[derive(Elicit)]` generates an elicitation routine, an MCP JSON schema, and proof methods; structs are elicited field by field; enums become finite selections; validation constraints are enforced; and the agent cannot skip required fields. In other words, the stop rule is **schema completion under constraints**, not “the conversation feels done.” Output is a typed, validated object rather than free text, which makes it unusually aligned with your requirement that the result feed downstream modeling stages. This is a library, not a product, so it is highly reusable if you are willing to code the schema/state machine yourself. The surfaced repo showed both Apache and MIT license files, GitHub surfaced “MIT licenses found,” and the snapshot showed 1,522 commits and 2 stars. citeturn29view0turn30view0turn30view2

**`Pythagora-io/gpt-pilot`** — GPT Pilot is one of the more direct “ask first, build later” coding-agent implementations. In the surfaced README text, the workflow starts with a **project description**, asks you questions to understand the project better, and then writes a feature/specification document before implementation; the project page also states that the repository is **not being maintained**. In other words, the mechanism is a live clarification interview in front of spec generation, but the accessible docs in this pass did not expose a precise numeric stop rule the way Spec Kit does. Output is a specification/project description that becomes the basis for subsequent development. It is a full tool rather than a prompt pack. In the returned snapshots, the repository had a visible `LICENSE` file, but I did not recover the exact SPDX identifier with confidence in this pass; the repo also carried a 2026 security notice about a removed supply-chain credential stealer. The surfaced metadata showed tens of thousands of stars. citeturn8view2turn8view3turn9view0

## Productized plan modes and hosted interaction designs

**Lovable Plan mode** — Lovable’s Plan mode is one of the cleanest product implementations of “do not rush into execution; first align on intent.” The docs say Plan mode is intended for cases where “thinking, exploration, or clarity is more valuable than immediate execution,” that it often asks clarifying questions to understand goals and constraints, and that it proposes a formal plan only when there is a clear implementation to propose. Many sessions end with **clarity or direction only** rather than a build decision. When a plan is produced, it appears in a dedicated Plan view and usually includes overview, assumptions, constraints, components, data models, APIs, step sequencing, and sometimes diagrams; Build mode begins only after user approval. Lovable also added a multiple-choice clarifying-question feature in its changelog, which is particularly relevant to your interest in structured alignment. This is a hosted product rather than an OSS library; I did not surface an open-source license in this pass, but the docs/changelog indicate active product evolution. citeturn27view0turn27view1turn21search8

**Replit Agent Plan Mode** — Replit’s Plan Mode has a similar shape but a more overt “project planning” framing. The docs say it is for asking questions, brainstorming, and planning without changing code or data; it can generate an **ordered task list** from requirements and, in the getting-started flow, it is explicitly described as a place where Agent can ask clarifying questions and produce a structured plan you review before approving the build. The product blog emphasizes safety: no code changes in Plan Mode, but repository inspection and context-aware discussion are still allowed. Its stop condition is therefore user-governed: a plan may be refined and then accepted, at which point the flow transitions into Build Mode. This is again a hosted product rather than a reusable open-source package; the surfaced docs also show that Plan Mode requires Replit Core. citeturn27view2turn27view3turn27view4turn27view5

## Research artifacts, benchmarks, and papers worth stealing from

**`jdm4pku/ReqElicitBench` and the ReqElicitGym paper** — This repository is not a deployable requirement-modeling front end; it is an **evaluation environment** for conversational requirements elicitation. It includes 101 requirements-elicitation scenarios, an oracle user grounded in predefined implicit requirements, and a judge that tracks which implicit requirements are elicited turn by turn. The mechanism is therefore a simulation harness for measuring how well an interviewer agent asks questions, not a finished product for stakeholder conversations. Its output is conversation logs plus quantitative metrics about elicitation performance. For your use case, this is valuable mainly as a way to **evaluate a self-built clarification stage** rather than as the stage itself. The surfaced repo had no license file in the returned snapshot, and showed 8 stars and 4 commits. citeturn19view0turn23view0turn23view2turn34search14

**`anmolsinghal98/Requirements-Elicitation-Follow-Up-Question-Generation`** — This artifact is more modular: it focuses on the quality of the **next follow-up question** in requirements interviews. The repo generates context-aware follow-up questions from interview history, evaluates questions against **14 quality criteria**, and then generates improved questions that satisfy those criteria. That means its mechanism shape is not “run the whole elicitation session,” but “improve the local question-selection and question-quality layer.” Output is CSV-based artifact data: generated questions, classifications against criteria, and improved versions. For a self-built system, this is quite useful because one of the major failure modes in clarification workflows is not lack of questions, but bad questions. The surfaced repo is Apache-2.0 and small/academic in activity. citeturn19view1turn23view3turn23view5turn34search0

**`ygan/ClarQ-LLM`** — ClarQ-LLM is a benchmark for models that clarify and request information in task-oriented dialogue. It is not requirements-specific, but it is directly about the skill you care about: deciding whether to ask for clarification and how effectively to do so. The repository includes tasks, interaction scripts for conversational agents, and evaluation tooling; the repo README reports benchmark metrics such as success rate, query discrepancy, and query length in Chinese and English. The mechanism shape is again **evaluation harness rather than production workflow**. Output is benchmark runs and metrics, not a PRD/spec. This makes it more useful as a testbed for your own clarification policy than as a plug-and-play requirement modeler. License is MIT; the surfaced repo showed 7 stars and 3 commits. citeturn19view2turn23view6turn23view7

**“Curiosity by Design: An LLM-based Coding Assistant Asking Clarification Questions”** — This 2025 preprint is one of the more relevant architectural references for your first stage. It proposes a two-part pipeline: first a **query classifier** detects whether the request is ambiguous/under-specified; then a fine-tuned LLM generates a clarification question; once the user replies, the assistant proceeds to the final code answer. If the input is already clear, it skips questioning. This is important because many current implementations ask questions heuristically, whereas this paper explicitly separates **ambiguity detection** from **question generation**. The output is not a structured demand model by itself; it is a clarification question followed by better downstream code answers. In the surfaced sources, this appears as a paper/prototype reference rather than a public mature GitHub product. citeturn19view3turn20view0

## Where existing solutions still miss your exact target

The strongest existing implementations are good at turning a vague prompt into a **plan, PRD, or spec**, but they are usually weaker at constructing an explicit, durable object representing **mutual understanding itself**. Spec Kit comes closest on the spec side because it writes clarifications back into the spec; BMAD comes closest on the conversational side because it treats analysis as its own phase and preserves artifacts such as briefs, memlogs, and forge reports; Lovable and Replit come closest on the product UX side because they visibly separate “thinking/clarifying” from “building.” But across these systems, the dominant artifact is still a markdown plan or PRD, not an explicit schema of propositions, assumptions, resolved ambiguities, unresolved risks, and accepted terminology that can be independently consumed downstream. citeturn5view3turn13view0turn13view2turn27view0turn27view2

A second gap is that **stop conditions are almost always heuristic**. Strong examples exist, but they are still pragmatic rather than epistemic: Spec Kit caps at five questions; `ai-dev-tasks` caps at three to five essential questions; `ai-prd-workflow` uses “sufficient detail” as the criterion; Lovable and Replit stop when a plan can be proposed or the user is satisfied; BMAD Forge ends in hardened/killed/clearer outcomes. I did **not** find an off-the-shelf implementation that publicly describes its stop rule as “question until expected ambiguity reduction falls below threshold,” or “until all high-value propositions reach mutual acceptance confidence.” That is a notable gap if your top priority is alignment quality rather than development throughput. citeturn5view3turn18view2turn31view0turn27view0turn27view2turn13view2

If you decide to build your own, the most promising directions are these. First, take **grounding/common-ground** seriously and make it an explicit artifact: track named concepts, accepted propositions, rejected interpretations, open ambiguities, assumptions, and evidence links rather than relying on chat transcript residue. Second, borrow from **typed elicitation**: the `elicitation` crate shows how to derive question flows from schemas and constraints, which is exactly the kind of structure that makes downstream evidence collection tractable. Third, separate **ambiguity detection** from **question generation**, as in *Curiosity by Design*, instead of prompting a general model to “just ask helpful questions.” Fourth, use a research harness like ReqElicitBench plus the follow-up-question-quality repo to evaluate not only final PRD quality, but also question efficiency, missing-need coverage, and conversational repair behavior. If your aim is truly “both sides now mean the same thing,” then the current market is pointing toward a **hybrid**: grounding theory for the objective, typed/schema-driven elicitation for the artifact, and benchmarked question-quality modules for the interaction policy. citeturn32search0turn40view0turn29view0turn19view3turn19view0turn19view1
