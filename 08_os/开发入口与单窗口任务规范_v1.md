# 08 OS 开发入口与单窗口任务规范 v1

> 状态：v1；仅当本文件存在于当前 `master` 时为活动规范。
>
> 适用对象：Human、前台审计模型、Claude Code、Codex 及其他被授权执行者。
>
> 目的：让一个全新的窗口只读取最小材料，就能判断 `08_os` 是什么、任务文件放在哪里、
> 哪些内容可修改、如何记录证据、何时可以提交或进入 `master`。

本文件只保存 `08_os` 专属的增量规则。所有执行者先遵循仓库根部
`AGENT_WORKING_DISCIPLINE.md` 与 `AGENTS.md`；输出控制、证据诚实、不可逆动作预告等
全仓纪律不在这里重复。目录语义、机制定义和机器契约仍以本文件引用的 canonical 文件
为准；本文件不复制或取代那些定义。

## 1. 新窗口最小加载顺序

一个新窗口只处理一个任务，开始时按以下顺序加载：

1. 读取远端 `master` 的当前精确 40 位 SHA；不要沿用聊天中的旧 SHA。
2. 读取 `AGENT_WORKING_DISCIPLINE.md`、`AGENTS.md` 和任务要求触发的协议入口。
3. 读取 `08_os/README.md`，理解区域职责和 ownership。
4. 读取本文件。
5. 读取任务直接涉及的 canonical README、实现文件和对应 registry。
6. 仅在任务需要复验历史证据时读取指定的 `_runs/<run-id>/`；禁止默认加载全部历史。
7. 读取 Human 给出的任务包、allowed paths、prohibitions 和 completion pointer 契约。
8. 若当前 `master` 已包含并在 registry 登记仓库级 Git hooks 守卫，在受保护发布前执行
   `git config --get core.hooksPath`，确认配置指向该 canonical hooks 路径；缺失或不一致时
   停止发布。若当前 `master` 尚无已登记守卫，记录 `hook_guard: not_applicable`，不得引用
   未进入 `master` 的 hooks 文件作为规则。

发现任务包与物理 Git 状态、registry 或 canonical 文件不一致时，以物理 Git 状态为事实，
停止写入并回传冲突。旧聊天、旧分支和旧 receipt 不能覆盖当前 `master`。

## 2. 一个窗口一个任务

每个窗口必须满足：

- 一个 `task_id`；
- 一个明确目标；
- 一个工作分支；
- 一个精确 base SHA；
- 一组精确 allowed changed paths；
- 一套验收测试；
- 一个 completion pointer；
- 不顺手修复其他问题。

发现旁支问题时，只记录为 finding 或后续任务，不扩展当前 diff。需要第二个目标时，结束
当前任务并开新窗口。这样做是为了压缩上下文、降低误合并和陈旧记忆风险，不代表形成了
技术访问控制。

## 3. 文件放置规则

| 内容 | canonical 位置 | 是否 tracked | 是否进入 registry | 处理规则 |
|---|---|---:|---:|---|
| 工作流阶段规格与实现 | `01_workflow/<stage>/` | 是 | 是 | 规格与实现分开，显式版本 |
| boot 清单与启动契约 | `02_boot/<name>/` | 是 | 是 | 只放启动顺序、版本、失败策略 |
| 跨阶段全局机制 | `03_mechanisms/<mechanism>/` | 是 | 是 | protected/versioned |
| 外部 skill 与工具说明 | `04_skills_and_tools/<tool>/` | 是 | 是 | 不因登记自动加载 |
| 文件/path-set 注册信息 | `05_registry/*.yml` | 是 | 本身为 registry | 与结构变更同一批次更新 |
| loader、wrapper、validator | `06_execution/<area>/<name>/` | 是 | 是 | 不放机制定义正文 |
| 领域内容 | `07_content/` | 是 | 按所属 registry | 不混入机制与运行流量 |
| 活动开发设计与被取代版本 | `_dev/` | 是 | 是 | supersede，不抹历史 |
| 共享 OS 开发/研究/迁移/验证证据 | `_runs/<unique-run-id>/` | 耐久时是 | 否 | core-owned，按证据策略保留 |
| 领域业务或领域 workflow 流量 | `.ai/PROGRAM_RUNS/<run-id>/` | 耐久时是 | 否 | domain-owned |
| private、scratch、临时 workspace | 仓库外或 run 内 `_runtime/` | 否 | 否 | 完成后删除 |

仓库级 hooks 只有在文件进入当前 `master`、有明确用途说明、正负例验证和 registry entry
后，才能作为 canonical 守卫引用；其具体路径由对应接入任务决定，本规范不预先声明。

判断口诀：

- 定义“系统是什么”放 canonical 区域；
- 定义“如何加载或验证”放 `06_execution/`；
- 记录“某次开发发生了什么”放 `_runs/`；
- 仅供当前执行过程使用的内容放仓库外或 `_runtime/`；
- 不确定时先不创建文件，先查 registry 和相邻 README。

## 4. registry 同步规则

任何新增或移动的 canonical 文件/path-set，都必须在同一任务中更新对应 registry；不得
先提交文件、以后再补 registry。

registry entry 至少说明：

```yaml
- path: <exact-path-or-path-set>
  purpose: <what-it-is-for>
  loader: <what-reads-it>
  loader_class: in_repo_program | external_tool_convention | host_application
  discovery: <how-it-is-found>
  evidence: <what-proves-the-loader-claim>
  cache_dirs: []
  failure_surfacing: <when-a-problem-becomes-visible>
  deletion_rule: protected | human_decision_required | free
```

`08_os/_runs/**`、`.ai/PROGRAM_RUNS/**`、`_runtime/**` 和角色 private/scratch 不注册。
registry 描述系统结构，不描述运行流量。

## 5. run 与证据目录

每个新 run 必须使用当前 `master` 中未被占用的唯一 `run-id`。旧分支上的 run 编号不能
直接复用；创建前必须搜索当前 `master` 和待引用历史分支。

只创建实际有内容的阶段目录。常用结构为：

```text
08_os/_runs/<run-id>/
├── run.yml
├── 01_任务输入/
├── 03_方案设计/
├── 06_执行/
├── 07_测试执行/
└── 08_结论/
```

`run.yml` 至少记录 task、base、branch、ownership、目的、输出、验证和生命周期状态。
状态必须与真实仓库状态一致，例如：

- `research_only`
- `candidate_pending_validation`
- `candidate_ready_for_independent_review`
- `verified_on_demand`
- `integrated_and_verified_on_demand`
- `deferred`
- `excluded`

不得用 `passed` 掩盖“只证明安装”“只证明可执行”或“只证明正例”。证据必须区分：
availability、functional correctness、security boundary、repeatability 和 integration。

## 6. 分支与发布纪律

`08_os` 的分支与发布遵循根级工作纪律；本区域额外要求：

1. 从当前远端 `master` 的精确 SHA 创建新分支，或使用 Human 明确指定的精确父提交；
2. 修改前确认分支、HEAD、远端 master 和 worktree；
3. 只修改 allowed paths；
4. 执行测试并生成可回放证据；
5. 普通 push 工作分支；
6. 回传 completion pointer；
7. 由符合第 9 节独立性要求的新窗口审核；
8. 获得 Human 明确授权后，才允许普通 fast-forward 更新 `master`。

旧分支只作为证据源。需要采用其中内容时，从当前 `master` 新建分支，逐项重建、复测并
重新生成 registry 与 run 证据。禁止把从旧 master 分叉的候选直接并入当前 master。

## 7. 任务包必须包含的字段

```yaml
task_packet:
  task_id: <unique-id>
  repository: chris2gao/Cybernetic_City_State_OS_v2---core
  risk_tier: T0_mechanical | T1_standard | T2_semantic | T3_high_risk
  exact_base_sha: <current-remote-master-or-approved-head>
  branch: <new-or-human-approved-task-branch>
  objective: <one-bounded-goal>
  source_evidence:
    - <exact-path-or-commit>
  allowed_changed_paths:
    - <exact-path-or-prefix>
  required_tests:
    - <command-or-machine-gate>
  prohibitions:
    - modify_master_without_human_gate
    - force_push
    - rebase
    - squash
  required_completion_pointer: <declared-shape>

  executor_profile:                 # 可选、运行时本地、只用于路由
    provider: <provider-name>
    model: <runtime-model-name>
    reasoning_effort: <runtime-supported-value>
    authority: routing_only
```

`risk_tier` 是供应商无关的任务语义，必须保留。`executor_profile` 是可变的运行时路由信息，
不授权任何动作，也不能代替 Human gate；使用前必须在当前执行环境核验可用性。

Human 当前提供的 Codex 运行时选项为：

```yaml
Codex:
  models:
    - "gpt sol 5.6"
    - "gpt terra 5.6"
    - "gpt luna 5.6"
  reasoning_effort:
    - low
    - medium
    - high
    - ultra
```

这些名称和档位不是 OS 的永久协议。它们变化时更新任务包或运行时配置，不修改
`risk_tier` 的含义，也不得把某个模型名称写成能力、正确性或授权的保证。

任务描述不能只写“完善”“检查一下”或“接入工具”。它必须定义成功、失败、停止条件和
不做什么。

## 8. 测试与证据标准

最低要求：

- 正例、负例和边界例；
- 预期退出码与实际退出码；
- 基线与候选对照，明确 candidate-caused failures；
- 版本、runtime、依赖和隔离状态；
- 重复性或输出哈希，适用时至少多次运行；
- changed paths 与 allowlist 精确比对；
- `git diff --check`；
- 无个人绝对路径、secret、临时二进制和进程残留；
- 失败时 fail closed，不能把 tool crash 算成业务失败；
- 不能观测的指标明确写 `not_observable`，不得估算成事实。

机器结果、环境 receipt、manifest 和 Human 结论之间必须一致。后生成的最终环境不能仍由
较早 `results.json` 代表。

## 9. 独立审核与 Human gate

实现/执行窗口与最终审核窗口必须是不同会话。独立审核窗口负责：

- 验证 branch/head 拓扑；
- 复核 changed paths；
- 读取关键实现与机器证据；
- 查找声明与证据冲突；
- 判断是否存在 blocking findings；
- 明确 `ready_for_human_integration`、`fix_required` 或 `rejected`。

对于 `T2_semantic`、`T3_high_risk`、任何 master 接入任务，或已经经历修正轮次的任务，
派单会话不得兼任最终独立审核；优先使用不同模型族。派单者可以做初步核对和整理
findings，但不能把该核对称为最终独立验收。

Human 明确豁免会话或模型族独立性时，审核报告必须披露：谁派单、谁执行、谁审核、哪些
角色重合，以及因此仍未被独立覆盖的风险。

Human 决定是否进入 `master`、是否改变架构语义、是否安装或连接高风险外部能力。条件授权
必须写清前置门；执行者不能自行扩大授权范围。

## 10. completion pointer 最小模板

```yaml
completion_pointer:
  packet_id: <task-id>
  status: ready_for_independent_review | blocked | integrated
  source_branch: <branch>
  source_base: <40-char-sha>
  source_head: <40-char-sha>

  validation:
    tests: <actual>
    candidate_caused_failures: <actual>
    diff_scope: passed | failed
    hook_guard: passed | failed | not_applicable

  repository:
    changed_paths:
      - <actual>
    out_of_scope_paths: 0
    binary_artifact_count: <actual>
    worktree_clean: true

  publication:
    push_performed: true | false
    master_modified: false | true
    force_push: false

  next_owner: foreground_independent_review | Human
```

所有计数、SHA 和路径必须来自实际运行或远端读回，不能复制任务包中的期望值冒充结果。

## 11. 停止条件与修正预算

出现以下任一情况时停止写入并回传：

- base SHA、branch 或 master 与任务包不一致；
- worktree 含不属于本任务的变更；
- 需要修改 allowed paths 之外的文件；
- run-id 与当前 `master` 冲突；
- 需要网络、sudo、系统安装、模型调用或数据外发，但任务未授权；
- 测试无法证明声明；
- 发现 canonical 语义需要 Human 决策；
- 已登记 hooks 守卫存在但未正确启用；
- 无法保证普通 fast-forward，或需要 force/rebase/squash。

初次交付后，同一任务最多允许两轮带有**新证据、新假设或新 remedy** 的定点修正。
原样重跑同一失败命令、重复同一声明或没有新证据的改写，不算修正轮次，属于无效重复。

第二轮修正后仍存在 blocking finding 时：

1. 不得在原任务中发起第三轮修正；
2. 冻结并保留当前分支与证据；
3. 把未闭合问题拆成新的根因任务；
4. 升级给 Human 或总架构决定继续、替换路线、降级或终止。

停止不等于失败。正确暴露边界比生成一个看似完整但不可审计的提交更重要。
