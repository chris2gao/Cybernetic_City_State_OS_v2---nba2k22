## 0. 这份文档解决什么问题

本文件不是运行规范的替代品，也不是一次性的项目复盘。它提供一个面向 Human 的长期总览，用来回答四个问题：

1. 实现上下文管理之前，第二代 OS 是什么状态；
2. 实现之后，系统结构和运行方式发生了什么变化；
3. 这些变化分别通过哪些需求、研究、实验、迁移和审核动作实现；
4. 当前哪些能力已经被证据支持，哪些仍然只是候选、限制或后续测试项。

运行时 canonical 规则仍以以下文件为准：

- `方法论_v1.md`
- `文件隔离与产物生命周期_v1.md`
- `实现/文件布局契约_v1.yml`
- `实现/verify_context_structure.py`
- `依据材料/requirement/A_需求建模_v2.yml`
- `依据材料/evidence/07_证据索引与可行性判断_v1.yml`

本总结的作用是把这些分散的规范、证据和开发历史连接成一幅可以直接检查的系统图。

| 发布边界 | 私有目录命名和角色自律承担较多保护责任 | canonical 要求精确 allowlist、禁止宽泛暂存/打包并执行 private sentinel 负测；受控实验已验证相应原语，全面发布执行器仍属后续实现 |
| 文件生命周期 | 机制、开发材料、运行证据和私有过程的落点不完整，容易混放 | 机制定义、boot、registry、loader、开发设计、OS 开发 run、领域 run、private runtime 均有独立路径和保留规则 |

## 2. 实现前的系统状态

### 2.1 已经具备的基础

第二代 OS 在上下文机制开发前并不是空白系统。它已经形成七个主要区域：

- `01_workflow`：01–07 工作流阶段；
- `02_boot`：启动与环境信息；
- `03_mechanisms`：通用机制预留区；
- `04_skills_and_tools`：外挂技能与工具；
- `05_registry`：文件和 path-set 注册；
- `06_execution`：初始化、重载和执行入口；
- `07_content`：领域内容。

同时，workflow 的基本开发纪律已经存在：A 需求建模、信息收集、B 结果建模、测试、步骤拆分、执行与审核形成显式阶段；设计依据保留在 `_dev`，运行验证保留在 `_runs`。

### 2.2 尚未形成的能力

上下文管理当时仍主要表现为设计意图，而不是一个独立、可加载、可验证的全局机制：

1. **共享聊天仍是事实恢复的重要隐含来源。** 新模型能否继续工作，取决于是否重读历史、是否有人重新解释任务。
2. **“最小上下文”缺少机器边界。** 虽然派单可以收窄信息，但没有统一入口、依赖指纹和失效判定。
3. **任务、角色和文件生命周期没有统一契约。** private、handoff、公开产物、开发证据和长期机制文件的落点没有被一套结构同时约束。
4. **工作区分离与访问控制概念混用。** 历史活动文件曾认为每角色 worktree 可以形成真边界，但没有运行负例支撑。
5. **孵化位置在机制成熟后不再适合作为 canonical。** 早期把“建设系统本身”作为完整 workflow 的手工自举题目，并在 workflow 实例中集中暴露上下文、角色和加载需求，是有意的按需提取策略。研究、实验和结构规则成熟后，若继续把该实例当作 workflow-owned canonical，才会让未来模型误解为“阶段二的一个项目”，并造成全局归属、加载与复用歧义。
6. **boot、registry、loader 和 validator 没有形成完整链路。** 机制可能存在于目录中，但系统还不能稳定回答“启动时加载什么、谁发现它、引用缺失时在哪里失败”。
7. **孵化产物在成熟后需要分层提升与归档。** 孵化阶段允许 A、研究证据、运行试验、活动规范和机制正文集中产出，以便从真实实现中测量需求；成为全局机制后，则应按 mechanism、`_dev`、`_runs`、boot 和 loader 的不同生命周期拆分，避免临时开发实例继续承担 canonical 职责。

### 2.3 最初真正要解决的问题

A v2 将目标稳定为：不依赖模型持续对话记忆，使一个完整需求从开始到结束可追踪，并让不同角色默认只获得完成自身职责所需的上下文，以降低污染、误读、注意力漂移和无效 token 消耗。

这个目标从一开始就不仅是“压缩提示词”，而是同时涉及：

- 角色有效上下文；
- 任务状态持久化；
- 结构化交接；
- 文件与访问边界；
- 版本和 stale；
- 发布与清理；
- Web 模型受限参与；
- Human 与规划角色的审批责任。

## 3. 需求如何在开发中被修正

### 3.1 A v1 的问题

初版需求曾把“每任务、每 Web 角色一个独立受限 GitHub 仓库”写成成功判据和约束。这把一种具体实现提前固化成了需求本身，并把尚未实测的仓库生命周期成本变成阶段二的阻断项。

独立审核指出：阶段二不能一边保留 A 中的硬实现，一边在最终证据中把它降级为 B 的可选候选。

### 3.2 A v2 的修订

Human 确认后，A v2 改成结果导向：

- Web 交接空间必须按任务和 Web 角色独立授权；
- Web 角色不能读取主仓库、其他任务或其他角色空间；
- 边界必须可撤销、可审计；
- 只暴露获准输入，只接收结构化结果；
- 独立仓库、受控网关或其他同等实现由 B 比较并由测试验证。

这个修订没有降低隔离要求，而是把“必须达到什么结果”和“采用什么实现”重新分开。它使阶段二可以诚实地完成研究闭包，同时把真实实现成本留到 B 选型后的相应测试门。

## 4. 这些变化是怎么实现的

## 4.1 第一条链：研究与证据闭包

阶段二使用了两条相对独立的外部研究路线、第三方候选匹配、内部证据抽取、同义裁定和 Chapman 开放发现统计。研究形成了几个稳定结论：

1. 长上下文、无关信息和位置效应会影响模型表现，但不同模型和任务的强度不同，不能绝对化；
2. 现有多代理框架普遍包含持久化、handoff、过滤、子代理、事件记录和依赖状态等机制族；
3. 固定入口、版本化交接、依赖指纹、最小加载和生命周期清理可以组合成一个低控制面方案；
4. workspace partition 与技术访问边界必须分开建模；
5. 当继续宽泛研究不再改变 B 的主要结构或验收标准时，应转向运行试验或停止。

最终证据索引将研究问题、首发来源、独立性、边界、截断、不可访问来源和停止理由结构化，并给出 `partially_supported` 的可行性判断，而不是“研究完成即机制完整”。

## 4.2 第二条链：run-007 本机运行试验

run-007 把最高 EIG 的问题转成六个本机实验：

| 实验 | 结果 | 对系统设计的影响 |
|---|---|---|
| ENV-01 | passed | 明确当前 Windows、非提升进程、Git/Python/PowerShell 和工具边界 |
| PART-01 | failed | executor 成功读取 planner 兄弟 clone sentinel，推翻“clone/worktree 是访问边界” |
| BOUND-01 | passed with limits | Windows DACL 可拒绝受测正常 read-data 路径，但不是生产沙箱，也不抵御管理员或主动改 ACL |
| RESTORE-01 | passed | 新进程只从固定入口列出的三个授权引用恢复并完成任务 |
| HANDOFF-01 | passed | planner→executor→reviewer 闭环完成；上游哈希变化后旧入口确定性 stale |
| SIZE-01 | passed as proxy | executor/reviewer 最小入口包显著小于全量材料，但只证明输入体积缩小，不证明模型质量提高 |

这个试验还暴露了一条关键发布规则：早期 helper 使用宽泛暂存时，private sentinel 可能泄漏；修复后发布改为显式 allowlist。因此“private”目录名不能当作保护机制。

## 4.3 第三条链：阶段二收口与独立审核

第一次收口候选通过了 Git、范围、YAML 和历史保留检查，但 Codex 独立审核发现 F-01：最终证据把 repo-per-role 从 A 的硬要求降成可选候选，却没有先修订 A。

修复路径不是修改一句状态，而是：

1. 保留 A v1 和 Human 确认 v1 作为历史；
2. 新增 A v2 和 Human 确认 v2；
3. 重新生成 RQ-05、证据条目、可行性判断和 mechanism 3 handoff；
4. 再次执行 YAML、交叉引用、九项阶段完成条件和历史保留回归。

这一步建立了一个重要开发纪律：**下游收口不能暗中降低上游需求；需求变化必须版本化并获得 Human 确认。**

## 4.4 第四条链：run-008 结构迁移

Human 检查发现，上下文管理在孵化成熟后本质上是全局机制，不应永久位于 workflow。这一裁决没有否定早期以完整 workflow 自举并从实现中提取环境机制的合理性，而是确定成熟后的 canonical 归属。run-008 依据旧 workflow 开发模型和完整 Claude–Human 开发日志进行了结构迁移：

- 20 个 requirement/evidence 文件通过 Git rename 迁入 `03_mechanisms/context_management/依据材料/`；
- 在全局机制下建立方法论、文件生命周期、机器布局契约和 validator；
- 在 `02_boot` 建立启动清单；
- 在 `05_registry` 建立机制注册；
- 在 `06_execution` 建立 loader 说明；
- workflow 阶段二只保留信息收集的通用规则，并引用全局上下文机制；
- `_dev` 新增开发产物与文件隔离规范；
- `_runs` 保留 run-007 原始证据，并新增 run-008 迁移记录；
- `.gitignore` 排除每个 run 的 `_runtime` 私有区。

这一步把“机制正文、开发依据、运行证据和私有过程”从混合目录拆成了不同生命周期区域。

## 4.5 第五条链：run-009 结构复核修订

结构迁移后又发现两个不能留给未来模型的矛盾：

- F-02：活动 D2 文件仍把 worktree 写成真边界；
- F-03：`CORE_MANIFEST.yml` 把 `08_os/_runs` 声明成 domain-owned，但 core 又实际跟踪 run-001 至 run-008。

run-009 的修复包括：

1. 将旧 `决定_谁执行.md` 版本化为 `决定_谁执行_v0.1.md`；
2. 新增活动 `决定_谁执行_v0.2.md`，明确 worktree/clone 只属于 workspace partition；
3. 同步阶段六 README、阶段六方法论、协作伙伴、workflow 活动设计、boot 和 registry；
4. 扩展 validator，使其检查 D2 版本、旧引用、假边界措辞和双 run root 所有权；
5. 将共享 OS 开发与验证 runs 定义为 core-owned `08_os/_runs/`；
6. 将领域业务运行流量定义为 domain-owned `.ai/PROGRAM_RUNS/`；
7. 两类 private runtime 都必须不跟踪并由 `.gitignore` 排除。

最终候选通过独立复核后，以纯 fast-forward 集成到 `master@cdf9ee4...`。

## 6. 当前机制的运行模型

本节首先描述已经建立的 canonical 契约和机器结构。除明确写明 run-007 实测的部分外，不应将这些规则理解为已经覆盖所有真实任务的自动运行编排。

### 6.1 三个信息平面

1. **角色有效上下文**：当前调用需要的最小入口与获准引用，可重建、可 stale；
2. **耐久系统事实**：A、证据结论、B、测试、正式 handoff、里程碑、审核和最终产物；
3. **事件与审计**：运行日志、失败证据和清理残余，不默认注入模型上下文。

### 6.2 task × role 文件区

机器布局契约规定每个任务角色逻辑上具有：

- `entry`：固定恢复入口；
- `inbox`：获准接收的结构化输入；
- `private`：角色私有过程，不进入 Git；
- `outbox`：待发布内容，必须经过 allowlist；
- `artifacts`：正式产物；
- `audit`：运行、失败和边界证据。

workspace 优先位于仓库外；必须位于仓库内时，只允许放在相应 run 的 `_runtime/`，并由 `.gitignore` 排除。

这些区域目前是 canonical 布局与结构 validator 的检查对象，不等于生产级访问隔离，也不证明它们已经由统一 runtime 为所有任务自动创建。

### 6.3 两种边界

```text
workspace_partition != enforced_access_boundary
```

- clone/worktree、目录和默认加载面负责组织分区；
- ACL、容器、受限 tool root 或网关负责技术拒绝；
- 任何强边界都必须同时通过允许和拒绝正负例；
- 当前 DACL 证据只支持受测正常读取路径，不支持生产级强隔离声明。

### 6.4 恢复、handoff 与 stale

固定入口至少绑定：

- task_id、role、当前阶段和状态；
- 待办、阻塞和获准引用；
- 依赖版本或内容哈希；
- 输出路径和 stale 检查路径。

canonical 要求跨角色 handoff typed、versioned，并包含状态、阻塞、产物、测试和补充申请。run-007 已在受控最小 planner–executor–reviewer 实验中验证恢复、handoff 和 stale checker；上游依赖变化后，规则要求 stale 角色停止，规划角色判断从哪个阶段重跑。覆盖所有真实任务的自动阻断、补充审批和重跑编排尚未形成。

### 6.5 发布和清理

canonical 要求发布只能从显式 allowlist 选择路径，private sentinel 负测证明私有内容不会进入提交、交接包或上传包，并禁止宽泛暂存和全仓打包。run-007 验证了受控原语；全面发布和清理执行器仍属后续实现。

任务清理顺序是：

1. 提取耐久事实；
2. 保留正式失败、残余和审计引用；
3. 删除低价值 private/scratch。

最终成功不能覆盖曾经发生的失败、副作用或未清理残余。

## 8. 还没有验证什么

当前可行性结论仍是 `partially_supported`，不能写成“上下文机制已经生产完成”。主要未验证项包括：

1. **真实完整小型 OS 任务闭环。** run-007 是受控最小任务，不等于真实开发任务中的语义完整度、补充轮次、错误率和最终质量。
2. **最小上下文的质量收益。** 已测输入体积，没有精确 token，也没有证明模型质量提高、遗漏减少或补充次数下降。
3. **生产级访问隔离。** DACL 只覆盖受测正常读取路径；容器、受限工具根或网关尚未完成选型和真实威胁模型验证。
4. **Web 受限交接的具体实现成本。** B 尚未选择独立仓库、受控网关或其他方案；选型后必须验证独立授权、越界拒绝、撤销、审计和运营成本。
5. **跨领域泛化。** 当前验证来自第二代 OS 软件/机制开发任务，还没有证明其他领域不需要新的字段、角色或交接分支。
6. **自动化成熟度。** 已有结构 validator 和受控实验脚本，但完整任务编排、自动补充审批、清理执行和全生命周期控制仍未形成生产自动化。
7. **两个早期合成临时目录残余。** run-007 已披露，需新的宿主权限或 Human 清理决定；不能因后续成功而删除记录。

## 12. 当前结论

这次开发完成的不是一个“给模型多放几个记忆文件”的功能，而是把上下文管理提升为第二代 OS 的全局控制机制：

- 它定义模型默认看到什么；
- 定义角色如何恢复和交接；
- 定义上游变化如何让下游失效；
- 定义 private、公开产物和长期事实如何分区；
- 定义 workflow、boot、registry、loader、validator 和 run 历史如何连接；
- 也定义哪些能力尚未被证明，不能被宣传性措辞覆盖。

截至当前基线，机制已经具备进入后续 B 建模和真实任务验证的结构质量与证据基础，但仍是一个经过验证的原型，而不是生产级上下文安全系统。
