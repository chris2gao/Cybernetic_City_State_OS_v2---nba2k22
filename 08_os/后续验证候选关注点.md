# 第二代 OS · 后续验证候选关注点

状态：**仅记录候选问题，不代表已经确认的系统需求，也不阻塞当前 workflow 核心机制的实现。**

记录日期：2026-07-29

## 一、已经确认的开发前提

1. 第二代 OS 不是第一代的升级版本，而是一套从 workflow 重新开始的新系统。
2. 当前阶段先做 workflow 原型，逐个实现各阶段的核心机制，并验证每个机制进入后能够有效运行。
3. 上下文管理、通信、任务记录、注册表、加载与重载等全局环境机制，不预先一次性设计；在 workflow 实现过程中根据真实摩擦逐步提取和完善。
4. 第一代 OS 只作为已经付过成本的经验库和可选机制来源。需要时选择性移植或借鉴，不整体继承。
5. 第二代开发完成后，新建独立仓库，直接放入新的 OS。第一代的活动状态、任务记录、历史运行产物和兼容包袱不迁移；新仓库从第二代的干净运行基线开始。

## 二、当前唯一优先事项

逐个实现 workflow 各阶段的核心机制，并以真实运行验证：

- 机制能否稳定接收上游产物；
- 能否产生下游可以直接消费的耐久产物；
- 完成和失败是否能够被判定；
- 第一版即使手工、缓慢、只覆盖主路径，是否仍然能够实际跑通。

在核心机制尚未跑通前，不因追求完整性而提前建设大规模全局控制面。

## 三、以后需要通过 workflow 验证的候选关注点

以下事项目前只是观察到的候选问题。每一项都必须经过第二代 workflow 的需求建模、证据收集、结果建模和测试生成，确认是真实需求后才进入实现；若证据不支持，应当删除而不是保留为“可能以后有用”。

### 1. 阶段契约

是否沿用、改造或替换第一代的任务契约形状；一个阶段最少必须声明哪些输入、输出、完成条件、允许范围、停止条件和返回信息。

### 2. 人类语义裁定的耐久表达

需求共识、结果 framing、凭证选择等必须由人类承担责任的语义绑定，是否需要形成可读取、可追溯、可参与状态推导的耐久产物。

### 3. 完成判定与独立审核结果

“测试通过、实现符合 B、没有绕过测试”三项判断如何落盘；是否需要结构化的 `review_verdict`，使完成状态可以从产物推导，而不是依赖聊天记忆。

### 4. `_dev/` 与 `_runs/` 的生命周期

设计稿、调研运行记录和方法论证据中，哪些是临时交通，哪些是后续判断所依赖的原始证据；保留、归档、删除和注册的边界如何确定。

### 5. 上下文分区是否需要成为访问边界

局部上下文只是一种加载纪律，还是需要通过独立工作树、路径挂载或权限机制成为真实访问边界；只有实测成本与收益后再决定。

### 6. 全局环境机制

从实际 workflow 运行中提取并验证：

- 上下文加载、卸载与重载；
- 模型间通信；
- 任务与运行记录；
- 文件与加载关系注册表；
- 工作流和机制加载器；
- 工具可用性与版本实测；
- 失败显形与恢复机制。

### 7. 新仓库切换

第二代成熟后，如何定义“可以新建正式仓库”的完成条件，以及哪些文件属于新系统最小干净基线。

## 四、使用规则

1. 本文件不作为实现清单直接派工。
2. 候选项不得因为已经写在这里就被视为需求。
3. 每一项进入开发前，必须由当前 workflow 形成 A、证据、B 与测试。
4. 若某项不能改变实际运行结果，或其信息增益不足，应当明确放弃。
5. 当前优先级始终是：**先让各阶段核心机制真实运行，再让全局机制从运行中生长。**
