## 原生交易路径与参数证据

窄范围名称发现扩大到`Franchise_Trade_*`后，找到原先仅查`TRADE::`等字符串遗漏的共享业务核心。静态PE分析结合运行时元数据恢复了1668-byte `FRANCHISE_TRADE`，内含18个92-byte交易元素。玩家元素的FromTeamId/ToTeamId、PlayerId和ElementType、估值字段均有原生读写证据；`IsAIInitiated`为+8的bit22，`ForceLegalMoney`为bit23。本测试只在自有输入缓冲区设置前者，后者保持false，没有改游戏对象来绕过规则。

| 入口 | RVA | 已确认参数/用途 |
|---|---|---|
| AddPlayerElement | `0x12dec20` | `int(TRADE*, TEAM* from, TEAM* to, PLAYER*)`；原生生成双向玩家元素及估值 |
| Validate | `0x12ec930` | `int(TRADE*)`；基础结构、身份及所有权校验 |
| Full Check | `0x12e1800` | `int(TRADE*, bool currentTeamInTrade, context*, int1, int0, int32* out)`；完整交易规则检查 |
| 共享提交包装入口 | `0x132b840` | `int(TRADE*, int32* optional_out)`；本地模式下先Full Check，成功后Process |
| Process | `0x12e93b0` | `int(TRADE*, context*, int32* optional_out)`；多片段业务核心，含名单/球员/财务及事件调用 |

包装入口本地分支的静态成功约定为Check=1、Process=1后返回0。这里不是把返回0当作所有函数的统一成功约定。`0x12e79c0`返回“当前球队是否参与交易”的bool，不能误读为球队索引。

进程重启后重新解析PID、模块、根对象、球队、球员和合同；不沿用旧绝对地址。实际窗口线程为5172，借助该进程`PeekMessageA.onLeave`执行一次业务调用；仅以WM_NULL唤醒，没有菜单点击。三项私有预验证分别通过：两次原生AddPlayer、Validate=1；随后新进程上的完整Check=1、out=0，四个实际游戏对象的完整原始字节仍未改变，私有canary完整。提案ReceivingTeamId仍为FFFF；当前业务函数根据元素枚举球队，私有Validate与Full Check均接受该输入，未凭猜测强填字段。
