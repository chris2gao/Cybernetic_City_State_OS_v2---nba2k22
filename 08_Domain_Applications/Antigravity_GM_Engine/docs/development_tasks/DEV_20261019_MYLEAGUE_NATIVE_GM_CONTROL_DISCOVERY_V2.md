## 1. 原则：模拟经营逻辑与落实到游戏是两层工作

- **GM Engine为经营规则权威**：市场、各队GM谈判、交易同意、虚拟自由球员签约、考察新秀、选秀决策和休赛期方案，在外挂数据库和派生工作台内完成。不因NBA2K22人类菜单存在相应按钮就要求复刻原生UI流程。
- **Codex为受控落地执行方**：获玩家批准后将实际变更应用到NBA2K22的球员所属、合同、人员岗位、必要的历史新秀落地、球队角色/教练配置等；**必须区分“虚拟市场结果已经确定”和“真实游戏状态已经写入读回”**。没有真实验收的执行器不能因为模拟结果已生成而自动宣称执行。
- **Antigravity主要负责原生观测和尚未覆盖的设置可操作性发现**：球队与个人训练、导师关系、疲劳伤病、原生心理状态、真实比赛事件与游戏反馈，以及有价值的其他设置；独立归档地址和验证证据。员工招聘/合同、完整Playbook与阵容业务交给Codex，不重复分工。
- **游戏依然是竞技/自然演化权威**：比赛胜负、球员自然成长、实际伤病、体力等由游戏生成。GM经营过程中不直接改个人能力/潜力/徽章或未经批准的原始倾向。
- **任何业务的责任三角**：外挂GM做商业决定→玩家批准→Codex按照唯一决定执行与确认；不能从一个内存地址可写推断有完整签约、选秀或员工任免业务闭环。

## 3. 新秀“全知选秀”——把信息层与真实球员模型分离

玩家指出：外部SQLite能读到选秀池球员真实能力值和潜力，若GM直接使用全部隐藏数据，等于取消球探不确定性，历史选秀“每次都选准”。**这不是数据错误，是外挂信息权限问题**。

未来可考虑并行保存两个视图：
- **事实真值库（仅采集和分析计算层）**：来自游戏/球员模型的真实55项能力与potential、身份、历史班，供游戏写入和事后追溯，不能故意改假。
- **虚拟GM可见球探档案（决策层）**：由真实可公开事实、球探资历/资源、时间和可信误差构造评级区间、风格描述与不确定度。每队的公开信息大致相同，但球探质量与调查重点可以使结论不同。每届选秀前冻结外部球探可见性；模型不直接读取真值字段或未来真实历史生涯作为选人理由。
- **开发/调试读取真值**与**正式独立GM信息视图**要分开，避免模型被提示“不要看潜力”但CLI照旧在同一个返回体暴露55属性。
- **当前不是M3阻塞**：M3A依已有全量名单/历史池事实继续开发；M3B对非在队pool持SCOUTING_ONLY；以后正式引入历史选秀/球探市场时，再另设受控SCOUTING_VIEW查询命令和玩家选择的难度/信息模式；目前不增加随机噪声或直接改游戏新秀能力。

## 4. M3与后续接口衔接

- M3A继续全员当前事实和30队分析，不应为了虚拟市场去实现原生球探/选秀查询菜单。`q_team_stats`必须读取已存在的球队累计数据，但数据差分不是整月比赛日志。
- M3B可提出`HOLD/INTERNAL/MARKET`并进行独立球队议价。当前合同市场/休赛期执行器未验收时，将签约方案标`RESEARCH/BLOCKED_EXECUTOR`；**商业上属于外挂市场，不等于经营逻辑必须等原生UI入口**。外部报价的接受来自既定GM/未来球员系统，不伪造已经签约。
- M3正式可交付与V4切换分开。员工合同和完整战术若后来由Codex落地，可按已验证capability逐项进入GM，不要求M3重写。
- 用户新开MyLEAGUE存档后独立career/save_id；用新同批事实而非旧MC M02策略直接认定新局球队价值。
- 全局GamePlay滑块已由Antigravity打通，但属于稳定世界级赛场配置，非单队GM月度调参。
- 仍坚持玩家逐次批准游戏改变；**虚拟市场决定不等于物理游戏写入已执行**。
