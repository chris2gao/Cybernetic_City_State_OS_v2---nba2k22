# DEV29 V3 — NBA2K20–23 游戏机制全域研究：面向多智能体篮球世界的能力知识库

> [**DEV29的最终开发意图**](../PROJECT_INTENT_AND_MODEL_DEVELOPMENT_BOUNDARIES.md)：研究有价值的游戏原生信息、操作/设置、作用机制和应用攻略，作为未来独立Coach/Player/GM模型的素材；不得从领域知识直接编写固定人格/谈判/行为规则。以下曾讨论角色自主的段落仅是未来背景，不能扩大R任务。

## 2026-10-21 用户确认的六阶段外挂游戏流程与DEV29职责边界（覆盖本计划的设计性措辞）

**权威流程及范围**：[DEV29研究原料与角色系统开发职责边界](../game_mechanics/RESEARCH_INPUTS_VS_AGENT_EXECUTION_BOUNDARY.md)。玩家再次明确每次循环由**六个独立模型步骤**组成：①采集最新游戏源→②数据分析模型加工各角色需要的信息→③各队独立教练模型进行执教并提出阵容/交易/轮换要求（**人格系统尚未开发**）→④全部或部分独立球员模型模拟职业生活并提出自身意愿（**人格系统尚未开发**）→⑤各队GM模型独立运营并综合教练和球员诉求（**目前主要已有的人格系统**）→⑥汇总可执行事项，交**执行模型**经现实玩家批准修改并读回原生游戏。典型按新赛季开始、月度、交易截止日前一天、季后赛每一轮、休赛期调用一次。

**本DEV29及后续R05–R07只负责提供这些角色需要的游戏机制、可见动态事实、完整静态设置/合法选项、作用联动、来源和技术未认证列表**；不构建Coaching/Player/Media的性格、权重、谈判、拒绝或人生决定程序。此前本V3§5的“世界循环”和R04互动例子**全部只能读作非规范性的素材需求示例，不是批准的Agent架构、状态机、人格流程或开发任务**。真实安全边界（游戏写入须玩家批准，普通经营不直改球员能力等）沿用既有项目规则，而不是把智能体性格简化为固定行为表。

当前R04-A/B/C/D研究已完成且仍有PC22 native缺口；R05为下一待用户触发的**原生经营数据和可操作机制资料搜集**，不执行角色人格开发。

>
> 核心方向：不是训练一个替全联盟求最优答案的GM，而是**建立一个能够让GM、球员、教练、媒体及其他角色自主行动的、长期持续反馈的篮球世界**。模型拥有独立目标、记忆、信息与选择权；游戏NBA2K22负责原生场上比赛、球员自然成长与可认证世界状态；外挂负责新增角色代理、互动、审批执行和持久历史。规则主要约束世界一致性、安全和执行权限；**篮球哲学、球队建队文化、历史战略是可参考知识，不应自动强制所有模型选择所谓最优方案。**

## 1. 定位改变：从GM数据仓库扩展为全角色能力层

### 四类必须同时发现的“游戏原料”

| 维度 | 研究问题 | 未来的作用 |
|---|---|---|
| **事实 OBSERVABLE** | 当前/历史每场比赛、球员/员工/球队、伤病、士气、合同、资金、奖励和事件有哪些真实事实？保留多久？ | 玩家/GM/教练/媒体基于不同权限与历史去推理、争论和讲故事 |
| **控制 ACTIONABLE** | 游戏允许设置哪些训练、Coach/Playbook/战术/球员PlayTypes/倾向、合同/名单/选项？完整合法值域是什么？ | 角色可提出可行且有差异的选择；不用只靠解释一条偏移 |
| **机制 MECHANISM** | 每项设置对谁/什么产生何种效果，与其它设置和模拟规则怎样互动？已证或社区经验？ | 让角色理解机会与代价，但允许试错、未知与不同风险偏好 |
| **语义/权限 OWNER** | 谁被允许修改、反对、谈判、拒绝或获知这一信息？哪些是游戏内真实偏好、哪些只能外部模拟？ | 真正独立的球员/教练/球队，非单一GM假装扮演30队 |

**DEV29先建立可验证的资料知识/能力全表；DEV28才研究如何从NBA2K22 PC读、写、读回和提供统一接口。** 不允许从已经有的内存偏移倒推“游戏只有这些功能”。

### 自主参与与涌现不是无约束写游戏

- **决定自由**：GM可以重建或守成，教练可能拒绝不适合其体系的打法，球员可能拒绝改变训练/战术倾向，巨星可开条件、要求交易或指定加盟球队，媒体可发布不同观察与批评。角色的选择不是必须通过最优值筛选；他们需要负担个人收益、机会成本与现实后果。
- **信息不对称**：每角色所见信息不同；受限球探与球员隐私、谈判公开程度、媒体传闻不同。内部原生真值和外部角色信念分离，不把未来新秀真实Potential泄给GM。
- **世界物理与权限**：比赛/自然成长由游戏引擎裁决；交易/合同/已授权原生设置通过现有DEV14与专用执行器的真实约束，并受**真实玩家批准**。角色在模拟世界中的同意/否决是独立的第一层，**不等于真实玩家游戏写入授权**；不能因为模型说“球员同意”而自动修改数据。
- **动态反馈**：真实比赛与角色行为写入事件时间线，角色根据记忆、关系、承诺和结果改变决策；支持失败、意外联盟局势、谈判破裂、不同队伍同时竞争而非GM单方操纵。
- **底线**：普通经营不得直接编辑球员Ability/Potential/Badge作为增强手段；仅已认可历史世界线等例外且每次经玩家批准。球员智能体可提出修改自身战术倾向或训练方案，但须验证本机实际控制、球员模拟同意与玩家审批。

## 3. R04专题：球员全部信息与可设置项（必须比传统属性介绍更完整）

**权威细目及执行模板**：[R04 球员完整原生资料与角色映射研究要求](DEV29_R04_PLAYER_FULL_PROFILE_AND_AGENCY_RESEARCH_SPEC_V1.md)。

R04必须研究并按**源界面完整可见菜单**枚举如下领域（未知不虚构）：

1. `VITALS / BIO / IDENTITY`：姓名、生日/年龄、位置、副位置、体型、身高体重、学校/国籍、队伍、签约状态、背号、经验、所属球队历史、球员卡字段、姓名/球员ID、退役或历史选秀等。
2. `ATTRIBUTES / POTENTIAL / PEAK`：完整篮球技能、运动属性、精神IQ与耐力/成长起止/潜力；真实游戏自然成长控制和球队训练关联；**只读与解释为主，不授予常规直接修改权**。
3. `TENDENCIES / PLAYSTYLE`：已命名及未知的所有倾向、球员4个PlayTypes/Initiator、Touches、Shots、Play Discipline、进攻防守偏好与ACE/Coach/Playbook互动；改变是否实际影响AI，谁能提出/拒绝。
4. `BADGES / PERSONALITY BADGES`：进攻、防守、身体/心理、人格徽章及级别，获取/退化机制、其他属性与训练的关系、是否原生可见/可读；**普通GM不可通过直接改徽章增强球员**。
5. `INJURIES / FATIGUE / DURABILITY`：具体伤病类别、受伤位置/各部位Durability、出勤、恢复、训练负荷、赛季疲劳、身体状况、球员个人健康诉求。
6. `CONTRACT PREFERENCES / AGENCY`：Play for Win、Financial Security、Loyalty、士气/球队角色、赢球窗口、金钱、忠诚与冠军荣誉诉求；现有NBA2K字段是否真正参与报价/去留/角色接受，不能把名称直接当确定性公式。
7. `PERSONAL GOALS / RELATIONSHIPS`：个人目标、奖项荣誉追求、城市/队友/教练/球队的关系、受伤/训练/出场或合同承诺；区别原生观测事实与**外部角色系统自建的目标/关系/记忆**，不能谎称2K22自身储存全部心理活动。
8. `INPUT_OUTPUT_RIGHTS`：每字段的读取/写入能力、用途、风险、是否可安全作为外挂扩展映射、球员智能体的同意权/否决权和真实玩家执行权限；不同版本的具体来源必须标注。

R04是**机制研究任务，不是自动开发球员AI**。具体多智能体执行设计在DEV29最终知识收尾后形成独立提案（暂定 Player Agency / League Multi-Agent），与DEV28基础数据和合法动作层分开，避免因为讨论涌现而立即扩写M3执行协议或改游戏。

## 4. 外部角色状态与游戏字段重用：关键安全技术规则

玩家设想“将部分游戏内部参数让渡为外挂球员系统的存储或接口”**可以研究，但不能一概将原生游戏数据抹成外部人格字段**。因为该参数可能参与原生比赛、签约、伤病、训练、AI、存档校验、界面显示、版本迁移。

研究给每个原生字段标两套合同：

- `NATIVE_SEMANTIC`：2K原游戏含义、范围、与其它系统的作用、真正读写来源/目标人物/持久性；
- `EXTERNAL_SEMANTIC`：外部球员Agent希望表示的独立状态或意图，与原生语义如何联动，以及究竟需要外部SQLite、只读映射、受控写入还是特殊闲置字段。

分四类，不先决定放弃哪些原生效果：

| 类型 | 建议 | 典型例子 |
|---|---|---|
| **A 原生权威、只读** | 保留2K引擎自然产生状态，外部Agent观察并解释 | 能力/Potential、徽章、真实伤病记录、自然成长 |
| **B 业务协商后的受控原生设置** | Agent提出/接受/拒绝，真实玩家批准后由Codex写入并回读 | 允许范围内的个人训练、战术倾向、PlayTypes、合同变更 |
| **C 外部持久状态** | 优先放到外挂自己的SQLite，保证角色记忆和长期行为不破坏游戏 | 荣誉执念、关系、信任、职业计划、约定、媒体态度、选择历史 |
| **D 候选闲置原生字段重用** | **仅在确认本机无其它引擎/UI/存档效果、不会冲突后，另行具体授权**；保留旧值、映射版本、回滚/导出策略，默认不用 | 经实际证明不用的特殊保留字段；“看似没用”绝不能当已安全 |

**重要边界**：Play for Win/Financial Security/Loyalty、可用球员倾向很可能已经有2K原生签约/场上效果，不应抢占当作任意外部秘密变量；最好让外部AI状态独立保存，以已证的游戏字段**有意传达**角色选择，而不是覆盖原游戏含义。若将已存在原生效果让渡为外挂控制权，必须明确用户批准、测试该副作用如何被替代以及如何避免双重模拟冲突。

## 5. 多智能体自主决策的最小世界循环（作为未来架构参考，不在R04实现）

```text
NBA2K22 世界真实事实（比赛/名单/员工/伤病/资金/事件）
    ↓ 经过角色权限与可见范围投影
GM Agent / Player Agent / Coach Agent / Media Agent
    ↓ 个人目标、记忆、信念、可选行动与后果，不同主体独立推理
提案/承诺/要求/拒绝/谈判/交易组合/训练要求/战术选择/报道
    ↓ 游戏世界的合法资产/时间/合同/行动前置条件校验
球员等角色的模拟同意 & 对手角色真实独立响应
    ↓ 玩家现实审批门槛（仅实际游戏写入，不代表Agent想法被批准/否决）
DEV14或业务执行器 → NBA2K22游戏数据更新 → 实际游戏结果
    ↓ 事件日志/状态回读/历史评价 → 角色下一轮认知
```

**不是让模型“优化到同一答案”**：球员可以为了个人荣誉错过冠军，球队可以错误判断未来，教练可以坚持不合适打法，媒体可以报道不确定传闻（必须标传闻，不能篡改客观游戏事实）。失败和悔改形成历史。避免单模型扮演所有角色却共享隐藏真值或总是自利于玩家球队。

角色权力需**按领域划分而非只按谁是AI**：GM能提交易与签约条款，Player能自行选择是否接受及提出条件，Coach可决定实际教练方案并和GM争论，Media可形成叙述/声誉反馈；遇到冲突通过谈判、退出、机制仲裁而非全局“最优建议”覆盖。超级球员的否决/条件谈判并非一律特权，应受其身份/合同/社会关系/团队目标约束并反过来影响世界。

## 6. 交付质量：不只“百科”，要作为未来Agent能力素材

研究主体每张机制卡除WHAT/HOW/WHY/INTERACTIONS/数据/来源，还需补充：

- `WHO_CAN_OBSERVE`：GM/Player/Coach/Media分别能知道什么；
- `WHO_CAN_PROPOSE / WHO_MAY_VETO`：能提出、接受、拒绝/谈判什么；
- `GAME_NATIVE_EFFECT / EXTERNAL_ROLE_EFFECT`：游戏原生效果与外挂角色决定分别为何；
- `LEARNING_SIGNAL`：经过多少比赛/合同/事件后能得到何种反馈；
- `ATTRIBUTE_REPURPOSE_CANDIDATE`：目前是否安全可作为外挂角色映射，仅`UNKNOWN`或已证候选，不自作主张；
- `DECISION_REFERENCE_NOT_MANDATE`：建议是角色可选择的参考，不强制所有角色执行。

同时继续保留来源版本、真实平台/模式、截图证明、原生可读与项目已采/已可查询分级，游戏中隐藏球探真值不能因追求全数据而泄露给角色。
