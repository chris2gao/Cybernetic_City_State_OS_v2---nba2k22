# NBA 2K22 历史选秀名单与 MC 模式选秀接管机制规范 (Historical Draft & Rookie Injection)

> 当前玩家玩法固定为 **1984 → 1985 → … → 2020 → 1984 顺序轮回**，完成一届选秀才推进，不随采集或游戏重启推进。完整边界见 [文档 26](26_GAMEPLAY_ROLES_AND_WORLDLINE_RULES.md)。只有数据库中已验证的新秀模型可导入，缺额保留游戏生成球员，不手填能力；目标槽位写入尚需独立实现、校准和玩家批准。

本文档定义 MC 模式历史选秀候选人的数据筛选规则，以及后续选秀槽位接管的实施边界。候选人由游戏球员池脚本采集、写入 SQLite，再通过已验证的历史新秀类型码筛选。1984 届是一个目标示例；各届实际可用球员取决于球员池标记覆盖，不能预设所有年份都完整。

## 二、MC 模式历史选秀接管方案与验证边界

在 **MC 辉煌生涯模式** 中，选秀名单入口受限，选秀由游戏原生 AI 模拟。外部数据库可以提供可核验的候选名单，但内存写入和选秀归属纠偏必须在目标槽位布局、写入时机和游戏状态都经过独立校准后才能执行。

当前代码实现的是 **球员池抓取、候选筛选、排重和查询**。下图中的槽位写入与赛后纠偏是后续机制，不表示已经完成实机验证：

```
                    【MC 模式历史选秀双层接管流程】
                                  │
    ┌─────────────────────────────┴─────────────────────────────┐
    ▼                                                           ▼
【层级 1: 选秀大会前夕 (DNA 覆盖)】            【层级 2: 选秀大会结束后 (GM 纠偏)】
校准球员池并采集原始结构
         │
按年份、类型码筛选并排重，得到 N 名候选 (N ≤ 60)
         │
目标槽位布局校准完成后，才设计字段映射和写入方案
         │
选秀后读取实际结果，再由 GM 提出归属调整建议
```

### 接管方案 1：选秀前夕“顺位诱导与偷梁换柱法”（Pre-Draft DNA Overwrite）

**候选人来源与克隆甄别**：从 `database/nba2k22_players.sqlite` 按选秀年份查询，再使用玩家原始结构 `raw_struct[0x70]` 的类型码筛选：`(raw_struct[0x70] & 0xE0) == 0xE0`（高三位 `111`）才是已确认的历史新秀模型。艾弗森全身照 ID `16558` 和科比全身照 ID `16565` 对应的克隆均命中；两人的其他同名克隆未命中。查询按规范化姓名、选秀年份、选秀轮次、当轮顺位排重并排序。仅按姓名、年份或面补 ID 不能选定新秀克隆。

每届实际命中人数由数据库决定，最多可用 60 个新秀槽位。只将通过类型码筛选且排重后的 N 名候选交给后续槽位映射，剩余 `60-N` 个槽位保留游戏生成的小人。预期球员缺少类型码时，将其记录为覆盖缺口，不使用现役或巅峰克隆自动替代。

1. **时机节点**：预期在休赛期选秀界面操作；实际可用时点仍需在 MC 实机确认；
2. **候选名单**：调用数据库查询接口，按历史新秀类型码筛选，按姓名、年份、轮次和当轮顺位排重，保留原始来源字段；
3. **槽位布局**：运行时重新校准目标数组基址、步长及各字段偏移。球员池来源步长 `0x4F0` 不等于目标新秀槽位步长，不能整块照搬来源结构；
4. **顺序映射**：`pick_proj` 仅表示已验证候选人在筛选名单中的排序序号，不是 NBA 原始综合顺位，也不是目标槽位编号。映射算法需单独决定并验证；历史选秀轮数或每轮人数不明时，不推算综合顺位；
5. **写入与缺口**：只有目标布局和字段映射验证后，才写入 N 名候选（N 不超过 60）；`60-N` 个槽位保留小人。缺少类型码的目标球员记为覆盖缺口，不使用未验证克隆替补。

### 后续方案 2：选秀大会落幕后的“GM 选秀夜交易纠偏协议”（Draft Night Trade Rectification）

以下为待实现的决策与执行设计，不代表当前已经能通过 `modifier.py` 修改游戏内存或完成实机交易。
如果由于选秀抽签爆冷，某支阵容位置极度重叠的球队选走了乔丹（例如已有两名全明星后卫的球队选了乔丹，而缺乏核心的公牛或步行者空有前锋）：
1. **外部 GM 峰会研判**：
   * 判定该队触发“战术位置严重拥堵（Positional Redundancy）”；
   * 由缺乏后场核心的球队（如手握首轮中段签的球队）提供未来首轮签 + 契合前场的即战力，发起 **“选秀夜大交易”**；
2. **内存热纠偏**：
   * 脚本直接调用 `modifier.py`，将刚选下的新秀所属球队 ID（`CURRENT_TEAM` at `0x60`）与合同归属（`CONTRACT_TEAM` at `0xA8`）与交易对象互换；
   * 模拟出如同现实中 1996 年黄蜂选下科比、并在选秀夜换去湖人的传世操盘！

## 四、执行工作流

当前可验证的候选查询流程：
1. 运行 `python src/draft_engine.py`，或调用 `DraftEngine.get_draft_class(year)`；
2. 查询只读球员池数据库，按类型码筛选并排重，输出实际命中人数、来源槽位及原始选秀字段；
3. 只有候选列表经检查后，才进入尚待单独实现和实机验证的目标槽位映射、内存写入阶段；
4. 选秀夜球队归属纠偏目前是 GM 决策提案逻辑，不能据此认为已经实现游戏内存写入或实机交易。
