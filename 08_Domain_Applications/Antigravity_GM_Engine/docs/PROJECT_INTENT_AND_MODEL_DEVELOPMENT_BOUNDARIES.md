# NBA2K22 GM Engine — 项目开发意图、六阶段运行流程与模型职责边界

> **Human 2026-10-28最新执行链补充（覆盖旧执行路由，但不重做数据层）**：角色使用既有真实数据采集、SQLite/分析结果，并**提前加载自己GM/Coach/Player身份的完整可用操作能力、参数与含义**；各角色模型独立决定/协商，输出**多条确定的待执行指令**；统一汇总器汇聚已同意动作而不重新评估薪资/选人/战术，按受支持游戏业务函数**通过REA原生服务批量按序执行**，单条结果定向读回并返回游戏世界。真实执行仍遵守OS与Human授权范围；批量命令并不保证游戏引擎提供跨命令ACID事务。既有数据与权限保护不变。这一最新架构在[ROLE_BATCH_NATIVE_EXECUTION_ARCHITECTURE_V2.md](development/ROLE_BATCH_NATIVE_EXECUTION_ARCHITECTURE_V2.md)和[全项目索引](../PROJECT_INDEX.md)中定义；以下较早的六阶段协作描述是历史/研究流程，**不是当前最终执行技术路径的优先说明**。



**状态：项目级权威开发意图（2026-10-21，玩家明确确认）**

> **一句话**：我们建设一个供独立模型真正参与和体验的 NBA2K22 篮球世界。现阶段的 R 系列与底层 I/O 开发负责**提供游戏的全部有用原材料和可执行工具**，**不负责替尚未开发的教练、球员等人格模型编写“应该怎么想、怎么选”的程序**。开发者不能将“列出允许的操作”“设置若干偏好阈值”“生成固定剧情”当作完成了人格系统。
>
> 本文为**所有研究GPT、数据分析GPT、教练/球员/GM模型的开发者、Codex、Antigravity、执行模型**共同遵循的项目宗旨与**工作范围判定规则**；不授权新增人格系统、自动调度、超范围编码、生产数据采集或游戏存档写入。人格系统的未来算法、提示词、记忆、谈判和自主决策方式，由**届时独立立项**的模型开发任务决定；本文**不得被解释成一种人格架构设计**。

> **2026-10-22 重要架构修订（覆盖第0节与旧文件的“必须保留双库物理结构”说法）：** 玩家批准以完整平行篮球世界为目标重做底层数据建模；旧SQLite两事实库、旧采集容器、表结构、程序API和文件布局都可以全面重构，并非永不改变的架构约束。**必须保留的是已验证原生事实、数据来源、存档身份、数据安全、发布一致性和玩家游戏写入批准**，可以通过新平台实现它们。概念与逻辑架构先行，实验性候选Schema与Codex验收并行；正式迁移另批。权威新基线见[平行篮球世界数据架构V2](development/PARALLEL_BASKETBALL_WORLD_DATA_ARCHITECTURE_V2.md)。

## 0. 最新长期架构共识（2026-10-22）：原生引擎 + 平行篮球世界

**NBA2K22 PC MyLEAGUE继续作为真实比赛、原生状态和球员自然成长的唯一权威引擎。** 外挂在此基础上构建**原生对象读取层 → SQLite事实镜像与跨赛季历史账本 → 独立AI角色与扩展游戏机制 → 经玩家本人批准的受控执行器**。游戏自己决定的事实不由AI模型或SQLite推断替代；执行器回写必须校验游戏实际状态。

这五层是**技术架构**，与本文件第2节玩家确定的**六阶段多模型运行顺序**并存，不能互相取代。已有`league_state.sqlite`、`player_pool.sqlite`、DEV14双库暂存/多存档代际、M0安全查询与审批执行底座必须复用；**不另建第二套生产事实库、审批系统或人物人格状态机**。任何新原生对象的研究样本、Decoder或实验数据库都不能自动升级为已采集、已发布、可供角色查询或已允许写入。

**实施次序共识**：Gemini Flash逆向原生对象与关联、提交样本和候选Schema；Codex独立验收并处理困难问题；验收后经玩家对独立工程包批准，再接入既有统一采集、SQLite批次、GM_SANITIZED脱敏、封存查询和执行机制。数据模型的**候选设计与逆向验收并行**，但**正式迁移与生产发布在验证之后**。完整比赛、赛季、球员卡、G联赛、新秀报告等以真实游戏页面为覆盖范围，以已证原生对象为Schema依据；未证字段保持UNKNOWN。

当前AG-NATIVE-01D提供了重要的**单场Box→PLAYER_STATS赛季累计**和生涯索引研究样本，但尚待Codex对真实布局、全量边界和正式系统集成验收。R01–R07研究知识库已广泛覆盖玩法与页面；GM、Coach、Player的全量**生产级**可查询原生事实和独立人格仍不齐备。详细成熟度、技术结构和限制见[平行篮球世界数据架构V1](development/PARALLEL_BASKETBALL_WORLD_DATA_ARCHITECTURE_V1.md)与[Native I/O蓝图V2](development/NATIVE_GAME_DATA_SYSTEM_RECONSTRUCTION_AND_IO_BLUEPRINT_V2.md)。

## 1. 最终想创造的游戏：让模型“玩”，不是代替世界求最优解

- 游戏底座：**NBA2K22 PC 本世代离线 MyLEAGUE**，2021–22赛季起步，1984–2020历史选秀轮回；真实NBA篮球文化、20–23系列玩法和次世代MyNBA攻略可用来理解机制，但具体PC原生源、菜单、内存和执行要单独认证。
- 参加者：各队 **GM**、将来的独立 **Coach**、独立 **Player**（全部或部分球员），以及以后可能加入的 **Media** 等。不同参与者具有自身视角，可有不同目标、喜好、误判、冲突、交易条件和经历；**真正怎样表现由其各自的未来独立模型任务实现**。媒体目前**不是**下面六步中的强制第七步。
- 项目价值在于**开放的选择、真实的限制、不可预先确定的互动与游戏结果反馈所带来的涌现**。好的篮球哲学、战术知识、历史经验、数据分析、球队文化是模型的**游戏知识与参考**，不是强迫所有角色得到同一个“最佳答案”的硬编码目标函数。
- 算法、校验与规则仍然必要，但职责不同：**验证身份、游戏物理、数据真实、动作合法、审批与执行完整性**的程序是底层基础设施；**人格怎样产生意愿/如何权衡/会否接受建议/如何改变想法**不是当前研究或基础设施任务决定的程序。
- **严格区分当前功能与最终愿景**：目前主要有 GM 决策系统，独立教练人格和球员人格**尚未实现**；研究里提出的“某球员可以拒绝”只是未来可能利用的需求场景，并非当前已有的角色代理、原生游戏功能或已批准的人格算法。

## 2. 每个外挂回合的六个**独立模型执行阶段**（玩家确定顺序）

| 顺序 | 执行主体 | 该阶段应做的事 | 不应做的事 |
|---|---|---|---|
| **1** | **采集模型** | 获取当前存档最新、完整、可追溯的真实游戏状态和动态事实（每场比赛、球员、教练、财务、健康等），验证存档/批次/游戏时间 | 不替球队做篮球选择，不把“现有采集字段”当作“游戏信息全集” |
| **2** | **数据分析模型** | 加工真实数据，提供后续教练、球员、GM所需的统计、动态变化与事实解释；标明来源/计算/缺口 | 不把赛季累计伪装为具体比赛，不代替下游主体作人格/经营决策 |
| **3** | **教练模型**（独立人格待开发） | 作为球队教练观察阵容、比赛与对手，负责教练工作，可向GM提出战术、人员、轮换、交易需求及理由 | 当前研究任务不替它设计性格、固定战术决策树或强制议价规则 |
| **4** | **球员模型**（独立人格待开发） | 作为全部/部分现役球员，经历职业与生活，自主提出需求、意见和行动 | 当前研究任务不把Loyalty/Play for Win等游戏字节直接变为其人格或固定抉择算法 |
| **5** | **GM模型**（当前主要已有） | 各队GM经营球队，综合教练、球员要求及自己掌握的事实/目标，形成球队行动方案 | 不把数据分析或DEV29“八个示例剧情”当成必须执行的最佳答案 |
| **6** | **执行信息汇总 → 执行模型** | 将本轮各队相关已确定意向/行动整理为受控方案；**经玩家本人明确批准**后调用合法游戏执行路径、核验游戏读回与适当持久性 | 不替角色重做性格/决策，不把同意、计划、通过模拟测试宣称为已写入游戏 |

**频率**：玩家通常在新赛季开始、常规每个月、交易截止日前一天、季后赛每一轮和休赛期触发上述独立步骤。阶段之间不是自动无限循环；每个独立任务按玩家触发交付/结束。完成执行后，NBA2K22后续比赛/自然成长产生新事实，供下一回合再采集、分析与参与。

## 3. 开发责任边界：R系列、DEV28、独立人格系统是三种不同任务

| 工作层 | **本层负责交付** | **本层绝不擅自实现** |
|---|---|---|
| **DEV29 R01–R07 游戏机制知识研究** | 从 NBA2K20–23（尤其22）社区、图文攻略、官方手册和真实游戏资料查清**游戏有什么数据、界面、参数/可选项、玩法、作用、联动、历史留存、不同版本差异**；列出各模型可能需要的**原材料**、可读/可写性及真实性证据 | 角色人格、固定行为规则、权重驱动的“模拟人”、谈判引擎、角色对话编排、事件剧情或游戏数据实际写入 |
| **DEV28 全透明数据/控制基础设施** | 按R系列需求和原生证据，建立**原始游戏数据采集→可查询输出**、全部已证设置/枚举及合法动作的**候选输入→审批执行→真实读回**；复用既有SQLite、Registry、M0、DEV14/专用执行器，标明未知与缺失 | 球员/教练思考算法、人格训练、角色仲裁协议或强制“最优”策略；不能从“找到的地址”反向删掉GM实际需要的数据 |
| **未来教练、球员、媒体等独立人格/参与者任务** | **以后另行立项**，由它们决定各角色怎样理解自己、形成意愿、自由选择、改变看法并和其他模型互动；使用R知识和DEV28工具 | 现阶段不得以R04研究案例或字段映射代替真正的独立人格系统 |
| **GM独立决策任务** | 已有GM作为参与者进行球队经营；将来可接入来自独立教练/球员的要求 | 不代表所有角色，也不预先替独立教练/球员决定其真实行为 |
| **FINAL-CODEX研究收尾** | 在网页GPT完成主题研究后，**有限**核查知识索引、原生数据/查询/动作接口缺口，形成DEV28实际工程清单 | 不负责数百篇攻略收集，不在收尾任务中顺带开发Agent或大量新执行器 |

**何谓“原材料完整”**：不仅是球队名单/赛季总计。尤其不能重演“全量采集却没有每场比赛/Box/Game Logs及高级指标基础”；应调查所有合理的动态数据源，以及静态操作选项，如教练ACE、战术/Playbook、球员Tendency、Badge、训练、健康、合同/工资帽、球探/选秀、员工等。某项公开资料存在但PC22内存未证、原生布局已注册但实时值未采、值能读取但没有GM查询、技术可写但未验收执行，都应**分别记状态**，不得用一个`DONE`掩盖。

## 4. 研发中防止越界的判别示例

**符合R系列职责：**
- 研究`'95 FIST 15 SIDE`的命名、游戏12种战术类别、1/5号位、Play Discipline/Coach Run Plays联动，标注原生分类CRC映射是否已认证。
- 列出所有能看到的球员档案、伤病、属性、倾向、徽章、`Loyalty/Financial Security/Play for Win`，各字段如何影响原生场上/合同、如何读写、哪些仍未知。
- 梳理每场Box、比赛历史、投篮和高级数据、薪资/选秀/训练/教练功能，指出GM/教练/球员可能需要哪些数据与游戏选择。

**越界，须另立人格/行为系统任务而不得顺手开发：**
- 写死`Loyalty > 80`就留队、`Play for Win > 90`就加盟最强球队，或决定球员必须接受哪个GM报价。
- 给教练写固定`if player 3pt > X → select play Y`当作独立教练人格；建立一套“个性权重自动决定打什么战术”的通用角色决策程序。
- 依据R04八个互动例子创建Agent谈判状态机、角色记忆库、人生事件生成器或媒体新闻人格；**R04八例只用来说明需要什么数据和原生可操作接点**。

**合规执行不是人格控制**：原生数据结构、动作合法性、球队人数、资金或写入批准可以用确定性程序校验；但此类检查器不是球员思考与人格模拟的替代品。如何设计真正可自由行动的人格系统需未来专项任务另行讨论、测试和批准，本文件不预先规定技术路线。

## 5. 权威来源与真实性／权限边界

- 版本/玩法以[游戏机制研究先行规范](GAME_MECHANICS_RESEARCH_FIRST_DEVELOPMENT_POLICY_V1.md)为准：先查玩家社区、攻略、官方手册；次世代机制可参考，PC22具体运行时接口需实证。
- 游戏现实：实际存档/批次/真实球员ID/比赛事实、可见字段与未知事实严格分开；真实比赛、自然成长由NBA2K22引擎裁决。现实2022之后历史/选秀信息不能自动泄漏给游戏内2021世界角色。
- 游戏写入：任何真实存档修改仍需**用户单独批准**，Codex/执行模型核对身份、时点、原值并验证结果；外部角色的意见、建议、未来模拟同意不能构成玩家批准。普通经营不得直接修改球员Ability/Potential/Badge，历史线例外另批；已核准的Intangibles窄例外遵守已有规范，不因本文件扩大。
- 球员人物状态：**DEV29先研究游戏原生字段的现有功能，不占用这些数值当外挂人格存储槽**；未来是否将某些数据让渡为外部用途属于另行技术与角色任务，并需查清原生作用与许可。当前研究表里的`role_rights`只是素材需求注释，并不表明现成角色人格/原生NPC拒绝权限。
- 现行文档可能描述早期“两/三阶段：采集→GM→执行”的已运行流程；这是**旧阶段/现行已实现子流程**，**不能推翻本文件确定的六阶段目标运行形态**。尚未实现的教练/球员独立模型仍必须明确标记`NOT_IMPLEMENTED`，不作已经上线的宣传。

## 6. 给所有开发模型的任务自检（只需几项，不增添新流程）

启动开发/研究前确认：
1. **这次任务处于哪一层？** R知识研究、DEV28数据/控制、还是已独立批准的Coach/Player人格系统？如果用户未批准人格专项，就只做本次底层或研究任务。
2. **输出到底是游戏本身的事实/参数/玩法/作用，还是我们臆造的角色想法/人格策略？** 后者不是R成果。
3. **结果会让后续模型真正“知道能看到什么、能做什么、怎么做”吗？** 未采到的真实每场数据、未认证的合法选项必须写明缺口。
4. **本次是否擅自新增了人格、对话、谈判、剧情、状态机、调度或游戏写入？** 有则应先剔除越界部分，另交未来任务讨论。
5. **已批准安全与真实性规则是否仍满足？** 玩家批准、按存档身份执行、禁止普通直接改球员能力、未知证据不冒充实证。
