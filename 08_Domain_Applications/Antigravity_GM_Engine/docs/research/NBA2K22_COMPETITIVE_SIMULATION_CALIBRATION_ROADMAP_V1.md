# NBA2K22 PC MyLEAGUE — 竞技模拟能力与比赛引擎调校研究 V1

> **范围纠正（2026-10-19，玩家最终明确）**：本V1中关于日历快速模拟、Sim Engine、赛季统计分布及三条游戏路径的内容**不属于本次竞技调校目标，已被V2正式替代**。新的权威计划：[NBA2K22实时3D赛场竞技调校 V2](NBA2K22_LIVE_COURT_ENGINE_CALIBRATION_V2.md)。唯一研究对象为USER vs CPU及CPU vs CPU的实时3D场上引擎；可研究全局Gameplay、球员Tendency、球队教练技战术和场上攻防调整，采用真人实战双向反馈。不因本V1自称路线继续修改Quick Sim或单独Sim Engine。

> 2026-10-19。研究基线/长期规划，**不是开发任务执行授权**。正式优先级：DEV10 M1/M2合并收尾 → M3A/M3B GM数据驱动经营决策 → 以本研究为起点独立实施比赛竞技调校；球员/媒体系统随后扩展。用户已安排Antigravity寻找全局/教练/训练等原生设置与内存地址。任何正式游戏内存改动仍需玩家明确批准。

## 一、目标定义

不是“让玩家更难赢”或“让分数看起来真实”两个简单目标，而是**在双方合理执行篮球战术、使用真实球员能力差异、具备真实攻防对抗及概率波动时，赛场上形成可观察、可信的胜负**。既不能玩家轻易用一个漏洞每场大胜，也不能靠给CPU无依据的投篮/防守加成强行维持难度，更不应把所有球队调成55%胜率。

我们的核心拆解：
1. **篮球行为**：挡拆、弱侧协防、转换、空间创造、阵地组织、传球、出手选择、犯规、篮板、体力与动作符合基本篮球逻辑。
2. **球员能力区分**：明星/普通、外线/内线、机动/慢速、强弱队的真实差异依然显著；不直接改球员原始55属性/潜力/徽章。
3. **战术博弈有效**：同等阵容、合理背景下，不同教练策略、对位防守和球员角色有可观察的不同表现；不能只对比分敏感却对GM策略不敏感。
4. **竞技公平**：高难度不是单方超人能力，强者能优势但并非100%胜；玩家不能利用固定2K漏洞无限得分，AI不能凭超现实反应确保胜利。
5. **统计/长期生态**：当季及多年得分、出手、助攻、失误、犯规、罚球、篮板、节奏、三分比例、胜率分布/主场优势等合理且有波动；伤病和自然成长维持独立真实规则。
6. **持续可用**：新MyLEAGUE真实开档、跨月、跨赛季、历史选秀轮回依玩家批准保留一个记录清楚的世界级配置，而不是GM每月为了单队取胜改全局滑块。

## 二、第一技术关口：三条比赛路径分离

| 运行路径 | 典型用法 | 参数/指标需要做什么 | 是否已有真实源码认证 |
|---|---|---|---|
| **USER vs CPU** | 用户亲自控制一队与CPU打比赛 | 操控/对抗难度、输入方式、射术、CPU防守、用户可滥用漏洞 | 游戏模式存在；现有每个参数的真实消费链**未认证** |
| **CPU vs CPU 3D live** | 两队由比赛AI控制，玩家观赛/控制教练 | 双方均有逼真技战术、空间/对位、AI决策、实际BoxScore与运动 | 需确认该模式消费哪个USER/CPU通道、ACE与策略重写机制 |
| **Calendar sim / quick sim** | 终极联盟从日历快速模拟大量比赛 | 游戏模拟数值引擎、体力、角色、场均/赛季数据及球队竞争格局 | 玩家与社区已展示该独立设置领域；**不应默认3D Gameplay Sliders改变此路径** |

正式调校之前选定我们各路径在一个赛季的主要使用比例。若以30队MyLEAGUE日历模拟为主，那么仅优化手打AI几乎不会改变大多数联盟比赛结果；必须优先确认Sim Engine的实际效果。若看季后赛CPUvsCPU直播，动作、临场AI和镜头表现也应进入目标。两个系统可以需要**不同配置集及不同校准指标**，严禁未经验证套用同一组。

### 每份外部经验的结构化采样规范

`source_url / platform(PS4/PC/PS5) / game_build / roster_version / match_mode(USER_CPU, CPU_CPU_LIVE, QUICK_SIM) / difficulty / quarter_length / parameter_group / suggested_values / sample_games / observed_problem / observed_effect / caveat / evidence_status`。

**禁止直接把“网上玩家值”为“当前PC22认证默认值/最佳值”**。很多滑块套装相互矛盾，可能还调整了整套球员属性/倾向——本项目严格禁止日常直接编辑个人能力/倾向；只能提炼**全局、已实机确认**参数与可合法设置的教练方案。放弃依赖全员改属性的套路，不能偷渡为合法调校。

## 四、四层调校架构

**L0 世界固定规则**：MyLEAGUE赛制、难度、时长、Sim Engine、全局USER/CPU Gameplay、犯规/伤病、成长、比赛节奏等。玩家开档批准`WORLD_GAMEPLAY_PROFILE`，中途原则上固定，以防GM人为调全局扶持个别球队。

**L1 GM合法动态策略**：30队独立教练19项默认/18项对手整体、Playbook、Freelance、POE、BenchDepth及后续原生训练/球员角色。可在月度/季后赛节点经玩家审批执行，属于**双方公平使用的经营变量**。精确个人上场分钟继续交给游戏AI。

**L2 比赛引擎**：3D gameplay、比赛AI、Sim Engine实际消费不同参数及ACE是否覆盖已有GM教练设置。读到UI值/写回不等于比赛中生效；不用完全逆向，但至少核对重要消费方向。

**L3 分析/竞技评分**：从已取得逐场、赛季/球队、情境/阵容数据衡量结果。已经采集的`games_box_scores_standings`仅`VERIFIED_PARTIAL_SEASON_TOTALS`，没有逐场BoxScore和完整回合日志；没有数据的指标要记为`NOT_OBSERVED`并允许人工赛场笔记，不编造逐球事件。

## 五、优先修什么：篮球真实性不是统一拉高命中率

1. **空间与运动物理观感**：持球速度、持球加速度、无球速度、切入节奏、启动/变向；球员角色速度差必须存在，不能把中锋调成后卫。用户之前的中锋持球“月球漫步”应在PC所用模式复测（不是帧率问题），并独立验证真实滑块消费。
2. **篮下对抗与协防**：单打强行突破是否无解、协防及时性、身体接触、投篮干扰、护框、掩护后的防守补位；不要用CPU投篮加成假装防守变好。
3. **AI攻防选择**：何时挡拆、投三分/中距/突破、背打、转换、传导、对手适配、掩护防守；先校准**投篮分布与质量**，再校准命中。
4. **犯规、罚球、失误、篮板和体力**：避免高比分但罚球极少/盖帽抢断超标/体力无惩罚，长赛季伤病也不能被过度训练干扰。
5. **玩家难度和反滥用**：识别简单可重复的无解套路（如不停突破上篮、无限挡拆），通过AI防守/移动/对抗等全局参数建立真实反制能力；不能只给CPU无条件命中率加成。
6. **日历模拟真实性与竞争格局**：全联盟强弱分化、合理波动、不同球队打法数据、晋级悬念、明星价值、赛季末统计。没有必要把每队拟合成现实2022的最终战绩；我们有架空球员与历史选秀，需要保留自然结果。
7. **战术对抗敏感度**：试验GM设置（例如对强射手绕上 vs 绕下、保护篮筐 vs 外线轮转）在相近阵容/对手下是否改变**过程**（对手出手结构、篮下得分、空位、失误），即使某场结果相反也不把胜负一场当效果定论。

## 六、科研式但适量的调校流程

**A. 固化基准**：先保留当前游戏build、名单/存档、世界配置、难度、USER/CPU参数、Sim参数、教练设置、可写字段来源；旧`src/slider_manager.py`里的`ADDR_SETTINGS=0x06332630`、`ADDR_SLIDERS=0x063319F8`**还不是现行游戏验证地址**。旧`docs/10_GAME_SETTINGS_AND_SLIDERS.md`虽然称“权威指南”，包含无正式来源验证的伤病/成长/士气/滑块及现实效果断言，**不得直接作为已证最优参数或执行器的正式基准**。需要在后续研究里逐条核验或移出权威索引。

**B. 建立三路径基线**：小量代表性`USER_CPU`、`CPU_CPU_LIVE`和`QUICK_SIM`，选择强队/弱队、不同打法、同级队两端基线；最重要的是**分别确认某参数在哪一种运行路径生效**。使用同一数据环境，固定各项可能改变状态的因素；避免把两次不同比赛单场波动误称效果。

**C. 先定位类别，再调参数**：只有表现明确偏离目标，才在同一个相关参数族做有限变更（示例：对手外线过多空位→研究协防/贴防/掩护路线，而不是一口气把所有CPU防守和三分命中都加高）。先保留源配置，再生成候选配置`CALIBRATION_CANDIDATE`；差分+原生写入执行仍需要玩家批准。

**D. 对比少量结构性指标**：一段比赛中观察可解释的战术过程；若对比快模季末统计则用合适样本。维度包括：Pace、FGA/3PA与3PAr、2P/3P/FT%、FTA/FTr、ORB/DRB、AST/TOV、犯规、分差与分布、强弱队表现/胜率区别。以2021–22真实NBA联盟/球队**分布范围**为锚而不是每场固定分数。缺逐场/回合/体力则标`NOT_OBSERVED`，不要求本轮先重做海量采集。

**E. 战术效果反证**：GM选择一个可观测目标（例如减少对手外线高质量出手），场上现象/统计改善或无效均保留，而不是把“我们改了教练参数→本场赢了”当因果。实际AI可能覆盖GM战术；ACE开关与Play Physical在RES2帖有冲突迹象，需要我们实机分析。

**F. 固化世界配置并回放**：发布经玩家批准的`WORLD_GAMEPLAY_PROFILE`版本、游戏版本、源/社区依据、参数前后、观察范围及已知副作用；在新的MyLEAGUE存档初始化阶段应用，常规赛除修复明确失真外不频繁改世界规则。任何开放性bug用运营反馈收集后修，而不是无限测试或不让游戏开档。

## 七、验收标准（方向性，而非过度承诺）

- **表现**：强队赢得更多但并非必胜；AI能够应对重复套路；中锋/后卫运动差异仍合理；篮下攻防、外线轮转和对位不出现明显常态性无解漏洞。
- **统计**：多队/多场结果大致落在真实NBA2021–22参照的合理分布，避免通过命中率强行掩盖少罚球或差出手结构。
- **GM的策略有效**：球队与对手改变防守策略/进攻方向可形成可辨别的战术过程差异；不要要求每项GM更改都保证赢球。
- **三路径分开验收**：日历Sim与观赛3D都能服务我们的30队经营，不能拿单一模式好看替代其它。
- **安全/边界**：不直接改任何普通球员原始能力/潜力/徽章/倾向；不开放未经证实的旧地址一键批量写入；每次游戏配置变更需玩家明确批准。
- **有限成本**：最初阶段用直接相关、适量对比，不为了每个参数扫全0—100值域；遇到实际问题再研究。

## 八、分工与何时启动

- **Web Development**：收集具来源和平台标记的滑块研究，形成问题→候选参数→观测指标的机制知识树；审批新的测试任务。
- **Antigravity**：实机UI菜单、当前内存地址/类型、USER/CPU侧与Sim侧、写后读取/重开保留情况；只读先行，不把UI缓冲当引擎消费事实。
- **Codex**：玩家批准后接入原生配置字典、快照版本、差分计划、恢复/回滚、限定目标参数写入；为重复可对照的结果生成报告。无需大规模修改游戏玩家属性。
- **Web Analytics**：当有可信已采游戏数据时衡量统计分布/趋势，关联不同世界配置与不同GM动作；没有完整比赛日志时必须输出缺口。
- **GM V4**：不在每个球队决策时改全局赛场滑块，只能在经玩家批准的统一竞技规则内更改球队阵容、战术、教练等合法变量。
- **玩家**：决定主要使用模式比例、批准竞技世界目标/参数配置与每次执行；正式新档优先于为了“最佳数值”无限循环测试。

**阶段顺序建议**：先GM V4可经营，然后引擎竞技调校先解决`QUICK_SIM`长期联盟统计+教练策略响应，再解决`CPU_CPU_LIVE`3D比赛智能与战术观感，最后解决`USER_CPU`人机对抗公平；如玩家实际玩3D更多可相应调整。完成后才是媒体/球员体系更真实运行的平台。

本文件仅建立研究依据和评估方法，不声称已调好任何NBA2K22参数、不代表已确认任何内存地址或修改游戏。
