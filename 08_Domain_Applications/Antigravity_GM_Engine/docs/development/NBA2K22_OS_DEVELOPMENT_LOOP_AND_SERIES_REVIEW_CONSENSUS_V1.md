## 二、统一开发原则（面向 Execution / Research 岗位）

今后从公共基线 Fork 的所有 `execution` / `research` 岗位必须严格遵守以下规则：

### 1. 默认采用证据驱动内部迭代（`evidence_driven_iteration`）
- 连贯的研究或工程任务默认采用内部 Loop，而非单次提交即完结。
- 模型必须持续比较**任务原始目标**与**实际完成情况**，**不得因一轮测试通过、一次 Git 提交或提取到若干新字段名称，就自行宣布未完成任务已全部完工**。

### 2. 标准五步工作循环（5-Step Cycle）
每轮迭代必须严格经历以下闭环：
1. **诊断与增量选择（Diagnose & Select Increment）**：对照任务目标、现有测试与证据缺口，选择一个有价值、有边界、可验证的具体增量。
2. **实施与研究（Implement / Research）**：执行实质性的源码改进、测试编写或逆向取证；当目标是代码实现时，不得用解释性散文代替可执行交付物。
3. **针对性验证（Focused Verification）**：运行单元测试、冒烟测试、边界测试与负例检查，捕获并保存真实 exit code、输入、输出和环境信息。测试失败应作为下一轮迭代的指导证据，而非向 Human 索要微观审批。
4. **比对分析与分类（Compare & Classify）**：比对预期与实际表现，保留失败尝试记录，确认是否存在回归；若发现新事实，提出可证伪的下一步假说。
5. **修正或归档并继续（Fix & Continue, or Classify Gap）**：在任务授权范围内修复自身引起的错误；若遇到需外部输入或实机条件的局部未知（UNKNOWN），登记具体缺口后**继续其他独立可执行工作**，不因单项阻断让整项任务闲置。

### 3. 证据收敛与停止边界（收敛而非无界循环）
- **无固定轮数要求**：以目标覆盖度、验证证据和可行的下一轮改进判断是否继续，不规定固定 3 轮、5 轮或 37 轮。
- **真停止条件（Stop Conditions）**：
  * 人类明确批准的有界目标与其测试已完全达成，残余缺口已明确分类并输出完成收据；
  * Human 明确指令缩小范围或停止；
  * 遇到真正的受保护操作边界（如未获授权的写游戏内存、写存档、切换 master、篡改历史事实）；
  * 缺乏新的客观证据，迭代已退化为无意义的反复猜测与重复试错（**严禁无新证据地无限循环**）。
- **一次性简单任务豁免**：小型、机械性、一次性任务若单轮即完全达成目标和全部验证标准，无需人为制造多轮。

### 4. 每轮迭代最小证据检查点（Minimum Increment Checkpoint）
每次循环产出必须记录：
- 精确候选 GitHub SHA 与工作分支名称
- 当前子目标与实际改动的文件列表（allowed paths 范围内）
- 实际执行的测试用例、负例及返回值（exit code）
- 改动前后的行为对比与回归状态
- 当前遗留缺口与候选证据认识论评级（如 `STATIC_DISASSEMBLY_LEAD` / `PENDING_GAMEPLAY_VALIDATION`）
- 下一轮优先改进事项或停止原因

### 5. 典型历史参考案例
- **NBA2K22 Codex WorldData 工程任务**（`nba2k22-world-data-full-implementation-01`）：
  在同一个大任务目标下连续记录了 37 个工程增量，通过持续编写代码、SQLite 迁移、Native 只读比对、单测与负例排查，将最初 16 张表推进至 100 张表 / 1,775 列 / 20 个 Reader，最终按 Human 缩小的常规赛范围集中完成 301 项回归。
  * **经验启示**：在明确目标下保持内部证据闭环能够扎实推进大型工程，但并不意味着 37 轮等于最优，也不代表原任务全部长周期目标已经通过独立验收。

## 三、统一审核原则（面向 Independent Review / Planning 岗位）

### 1. 默认审核节奏：任务内部持续验证，系列完成后集中独立审核
- 研发期间**不需要**对每个微小任务、每个函数提交或单字段研究单独开启新窗口执行独立审核。
- 允许在以下条件满足时采用**延后至系列结束审核（`deferred_to_series`）**：
  1. 任务产出仅为候选研究、离线分析或可逆的原型实现；
  2. 结论尚未进入受保护分支、未正式对 Human 宣告生产交付；
  3. 下游任务具备独立辨别上游错误的能力，不会盲目将未经验证结论当作权威接口或事实基准；
  4. 任务已完成完备的本地自测、负例检查与现场运行时证据捕获（**延后审核绝不等于免除测试**）。

### 2. 即时审核触发边界（`immediate_required`）
一旦触碰以下任一边界，必须立即终止延后，**在跨越该边界之前完成新窗口独立审核**：
- **边界 A（受保护集成与交付门）**：结果准备合并 `master`、合入受保护基线、正式向 Human 宣告验收，或七阶段 Workflow 到达规定的独立审核/完成门。
- **边界 B（下游承重采用）**：下游工程准备将未审结论作为**权威公共接口、生产规则、原生函数地址/结构体布局、数据库物理 Schema、允许写入的游戏机制、全自动决策模型**使用，且错误无法被下游可靠吸收。
- **边界 C（高影响与安全风险）**：涉及安全、私钥、权限边界、持久化真实存档或用户数据等高风险动作（`T3_high_risk`）。
- **边界 D（证据不可逆风险）**：源证据即将在后续流程中丢失、不可恢复，或缺陷可能污染其他任务的历史事实使其无法解释；或 Human 明确要求立即审核。

### 3. 系列集中审核的执行纪律
- 系列结束时由**全新隔离的独立审核窗口**统一复核。
- 审核员读取系列各任务的固定 SHA、共同目标、原始证据、跨任务依赖与集成测试。
- 承重接口与明确冲突必须 100% 深入核查，不能仅依靠抽样。
- 同一根因的缺陷只签发**一次集中整改清单**，整改后优先核查变化量与回归，不机械开启逐提交的审核死循环。

## 五、岗位职责四分立纪律

在多代理协作体系中，必须严格贯彻四类岗位的职责分离：

1. **开发规划岗位（Planning）**：
   - 负责拆解业务需求、定义单一任务目标（`task_packet`）、划定允许变更路径（`allowed_changed_paths`）、设置测试标准与审核排期模式（`review_mode`）。
   - **禁止**：不越权直接编写大量工程业务代码，不自行合并 master。
2. **开发研究岗位（Execution / Research）**：
   - 负责任务范围内的内部 Loop 施工、逆向取证、测试编写、差异比对、更新断点与交付工作分支。
   - **禁止**：不自审自判通过，不擅自合并 master，不执行未获授权的游戏写入或受保护操作。
3. **独立审核岗位（Independent Review）**：
   - 必须由**独立会话**担任，负责核对任务输入、独立复跑验证、核查代码事实与反汇编机器码、评定认识论等级并出具正式审计结论（`PASS` / `REWORK_REQUIRED`）。
   - **禁止**：不作为上游代码的顺手修改者（发现问题出具整改清单，由开发者集中闭环）。
4. **人类用户（Human）**：
   - 拥有最高战略裁决权，负责产品关键语义裁决、受保护动作授权、Core/NBA `master` 合并确认及跨模型协作调度。
