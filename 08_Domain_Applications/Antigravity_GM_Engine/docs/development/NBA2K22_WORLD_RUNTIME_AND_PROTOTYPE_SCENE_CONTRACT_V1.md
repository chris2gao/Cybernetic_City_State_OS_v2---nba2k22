# NBA2K22 世界数据原型场景、正式年度游戏循环与底层操作契约 V1

> **Human 产品裁决：2026-10-25。适用范围：NBA2K22 PC 离线 MyLEAGUE 及本项目未来底层/人格工程。**
>
> 本契约用于让规划、Codex 实现、Native 逆向、独立审核和未来 GM/Coach/Player 模型在进入任务前拥有相同的范围定义。属于 NBA2K22 **项目级业务规则**，不修改通用 OS、不构成任何游戏写入授权，也不自动更改已经运行中的 Codex 任务包。
>
> 必须区分：**A. 原型开发期间为发现所有来源而设置的测试场景**、**B. 游戏正式运行期间由 Human 主动选择的采集节点**、**C. 日后由 Human 独立启动的人格决策过程**。三者不是一个自动工作流。

## 1. 产品目标、能力层级与排除项

当前建设的是完整的 **NBA2K22 底层数据应用能力**，不是 GM、教练、球员的决策系统。数据读取/原生逆向、全场景对象/字段/身份、存档隔离数据库、增量采集、不可变历史与回看、查询/导出、字段意义/合法值域/编码/操作限制、经授权的可写字段与增删改查、批量执行、写后读回、验证/回退与失败恢复，**都属于底层开发目标**。写操作的实现和实机许可应分阶段单独确认；当前已有的只读取证绝不自动扩展为游戏进程写入许可。

**以后才开发的决策层**负责：GM/Coach/Player 使用哪些事实、提出什么行为、为什么选择特定球员/球队/战术/签约、为何将某字段设为某值、人格/目标/谈判/意愿如何形成。底层只回答“数据是什么、何处可读、值何意、可否操作、怎样安全准确地执行”；不能把签约、选秀、训练决策算法偷做进当前原型。

原生游戏的交易、签约、选秀和训练可以作为读写接口及生命周期来源；项目未来可在外挂模型里决策，再经**合法且已验证的**底层原生修改接口反映到游戏。原生选秀抽签可以保留；原生选秀大会完成后，将来外挂选秀可能通过改新秀球队归属实施，但必须先验证名单、合同、原生选秀结果和资产关系是否要求联动修正，不能因为一个球队字段可写就宣称流程可执行。自由球员、员工签约和训练同理。

项目存档之间**独立隔离、一档一库**；不构造跨存档分叉、继承、合并或默认跨档身份。存档身份依照 Human 确认的游戏文件绑定；PID、内存地址和运行时指针每次重新发现。隐藏 Potential 等普通角色不获准读取的字段不得借底层或新秀侦察机制泄漏；实际安全读取边界以当前 Native 证据为准。

## 2. A — 原型逆向与场景来源确认：8 个取证窗口

这 **8 个场景是研发取证矩阵，不是正式游戏的采集频率**。Human 将专用测试存档手动运行到某一窗口；Codex 在此时做 Native 来源发现、身份/值域验证、读取/入库/查询实现及必要回归。Human 掌握进入下一窗口的时机，Codex 不自动推进游戏，也不默许保存/修改游戏。窗口中无法重复获得的原始来源，应优先保留已批准范围内的最小可复查证据，然后才离开窗口。

| 编号 | Human 准备的游戏窗口 | Codex 必须识别/验证的新增或变化来源 |
|---|---|---|
| **S1** | 当前赛季已进行约一个月（已取得，可作为“赛季初期基线”） | 当前常规赛赛程、已赛 Box、当前赛季统计、球员/球队/职员、合同、训练、设置、来源成熟度；不谎称已经完成全年数据 |
| **S2** | 全明星周末 | 入选/首发/替补、赛事与奖项在何时出现、对应球员/比赛对象及赛前赛后变化；研究覆盖不等于正式必须触发 |
| **S3** | 交易截止日前 | 原生交易限制时点、球队名单、选秀权归属、交易与自由球员状态、合同变更；截止日限制是游戏机制，不假设数据库随之大变 |
| **S4** | 常规赛结束且 MVP 等常规赛奖项颁发后 | 常规赛最终统计/排名/纪录、年度奖项与获奖者、赛季定稿时点、后续不可重写的事实 |
| **S5** | 季后赛开始 | 季后赛赛程/轮次/系列赛/种子/对阵、赛程与常规赛结构差异、季后赛 Box 新数据窗口、可能初始化的新秀来源 |
| **S6** | 季后赛结束但尚未进入休赛期 | 冠军、总决赛 MVP、系列赛终局、季后赛个人和球队最终统计、历史定稿；核查是否出现正式新秀池 |
| **S7** | 休赛期（需要拆成独立子窗口） | 员工池/职位/合约、选秀抽签、正式新秀池、原版选秀后新秀实体/归属、自由球员与续约、球队训练营（每队人数/训练项目与成长）以及阶段切换 |
| **S8** | 休赛期结束，开始新赛季 | 新赛季身份、名单/合同/选秀来源、人员和训练变化、赛程重建、年度历史衔接及新赛季初始设置 |

**S7 必须按真实游戏分阶段取证，不能进入休赛期就假设所有来源同时存在。** Human 可依次提供员工市场、抽签前后、选秀前正式候选池、原版选秀结束、球员自由市场/新秀签约、训练营、休赛期末等子窗口。每一子窗口至少记录：来源首次可读的时机、数据池何时消失、对象身份及关联、原始/显示值/字段意义、未知缺口。完整游戏休赛期可能超过这些子窗口，实际以实机界面和来源为准。

选秀候选研究至少区分：**常规赛可球探查看的评级池**（可能显示 D- 到 A+，不等于实值）与**正式参选/原版选秀后生成的实际新秀对象**。正式池究竟季后赛何时初始化当前为 UNKNOWN；不得从空 Native ID 模板生成虚假球员，也不读取隐藏 Potential 代替球探评级。

## 3. B — 正式游戏运行：Human 选择的年度采集节点

下面是 Human **目前确定的运行节奏**；用于未来提供可手动调用的采集入口，不是要求 Codex 在现实时间或游戏时间自动监控、定时执行或调度模型。每次节点选择、何时让模型采集，都由 Human 主动发起。可选频率保留配置空间，不擅自固定。

| 顺序 | 正式游戏节点 | Human 确定的采集安排 |
|---|---|---|
| **P1** | 新赛季开始 | 采集一次 |
| **P2** | 新赛季开始后一周或一个月 | 默认开始一个月后采集一次；若实际数据量/成本允许，可改为开始一周后一次；不是自动每周循环 |
| **P3** | 全明星周末开始前与结束后 | 各一次，**可选**，未来看是否开发全明星相关机制 |
| **P4** | 交易截止日前 | 一周或一天前采集一次，供 Human 后续启动决策 |
| **P5** | 常规赛结束，常规赛奖项颁发完 | 采集一次 |
| **P6** | 季后赛各轮 | 暂定按每轮开始前或结束后安排采集；可按未来游戏效果调整，甚至每比赛日一次；不写死 |
| **P7** | 总冠军得出，赛季结束 | 采集一次 |
| **P8** | 休赛期开始 | 采集一次 |
| **P9** | 员工市场开启 | 采集一次；**未来**由外挂系统完成员工签约决策，底层只负责读写数据接口 |
| **P10** | 游戏原生选秀大会结束 | 采集一次；**未来** GM 在外挂进行选秀决策，通过经验证的球员归属/相关字段修改落实选择 |
| **P11** | 自由球员市场与签约时点 | 采集一次；**未来**外挂处理新秀/自由球员签约与允许的交易，底层提供经验证的接口 |
| **P12** | 休赛期结束 | 采集一次；由 Human 继续进入下一赛季 |

这里的“采集一次”指 **Human 在该节点主动调用一次正式采集程序**；可包含内部多个一致性单元、来源增量和必要校验，不指每张表必须全读或全存一次。游戏 P12 与下一赛季 P1 不得盲目重复保存一份完全相同的基线；可以复用已验证来源和增量检查，但 Human 仍可分别选择是否发起正式采集/决策。具体节点按游戏实际状态识别，不是现实日历定时器。

## 4. C — Human 手动触发的采集、独立模型决策与游戏继续

**真实运行循环（Human in control）：**

1. Human 在 NBA2K22 内自己玩/模拟/推进至合适的游戏节点。
2. Human 通过聊天窗口**主动要求模型调用采集脚本**；脚本完成存档验证、只读 Native 采集、差异入库、来源和完整性检查，并返回可定位的有效世界数据状态。
3. Human **另行主动启动**独立 GM、教练、球员模型，让未来人格系统依据对应最新数据和其自身机制提出决策。这一步**不是采集脚本自动唤起**，也不包含在现阶段底层实现。
4. 对 Human 允许的操作，未来经底层验证接口提交批量游戏修改，执行后读回，并记录哪些成功/失败。人格决策原因属于未来模型而非 CRUD 实现。
5. Human 回到游戏继续玩，直至下一个主动选择的节点。

**关键规则：** 技术性重试、失败补采、历史补录、写后读回、为了 Native 探索发生的研发采集 **不自动产生决策窗口**。成功采集只提供一个可供人格使用的有效数据状态；是否启动哪一个模型、是否多次使用同一状态，都由 Human 自行选择。**不建设**实时游戏阶段 watcher、无人值守 scheduler/daemon、自动推进日期/游戏、自动唤醒全部人格、无条件自动调用下一环节等设施。

底层可以提供批量自动执行**脚本内部步骤**（读→校验→入库，或经授权的写→读回），但其触发是 Human 发出的当次命令，不是无人值守的持续运行。此项规则优先于旧文档中“采集后自动生成/调度决策任务”的候选措辞。

## 5. 增量采集与历史契约：不按节点重复全量扫描

**采集模式须按来源/领域分类，不采取“每次全库重读”默认策略**：

| 数据性质 | 后续应如何处理 |
|---|---|
| 已完成且完整核证的历史比赛、个人/球队 Box | 保存一次并冻结。下次只需轻量目录/状态核对，**不重读旧完整 Box**；新完成比赛只采新增部分。若发现原始冲突保留证据并交 Human 裁决，不覆盖旧终局 |
| 尚未完成的比赛/未来赛程 | 轻量核对目录与状态；新赛事/新季后赛对阵、状态从未赛到终局的变化才采集详情 |
| 当前累计统计、现役球员属性/徽章/合同/名单、职员、战术、训练、财务、市场池 | 随 Human 正式采集节点检查；必要时对新变化字段做 typed 观察。**某字段不是本次实读就不能刷新其最后有效观察时间** |
| 新人/自由球员/员工池与短时可见对象 | 首次可读时建立来源和身份基线；后续记录成员增减、状态/归属变化及退出池的事实 |
| 冠军、赛季最终统计、年度荣誉、历史纪录簿 | 与对应**真实定稿事件/游戏年度**匹配；优先年度采集，正常重复调用只做轻量检查；失败不消耗年度额度 |
| 新闻、交易事件 | 独立增量来源；不能因为年度纪录已采就漏掉新的事件 |
| 设置和稳定资料 | 保留首次读取与后续变化/关键设置核对；没变的值可引用已证明的历史观察，不盲目制造巨大重复快照 |

**增量读取 ≠ 增量保存**：仅省 SQLite 重复行，但 Native 仍读取整个赛季 Box，不算达到读取成本目标。优先利用游戏原生稳定 ID、索引/状态、变化时间或有界轻量指纹找到实际变化；没证据时不能臆断源未变化。特殊源可能需要轻量全目录核对，不能以全量扫描数千条历史 Box 作为每次普通采集的默认步骤。

保持 **append-only 历史语义**：原始事实不修改、不覆盖；纠错单独追加且依据 Human 裁决。按采集时间可还原当时**实际已知**的数据；未变化事实可由最近一次有效观察加来源/新鲜度证据重建，但不得冒充新观察或伪造已读取字段。已知缺口需显式 UNKNOWN/NOT_OBSERVED、来源等级和影响；Q10 例外只能由 Human 明确批准。补录针对新发现的缺失数据，正常采集不重扫所有已保留历史。

**同一年度常规赛奖项与季后赛奖项时点不同**：P5 产生常规赛 MVP 等，P7 产生冠军/总决赛 MVP。现有“存档+游戏年度+来源族仅刷新一次”的节流实现不能导致 P7 奖项丢失。后续 Reader 可分离常规赛定稿/季后赛定稿的来源族，或保留轻量差异补录/阶段定稿记录；以实机来源证明具体结构，不能事先把 P5 的年度成功视为季后赛全部荣誉已完成。旧成功快照保留不删除。

## 6. 原型开发次序、验收与模型协作

1. Codex 在已授权底层开发范围内，先完成真实查询正确性、批次一致性、场景来源及增量采集。**Game Box 默认只能输出同一采集单元**，可选指定历史单元；累计与场均口径、比分来源、身份缺口明确标识。业务小缺陷直接修复，不要求逐增量交给 GPT 审核。
2. 在当前 S1 基线可用后，Human 按 **S2→S8** 实际提供场景；Codex 逐窗验证新源/数据池/失效边界，现有 Reader 可复用不重建。场景离开前仅需确认最关键的窗口证据已保存，不设频繁全系统审核关卡。
3. 对真实游戏一年完成后，衡量全年数据体量、重复读取/节省量、跨年度关联、恢复/备份与 100 赛季目标的实际成本。**没有完整年度证据前暂缓虚构性的长期容量压测**；容量不足时由 Human 决定允许保留的年限，不擅自删除历史。
4. 只读完整候选做集中系统级评估；再针对字段是否可写、原生合法值域、依赖关系、批量修改、失败处理及读回逐项研发；**真正访问/修改游戏内存或存档须另有 Human 明确许可**。写能力是当前底层完整交付目标，不是未来人格任务。
5. 完成已确认的数据操作字典和模型可调用的安全读写脚本后，才另立 GM/Coach/Player 决策或人格开发任务；没有必要为本阶段实现完整原生 GM 交易/选秀决策规则。
6. 工程主 Owner 仍为 **Codex**，默认由其自行编码、测试与一般 Native 查询；**只有大量重复、批量化 Native 逆向任务且净收益明显时**才考虑经 Human 转交 Gemini/Antigravity，严禁默认通过 Computer Use 操纵另一个模型完成零碎任务。共用同一台本地机器与仓库，不并行工作。当前已运行的 Codex 长任务不因本文自动中断、换任务或追溯修改。

所有模型的任务开始都应以本契约 + 实际任务包 + 已经确认的现行 Native/Schema 证据为依据。这里的“规划须支持”不代表某个 Reader、脚本、游戏效果、UI 语义或完整世界数据**现在已经实现/实测**；以对应代码、游戏来源与验证批次为成熟度权威。

## 7. 最小执行/交接清单

- **Human 准备场景**：明确当前真实游戏阶段、所加载存档文件；是否允许进入下一阶段或进行任何写操作分别声明。
- **Codex Native/采集**：报告新增/已变化/已跳过的数据域，读取依据、首次与最后可读窗口、领域对象 ID 和来源等级，记录 UNKNOWN 和失败。
- **增量结果**：提供每领域的新事实数、最新状态/来源时间、已完整冻结比赛数、身份无法关联数、重复跳过与实际读取量；不得用表列数量代替覆盖率证据。
- **未来写接口**：每字段的原生/显示语义、合法值域、联动约束、预期原值、操作批次、写后读回/失败回滚；未经 Human 授权绝不访问写入路径。
- **交付状态**：区分设计/研究、实际 Native 只读、SQLite 查询、写入验证、存档重载验证、完整候选验收、独立审核及 Human 接受，不以“文档已写”或“一个场景跑通”冒充完成。
