## 3. 三层字段状态：避免把“待核实”变成凭空完成

每个目标字段用独立、可追溯的三个状态判断：

- **需求覆盖状态**：`REQUIRED / AUTHORIZED_EXCEPTION / OUT_OF_SCOPE`。01b Human批准的字段目标不能由开发者把未知改成OUT_OF_SCOPE；Q10例外必须Human批准。
- **来源验证状态**：`RESEARCH_LEAD / RAW_OBSERVED / UI_NATIVE_MATCHED / UNKNOWN / REJECTED`。状态必须有真实证据引用；读取测试与正式独立验证另标。
- **数据库实现状态**：`UNMODELED / PROVISIONAL_COLUMN / DDL_CANDIDATE / FIXTURE_TESTED / ACCEPTED`。数据库表可先有证候选，不能拿DDL存在替代真实字段来源；未证字段不要伪装成有效玩家事实。

滚动覆盖报告必须给出 **按领域的需求目标项数、证据达到的具体级别、候选表/列数、SQL测试覆盖及未闭合UNKNOWN**，同时明示它们是不同统计口径，避免把146注册与39研究入口简单相加。

## 4. 谁做什么：防止“两个Codex主责同时悬空”

| 角色 | 稳定职责 | 禁止替代 |
|---|---|---|
| Codex 架构owner | 全域逻辑身份/无分叉ER、候选表与最终字段结构、DDL、旧表去向、数据一致性与SQL验收 | 不把未核实的Native猜测升格为字段真相；不自审最终独立PASS |
| Codex Native验收owner | 针对Gemini或已有AG Native候选，检验Game/PLAYER/STAFF等字段、值域、UI/Reader/fixture、反例；以证据更新字段字典 | 不抢夺架构owner的全球表设计决策；若共享一个Codex执行实例，按R1→R2顺序，不伪装成并行 |
| Gemini/Antigravity探索owner | 独立小疑点的静态分析、可授权只读逆向、Reader/Codec、字段枚举/验证路径与失败例；先提交证据给Codex | 不做全局表架构裁决，不替代Codex正式Native验收，不碰未授权进程/存档 |
| GPT规划owner | 拆OS现有task ID的具体交付顺序、核查需求不漏、汇总冲突和Human提问、控制计划版本 | 不冒称研发/实机独立审核已完成 |
| 独立评审 | 复测单一证据包、Schema方案与关键失败路径，给PASS/FIX_REQUIRED/REJECT | 不由本规划模型兼任自己计划/代码的正式验收 |
| Human | 审批计划、影响长远的数据库存储拓扑或数据语义、Q10豁免、各类DCR/写游戏/合master/生产切换 | 一般可逆表字段命名/索引不逐个问 |

**并行条件**：只在真正存在独立执行窗口/环境、文件所有权互不冲突、共享证据接口明确时并行；否则以Codex架构→Native验收→候选Schema的短闭环顺序执行。Gemini可以同时进行不触及游戏/私有机器的现有源码与研究资料编目（按正式任务包授权）。

## 5. 可核查的交付格式：首个里程碑就看到具体表

R1每张候选表必须提供 `Table Design Card`（未来工程包实际文件名由OS任务确定），最少：

- `candidate_table_name`、`responsibility`、`record_grain`（一行代表什么）、`lifecycle`（静态/状态/事件/观察/汇总）
- `key_scope`、`primary_key_candidate`、`foreign_key_candidates`、`cardinality`、`save_isolation`
- `columns`：**每个已知列**的字段名、真实/候选来源、逻辑类型、初步/已证合法值域、NULL/UNKNOWN、单位、角色权限、证据链接；没证据则显示候选与未知，不编造
- `design_reason`、`why_not_merge`、`query_examples`、`migration_source`、`acceptance_status`

R1全域表数仅为可修改的 **候选数字**；到 R5 给出**最终准确数字和全部完整字段字典**。旧27表需要有去向；若未决定，每条旧表明确 `UNRESOLVED`，不能静默遗失。

## 6. 人类决策和检查节奏（少打扰，但不会只在最后揭晓）

- **讨论门（现在）**：V0.2只是讨论候选，Human暂不批准V0.1不得被当成已授权派单。需要听取 Human 对“先表卡、再来源闭环、逐领域迭代”的意见；不要求同时授权本地DCR。
- **H1：全域候选表目录首轮审议**。呈现候选表数量/职责/关系、旧27表去向、已知Native风险及未证假设；仅有不可逆/跨域语义或数据拓扑重大分歧时向Human集中提问题。
- **H2：核心GAME闭环/首批离线SQL样本报告**。报告哪些来源确实经核、哪些只是fixture、哪几张表跑通、错误/权限案例；默认作为**进度检查而不是另一个自动要求Human签字的门禁**，除非出现新的受保护操作或重大范围问题。
- **H3：数据库全面Schema候选与Q10缺口审核**。列出准确的候选表数、每表全部字段/约束/值域/来源、不可得字段的影响；只请Human对例外与重大业务结构分歧做有证决策。
- **H4：完整工程验收**。等离线实现、真实来源回归、查询/导出/权限/失败测试完成，提交精确表数、DDL/迁移/测试证据和独立复验结论，Human再决定是否接受与是否允许下一阶段/生产操作。

每个报告固定包含“本轮实际表及列变化、证据等级变更、真实运行测试和未关闭问题”。**无固定每轮三题**：重大选择一次1–3题，给真实方案、成本和推荐。普通工程可逆细节由owner自行在获准任务包内定案。

## 7. OS前置与权限边界

- 使用已有 `WORLD-DATA-ARCH-01`、`NATIVE-ACCEPT-01`、`WORLD-DATA-COVERAGE-01`、`WORLD-DATA-SCHEMA-01`、`WORLD-DATA-PROTOTYPE-01` 等ID；本计划不擅自改写master的OS backlog，计划通过后才准备实际任务包/受控验证。
- 目前读取 `master` 的 OS backlog 中 `OS-BASELINE-01` 仍为 `candidate_pending_independent_review`，**须核实真正OS run/独立审核结果**，而不是以文字静态状态永远阻断，也不能未经确认宣布已解除。
- Human已批准的01b结果A仍在工作分支；不自动获得 `master` 合并许可。正式工程任务应以实际最新master精确SHA开新任务分支，引用经过批准的A基线和真实证据。
- 对本地路径、游戏进程/内存、Save、受控权限与DCR必须在**具体操作前**核对权限；计划讨论批准不等于授权Native本地实机操作，亦不包含真实游戏写入/模拟赛季推进。
- 永久存档规则：不同存档完全隔离、无任何跨档继承/分叉/合并；不得沿用旧架构V2中的`generation fork`默认设计。保存历史不可改写、普通GM不能读隐藏Potential、外部模拟交易/选秀与游戏原生规则/状态分层。

## 8. 此版本与V0.1的审批差异

1. **不是**“Codex同时扛两项全局主责直接并行”，而是单一架构owner与Native验收owner职责分开、是否并行以真实资源和任务包为准。
