# 第一大任务 · 全字段历史存储资源评估说明 V1（合成验证）

日期：2026-10-23。状态：仅用于阶段 01b 需求选择；不是真实 NBA2K22 数据基准，也不是在 Human 的电脑上实测。

## 结论
- **每个数值有历史不需要各自建立一张历史表**。同一个历史表可以按对象+时间保存一个字段组的快照；也可以一张字段变化表按对象+字段+观察时点保存变化。
- **全目标字段“正常采集观察历史”是值得优先考虑的候选**，但不意味着游戏中两次采集之间的每一次变化都可重构。
- 对于数百对象、数百整数字段、每赛季12至52次采集，合成基准外推在单域通常不到几个 GiB；**每赛季365次重复全字段、数十存档、重复备份**需要另行精算。
- 具体物理快照/Delta混合方案仍由阶段02证据与03结果建模B比较决定，本报告不冻结Schema。

## 合成 SQLite 测试
环境：Python标准库sqlite3, SQLite3.46.1，PRAGMA cache_size=-16384 (16MiB)。全部在临时模拟库中运行，与用户电脑、游戏进程、生产存档/数据库无关。样例500位球员、每位200个整数值、40次采集；宽行20,000条/400万数值，数据库9,748,480字节、写入0.69秒；逐字段800,000条，20,475,904字节、写入1.68秒；首次全量加约5%字段变化，295,000条、7,892,992字节、写入0.93秒。以上写入时间仅为当前计算环境的有限微基准，不能当成用户本机性能承诺。

## 工程解释
- 这是每行单位容量外推，不是全量100年写入测试；真实字段值分布、JSON/文本/Null、索引、数据变化频率和对象增长均可改变结果。
- SQLite不是把磁盘中所有数据库记录常驻加载到RAM。16MiB仅是本测试SQLite page cache配置，不能视为实测用户机器进程总内存；OS页缓存可能额外使用内存。
- WAL、同步设置、长事务、并发查询和备份会影响真实性能；需安全真实样本专项验证。
- 正常采集没有观察到的中间变更不能补造历史；首次导入游戏真实拥有的历史，不意味着完整还原其未存档的状态。
- 多个NBA2K22存档彼此严格隔离；本报告没有采用任何跨存档分支/合并假设。
