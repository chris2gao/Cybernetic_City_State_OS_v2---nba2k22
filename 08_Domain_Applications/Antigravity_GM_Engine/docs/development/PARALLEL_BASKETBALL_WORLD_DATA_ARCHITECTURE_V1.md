# NBA2K22 平行篮球世界：权威引擎、原生数据镜像与长期历史账本 V1

**2026-10-22；项目级技术共识。** 本文承接[项目开发意图](../PROJECT_INTENT_AND_MODEL_DEVELOPMENT_BOUNDARIES.md)与[Native I/O蓝图V2](NATIVE_GAME_DATA_SYSTEM_RECONSTRUCTION_AND_IO_BLUEPRINT_V2.md)，明确架构方向、数据接收顺序及当前食材成熟度。它**不是**生产Schema迁移批准、任何游戏写入批准，也不宣布AG研究模块已通过Codex验收。

## 1. 不变的世界观与五层分工

**NBA2K22 PC MyLEAGUE是篮球比赛、原生状态与球员自然成长的权威模拟引擎；外挂构建可追溯的游戏事实镜像、长期历史账本、AI参与者和受控扩展行为。** 项目2021–22赛季开始、按玩家规则循环使用1984–2020历史选秀素材。外部事实库不得推测代替实际比赛或直接改写球员自然能力。

| 层 | 职责与边界 |
|---|---|
| ① 原生游戏引擎 | 比赛、模拟、球员自然成长、规则/实际存档；游戏结果优先于外挂推断。 |
| ② Native Object Reader | 根据当前版本和存档的真实原生Getter/数组/关联，安全读取原始记录及字段；未知语义保留UNKNOWN，不把UI页面视为原生SQL表。 |
| ③ 平行SQLite世界层 | 在既有双事实库及DEV14发布机制上建立对象镜像、逐场事实、赛季切片、跨年历史、可追溯来源和计算视图；在原生记录被覆盖前，依授权采集保存真实历史。 |
| ④ 独立AI角色与扩展游戏机制 | 采集→分析→未来独立教练→未来独立球员→GM→汇总执行；不同角色有不同可见性、意愿和决策，研究/底层I/O不得替代人格算法。 |
| ⑤ 批准与受控执行 | 玩家对游戏修改逐案明确批准，复用现有交易、教练、合同/Native控制的已验证能力与审批、读回及回执。未认证写入保持HOLD。 |

这五层是**架构分层**，不改变玩家已经确定的**六阶段执行顺序**；教练、球员人格尚未正式实现。游戏属性/潜力/徽章不得为通常经营直接编辑，只有用户明确批准的历史线模拟例外等既有窄规则可实施；玩家角色成长例外目前不启用。

## 2. 数据建模：原生对象图 + 游戏事实 + 历史 + 查询视图

**不要按每个UI页面新建一张表，也不要把69,040条纪录槽位或1260条矩阵槽位视为同等数量的已验证事实。** 按已证实的原生对象、稳定身份和时间域建模：

1. **原生观测层**：对象类型、slot/index、Getter或相对偏移、格式/Reader版本、原始记录或受控摘要、字段及UNKNOWN区间、原生证据、当前PID/模块签名（仅观测元数据）。运行时指针不是永久数据库主键。
2. **关系事实层（候选，不代表已上线）**：比赛/双方球队/双方Box、赛季累计、球员生涯索引与每赛季记录、球队交锋矩阵、原生历史纪录、签约与死钱、队伍/合同/员工等。由真实样本决定Schema，不为未找到的字段预建大批NULL列。
3. **时间与历史层**：显式`save_id / save_instance_id / generation_id / batch_id / snapshot_id / game_date / season / phase`及source timestamp。GameID只在经过验证的身份域内使用；同GameID在不同存档/赛季不自动视为同一实体。观察事实按来源版本保存，避免未来快照覆盖历史原值。
4. **派生统计与页面视图**：按比赛事实得到Win/Loss、Starter/Bench、Home/Away、Last5/10、球队对比、排行及高阶公式；每一项保留原始口径、范围、计算版本，区别`NATIVE_OBSERVED`与`DERIVED`。页面是验收视图，不是物理表设计依据。
5. **角色可见性与动作回执**：复用现有M0只读查询、GM_SANITIZED Potential规则、能力Registry、审批/回读/journal；不把全知球员池或未经证实的隐藏字段公开给角色。执行后以游戏实际读回作为新事实，不通过修改事实表假装游戏已执行。

现有接收底座已经存在：`database/schema.sql`中有teams/players、monthly_snapshots、team/player月度统计及部分season/history实体；`src/source_extensions.py`与`src/gm_state_io/`提供部分Native读取/状态机制；`src/auto_pipeline_ingest.py`及`gm_state_io.capture_files.install`提供既有采集与双库暂存安装；`src/gm_data_access/query.py`提供批次绑定的M0只读访问。**这不是说比赛Box、StatBank、职业生涯索引和交锋矩阵已经接入上述正式生产表。**

## 3. 研发顺序：建模与验证并行，生产集成在验收之后

- **探索/候选Schema现在就做**：Gemini Flash在`dev/native-io-exploration`中读取真实游戏，提交Decoder、原始脱敏fixture、原生关系、候选表和SQL样例；以游戏UI完整页面/列校对覆盖，不虚构字段。
- **Codex独立验证后才升格**：核对当前exe签名、实际偏移/Getter、statbank边界、记录有效性、GameID与球员/球队身份、Box→赛季累计、跨档隔离、特殊赛况及错误样本；指出字段级证据和局限。
- **Codex按独立获批工程包正式接入**：沿现有`full_verified_v1`和DEV14多存档机制，完成确定性的增量Schema迁移、原始/派生数据分类、批次质量报告、失败阻断、双库发布、M0 Query View、Potential脱敏与来源标记；禁止复制实验性`DROP TABLE`脚本直接上生产。
- **验收链**：真实同档原生样本→对照游戏UI/已证原生统计→跨表守恒及独立时间/身份校验→SQLite批次一致性→封存快照只读查询→（必要时另获批）游戏Save/Reload持久性。运行单元测试不能自动升级为`CURRENT_GAME_VERIFIED`或`PUBLISHED`。
- **触发和自动化**：可由玩家既有开赛、月度、季后赛、休赛期节奏触发脚本采集、校验、生成数据库与发布；不默认常驻抓取、推进行程、写游戏或绕过人工批准。过去游戏已遗失、未曾采集的单场记录不得由赛季累计逆造。

## 4. 截至2026-10-22的证据与能力缺口

权威工程基准是[FINAL-CODEX覆盖审计](../development_reviews/FINAL_CODEX_NATIVE_IO_COVERAGE_AUDIT_20261021_V1.md)（对应`codex/final-code-audit-20261021@d1038811`，尚未自动合main）；40族分类为历史批次部分能力16、源码已实现但未发布7、未合并候选3、签约受闸门阻断1、参考/未知13；R06的20项缺口仍保留。此分类**不是40族完整成熟度评分**。

| 模块 / 角色 | 已有可用“食材” | 阻断或欠缺；当前结论 |
|---|---|---|
| GM经营 | 30队名单、球员属性/合同部分原生数据、赛季累计、财务/选秀权/Staff来源、既有部分交易和教练控制、M0与球场知识/战术资料 | 缺正式逐场/多赛季完整事实、财务部分语义、合法签约闭环、完整管理对象；旧Oct18批未Potential脱敏，不能作为当前GM生产批。**可做有限GM建议，远非全域自动经营闭环。** |
| 教练人格 | 教练参数、体系、战术/Playbook部分来源、球员倾向和部分赛季统计已有工程基础 | 缺可靠逐场对手/阵容对位、真实战术效果、部分模式与场上数据；**教练设置工具≠已开发的独立教练人格。** |
| 球员人格 | PLAYER原始记录/部分能力、倾向、合同、原生统计；AG-01D初步发现生涯统计索引 | 士气/偏好/伤病、动态关系、角色意愿与历史事件尚未完整验证并安全开放；**球员人格尚未开发，隐藏Potential不得泄露。** |
| 比赛与历史 | AG-01D研究分支已有60B SEASON_GAME、24B StatLine、48B PLAYER_STATS和单球员16场与累计18项一致的离线fixture；AG-01C发现原生纪录簿 | 研究证据尚未经Codex独立实机验收/正式生产集成；“238场读取”“完整UI页/G联赛/新秀报告”等结论不得无条件升级为全量已证。 |
| 执行与长期运行 | DEV14身份、代际、审批、双库暂存和现有限定执行器 | 动作各自需权限与回读；部分生效/Save-Reload/跨季留存未证。不能用数据库中存在新值声称游戏已发生。 |

**结论**：研究知识“原材料菜单”已较广，技术“采集管道”已有可复用地基，核心比赛事实首次形成强关联样本；但是**生产可追溯事实、身份/时间、角色可见性及跨季完整性仍不足**，不能宣布GM/Coach/Player三类人格已经有完整而规范的输入。优先做**比赛-赛季-生涯闭环验收与生产数据接入**，再依完整玩家卡、教练实战、健康/士气、市场/选秀等原生覆盖补足各角色素材。

## 5. 后续分工与禁止事项

Gemini Flash负责高并发探索、原生结构证据与受控fixture；Codex负责困难字段、独立验收和经另行批准的生产工程集成；网页版GM/开发规划负责需求、方案和审核；玩家批准真实游戏修改。研究Commit与审核Commit必须各自有清晰的身份、版本及来源。不得从AG研究分支直接合入正式生产Reader或旧match-history候选，旧候选中事务提前提交、跨档查询回退、吞异常等风险必须先修复。

本文件是长期架构共识与数据完整性契约，**不构成AG-01D工程验收通过，不授权任何游戏写入、属性修改、自动赛季推进或正式数据库迁移**。
