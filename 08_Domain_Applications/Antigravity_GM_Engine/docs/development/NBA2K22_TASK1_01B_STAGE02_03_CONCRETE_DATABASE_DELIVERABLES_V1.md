# NBA2K22 第一大任务 · 02/03 实质交付与物理数据库验收规格 V1

**状态：01b 需求结果 A 候选的交付约束。** 对应 Human 最新澄清：阶段01b无需寻找世界线“最优设置”，但第一大任务必须最终产出完整可用、字段级可验证的数据库。本文只**规定未来 02/03 必须提交什么及如何验收**，不伪称已做完真实游戏实证或 SQL；02/03 尚未启动，亦未获最终 A Human 确认。

## 一、责任分界：数据采集、结构与配置取值

| 阶段 | 必须产出的具体内容 | 不属于该阶段 |
|---|---|---|
| 01b / 结果 A | 需求范围、逻辑对象/关系、保真/隔离/历史/权限约束、证据缺口、阶段02/03的具体成果规格和验收标准 | 真实完整字段字典、最终DDL、最优世界线参数 |
| 02 / 实机与 Native 证据 | PC22真实界面/可取得字段的逐项证据、Native来源映射、类型/取值范围、枚举、单位、是否可读、历史窗口及未知列表 | 虚构未读值；编写 GM 自定义交易算法；把“数据源可读”直接宣布“支持修改” |
| 03 / 数据库实现 B | **确切物理表总数、每表完整字段清单、建表理由、表间关系、主外键和索引、类型/有效值/约束、采集与查询策略、完整可运行 SQL DDL、必要数据流与验证用例** | 以一张空白示例表代替覆盖全部对象；世界线最优值求解；原版游戏写入器 |
| 后续独立机制 | 在已确认来源和安全验证的基础上建立游戏当前设置/球队归属/合同的修改能力；另行由世界线/GM规则选择配置值，执行回执和游戏再观察按统一数据契约入库 | 改写已保存的游戏/数据库历史，绕过Human规则审批 |

**关键区分**：02负责“实际能读到什么、合法值域及游戏含义”；03负责“数据库如何持久化这些值和关系”；后续机制负责“是否改、改多少及怎样安全修改”。`legal_game_value_range` 不等于 `optimal_worldline_value`，前者是字段字典要求，后者是未来独立业务决策。

## 二、阶段02：全量真实字段与来源证据的最低交付物

必须形成可审计的 **Game UI / Native / Decoder Field Evidence Catalog**。每条字段至少明确：

1. 真实游戏页面、Tab/栏目、游戏模式、玩家可见文字标签与实际数据示例，或对不在UI显示但被合法读取的原生字段明确标出“非UI/权限受限”。
2. 本存档领域/实体、赛季及游戏时间粒度；Game Native 来源对象/槽位/偏移/Getter、数据类型/字节或bit编码、读取前置条件和来源证据；未成功读取时只写 UNKNOWN、不得伪造。
3. 游戏内部合法值域、枚举、NULL/特殊值、显示单位、精度与格式，及原生→解码→UI展示的可复验转换。如果只能观察部分取值，要区分“确认区间”与“待证完整值域”。
4. 来源可获取窗口（尤其过去比赛 Box/高级统计、职业历史及已退役群体）、可访问角色、安全读取边界、时间及存档作用域。
5. 真实游戏证据引用/研究成熟度、反证/负例、读数失败模式、同一字段的替代来源；不得将现有注册或研究声明自动标为实机通过。
6. 对目标结果中每一个找不到真实来源的UI项目，按 Q10 记录“缺失字段/原因/影响/替代/负责阶段/是否申请Human例外”，不擅自通过验收。

**阶段02验收**：字段/页面与来源可逐项反查；有数据类型和值域证据、可读与不可读边界、标识符可靠性/访问窗口核对；成果能实际指导阶段03逐列设计。对尚未实证的项目保持明确缺口并提交Human评估，而非夸大覆盖。

## 三、阶段03：必须实际交付完整关系数据库，而非抽象模型

下面是 **每张最终物理表**必填的设计模板要求。真实表数必须由证据和实际关系推导，**不得在01b拍脑袋冻结，也不得借“未冻结”回避03最终给出确切数量**。

| 必填项 | 对每张表必须说明 |
|---|---|
| 表名与职责 | 精确名称、单一或明确说明的多个数据责任、保存的业务事实/当前状态/观察历史/外部执行回执及为何需要本表 |
| 字段全集 | 逐列字段名、中文/英文含义、原生字段对应、业务含义、数据类型、单位、精度、默认值、可空条件 |
| 值域与枚举 | 合法最小/最大及特殊编码、枚举映射和未知/未读/不适用语义，来源证据与校验条件 |
| 关键字与关联 | 主键/候选键/唯一性、每个外键目标、实体关系基数、是否可空、级联/限制策略及存档级防串联设计 |
| 时间与身份 | 存档、游戏日期、赛季、实际发生时间、观测/录入时间、历史定稿、冲突/补录及幂等身份 |
| 设计理由 | 归类、规范化/反规范化取舍、为什么不能直接合并进另一表、索引和访问模式、重复与权限风险 |
| 数据进出 | 何时读取和提交、依赖哪个字段源与Reader/Decoder、局部失败如何处理、当前读视图和历史如何查询/导出 |
| 实证与验收 | 对应阶段02真实来源、DDL、样本导入、正/反例、跨域关联、字段级缺口的验证用例 |

同时必须提交以下**实际工程成果**：

- **一份完整的总表目录**：确切表数、按业务/核心支撑分类、每表职责及彼此关系图；覆盖 RES-P、RES-T、RES-C、RES-G、RES-L、RES-M、RES-H、RES-S、RES-D，不能漏项；允许合并实现但要说明去向。
- **完整结构化字段字典**：不是仅靠列名猜语义；所有字段逐一给数据类型、合法范围/枚举、来源、单位、默认/空值、权限、时间类别及用途。
- **可执行 SQL DDL/迁移**：有所有建表语句、完整外键和唯一约束、查询索引；对已有 `database/schema.sql` 逐表/字段标注保留、重构、迁移或废弃的理由及真实数据历史保护方案。
- **采集与历史设计**：实际字段入口→验证→一致性单元→提交→当前视图/不可变历史→结构化导出，说明幂等、补录、Q22 Human 冲突裁决与本地100年容量目标；不等同于拍快照就已覆盖全部真实数据。
- **可运行的样本验收**：至少单球员完整档案、单球队及轮换、实际一场基础/高阶 Box（仅取得者）、教练战术与训练、合同及真实外部事件回执、联盟设置、历届荣誉；负例包括不同存档原生ID相同、权限限制、来源不可读、部分采集失败、已固定历史冲突、重复提交与未知选秀关系。
- **需求覆盖矩阵与交付报告**：每项 Human 确认的目标数据字段和关系指向具体表/字段/读取来源/测试证据或 Q10 例外审批，不得以“建一张总表”“保存JSON”或“有Schema文件”直接判为完成。

## 四、世界线设置：当前不需要最优值，也不需要现成的关键清单实例

- 当前工作只确认：需要有真实游戏设置的可读取来源、真实字段语义及合法取值，数据库能保存**实际观测值**；可区分未来世界线的预期配置、游戏读回及核验状态。
- Q52 的 `Critical Settings Manifest` 是**未来机制对特定世界线版本的治理接口**。具体哪个字段算关键、取什么值、用什么阈值、哪些模拟动作依赖它，必须在对应世界线/开档设置机制开发时再由 Human 审批。
- **01b/02/03不可将“尚未选定最优世界线值”或“尚未审批某世界线关键设置清单实例”作为停止数据源调查或数据库物理建模的条件**；配置实例缺失不代表数据库字段结构/合法值域可以不做。
- 后续是否可以实际修改对应游戏设置，须另有写入机制的安全授权和真实成功证据；现在不能以Native offset存在就宣称可写。

## 五、最终失败判据

出现以下任一情况，不得宣称**第一大任务的最终工程成果**已完整交付：

- 只有需求规范，没有完整表总数、逐表职责和逐字段解释；或者只有一张万能表/JSON字段就声称所有逻辑对象已建好，而没有完整来源、关系、合法值域、验收覆盖说明。
- 数据库列没有来源、真实含义、类型/约束和关系说明；把游戏不可读取的项编造为实测字段；允许普通GM泄露隐藏Potential。
- 不保证不同存档绝对隔离、已确认历史不可变、失败单元不污染当前可信数据，或外部业务事实被当成游戏原生事实。
- 阶段03只提供设计图/文档，缺可运行 SQL DDL 和实际样本/反例测试；不能从真实证据说明为什么采用该表结构。
- 把世界线“最优设置选择”与“合法字段值域证明”混为一谈，或在未授权下修改真实游戏。

**门禁**：这是01b规定的未来验收约束，不等于阶段02/03获得启动许可；完整 A 仍需 Human 独立整体确认后才能按既有OS阶段门推进。
