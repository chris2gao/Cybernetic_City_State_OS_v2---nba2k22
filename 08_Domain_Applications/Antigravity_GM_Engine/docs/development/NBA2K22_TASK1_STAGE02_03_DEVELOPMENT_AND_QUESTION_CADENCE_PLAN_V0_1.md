# NBA2K22 第一大任务 · 02/03 实质开发总规划与 Human 裁决节奏 V0.1

**性质**：拟提交 Human 批准的候选开发计划，**不是已获授权的本地逆向、真实游戏读取/写入或生产数据库迁移任务包**。编制依据为 Human 2026-10-24 批准的完整需求结果 A、[A v1.9](NBA2K22_TASK1_REQUIREMENT_RESULT_MODEL_V1_9.md)、[完整A审核包V0.3](NBA2K22_TASK1_01B_COMPLETE_A_REVIEW_PACKAGE_V0_3.md)、[02/03实质交付规格](NBA2K22_TASK1_01B_STAGE02_03_CONCRETE_DATABASE_DELIVERABLES_V1.md)、当前 master 旧架构V2与原生研究/攻略，以及已有 OS backlog。**计划批准、真实本地执行授权、master合并授权必须分别核实。**

## 0. 最高优先级和执行原则

**目标不只是收集更多边界规范**，而是完成 NBA2K22 离线 MyLEAGUE 全目标数据覆盖的关系数据库：最终提供确定的表总数、全部表名和用途、逐列业务含义/类型/允许值域/原生来源、PK/FK/基数/索引、正交时间/不可变历史、完整SQL DDL、真实取证与可复测的采集/查询样本。

- **先利用已有材料，缺口才探索**：旧 `database/schema.sql` 现有27表为迁移/反例线索；`docs/02_DATA_STRUCTURE_SPEC.md`、`docs/17_MULTI_SEASON_DATABASE_AND_MODELING_SPEC.md` 属早期规格与候选，不能自动升格为实测字段证据；`AG_NATIVE_01D`、现有读取器/解码器与 R01–R07、游戏机制/攻略交叉取证。146字段工程注册与39研究入口不是游戏全字段全集。
- **物理设计尽早可见，但不能用猜测取代来源**：从首批证据和现有旧表开始形成有表名/字段名/职责/关系/理由的**可检验候选表目录**；每次证据增加，更新表字段、枚举和值域状态。凡来源未实证的列单独标 `PROVISIONAL/UNKNOWN`。不等所有UI来源穷举后才允许离线候选建模，也不提前宣布最终SQL定稿。
- **绝对存档隔离**：Human最新约束禁止一切跨存档分叉、继承、合并。旧目标架构V2中 `World/SaveInstance/Generation` 的 forks/restore-lineage 是**过时冲突假设**；新的 `ARCH-01` 须删除“不同存档继承”语义，而不是换个名字保留分叉图。游戏时间与采集时间、真实身份及各类历史只在一个独立存档内成立。
- 游戏引擎是真实比赛与自然成长权威；第一任务只做可靠读数、真实业务事实及未来受控事件回执的数据平台，**不运行交易决策、世界线最优参数求解或游戏写入**。自定义GM等后续规则/选秀权简单直转、权限、旧历史不可修改不退让。
- 设计和执行的开发候选、独立审核、Human裁决三者不能互相替代。

## 3. 数据库建表工作的可见成果节奏

下面是**首轮 Codex 必须提交的可观察里程碑**，不会等到整个02结束才看到表。它们是任务目标，不是现已取得的事实。

1. **T0 · 旧表和新对象对照**：列出旧27表的全部表名与原用途、证据成熟度、风险、拟保留/拆分/合并/废弃、历史迁移位置，并给出实际原生Reader/UI来源链接。
2. **T1 · 全域候选表目录 V0.1**：至少覆盖九类RES，逐个提出候选表名、职责、身份键、主要字段族与来源、和哪些表怎样关联、分类理由；**明确候选表总数与待定行**，不得只有一张泛用JSON表。这里的表数为**候选**，证据增多可以调整。
3. **T2 · 最小真实数据库纵向切片**：Game、Team、Player、比赛得分与真实球员Box、SeasonTotals/来源批次通过独立验证的样本，在离线SQLite建立可查询表与索引，至少一次跨表查询及负例（错Game、跨档相同原生ID、失败字段、重复采集）。
4. **T3 · 分域字段字典深化**：依次补完（P/G/T核心统计）→（P完整卡/合同/健康）→（C教练战术训练）→（M财务选秀/外部业务）→（L/H/S设置历史荣誉）以及D来源与历史，所有真实字段对应物理列/键/值域/来源和验证状态。
5. **T4 · 完整候选 DDL + 报告**：最终明确表总数、每表所有字段及取值含义、每张表设计理由、PK/FK/索引/外键检查、迁移方案、查询/导出、容量及负例证据；未证项不能默认为完成，任何Q10拟例外进入Human独立批准。

**原则**：OS旧任务中的 `ARCH-01`、`SCHEMA-01`、`PROTOTYPE-01` 等用于这些交付；不把“03最终DDL”与“02可以提前做的候选逻辑/物理设计实验”混为一谈。

## 5. Codex、Gemini、网页GPT及Human的分工

- **本规划GPT**：任务边界、优先级/依赖、候选Schema的产品完整性检查；提出确实会影响业务/拓扑的Human选择，不自称独立审核。
- **Codex**：复杂Native/身份复核、体系ER和全部候选/最终物理表设计、字段类型/值域、迁移/SQL实现、负例与受控验证，拥有对应OS包允许的本地环境（授权范围内）。
- **Gemini Flash / Antigravity**：范围狭窄、需要实际查地址/UI/Getter的探索，交付可重放样本与小型Reader/Codec；不让它自行决定全局表结构、裁剪业务范围或宣告复杂设计完成。
- **独立审核窗口**：由另一会话/适当模型重新验证原始证据、关联假设、SQL行为与边界，分别给出 `PASS/FIX_REQUIRED/REJECT`；不能用 Codex/Gemini 自证代替。
- **Human**：批计划与重大拓扑选择、Q10最终例外、实际本地/游戏DCR读数、写游戏、合master/生产切换等受保护行为，最终确认各重要工程阶段成果。

## 6. Human追问机制：只问有决定性影响的项目

**不采用固定“每轮三道题直到无限多轮”**。每个里程碑先由模型进行证据盘点和推荐选择，仅当存在两种均有合理证据且影响用户体验/长期维护/权限或不可逆代价的选项时才请 Human 选择；每次最多1–3个明确问题，必须附真实证据、方案A/B、成本/收益、我的建议与默认不执行项。

**预计需要Human审阅的节点**：

1. **本计划审批（当前唯一待决定动作）**：是否采用“W1架构与W2原生并行、首轮即交候选表目录、随后按证据迭代DDL”的节奏，并允许我建立**正式OS任务包候选**。批准计划不等于本机DCR或写入权限。
2. **首个实质性架构裁决（T1之后）**：Codex给出表目录、存档拓扑一库/多库A/B、关系/容量/跨库事务与历史方案后，仅对关键结构分歧请 Human 做一次集中选择；一般可逆索引/表名/数据类型不必每列都问。
3. **来源不可得与Human权限例外（随W2/W3出现）**：对真实目标字段源缺失、人为权限取舍、Q10豁免、是否同意只读实机/DCR，按证据和影响决定；不猜测、不自行接受缺口。
4. **阶段03完整表/DDL/测试审核**：汇报**精确表数、逐表字典、遗漏缺口、样本SQL和测试结果**，提交Human决定是否接受；未通过则按缺口修订，不把小切片PASS冒充全量PASS。
5. **生产迁移/游戏写入**：是独立任务和新授权边界，绝不被以上任何计划批准隐含覆盖。

**非问题式进度汇报**：每个有界任务闭环向 Human 展示“本轮实际新增已证字段/仍UNKNOWN、表候选增减与理由、测试证据、下个阻碍”；无重大争议时直接提出下一任务包，不机械索取确认。
