### 模拟容量调查与决策解释

见 [全字段历史存储资源评估说明 V1](NBA2K22_TASK1_HISTORY_STORAGE_FEASIBILITY_NOTE_V1.md)。本轮测试发现：**一项字段的历史不等于一张历史表**。SQLite 可对大量字段使用少量按实体分组的历史表；全字段采集观察历史在合理频率下是可行的工程候选，不能因为“几千张历史表”的误解而过早删减需求。

实验用500位活跃球员、200数值字段、100赛季外推：每赛季12次，分组快照约0.27GiB，按首次+5%字段变化的长表约0.15GiB；每赛季52次约1.18GiB/0.65GiB；每日365次约8.28GiB/4.55GiB。**这仅是球员数值状态的合成外推，不是全项目100年真实磁盘预算**；真实字段数、对象增长、日志/备份、多存档、读写频率和机器硬件待核查。

当前规划推荐（**未自动改写 Human Q11–Q13 选择**）：首选所有可变目标字段保留**实际采集观察历史**，以少量业务历史表/定期校验快照+变化记录控制开销；与真实游戏自动生成的比赛、合同、交易等事件事实分开处理。若真实评估无法满足资源预算，才回退谨慎范围。

待后续问答明确：历史覆盖愿望与可接受的采集频率；阶段02/03据此对实际来源、最终表数、成本和真实性进行验证。**不保证重构采集间每次游戏变更，也不泄露角色禁止查看的内部字段。**

### 工程复杂度裁决

详见 [全字段历史工程复杂度和频率裁决 V1](NBA2K22_TASK1_FULL_HISTORY_ENGINEERING_DECISION_V1.md)。

- **历史记录不要求每字段独立表，也不必每个字段单独开发历史更新代码**。优先评估共享采集账本、按对象/字段组保存状态、与当前状态统一协调的采集实现，避免“一个字段一张历史表”的误解。
- 同一个可变字段在实际观察历史中可按时间查询，但**同名/同值不表示同对象**：保存身份、存档、赛季、时点和来源；不同存档绝不继承或分叉合并。
- **状态 vs 事实**：能力、倾向等属于观察状态；逐场 Box、赛季统计、交易、选秀等真实业务事实按比赛/赛季/事件身份保留，不能简单重复写入同一时间快照来伪造事件。
- “按日期用同一模板存变化”是可评估的结构思路，必须区别真实游戏内日期与采集时间；不提前冻结 JSON 单表、长表、分组快照或 Delta 方案。
- 已完成小规模**合成**概念验证：批次当前/历史协调、重复写入幂等、冲突批次拒绝、存档隔离、外键拒绝无效批次。不是用户个人电脑、游戏实机或生产数据压测。
- 未知字段/无法读到的字段继续按 Q10 逐项登记，不能凭历史要求制造数值；特殊内部字段保持原 Q2 的可读写边界和普通角色输出隔离。

### 资源与验收门

已有模拟（500 名玩家 × 200 整数字段 × 100 赛季）在 **20–40 次/赛季**时：分组宽行全快照约 **0.45–0.91 GiB**；假定每轮 5% 变化的长表增量约 **0.25–0.50 GiB**；逐字段全量长表约 **4.77–9.53 GiB**。仅是单个球员属性领域的线性外推，非全部项目真实容量，更非硬性存储预算。

阶段02/03必须以可安全使用的真实字段样本、对象增长、索引、赛季事实、备份和存档数量，实测采集开销、查询/回看、100年容量与系统负载。若不能达到实际电脑可接受的成本或稳定性，列证据与备选方案交 Human，而不是在技术过程中悄悄缩减历史需求。

**本裁决只确定“需要支持全字段采集观察历史”；最终需要多少物理表、每表完整字段与键、存档存储布局、序列化/增量方案，仍由 02 实证与 03 的实现结果 B 决定。**

- 字段级查询、过滤和结构化导出；逐项保留字段名称/单位/原生来源、是否游戏原值/有公式的计算值、采集时点、字段状态与角色可见性。
- 允许下游在同一档案中关联该球员在游戏中真实可获取的能力、倾向、徽章、战术类型、基本信息、合同、健康、训练、球队、赛季统计/生涯统计及比赛数据；不代表所有群体必然都有全部项目。
- 能按实际采集时点查看所有可读且允许保留的可变字段的**观察历史**（继承 Q14=A）；比赛/签约等发生型事实按真实事件身份记录，不推导采集间未观察的修改事件。
- 不能将内部隐藏 `Potential` 等原本不允许普通角色阅读的字段，通过“完整档案”或导出间接泄漏；内部必要读取与普通角色输出必须有界隔离（继承 Q2）。

**可验收情景（逻辑示例，非现有 API 声明）**：选择一个指定存档内某名球员 → 输出按实际 Tab 分组的档案 → 可按字段过滤、导出 → 关联当前球队/历次球队/合同/逐场及赛季数据 → 选择一个曾成功采集的时点，回看当时已观察的属性。未发现的原生字段明确显示未知状态而不是伪造数值。

### Q18=A · 单个独立存档内跨赛季连续身份

- 对于有可靠来源证据证明的**同一个存档内的同一球员**，转队、自由市场、进入 NBA/G League、年龄与赛季变化、合同签订、退役等过程不使其历史断裂。可完整关联各次球队归属、合同、比赛与职业统计、获奖（如游戏实际存在）、状态观察历史。
- 同一姓名、号码、出生信息或相似表现**本身不足以证明同一个人**。真实 ID 可能复用/变化、选秀候选到正式球员的对应关系可能未证；证据不足必须 `IDENTITY_UNRESOLVED` 并保留独立来源引用，**不得强行合并**。
- **不同 NBA2K22 存档绝对独立**：即使姓名、人物和原生 PlayerID 字面值相同，也不得建立跨存档同一个“继承玩家对象”或存档分叉/合并关系。所有实体归属和关联必须在目标存档身份范围内成立。
- 上述是用户要求的**逻辑身份与可查询关系**，不是提前批准某一种物理主键、身份证明算法或特定表名；原生 ID 稳定性须在阶段02证实，阶段03选定实现 B。

### Q19=A · 三层数据含义分别留存

- 对实际能获取的目标字段，保留 **原生数值/原始枚举（受许可）→ 有版本的转换/解码规则 → 游戏真实显示文字或数值** 的可追溯链路；原生/显示不必数值相同，类型、单位、精度和未知状态不可互相冒充。
- 只有原生值确实可获取时才保存，不可为了满足“三层”虚构一个原始值或转换公式；显示值和原生来源须分别标 `observed`、`derived`、`unknown` 等成熟度。
- 角色权限由字段/来源策略控制：内部可为合法关联需要保存某些隐藏数据（如 Potential），但普通 GM/Coach/Player **不得通过整档导出、聚合、历史回看或衍生输出绕过可见性边界**。
- 对可变数值的历史保留，当时可确认的原始值、转换规则版本和实际显示值/来源要能相互解释，后续更换 Decoder 不得静默改写历史观察事实。

### Q20=A · 统计结果的粒度与类别

- 在目标 PC22 MyLEAGUE **实际存在且可取得**的范围内，提供逐场统计、各赛季统计、整个职业生涯统计，普通/进阶统计同样处理。
- 在证据支持时按 **球队、赛季、常规赛/季后赛及其他真实比赛类型** 区分；同一球员赛季转队前后应可分别查和按照明确统计口径汇总。
- 逐场真实事实和赛季/职业聚合不能混为同类源事实。原生游戏提供的总计优先明确其真实口径；自主可证计算的聚合标明公式、输入范围和精度，不能以不可证数据推算一场未实际取得的 Box。
- 对命名相同但粒度或分母不同的统计（如 totals、per-game、per-36、percentage、advanced metric），最终字段字典必须分别说明口径与时间/比赛类别；不默认所有页面、历史赛季都可取得同样完整度。

### Q21=A · 部分采集时当前档案的正确性

- 成功采集某玩家部分字段时，允许更新**这些新观察到的当前字段**；其余字段使用同一存档同一实体的**最后一次有效观察值**来生成当前读视图，并标注独立的 `last_observed_at`、对应游戏内时点、字段新鲜度/来源和是否本批次观测到。
- **不能假称旧值是这次采集的新观测值**。当前读视图和实际历史观察事实分开；不能以当前缓存替代真实历史或为未观测字段创造虚假的本批次历史记录。
- 从未观测字段显示 `UNKNOWN`；已确证该群体/界面不适用的字段应能区别 `NOT_APPLICABLE`；解码/校验失败的字段也不能直接变为零。
- 角色访问控制同样适用于部分采集、历史查询和字段级导出。

### Q22=A · 冲突隔离，不自动改旧历史

- 若同一独立存档内同一历史事实（比赛结果/Box、已完成赛季、奖项等）后来出现不同值，**最早已确认并写入的历史保持原样**，不得由本次采集自动 UPDATE、DELETE、覆盖插入、变更该记录来源/校验值，也不得静默替换“权威真相”。

## 16. 第十三轮 Q43–Q45：财务、交易、选秀与自定义模拟机制的业务边界

> Human 单项决策 **Q43=A、Q44=A、Q45=A**，并明确后续覆盖性补充：**球员和员工的交易、签约、选秀完全由自定义 GM、教练、球员模拟机制按自定的仿 NBA 规则进行，不使用原版 NBA2K22 的交易/签约/选秀决策引擎；最终生效动作将通过修改原版游戏中的球队归属、合同等字段完成。自定义选秀权交易采用无复杂保护/互换的直接所有权转移。**此补充优先约束三个A选项的原有较宽解释。以上只确定系统边界和成品数据需求，**并未授权第一大任务开发或实际执行对游戏的写入**，也不代表所有相关原生字段已验证可写。完整 A 尚未最终确认。

### 统一的三层数据来源和职责（跨 RES-M、RES-P、RES-T、RES-C）

1. **外部自定义模拟事实**：由未来 GM/教练/球员机制根据经 Human 授权的自定义规则做业务决策；例如某球队与另一球队达成球员交易、签约、解约，或在选秀中选择某人。需要可追溯的已确认决策/成交事实、参与者、资产、约定条款和业务发生时点，**由真实发生的外部机制提供**，不得由本采集系统从两次存档状态差分中假造。
2. **游戏执行/同步状态**：其他独立且获授权的执行机制负责将外部决定所需的球队归属、合同等字段应用至游戏，并确认是否真正生效；技术可写性、失败恢复与执行权限由对应后续开发核证。外部决定成功并不意味着游戏已执行成功，也不能把待同步状态记成成功同步。
3. **第一大任务底层数据库**：原生读取、保存真实游戏文字与数值、当前视图和不可变采集观察历史；并为未来真实的自定义决策账本、人员/球队/资产身份、游戏执行确认、状态核对预留**可关联的底层数据契约**。第一大任务**不负责交易规则引擎、谈判、合法性裁决、选秀决策、游戏写入、自动同步或新高级产品**。

以上各项均按独立游戏存档隔离。外部真实成交事实的不可变记录与游戏观测事实分别保留来源、时点及可验证关系；对游戏原生未保存的“成交缘由/完整条款”不能凭现态推断。如以后发生执行失败或读数不一致，应能表达业务决定与游戏状态尚未一致，而非更改以前已确认的历史。

### Q43=A（限缩）· 财务原生状态与自定义规则必须分开

- `RES-M-FINANCE-OBSERVATION`：逐项保存目标游戏实际可读取的球队总工资、薪资空间、工资帽/奢侈税、预算、球队财务和与之对应的原版 MyLEAGUE 设置，保留单位、游戏原始/显示值、球队及赛季、游戏时点和采集新鲜度；部分来源不存在按 Q10 明确登记。
- 原版游戏的工资帽、薪资配平和 CBA 限制等作为**真实游戏状态/设置来源**，不自动上升为外部自定义 GM 的交易合法性与薪资规则。具体自定义规则另由 Human 在对应模拟机制任务中裁决；此轮**没有确定自定义工资帽、奢侈税或合同限制的具体数值和算法**。

- 当游戏原生数值与自定义模拟账面规则不同，保留**来源/口径差异**，不得将一方静默覆写另一方；若仅原生可读，仅记录可证实的原生状态。

### Q44=A（限缩）· 交易、签约与市场状态：自定义决定为业务来源

- `RES-M-CUSTOM-TRANSACTION-FACT`：可关联未来由外部机制实际生成、确认的球员及员工交易、签约、解约、续约、转队等事实，包括涉及的球员/员工、参与球队、合同及选秀资产、真实约定条款与可证时间；**没有外部真实决策记录时不得仅凭采集差分制造过去的成交**。
- `RES-M-MARKET-OBSERVATION`：游戏原生自由球员、合同与球队归属等可见状态是独立观察数据；自定义机制的挂牌、报价、谈判、结果如确有外部真实记录可以保存但不是原生读取值。**市场状态与已发生交易/签约事实分开**。
- `RES-M-EXECUTION-RECONCILIATION`（逻辑数据责任，非确定物理表）：需要在基础数据关联层区分外部已达成事实、是否计划/尝试执行至原版游戏、实际游戏读取验证及不一致/未验证状态。业务决策、执行回执与游戏观测各自保留来源。此轮不固定具体状态机、表名或自动重试实现。
- 各类真实事件均只追加，不能用市场最新挂牌/合同变化回写已经确认的历史；旧游戏历史依 Q22–Q24 处理。
