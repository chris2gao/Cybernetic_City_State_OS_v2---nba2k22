## 1. 第一任务最终必须交付的真实东西

面向 NBA2K22 PC 离线 MyLEAGUE，成品应是一套能长期保留各独立存档的**真实文字和数值**、带可追溯原生来源的数据库；用户能按对象、赛季和状态查询、联合统计、筛选与导出，数值与目标游戏 UI 尽可能一致。单存档最长100年历史需求；正常采集保留重要状态的时间记录。无需图片/图表，不提供普通 GM 的隐藏 Potential，不在此任务开发 AI 人格或游戏写入。

| Result ID | 交付对象 | 完整数据与查询要求 |
|---|---|---|
| RES-P | 球员对象 | Player Card、全部可见能力、倾向、徽章、PlayTypes、Vitals、合同、伤病、训练、逐场/赛季/生涯统计，所属球队与历史身份 |
| RES-T | 球队对象 | 名单/轮换、球队统计/战绩、员工、合同/财务、球队历史与赛季 |

## 2. 这个任务结束前必须提交的细致工程成品

- **原生资产完整总账**：已拿到的每个对象和字段、类型、来源/Getter/Offset/Decoder、真实读出及当前成熟度；未知不冒充已验证。
- **UI → 来源 → 数据库矩阵**：按目标 PC22 游戏真实页面、Tab 和文字数值列逐行建立双向可追溯对应，标明单位/显示处理和来源缺口。
- **最终数据库物理方案**：**全部表的确切数量、表名、每张表所有字段、字段含义、数据类型/允许空值/单位、主外键/索引、实体关系、静态动态与历史、采集策略、设计理由和 SQL DDL**。
- **可复验使用结果**：完整球员/球队/比赛/赛季/设置导出、跨对象关联、条件筛选与确定性统计，逐列对照实际游戏。
- **历史与质量验证**：单档100年容量与隔离方案、正常采集的状态历史、无真实来源不制造历史、源/库/UI一致性测试与可追踪证据。

**已知工程基线**：旧 `database/schema.sql` 静态定义27张表/415列；`memory_field_profile.json` 登记 PLAYER72、STAFF13、TEAM_STATS27、PLAYER_STATS34个字段；`AG_NATIVE_01D/ui_native_source_matrix.json` 研究了6组 UI 来源；R07中40族/694研究项不等于已验证字段。旧表不限制最终设计。以上是来源盘点，不是完成验收。
