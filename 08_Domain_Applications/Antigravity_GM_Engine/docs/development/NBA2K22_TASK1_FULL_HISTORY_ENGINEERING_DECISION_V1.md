# NBA2K22 第一大任务 · 全字段历史开发复杂度与采集频率裁决 V1

状态：阶段01b的设计方向裁决，尚未冻结物理DDL或获独立生产验收。
来源：Human Q14=A、Q15=B及其采集频率补充，并委托模型判定激进/谨慎方案；此前合成测试脚本 `sqlite_history_benchmark.py` 与 SQLite 原理。

## 1. 结论
**接受激进历史需求：全部确认可读取、允许保留的可变字段都具有正常采集时点的可回看历史。** 采集预计每赛季常见20多次，实际最多40次。若真实压测不达标则记录事实并重新进行Human范围裁决；不自动回退Q11–Q13的谨慎字段名单。

## 2. 不能把数据的数量换算成同样数量的历史表
历史是对象随时间变化的多个观察值，不是“一个字段对应一张表”。候选结构共享采集身份、按对象或字段组版本化，历史字段不必各有单独更新函数。

概念上的最小关系：
- `capture`：存档内采集身份、游戏内日期、赛季、实际采集时间、结果状态与来源。
- `entity_current`：每对象/字段组当前值（也可由历史最近有效版本导出，是否物化待选）。
- `entity_group_observation`：同一对象一组属性在某采集批次的完整观察状态，或只保留变更的有效版本；以源映射记录字段含义。
- 比赛、合同、交易、选秀等**发生型事实**独立按本身事件/比赛/赛季身份存储并链接采集来源，不强制同表。
这些只是**逻辑候选**，不是要按上述名字创建三张通用生产表。

### 同步/关联要求
一次有效采集按存档批次原子提交；重试不可产生重复历史；相同采集ID但不一致的数据要拒绝静默覆写。历史查询必须在指定存档与采集时间选择唯一合理的最后观察值，不能将缺失值当作零，不能以名字代替真实实体身份，不能将未来观察值放回过去。游戏内日期与实际观察时间均保留，明确只观察到的事实，不补造采集间修改事件。

## 3. 资源估算（旧合成实验参数）
500 位活跃玩家、200 个整数属性；100 个赛季（假定对象规模恒定）。此前本项目合成 SQLite 测试数据：
| 每赛季采集 | 分组完整快照 | 每值均记录的长表 | 假定5%字段变化的增量长表 |
|---|---:|---:|---:|
| 20 | 0.45 GiB | 4.77 GiB | 0.25 GiB |
| 25 | 0.57 GiB | 5.96 GiB | 0.31 GiB |
| 40 | 0.91 GiB | 9.53 GiB | 0.50 GiB |

**这些不是NBA2K22全库或普通个人电脑上的真实结果**：100年累计选秀与退役、教练/战术、真实数值/文本、全比赛日志、索引、并行独立存档、备份、事务日志均未计入。全量重新复制每次采集的所有事实会增加不必要的容量，因此事实表和状态观察模型应区分。

## 4. 开发复杂度比较
| 策略 | 开发工作量倾向 | 风险 |
|---|---|---|
| 每字段单独历史表/更新逻辑 | 很高，不推荐 | Schema爆炸、重复维护/迁移、长时间稳定性差 |
| 按领域分组完整状态快照 | 中等，优先建立正确性原型 | 额外存储、重复值与宽字段组版本管理 |
| 全字段长表仅记录变化 + 定期重建 | 较高，需实测后再决定 | 批次间状态重放、索引/查询复杂、类型/关系约束 |
| 按组快照 + 数据变化去重混合 | 中等至较高，备选 | 多一层版本索引及一致性校验；需要维护查询接口 |

**首个实现候选优先“分组完整观察快照”**，以较少状态写路径降低开发成本；只有真实容量/查询测试证明值得才加 Delta 优化。不应为了节省少量磁盘先发明复杂全字段增量回放框架。

## 5. 独立极小合成 smoke test
在当前临时环境、SQLite3.46.1 用3张逻辑原型表和JSON字段组模拟2个严格独立存档、3个已提交观察状态；已通过下述局部条件：
- 指定批次按时间读取与当前状态一致；
- 存档A和B共用相同玩家符号ID，历史仍不串档；
- 重放相同批次不增加历史；
- 相同批次的冲突值被拒绝；
- 无效采集批次被复合外键拒绝。
这证明候选读写语义可表达，不证明在真实NBA2K22数据源、全量字段、100年规模、真实用户硬件下通过性能测试。演示脚本在本次对话生成，不是正式项目代码。

## 6. 后续验证
1. 使用原生字段/真实安全样本划分数据家族和属性组，逐字段保留出处、类型、角色可见性、当前/观察历史语义。
2. 测量一次20–40次/赛季模式下的采集耗时、数据库增量、历史回看性能与失败重试；比较“仅当前值”“分组快照”“优化Delta”同负载结果。
3. 对100赛季和多个独立存档场景外推/压测，记录备份、WAL文件、索引与增长率，不擅自设定Human未提出的硬资源阈值。
4. 如果资源不接受，提交具体证据、替代路径、被影响的成功判据给Human做例外裁决；不能在代码里静默丢弃某些历史字段。
