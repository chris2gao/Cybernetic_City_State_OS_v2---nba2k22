## Human 对下一阶段总目标的补充（2026-10-26）

Human 明确本轮需求不只是继续取证：**先对既有二十余轮/现有 v25 真实能力做重复开发排除；多场景查漏补全可读来源；在需求阶段分类只读事实、基本一次性配置和可经常修改的状态；随后建立统一采集与经授权写入的底层框架，支持按字段合法值域、Native 对象约束、前置条件、写后读回、失败恢复进行自动化批处理。**

这是 Human 已明确提出的产品目标，**但并未裁决“下一次单一 Codex 任务应同时实现全部功能”，也不是实时游戏写入授权。**

建议先用一套 01/01b 需求及原型成果统摄项目，再分有界工程交付：
1. **A：全生命周期 Native 来源覆盖与增量观察闭环**：以 v25 20 族 Reader 与现有槽位/历史工程为输入，先盘点实证，真正缺什么补什么；验证 S2–S8 及 S7 子窗口。
2. **B：字段读写能力、变更权威、频率和操作依赖契约**：只读终局比赛/荣誉；低频全局/世界线设置；频繁变化且可能同时被原生引擎和经批准外挂操作影响的球员/教练/球队状态。字段级说明是否可写、游戏何时自动变化、合法范围来源、依赖、敏感级别、是否需要跨字段/跨对象操作；“可写”绝不等于无条件任意改。
3. **C：统一 Native I/O/CRUD 与有界批量执行框架**：重用已实现的 SQLite/采集/审计/恢复，不造平行数据库；确定性定位、版本与旧值前置校验、权限白名单、计划/预检、分批执行、写后读回、幂等、冲突、失败/恢复与审计。计划、抽象接口和离线测试不授权现实游戏写入。
4. **D：受控实机写入及端到端大批量验收**：另获 Human 对测试档、字段族、影响范围和现场操作的明确授权才可执行；验证保存/重载、Native 反写/自然成长、关联副作用、批次失败和性能。不可承诺零风险或凭模拟断言全量成功。

**细节界限**：
- Human 所说“设置成熟后只设置一次”是**低频写入期望**；关键世界线/配置在新开档、真正写后和依赖模拟前仍须低成本读回核对。不能把“不再反复调参”误写成“永远不做防漂移验证”。
- 比赛与自然成长仍由 Native 引擎权威产生；普通角色不能修改原生终局统计；仅有明确授权的字段和状态转移才进入写操作许可清单。
- 用户预期批量数千/数万字段可靠执行，是工程目标，要求失败可报告、可定位、可恢复、可证明，而不允许文字保证绝对零错误。
- 旧研究文档可能有 RETRACTED 或候选身份，不能因含“可写”二字就升格为当前已证写入能力。
- 独立审核和 master 发布门禁保持；PR #8 的业务契约仍待正式主线整合。

## Q3 — 统一字段能力契约与可扩展缺口：Human 已批准 A

**Human 原裁决（2026-10-26）**：「批准，并且如果我们的字段有模糊的，这个并不影响我们的任务，这些模糊字段，后续可做独立的扩展开发，慢慢补全。」

**已批准的业务结果**：建设统一字段级能力契约，作为后续统一采集、查询、经单独授权的操作和批量执行的权威输入；按现有 v25 Schema/Reader/Native 来源证据优先填充，避免重做已验证研究。字段分类至少分别说明：

1. **来源/读取成熟度**：来源已验证、原生字节可读但含义不完整、暂未读到、尚未验证等；不能以非 NULL 代替语义证明。
2. **操作权限**：只读 / 有条件可修改 / 待证 / 禁止向普通角色提供；“潜在可写”或“UI 可编辑”不等于已授权执行 Native 写入。
3. **变化时机与生产权威**：冻结比赛/奖项事实、低频世界线/游戏设置、原生自然变化和允许外部操作的高频球员/球队/职员状态、需要跨对象联动的复合操作。
4. **值域/表示/证据**：原值、显示值、必要转换/计算值、单位、上下界、枚举、NULL/特殊值、版本及其证明等级。
5. **对象身份/依赖及验证等级**：存档、Native 对象、场景/赛季、联动影响、预读/写后读回、保存重载、失败与恢复要求。
6. **访问边界**：owner/普通角色/隐藏或敏感字段的读取、导出、修改权限分别受控。

**新增 Human 批准的不阻断规则**：
- 对不影响当前可靠功能的模糊字段，记录具体 UNKNOWN/缺口、来源和证据等级、影响、未来触发条件及独立扩展开发入口；不为少量难懂 Native 字节或 UI 对应问题无限延长主体工程。
- 后续可以为模糊字段另立小任务，逐次补上原生定位、含义、合法范围、可读性、可写性或 UI 验证；扩展须保持既有字段/历史/接口兼容并记录版本。
- 不阻断意味着主体覆盖与工程验收可按**已证明的有效范围**推进，绝不意味着模糊字段自动通过、全字段已完整验收，或允许将未知值/身份/写入效果猜成确定事实。
- **安全阻断仍存在**：若某字段本次要真实写入，却无法证明对象身份、目标地址/合法取值或关键联动，只有该操作不可执行；不能以此阻断其他已经证实安全的字段族与只读场景。涉及隐私、跨档混淆、历史破坏或其他全局不变量的风险按 OS 门禁处理，不由“模糊字段不阻断”豁免。
- 需求的“全量获取”应以目标游戏真实存在且有证据的来源及可达窗口逐项覆盖/缺口闭环为准；未知项须计入覆盖矩阵，不可声称已取得其真实数值。

**本决策尚未授权**：实际游戏写入、自动大批量执行、跳过独立审核、将候选语义提升为已实证。任务 A/B/C/D 分包仍是建议，尚待 Human 决定明确的工程包和验收边界。

## Human 追加澄清 — 多场景原型目的与真实游戏运行语义（2026-10-26）

Human 明确纠正上一轮 Q4 的重点：

1. **研发取证阶段的主要交付是可复用的数据源/容器结构，不是某个球员的实际历史经历。** 例如常规赛场景识别常规赛结构，季后赛识别季后赛结构，休赛期识别自由球员池、员工市场和其他短时对象池的 Native 结构、字段、身份、可读时点及关系。先排查已有 v25 Reader/槽位证据，避免重复开发。
2. **正式运行阶段才由 Human 在适当游戏窗口触发统一采集。** 系统使用已建好并验收的适配器/容器结构读取**该窗口此刻的真实内容**，进行准确填充、查询和历史追加。研发时取得少量或有界验证样本属于验证结构和端到端正确性，不以特定球队/球员在原型中取到的值定义产品能力。
3. **时间连续性不是并存的当前状态**：球员常规赛在原球队、休赛期成为自由球员、之后在新球队，属于依次发生的实际状态迁移。每个观察时点的“当前”查询只表示该时点有证据的有效状态；历史数据库可以按不同时间保留三次观察而绝不能把三条历史同时宣称为同一时刻的三个当前归属。
4. **未来签约动作在外部决策层和经验证底层执行层分开**：Human 未来启动独立 GM 自由市场决策；决定签约后，才通过另行开发、验证与获准的合同注入、所属队伍修改以及必要联动完成游戏状态变化。这不是本轮原型自动模拟出来的人员转会，也不因为旧读取源已经存在就获得游戏写入权限。
5. **历史人物身份与来源歧义仍需保守处理，但不是本轮 Q4 的主要讨论主题。** 已证实的身份可以按时点关联；未知复用槽位、历史共享对象可留独立原始事实和缺口，后续小任务解决。不能因一个模糊身份阻断容器级来源覆盖，也不能在查询或写入中强行合并。

**据此修正任务成果层次**：
- **阶段取证/原型层**：游戏窗口 → Native 对象/池/字段来源 → 容器结构与阶段生命周期 → 至少必要样本证明与错误边界 → 可复用 Reader/Codec/映射/填充路径 → 证据成熟度/缺口。
- **正式采集层**：Human 主动触发 → 识别当次真实存档与场景 → 用已证 Reader 读当前池子 → typed 数据库观察/增量与回看 → 供后续独立模型查询。
- **独立的未来修改层**：字段操作合同 → 授权的 GM/Coach/Player 决策提出变更 → 底层校验、批量安全写入、原生读回、保存重载和审计。当前规划/原型不授权实际写入。

## Q4 — 场景容器原型验收强度：Human 已批准 B

**Human 原裁决（2026-10-26）**：「下一任务需求共识建模 Q4：我选择 B。无额外补充。请结合我的意见记录正式裁决，并继续下一项需要讨论的问题。」

**正式选择：B — 结构映射 + 真实游戏场景中的端到端填充验证。**

每一目标数据容器的原型完成证据，至少应覆盖：
1. 对照 v25 已存在的 Native Reader、来源研究和已采数据，标明已有可复用能力；已充分实证的部分不为满足形式重新开发。
2. 在适用游戏窗口确认池/表/对象来源、Native 结构、对象枚举和稳定或待证身份、已支持字段的原值/转换、关系及可用时机。
3. 至少一次有界实际采集证明：Reader/Codec 能读取该容器的当时实际对象与已支持字段，通过合法值/约束校验、typed 入库、查询与必要的增量/失效语义；保存可复验样本、来源时点、哈希及 Native 读取成本。已有等价的可靠实机证据可以纳入验收对照，不强制制造重复场景。
4. 碰到部分字段名称、值域、复杂身份、UI 对应等未能证实的情况，按 Q3 保留来源/UNKNOWN/影响和扩展入口，不要求为了一个模糊字段卡住整组容器；未知字段不得被标为已经完整验证或安全可写。
5. 本轮原型验证的是可重复使用的**结构与正确填充能力**，不是要求累积某个人物全部职业经历、多个年份全部真实值或每阶段反复全量扫描。
6. 可读取和安全可写是不同证据级别：**Q4=B 不是任何实机游戏写入授权**。未来写入能力仍须单独建立字段权限、合法操作前置条件、关联约束、写后读回及保存/重载实证。

**完成判定的准确表述**：对该容器/当前获准字段子集，可接受为「真实场景中已验证端到端填充」；未知字段或暂不可访问的场景持续处于明确缺口/独立扩展状态。不得将「容器可用」夸大为「全部字段、全部阶段、全部游戏状态均完整支持」。

## 下一讨论问题：Q5 — 场景证据、覆盖矩阵与例外的标准交付（待 Human 裁决）

Q2 已经决定**Human 是否推进场景**；Q4 已经决定**单个容器原型验证强度**。Q5 只决定：每完成一个 S1–S8 场景（特别是 S7 子窗口）是否要求交付一份**统一的、机器可比对的覆盖与缺口证据包**，使后续工程可自动计算已覆盖、已验证、仍缺的容器和字段，并按事实决定是否需要补采/小型扩展。

候选：
- **A：轻量总结**：场景结束由 Codex 出简要文字报告、关键日志和未解项；减少文档成本，但以后难以跨场景自动汇总覆盖率或消除重复开发。
- **B：标准场景交付包（推荐）**：有结构化 manifest 标注存档/场景/游戏时点、已见容器、Native 来源、字段能力覆盖、Reader/采集单元/查询与入库校验、原始证据哈希/限制、未完成项目及严重度、验证等级，并标记可复用或需后续小任务的项目；自动生成机器汇总，不要求 Human 人工填写上千列。**可读 UNKNOWN 和已登记的非关键缺口不阻断整个场景，Human 仍决定何时推进游戏。** 真实容器缺失、没有读到关键对象、权限不明等不可假称完成。
- **C：每场景完整手工验收**：逐字段人工确认游戏 UI/Native/数据库一致后才出正式报告；最严格但容易重复现有研究并阻碍整体工程。
