# NBA2K22 第一大任务 · 原型驱动的02/03连续开发计划 V0.3（待Human审批）

**状态：DRAFT_NOT_APPROVED**。Human已否决V0.1，对V0.2的“分R1–R5顺序验收”提出根本性纠正：实际工程应**先设计全域数据库原型、实现、探索新原生数据、持续反向修订原型，形成完整开发候选后集中测试/独立审核，再按OS预算修复**。本稿只修订开发组织，不改变已获Human批准的01b结果A，也不自动授予本地DCR、真实游戏读写、生产迁移或master合并。

## 一、开发目标与原型地位

要真正交付完整可运行的 NBA2K22 离线 MyLEAGUE 数据库，不是无限继续定义边界和审核任务。第一轮就形成**全域原型设计和可执行数据库骨架**；原型被真实开发和逆向证据持续修订，原型的表名/数量/字段/外键/分库可以变化。每次修改保留原因与来源，不能因一开始规划了多少表就排斥新证据。

永久目标：**完整表总数、逐表责任及设计理由、所有字段/类型/游戏意义/合法值域/单位、原生来源、关系与PK/FK/索引、历史/身份/权限、全部可执行SQL DDL、采集/查询工程、真实来源验证和有界UNKNOWN报告**。不同游戏存档彼此独立、没有跨档分叉/继承/合并；游戏历史只追加真实事件与观察，不补造未读数据。游戏写入、外部GM交易规则、世界线最优设置均不在本数据库开发目标内。

## 二、一项连贯工程目标，原型与来源并行生长

**工作流不是五次独立验收门，而是一个连续的工程闭环**：

`仓库已有研究/旧库/攻略 → 完整候选ER+表清单+字段字典 → 可执行SQLite原型 → 读游戏/Native探索与工程实现 → 发现缺项/关系错误 → 直接修订Schema/Decoder/代码 → 再次用真实数据填实 → 完整开发候选 → 集中受控验证/独立审核 → 定点修复 → Human工程验收`

1. **原型首先产出（Codex）**：全面读取已有旧27表的完整定义、已注册146工程字段与39个研究入口、PlayerCard/Team/Coach/League/Box/选秀/历史/设置各类UI研究、原始Reader/Codec、已有游戏机制攻略。一次性建立覆盖已批九类RES的**具体候选表目录**：候选总表数、每张表一行表示什么、字段清单与类型/含义、已知合法范围与未知点、PK/FK、关联基数、分表原因和旧表去向；首批可执行SQLite DDL、fixture和示例JOIN。证据不足的字段标PROVISIONAL/UNKNOWN，**不能编造原生取值**。
2. **原型驱动的开发持续进行（Codex主Owner）**：实现源采集→Decoder→身份映射→字段校验→单元入库→当前与历史→基础查询/导出。按GAME/Box/Season与球员等已证对象首先贯通真实纵向闭环，但持续按数据库总表清单填实全部业务领域；编码过程中发现新字段、新表关系或原型错误，可在任务包批准的语义和allowed paths内**直接改原型与实现，不回到Human等待每一次小调整**。
3. **缺失来源实际逆向（Gemini/Antigravity）**：根据原型字段缺口及仓库研究，领取有界字段族/原生结构/界面验证子任务，在批准的环境内探索读取、Getter/偏移、bit/enum、游戏展示、正反例、历史读取窗口；交付可复播原始样本、Reader/Codec候选、异常与UNKNOWN。**Codex负责核证并合入Schema和实现**；Gemini不担任全局数据库Owner或正式独立审核。可在Codex编码时并行执行，无须等待全局架构先获一次独立审核。
4. **真实发现持续回灌**：字段在“需求目标 → 研究线索 → 原生验证 → 物理表列 → 读取器/测试”矩阵中升级证据；需要新增表、拆表、调整键、数据源、索引时，Codex在已获批准的范围内落地并记录设计差异。**不会把第一版原型当不可变标准**。源缺失则保持UNKNOWN且继续已证部分开发，不以假值补缺或悄悄削减Q10必需字段。

本任务强调同一目标的连续开发窗口和必要的有限子任务，不要求每编写一个文件、每得到一项实验字段或每修一次Schema都重建一个窗口/任务包。OS已有`WORLD-DATA-ARCH-01`、`NATIVE-ACCEPT-01`、`WORLD-DATA-SCHEMA-01`、`WORLD-DATA-PROTOTYPE-01`及后续INGEST/PUBLISH/QUERY依赖应作为**已有任务治理与成果定位**，而非技术上一条“必须先全部验收Native才能开始Schema原型”的串行锁。正式派单时要核对真实OS依赖，必要时提出有证的任务包/依赖调整草案交Human按适用权限批准，**不可私自绕过已有OS门禁或扩大allowed paths**。

## 三、避免过度测试与审核的真实OS要求

已核对当前master的`01_os/开发入口与单窗口任务规范_v1.md`（§2、§8–11）和`AGENT_WORKING_DISCIPLINE.md`。区分如下：

- **开发中**：Codex/Gemini可在有界范围反复运行少量直接相关单元/SQL smoke tests、检查新Reader真实值与表关联，错误直接修；这些是研发反馈而不是每轮正式独立审核。一次施工内部确定性验证可不断收敛，不规定人为固定轮数上限。
- **形成完整候选后**：按任务包必需的verification_plan进行一次集中、受控的正/负例与范围检查，保留退出码、差异和可回放证据；之后由**独立于执行窗口的审核窗口**复核，不由开发者自行宣布最终PASS。
- **交付后**：针对独立审核发现的 blocking findings，OS §11最多**两轮有新证据/新补救措施的定点修正**。第二轮后仍阻塞则冻结证据，拆根因新任务并由Human决定，不自行开启第三轮。
- 不因为进入新领域/新表就常规要求Human再次审批；只有超出任务目标、需要新产品语义、受保护操作、真实游戏本地执行、master合并等情况才提出确认。必要的轻量自动检查与最终一次独立审核保留，不把它们扩张为不停的“前置验收关卡”。

**测试强度要匹配声明**：最小切片PASS只能证明该切片；最终全库PASS必须同时覆盖全部获批领域、字段、跨档隔离、历史不可变、权限、错误恢复与查询。对未证目标字段如实登记缺口并按Q10要求交Human处理。

## 五、向Human报告的节奏

- **计划审批（目前）**：只决定是否授权上述开发组织与正式OS任务包准备，不隐含DCR/游戏实机/写入/master权限；当前仍是讨论稿。
- **开发期间**：有实质成果时简要报告**现有表数、增加/拆分表及字段缘由、已实现的SQL读写/查询、原生来源证据与UNKNOWN**，不每批请求Human选择。若在授权内且无新负载关键选择，Codex持续开发而非等待。
- **出现真正重大分歧时**：例如多库跨事务架构、实体身份无法建立、游戏目标字段经充分探索始终无源、需要Q10例外、触及真实进程/存档或准备master/生产迁移，才请Human一次解决1–3个问题；问题必须给出实际证据、代价和推荐方案。
- **完整候选形成后**：集中受控验证、**一次独立审核**；需要时在OS §11两轮交付后修正预算内解决blocking问题，再由Human最终验收。无额外按领域/按阶段Human签字流水线。

## 六、第一批完成什么才算实际进度

**第一份 Codex 交付不能只是新规划**：需有全域候选表目录及具体表卡、真实可执行初始SQLite DDL/样本、旧27表去向、已知字段到列映射、可直接指向Gemini的逆向缺口清单。后续持续提交有源数据的Reader/Codec/表和查询，改原型时记录版本/原因。最终必须有全部领域逐表完整字段和值域/来源、完整DDL、真实来源实现、测试证据和未解决缺口。

**硬边界**：不设计跨存档fork/继承/合并，不伪造隐藏潜力或不可读历史，不执行未授权游戏写入，不擅自改历史/生产库或强推master。世界线最优参数由后续机制独立决定。
