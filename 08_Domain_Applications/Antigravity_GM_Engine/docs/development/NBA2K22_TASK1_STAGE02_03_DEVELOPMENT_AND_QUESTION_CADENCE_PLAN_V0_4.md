## 1. 明确四方职责：总体架构共同设计 vs 单一工程Owner

| 参与者 | 明确责任 | 关键边界 |
|---|---|---|
| **本GPT规划模型** | **首版全域数据库架构提案的设计主持人**：梳理已批准A、仓库旧27表与来源证据，提出具体全域候选表清单、初始字段/实体ER、存储方案备选、重要决策备忘录，组织Human逐题/逐议题裁决，交出已决架构规范 | 是方案设计与Human讨论的主持方，不是多个工程owner之一；不得把自己的提案冒充已由Human批准 |
| **Human** | **首轮模型核心选择的决策者**：长期存档组织、实体和历史模型、重要表结构与关联、影响未来扩展/权限的不可逆语义；审阅具体表与关系举例及方案代价后裁决 | 已定的存档完全隔离、没有分叉/继承/合并、数据完整性和范围，不重复询问 |
| **Codex** | **工程任务的唯一实现Owner**（适用OS的`WORLD-DATA-ARCH-01`及正式后续任务）：评估设计可行性并指出冲突；将已达成共识的架构落实为真实SQLite原型、DDL/字段字典/迁移、Reader/Codec/查询骨架和测试；在授权边界内连续修订 | 技术可逆细节有裁量权，但不能未经Human决定就改写核心存储语义、删减已批准的目标字段或擅自宣告成熟 |
| **Gemini/Antigravity** | 针对有界未知的独立来源探索：真实UI字段/Native对象/offset/编码/Getter/字段合法值域、正反例样本；探索产物作为Codex设计/实现输入 | 不承担全局数据架构最终决策或生产独立审核 |

**Owner一致性**：项目`MULTI_MODEL_TASK_OWNERSHIP_AND_VERIFICATION_V1.md`规定**一项工程任务只有一个Owner**。架构提案与Human讨论是Codex实现前的**规划/产品裁决工作**，并非把同一个Codex工程任务再同时指派GPT执行。真实编码和可运行原型交付的唯一工程Owner仍为Codex；Gemini子包各有其自身清晰owner。涉及不同OS task ID的Owner依各自任务包记录，不据此偷偷合并。

## 2. 初始设计追问：与01b不同的“架构决策轮”

最初的共同设计不以抽象规范代替具体表。由GPT准备**可以直接讨论的候选方案**，每个问题都有真实源码/Native研究或合理工程推断的来源等级、实际表/关系例子、备选、代价、推荐和未知点；先与Human议定根本结构，再由Codex投入大规模实现。

**应优先讨论的架构主题**：

1. **存储文件与存档隔离**：一个独立save一个SQLite事实库，还是统一库用组合键`save_id`隔离；原生字节证据、控制日志是否同库；横跨不同数据库文件的一致性/发布恢复成本。**两种方案均不能存在跨存档fork/继承/合并关系**。
2. **真实身份体系**：save内Player、Team、Staff、Game、Season、DraftAsset的稳定ID、原生ID/Slot复用与历史版身份；有哪些可靠映射证据、尚未证实如何隔离。讨论表PK/FK实例，不靠姓名拼人。
3. **事实与时序物理模型**：球员Attributes/Tendencies/Badges、合同/名单/训练/设置、Game Box、赛季累计与已定稿历史的表粒度；宽表、typed family表、field observation、raw evidence怎样组合；100年×定期采集对容量/查询/值域的影响。
4. **数据源/权限与全域覆盖**：原生原值、游戏显示值、可证转换、外部真实成交事实/游戏写入回执、隐藏Potential权限；是否需要独立原始证据存储；不允许用一张万能JSON表冒充全部实体关系。
5. **旧27表迁移思路**：哪些表可复用，哪些需拆分/重建，如何保留真实历史；“旧库是事实线索”不等于默认的新Schema约束。

Human已确认：**不同游戏存档严格独立、没有存档分叉或继承式分支**；世界线“最佳配置取值”不在当前第一任务。故二者不能作为重复选择题。

**提问规则**：每轮至多1–3个实际影响架构的重要问题；题目只有真实证据、设计方案和比较时才发出，不固定需要多少轮。Human可随时额外补充；答过且未变化的不再问。对影响大量关系的选择先问，纯技术可逆细节不让Human逐列批准。形成有证的首版架构裁决记录和 **Initial Prototype Architecture Brief**，其中每项标`HUMAN_DECIDED`、`DELEGATED_TO_CODEX` 或`OPEN_EVIDENCE`。

## 3. 原型共同设计的实质产物（不是只交提问记录）

进入大量代码开发前，GPT应向Human提交**可核对的首版完整蓝图**：

- **完整候选表目录与明确“候选总数”**：逐张候选表列职责、每行对象粒度、初始全部已知字段、类型/合法值域与证据等级（未证标UNKNOWN）、PK/FK、关系基数、归属业务域、典型JOIN，注明为什么分表；不以旧27表或早期21表直接作为数量上限。
- **跨领域ER与数据流**：Save→Season→Team/Player/Staff→Game/Box/Season totals，Roster/Contract/Coach/Training/League/Honors/外部真实交易，当前/观察历史/最终事实；绝无跨档fork。展示确切关联方案而非泛化方框图。
- **关键取舍ADR/人类裁决清单**：文件组织与事务边界、ID可信度、字段族储存策略、历史与敏感性隔离、旧库迁移。Human已决、Codex自行决、待原生证据分别标识。
- **进入编码的目标与验收口径**：Codex需要具体的表目录/字段定义/SQL实现目标、原始来源清单、UNKNOWN和允许迭代范围；Gemini得到独立、有界的字段来源追踪任务。

**注意**：首版蓝图是`DESIGN_CANDIDATE`，Human批准其根本方向并不冻结所有表数、字段或索引；允许Codex在实际开发和逆向发现后持续合理调整。新发现若影响重大产品语义或已Human决定的原则，才回来继续讨论。未证 Native 字段不能冒充游戏已验证事实。

## 4. 编码和探索：连续开发、不中断于小修小问

在OS真实任务包、现有前置及权限门满足后：
- **Codex**承担 SQLite可运行原型与后续完整开发的**单一工程Owner**；接收Human认可的根本架构、自己选定其余可逆技术细节，直接在`allowed_changed_paths`内不断增加/重构表、Decoder/Reader与测试。
- **Gemini**可针对合同offset833、Badges位编码、Game/StatBank的身份及读数边界、Staff归属、Draft和游戏设置等有界问题并行发现字段，交可重放原始证据与小型Reader。Codex按最小成本核验并吸收成果，不为每个新字段单独启动Human审批。
- **开发期只做必要小测试/SQL smoke/来源正反例**，发现原型不适配实际就修订并记录原因。不能因每一轮补字段、拆表、改FK而安排正式独立审核或要求Human重批。
- **完成一个覆盖全域的开发候选后**再集中运行有界验证、由与执行窗口分离的独立审核会话复核。OS`01_os/开发入口与单窗口任务规范_v1.md` §11 的**交付后最多两轮新证据/新remedy定点修正**独立于开发中可持续的确定性调试；不要混为一谈。
- 每次有实质进度，只报告真正的候选表/列变动及原因、已证游戏源、可运行查询与未解决UNKNOWN。Human只在新的重大架构语义、Q10字段缺口例外、受保护操作及最终工程验收时需要决定。

## 5. 需要保留的OS权限和门禁

本次仅修订规划，未批准本地仓库/原版游戏进程/内存的授权、真实存档写入、最终SQL生产迁移或master合并。已有OS backlog`OS-BASELINE-01`需读取真实最新完成指针；`WORLD-DATA-ARCH-01`、`NATIVE-ACCEPT-01`和`WORLD-DATA-SCHEMA-01`等任务沿用已有ID。若需要跨现有OS任务范围或依赖更改，先形成理由与对应授权；不能通过“一项持续开发任务”的说法绕开既有source分支、路径范围或protected gate。
