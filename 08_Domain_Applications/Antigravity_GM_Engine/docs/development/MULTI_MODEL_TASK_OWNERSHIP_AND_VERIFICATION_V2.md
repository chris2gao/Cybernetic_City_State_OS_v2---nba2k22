# NBA2K22 跨模型协作与原型驱动开发规范 V2

**Human 决策日期：2026-10-24。** 本文件进入 `master` 后作为 **NBA2K22 项目级默认协作规则**；不修改仓库通用OS、其它领域或其它项目。原 [V1 规范](MULTI_MODEL_TASK_OWNERSHIP_AND_VERIFICATION_V1.md)保留为历史记录；V1的单一Owner、证据真实性、有限辅助包、子代理约束和权限底线仍有效，与本V2不一致的未来任务组织方式以V2及Human最新明确指示为准。

**适用**：NBA2K22世界数据系统、GM引擎及今后Coach/Player等经批准的项目工程任务。对每个具体任务，最高优先级仍是**最新Human决定、仓库OS的权限/任务包/受保护发布规则及真实Git状态**；本规范不能授予游戏写入、真实存档修改、master合并或操作系统访问权限。

## 1. 模型职责与时间/上下文预算

| 角色 | 项目级默认职责 | 不默认承担 |
|---|---|---|
| **GPT 规划窗口** | 长程开发路线、需求/结果建模、初始总体架构和原型方向、项目开发任务拆分、Human重大决策追问、重要工程成果对比与下一轮规划 | 日常代码编写、反复本地调试、完整Native逆向、替Codex完成工程实现或自任独立最终审核 |
| **Codex** | **每项工程实现的唯一主Owner**；评估初始设计可行性，持续开发SQLite/Reader/Decoder/查询和其它实际系统，接收探索证据、修复问题并提交完整工程成果 | 将主要工程任务无授权转给辅助模型；把未验证研究声明当Native事实 |
| **Antigravity / Gemini** | **有界辅助**：游戏内存/对象结构探索、UI来源对照、重复性搜集/转换、批量机械处理、小范围Reader/Codec和可复验负例；向Codex提供证据 | 全局复杂架构裁决、替Codex全面实现/集成、最终独立验收、直接接管主任务 |
| **Human** | 决定长期架构/业务语义，批准计划、关键异常/缺口例外和受保护操作，接受最终成果 | 逐字段命名、每个局部SQL修改、开发期常规测试的微审批 |

**节约规划窗口**：GPT优先保存长期全局上下文，不默认用有限上下文/额度进行工程编码。仅当任务特别重要、GPT确有更合适的开发条件时，GPT**先说明价值、范围与理由并请求Human批准**，才临时承担有界实现任务；不得因此自动变成工程主Owner。额度或上下文中断时，保留状态并交接长期决策，不用其他模型私自抢占未完任务。

## 2. 共用本地仓库：Codex 与 Antigravity 必须顺序结对

**当前物理前提**：Codex 和 Antigravity 使用**同一个本地仓库与主要开发/测试环境**，因此不安排两者的开发任务同时执行，哪怕属于同一项目的不同文件。可在**同一个持续工程任务内交替执行多轮**，无需每次局部探索都创建新的全局主任务或请Human再次批准既有范围。

1. **Codex 主开发**：实现表/字段/软件，遇到可分包的Native未知或重复性工作，明确一个有界辅助目标与可验收输出。
2. **交给Antigravity之前**：Codex停止该工作区和相关游戏进程的操作；记录 `head_sha`、`git status`、待处理文件/未提交状态、允许路径、问题、证据与下一owner。正常优先提交并保持干净工作区；不得擅自清理用户/其他任务的更改。
3. **Antigravity 在独占阶段工作**：只处理已交接的范围并提交可复现成果、证据等级、未证事项与最小验证方式；不修改Codex未移交的代码或决定全局Schema。期间Codex不并行读写该共享工作区或操纵相同进程。
4. **交还Codex之后**：Antigravity停止工作；记录实际HEAD/状态/产物和UNKNOWN；Codex接手做**低成本足够的接收核验**并整合，继续主开发；必要时再顺序交出下一个辅助包。

跨模型辅助包仍遵守V1的`producer/consumer`、`input_refs`、`exact_scope`、`artifacts`、`reproduction`、`evidence_level`与`ACCEPTED_FOR_DEFINED_SCOPE`等契约；但**不能把每次小交接都升级为完整项目独立审核**。如将来物理环境不再共享，可由Human另行调整执行策略；当前不默认并行。Antigravity的subagents继续适用V1的可证明型号/默认禁用限制。

## 3. 原型先行，开发中连续修订，而不是无限调研/逐步批准

新系统在完成必要需求分析、信息盘点和Human关键架构决定后，应**先产出具体的全域原型**（表目录、逐表字段及关系、实体/时间/来源语义、可执行软件骨架），再围绕原型做连续实际开发。

- **原型设计**：GPT与Human讨论会影响长期结果的初始架构，Codex负责工程可实施性；可提供已有原生证据支持的候选字段，UNKNOWN不得虚构。原型是**预期实现**，不是最终固定答案。
- **原型实现和迭代**：Codex负责连续编码，Antigravity顺序协作探索。实际游戏/Native发现新字段、值域、主键关系或原型缺陷，Codex在已授权scope内**直接修订原型、DDL、Reader和查询**并记下原因。不得每次补一列/拆一表重新请求Human；只在与已批准重大业务/架构语义冲突时请Human裁决。
- **交付以真实工程为中心**：有实际DDL、完整表列定义与值域/来源、可运行数据库/采集/查询、必要样本和历史/权限保障，才可称工程实现进展；纯调研文档、示例表或合成测试不能冒充已完成的整套系统。
- **历史任务作资料**：早期研究、采集器、原型和攻略可复用；新经Human明确指定的系统开发主线**不以过去未结案任务的阶段顺序作为自动先决条件**。真正适用的OS路径范围、物理安全、受保护发布/运行激活门禁不因此取消。

## 4. 开发期间测试少而准，完成候选之后集中审核

- **研发期**：必要的局部SQL smoke、Reader解码正反例和直接相关的确定性回归，问题当场修；不为每个字段/表/辅助包排一次独立审核，不反复跑无变化的全套测试。
- **候选完成后**：对**完整目标范围**做一次集中验证，证明实际源码/表字段来源、功能、异常、存档隔离、历史、权限和真实游戏读取；交由与执行窗口不同的独立审核窗口做正式审查，最后再由Human决定是否验收/合入。
- **交付后修复**：遵守活动OS对交付后blocking findings的修正预算；开发中的正常迭代不计为“交付后修复轮次”。
- **证据不可夸大**：研究声称、合成fixture、当前实机读数、游戏UI对照、SQL测试、独立审核的证据等级互不替代；未完成项目明确记录缺口，不能为了赶进度虚构事实。

## 5. 开发测试环境及授权边界

Human已经说明**当前NBA2K22游戏数据与游戏进程是专门准备的开发/测试环境**，可用于在适用OS任务边界内探索性开发和Native只读核证。此事实不代表可以不经具体授权覆写游戏存档、改变游戏运行状态、注入进程、读取不在任务范围的本地秘密，或绕过DCR/本地OS安全规则。游戏事实、外部模拟、执行回执必须按项目已决来源和存档隔离约束记录；不同存档不分叉、不合并、无继承式关联。

## 6. 规则生效与变更

- 本文是 **NBA2K22 项目级默认规范**，不写入根`AGENT_WORKING_DISCIPLINE.md`或通用`01_os`机制；根OS对权限、独立审核、发布和证据拥有更高优先级。
- 新任务默认按此分工编制**一个主Owner + 顺序辅助阶段**；Human对某项任务另有明确指示时，按该指示执行并留档。
- 2026-10-21 V1中的具体FINAL-CODEX/AG-01实例描述属于历史事件；本V2对未来新任务的协作方式优先。过去任务代码、既有成果和历史裁决不因此自动改写。
- `master`的本次集成必须按GitHub API传输等效门、真实提交差异、独立审核和Human对受保护发布的确认执行。本文件自进入`master`起作为新NBA2K22开发窗口的加载规则。
