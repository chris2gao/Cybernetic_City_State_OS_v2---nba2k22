# NBA2K22 GM Engine — 跨模型开发任务所有权、验证与子代理规范 V1

**制定日期：2026-10-21。状态：玩家确认的项目级开发协作规范。**
**适用对象：Codex、Antigravity/Gemini Flash、网页GPT开发规划与独立审核、数据分析以及今后的辅助执行模型。**

> **最高原则：一个工程主任务只有一个明确的负责模型（owner）。其它模型只能完成独立、可测试、可追溯的辅助工作包；接收其成果必须核验，但不应因此被迫重做生产者的整个任务。多模型分工只有在验证成本显著低于重新完成成本时才合理。** 此规范不改变 [项目意图与六阶段角色边界](../PROJECT_INTENT_AND_MODEL_DEVELOPMENT_BOUNDARIES.md)，也不构成游戏内存写入、存档推进、DEV28正式代码开发或PR合并授权。

## 1. 单一主任务所有权与中断恢复

1. 每个任务必须指定唯一 `task_id`、`owner_model`、输入版本/分支、允许写入路径、禁止操作、完成定义和人类验收门槛。模型、会话、Goal和worktree不等同，但要在交接中明确关联。
2. **主任务由原负责人完成。** 额度耗尽、上下文压缩、模型暂停或异常中断时，先保留工作区、未跟踪文件、临时脚本和未发布证据；原模型恢复后按断点继续，不默认让另一个模型接管尚未完成的总审计/总开发。
3. 更换主任务owner必须经过玩家明确安排，说明切换原因、确切完成/未完成边界、原产物完整性与新的独立验收责任。**额度恢复前有别的模型可用不是自动移交理由。**
4. 辅助模型不得自行清理、reset、stash、rebase、覆盖主任务worktree，或把其初稿改名/移动为主负责人正式交付。对共享文件与单一分支保持单一写入所有权。
5. `TASK_CLOSED`只表示**该模型自身承诺的工作包已提交或已结束**，不表示另一模型已接受，也不表示原生运行/生产/游戏Save得到认证。

## 2. 合理的模型分工标准

**优先将可交付、可独立验证的底层工作给辅助模型：**

- 只读事实采证：文件列表/路径、版本SHA、SQLite只读schema或行数、注册字段清单、原始字节及来源。
- 可重复的确定性计算：CSV/JSON目录转换、索引和校验和生成、schema一致性测试、离线单元测试、最小故障复现。
- 经玩家**单独明确授权**的局部PC22实机只读验证：限定进程、区域、字节数、样本数及停止条件，记录与游戏UI的独立对照，绝不推定写入权限。
- 独立测试夹具或小型验证脚本：只写指定隔离目录，不修改主工程权威业务源码。

**通常不适合跨模型分派：** 半途接手总审计或总开发、让辅助模型写主模型尚未完成的正式结论、跨数百文件重新归纳、重构主分支与DEV14全链路、无明确验收边界的“一并完善”任务。若辅助产物需要主负责人重新全面审查/重写，说明分工失败，应恢复单模型执行或重新拆分为更小模块。

## 3. 跨模型交付契约：交付不是口头“完成”

每个辅助包开始前，应写明：

| 字段 | 要求 |
|---|---|
| `task_id` / `producer` / `consumer` | 固定生产与验收责任，不自动改变主任务owner |
| `input_refs` | 源分支、commit SHA、文件路径、数据库/存档/批次身份（如涉及） |
| `exact_scope` / `non_goals` | 具体允许检查或开发的内容、排除项与停止条件 |
| `artifacts` | 确切输出路径和格式；按需提供SHA-256及版本 |
| `reproduction` | 可复核命令、离线环境、输入夹具、预期结果/失败结果 |
| `evidence_level` | STATIC / SYNTHETIC_TEST / PRIOR_RECEIPT / CURRENT_SAVE_READ / UI_CROSS_CHECKED 等分别保留，不混用 |
| `known_limits` | 缺失证据、UNKNOWN、未测试情况及禁止冒充认证的范围 |
| `acceptance` | 接收者可执行的最小验收命令、关键断言与需人工判断的事项 |

**推荐交接状态**：`DELIVERED_UNVERIFIED` → `RECEIVER_CHECKED` → `ACCEPTED_FOR_DEFINED_SCOPE`；失败则`REJECTED_OR_REWORK_REQUIRED`。可用`TASK_CLOSED`同时表示生产者会话结束，但不能替代以上证据状态。

## 4. 消费者验证要“便宜、充分、独立”

1. **第一层：身份/完整性**——比较commit、路径、文件hash、JSON schema、数量、有效存档/批次及输出目录；确保无跨分支或跨存档混入。
2. **第二层：边界内行为**——运行小规模可隔离测试或抽样复现；检查主要失败路径、数据守恒、文件写入副作用、权限策略。测试操作只能在事先授权的隔离环境内执行。
3. **第三层：业务与原生事实**——涉及NBA2K22实时内存、真实比赛、Save/Reload、生产采集和交易执行时，按各自许可与实际证据单独核查。合成数据测试和静态Reader解码不能替代原生回读证据。
4. 若发现验证成本接近重新开发成本、交付只有叙述没有源数据、无法复现，**拒绝接入并要求同一生产者补足可复查底层证据**，不让消费者默默完成生产者未完成的工作。
5. 审核者只确认其实际验证的层级；`4 passed`、`40/40`、SHA匹配分别表示测试结果、目录覆盖、文件一致性，均不是天然的运行时/生产能力证明。

## 5. Antigravity / Gemini Flash 子代理（subagents）约束

**默认：禁用自动subagents，优先单一主模型完成一个有界任务。**

- 仅在**能够实际确认**子代理使用的模型与用户指定的主模型为同一具体版本（例如 Gemini Flash 3.8；如不存在强制版本选择，至少必须能证明同等能力且由玩家同意）时，且任务书明确许可，才允许使用subagents。
- 未确认模型标识、供应商自动分配、可能下沉到更弱模型、无法锁定版本等情况，**不得将“主模型是Flash 3.8”视为子代理也是Flash 3.8**；优先通过产品提供的有效配置关闭子代理。
- 若工具无法保证禁用或同型号，标记`SUBAGENT_MODEL_UNVERIFIED`：不把未经复核的子代理结果当作权威，不委派数据真实性、工程安全、权限或验收结论。无法约束而任务又依赖可靠子代理时，应停止该种分派，改成单代理工作包。
- 真正采用subagents的任务须记录实际模型身份确认方式、分包界限、各子代理产生的原始文件和主模型复核情况；子代理不得代替主任务owner承担最终交付责任。
- 此条是**项目要求**，不是关于Antigravity平台目前支持哪些开关或能够验证底层模型的事实保证。

## 6. 额度与任务规模设计

- 默认把机械化静态检查交给确定性脚本或较省额度的合适模型，把有限复杂冲突留给高推理模型。
- 每个任务仅一个可验收闭环，避免“全仓扫描＋大量研究目录＋旧分支＋实机验证＋工程集成＋全报告”一并启动。
- 先缓存已验证输入的索引/manifest，再增量检查；不重复读取已结案的694项研究资料，不重复已通过且无代码变化的离线测试。
- 交付既定结果后结束`TASK_CLOSED`，不把等待用户/下一阶段工作留成后台持续Goal；无需玩家重复授权已有的只读文档核对，但真正游戏动作始终独立审批。

## 8. 执行前的任务模板自检

派单者只需确认：**谁是唯一owner？其他模型究竟交付什么独立可测的物件？消费者用什么最小测试验收？子代理型号是否可保证，否则是否禁用？失败如何返回原owner？哪些真实游戏动作未授权？**

若无法准确回答这些问题，**先收缩任务范围而不是增加模型数量**。
