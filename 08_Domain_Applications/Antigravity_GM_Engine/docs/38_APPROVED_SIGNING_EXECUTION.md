# GM已定案签约的执行源码（待以后签约时验证）

2026-10-17。玩家明确本地只做执行：报价、谈判、择队、合同决策等全部在GM/外挂系统那头完成；到Codex时是确定的球员、目标队和合同。玩家授权先开发签约执行，实机验证留到以后具体签约。本次只写源码和模板，**没有运行/测试/编译签约模块、没有签人或改合同、没有运行本地报价模拟**。

## 输入与职责

`examples/approved_signing_request.json` 包含 save_id、season、action_id/方案版本、球员姓名（face/DOB可由实时核对固定）、目标球队及 `contract.salaries` 整数美元逐年金额、年限、option和明确合同类型。现有外挂/GM输出可由Codex整理成此输入，玩家不需要手填地址或二进制。

本地不判断报价优劣、不生成报价、不重新择队、不把模拟资格当执行批准，也不依赖游戏原生谈判。只核对技术前提：人物/归属/原值/空位/字段编码/名单引用和计数，按本聊天针对具体结果的玩家批准执行。不能用approved=true或模拟器PASS代替批准。不修改能力、策略、比赛或游戏日期，不手工计算/写入球队资金。

## 已写入的执行实现

- `src/approved_signing_executor.py`：确定性合同编码、原值计划、当前人物定位、目标队名单关联、受控写入/回读及逐写回执源码；版本 `approved_signing_v1_unvalidated`。
- `scripts/execute_approved_signing.py`：未来的 plan/execute/verify 入口源码。默认签约布局/写入开关均关闭；执行拒绝发生在打开游戏句柄前。`--inspect-unvalidated` 仅允许未来玩家触发的只读计划，不能启用写入。
- `scripts/plan_approved_signing.py`：纯本地准备入口；没有实时context时只保存GM给定的合同与待核对项，不编造原值或地址。有机器产生的context时可生成候选字节计划，仍不认证实机。

两个源码闸门 `SIGNING_LAYOUT_VALIDATED=False`、`SIGNING_EXECUTION_ENABLED=False` 保持关闭。未来签约任务再确认精确字段和名单布局，完成对应技术验证后按具体批准范围启用；不是要玩家再批准同一经营方案。JSON不能打开闸门。

合同编码复用当前field profile：六个薪资槽各31位、共享高位保留；年限与选项按当前字节读改写，保留未批准位。只编码明确输入的整数金额；拒绝浮点、布尔、负数、溢出、未知选项，指针始终写完整uint64。未使用的六年槽在批准的新合同中设零金额而保留共享标志。没有擅自清除延期/Bird等其他位域。

球队归属为球员当前队`+0x60`与合同归属队`+0xA8`。普通签约为目标队15人常规名单添加该人物、更新`+0xCB1`，核对活动和双向人数；不擅自裁掉其他人腾位。原合同替换续约有单独明确kind，不把“下一年生效延期”当当前合同改写。已经达到目标合同和归属时只读核对，不重复签入；已有尝试标记时必须调查而非重放。

## 尚待未来技术验证的范围

1. 实际待签人物的唯一模型、当前自由球员关联。候选定位源码只支持当前/合同归属为空且不在NBA名单的模型，或明确的本队原合同替换；若自由球员具有非空专用球队/名单指针，必须先定位并实现其关联，当前拒绝猜清指针。
2. 实际签约时六年金额的当前年/目标年口径、年限与选项在界面中的效果，以及名单/人数一致性。
3. 保存、重开后合同和归属是否保留；不通过推进日期或模拟比赛验证。

这不是报价模拟的来源准入或经济资格审查，而是执行对象及内存布局的技术核对。签约代码尚未运行，不能将交易的成功直接扩展为合同写回已验收。现有 `src/gm_core/offseason*` 属独立历史开发，不被本执行模块导入、调用或自动触发。玩家每月主动触发的现有数据更新流程保持原样；签约之后是否采集/上传另按当次要求。
