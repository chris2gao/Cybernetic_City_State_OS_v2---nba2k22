## 1. 玩家已经回答的机制（E09/E10，PLAYER_REPORTED_UI）

- **先类型，再具体战术**：同一条战术可以出现在多个类型分类中。球员槽装载的是类型；类型不匹配便无法装载对应战术。未来类型元数据应允许多类型关系，但同名不自动等于同一原生ID，不能只靠字面名称合并CRC或条目。
- **球员四槽有强优先级差异**：CPU多数情况下使用第1/2类型，3/4偶尔使用。玩家描述3/4一场通常只有几次，是定性经验，不作固定次数、比例或保证。执行效果差时会逐渐寻找其它类型，同时受教练及多个因素影响；不推导严格逐槽顺延、失败阈值或概率公式。
- **手动与自动调用**：玩家可通过按键指定具体战术；CPU对打由游戏AI自动调用。这不证明外挂有“赛前指定某条战术→CPU保证执行”的接口，不新增此执行器。
- **影响因素不止四槽**：球员类型、球队进攻方案、教练体系、进攻/防守策略及偏好选择都有关联。玩家明确要求知道这些设置的用途与关联即可，**不深究精确频率和内部关联算法**。

Q4/Q5/Q6已在所需操作层面回答，不再要求玩家逐条提供菜单截图或固定受益人。具体CRC类型仍属于技术元数据缺口，不转换为新的待答问题。

## 3. 关联到已经整合的项目接口

这里是术语与既有字段的对应审阅，不是新的写入授权；“相关”不等于该字段已证明对每个回合有定量作用。

| 层 | 现有字段/接口 | GM可理解的用途与边界 |
|---|---|---|
| 球员类型优先级 | `playtype.slot1..4` | 填战术类型，不是填四条具体PlayID；前两项主用、后两项备用（玩家定性说明） |
| 具体战术池 | 本队68槽/CRC | 类型元数据有证据后，按类型找可用条目；同名跨类型保留成员关系，不从名字前缀猜native type |
| 球队Freelance四槽 | `coach.FreelanceType`、`Type2/3/4`（字段完整名见registry） | 当前项目已整合的四个有序自由进攻方案槽，与球员四类型不同；不推定自动切换频率，也不凭玩家简称给某个菜单强行定名 |
| 教练体系 | `PreferredSystem`、`ActiveSystem` | 已有八原生体系与角色/空间配置相关，仍不与十个BPTI家族一一对应 |
| 进攻侧重点 | `POEOffense` | 目录有攻框、给射手机会、低位、挡拆、围绕得分手等原生值；可理解为进攻倾向方向，不保证某球员某条战术必执行 |
| 进攻节奏/篮板方向 | `POEOffense2` / `POEOffense3` | 当前目录分别是节奏、进攻篮板/退防选择；**不是“第二/第三得分手”或第二/第三战术优先级** |
| 调用倾向与球员行为 | `RunPlayTendency`、Initiator、具名Tendencies | 可作为相关配置输入；用户与社区说明不产生确切频率/因果系数 |
| 个人/球队防守关系 | 既有PERSONAL18，OVERALL只读 | 防守计划和对手反应会影响进攻环境；不能据此新增整体防守写入 |
| 第一/第二得分选择 | GAMEPLAN原生schema出现`ScoringOption` | 仅说明已知schema有此字段，不认证其菜单映射、完整对象值或受控GM执行能力。不能拿POEOffense2冒充第二得分选择，也不在本轮扩展实现 |
| 人类临场叫战术 | 官方手册按键入口 | 属于人类比赛操作；没有因此赋予GM/外挂实时按键或自动调用能力 |

项目核对位置：`config/coach_tactics_profile.json`、`src/gm_state_io/registry.py`、`src/coach_locator.py`、`web_gm/manuals/GM_COACHING_OPERATIONS.md`及M3手册。用户所说“球队进攻那四个设置”与当前已整合Freelance四槽属于相关的术语核对范围，但未直接核对其所指菜单，因此不伪造精确UI映射，也不再为此要求玩家补截图。

## 4. 给后续GM的可用认识

选择打法时一并考虑：球员的主用/备用类型、本队对应类型的战术池、Freelance和教练体系、进攻侧重点、调用倾向及对手防守环境。先判断配置是否支持目标动作，再给出定性意图和不确定性；不承诺精确调用率、固定指定球员或比赛结果。

不为未知建立万能阈值。当前三队逐CRC类型尚未认证、37个非零槽名未知和同名书后缀匹配缺口继续如实保留。原生实际动作受益人未知不再作为一般类型资格的门槛；已有接口仍按M3/DEV14同批来源、业务限制和具体批准处理。
