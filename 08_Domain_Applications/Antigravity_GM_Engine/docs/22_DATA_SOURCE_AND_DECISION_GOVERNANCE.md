# 数据源、GM 决策与玩家审批总规范

本文是当前数据采集和游戏决策流程的最高级项目规范。它统一数据真实性、数值计算、内存地址重校准、决策来源和玩家审批规则。具体实现以当前代码为准；旧方案或未来玩法说明与本文冲突时，以本文为准。

玩家最新玩法见 [26_GAMEPLAY_ROLES_AND_WORLDLINE_RULES.md](26_GAMEPLAY_ROLES_AND_WORLDLINE_RULES.md) 和 `config/gameplay_policy.json`：Codex 处理本地数据/发布与批准后的执行，网页 GPT 担任 GM，网页读取验收由玩家负责；1984–2020 逐届轮回。球员自然成长由游戏决定，普通属性编辑禁止。仅历史重力具体方案可在玩家明确批准后进入受控开发/执行；MC 成长故事暂缓，不启用。旧自动觉醒、体系属性加成及交易附赠成长规则作废。

## 一、系统闭环

```text
游戏当前情境
  → 管理员级只读进程连接
  → 地址校准与签名验证
  → Python 抓取、清洗、入库
  → 确定性脚本与实时内存抽样核验
  → 仅向 GM 提供通过审计的数据库事实和计算结果
  → 数据任务结束，由玩家另行触发 GM
  → GM 输出带数据依据的决策建议并结束
  → 玩家批准具体方案并另行触发本地执行
  → 才执行游戏写入或修改决策文档/脚本
  → 回读验证并交付，等待玩家下一次数据任务
```

采集自动化不依赖大模型。采集失败、关键字段缺失、地址不确定或审计失败时，本批次不得进入 GM 决策阶段。

阶段之间不自动衔接。数据窗口入口见文档 27，执行窗口入口见文档 28。采集/初始化脚本不调用本地 GM 候选生成器；数据交付不代表玩家已要求决策，批准方案也不代表后台自动开始执行。

## 二、数据源范围与真实性

只把当前情境下实际观测到的数据写作事实。当前目标数据源包括：

- 全局球员池：完整原始结构、面补 ID、选秀信息和原始类型码；历史新秀依据原始字节 `raw_struct[0x70] & 0xE0 == 0xE0` 筛选。
- 当前联盟：30 队身份、球队财务/商业/POE 字段，以及从球队球员指针抓取的球员、位置、合同和已验证能力值。
- 制服组：按当前名单目录数量采集完整原始结构，不能遇空姓名就结束。球队归属读取 `+0x18` uint64 指针，并与球队八个角色槽反向核对；旧姓名锚点 `+0x60` 的字节不是 TEAM_ID。扩展实现和未解字段见文档 31。
- 比赛表现：只有游戏内可读且已验证的战绩、出勤、场均、伤病等字段才可入库。当前未观测字段保留 SQL `NULL`，不得用工资、POE 或模型判断补造。

每条数据必须能追溯到存档 ID、快照 ID、来源类型和批次清单。`NULL` 表示没有可靠观测；不得用 0、默认值、姓名猜测或旧存档值填补。派生数据必须与直接观测分开标记，并记录输入、计算规则和单位。

## 三、每次启动与内存地址变化

1. 每次运行都重新识别当前 `NBA2K22.exe` 的 PID 和主模块基址，并重新读取缓存锚点进行签名检查。磁盘中的 `runtime_memory_map.json` 只是定位提示，不能证明地址当前有效。
2. PID、模块基址或锚点不匹配时，必须按当前进程重新扫描可读内存，再按球队、焦点球员、球员池和制服组锚点验证。不能通过把旧地址加减偏移来“修正”失效地址。
3. 只有所有必需锚点和结构范围校验通过后，才可抓取。进程权限不足、读数不完整、签名冲突或对象数量异常时立即失败关闭；不得沿用旧批次或降级为推测数据。
4. 抓取句柄必须只读。`GameMemory` 默认只读；游戏写入使用单独的显式批准入口。读权限和玩家批准是两个独立条件：有批准但无法读/写进程，仍然必须停止。

常规采集需要能获得 `PROCESS_VM_READ` 与模块查询权限的 Windows 进程令牌。若 `OpenProcess` 返回错误 5，说明本次采集没有读到任何游戏字段；应让实际执行 Python 的进程以与游戏相同或更高的 Windows 权限级别启动。桌面应用显示为管理员不代表其后台执行器一定继承了管理员令牌，必须检查实际采集子进程。Cheat Engine 的存在或关闭都不能替代这个检查。

地址重启校验的验收要分开记录：同一 PID 的缓存锚点复验，只证明当次地址有效；游戏重启后出现新 PID，并成功走过失效缓存、完整扫描和锚点重锁，才证明重启漂移恢复路径通过。

## 四、采集、清理、入库和审计

玩家统一使用 `scripts/run_data_update.ps1` 触发独立窗口任务及可选发布，详见文档 24。`src/run_monthly_cycle.py` 是其底层标准采集入口。它按存档隔离数据库、刷新历史球员池、抓取当前球队/球员/staff 数据，输出 manifest，然后运行确定性脚本抽样审计。球员池先写临时 SQLite，校验通过后原子替换正式文件；快照数据库提交后如未拿到绑定当前清单和数据摘要的 `PASS_VERIFIED` 审计凭证，GM 闸门拒绝使用。

审计必须核对数据库完整性、外键、行数、球队 ID 集合、必需/未知字段规则、球员池摘要和锚点，并对球队、球员、staff 样本与当前进程内存逐字段或逐字节对照。审计器是 Python 确定性脚本，不是 AI。当前凭证 JSON 文件沿用 `ai_sampling_audit_*.json` 的历史文件名；文件名不代表模型参与审计。

重复采集同一快照会按代码中的幂等规则更新该快照行，因此必须使用正确的 `save_id` 和时间节点。不同游戏存档必须使用不同 `save_id`，不得写入当前正在运行的正式存档库做验证。

## 五、数值计算和模型职责

玩家于 2026-10-17 简化合同采集范围：只要求记录各队大名单球员的薪资。已取得的六年薪资及合同条款可以保留，但不继续将保障金额、死钱、例外、占位或完整现实 CBA 账本作为本次数据采集的必需项。大名单薪资采集完成，不代表交易方案已合法或获批。

- 数值计算交给 Python/SQLite 等确定性代码，包括工资差、阈值比较、排序、评分、CBA 配平和组合搜索。输出要能说明数据来源、快照、公式、单位和校验状态。
- 大模型只读取通过审计的只读数据视图和确定性计算结果，负责策略判断、解释和生成候选建议；不能凭语言模型记忆补造球员属性、工资、比赛结果、教练归属或交易资产。
- 任一决策字段缺失时，应输出“证据不足/待补数据”，而不是隐式估值。候选交易不得被描述为已合法，除非完整 CBA 工资账本已由代码核验。
- 当前 `gm_engine.py` 包含审计闸门及旧 Python 启发式候选生成器，尚不是连接到外部大模型的 GM 服务。审计闸门可用于数据导出校验，候选生成器已退出初始化/采集流程；实际 GM 由玩家另行触发对应模型，按当前项目机制读取数据库和计算结果决策。
- GM 数据库连接以 SQLite `mode=ro` 打开；决策输出写入单独的建议 JSON/报告，不回写作为事实的数据表。

## 六、玩家批准闸门

1. 数据抓取、清理、数据库快照、manifest 和审计凭证可在玩家选定存档及节点后自动生成；这些步骤不得写入游戏进程。
2. GM 默认只提出建议，不自动改球队阵容、球员、制服组、POE、门票、全局游戏设置、历史选秀槽位，也不自动改球队决策档案、规则文档或执行脚本。
3. 每项会改变游戏状态或项目决策规则的动作，必须先提供明确的变更内容、影响球队/字段、依据快照和回读方法，再取得玩家针对该动作的批准。未批准时只保留 `PROPOSED/PENDING_APPROVAL`。
4. 执行批准动作时，使用独立写入步骤；先验证地址和目标结构，再写入、立即回读比对，并保留执行记录。任一写入或回读失败就停止，不继续下一项。
5. 新局模板设置和独立全局设置脚本都要求显式传入 `--approve-game-writes` 才能写游戏内存。没有该参数时保持只读并跳过修改。该参数只批准本次对应入口定义的写入，不能代替对其他交易、球员编辑、档案/脚本变更的批准。

## 七、文档冲突处理顺序

项目文档按以下顺序解释：

1. 本规范 `docs/22_DATA_SOURCE_AND_DECISION_GOVERNANCE.md`：数据、计算、地址重验、GM 只读和批准的共同规则。
2. `docs/21_DATA_CAPTURE_AND_SAVE_TEMPLATE.md`：当前数据库模板、采集字段、地址校准和审计实现细节。
3. `docs/18_NEW_GAME_SOP_AND_SYSTEM_VERIFICATION.md`：当前操作步骤和验证边界。
4. `docs/20_HISTORICAL_DRAFT_POOL_AND_INJECTION_SPEC.md`：历史新秀分类和候选查询规则；目标选秀槽位写入仍属未完成的独立功能。
5. `docs/16_*`、`docs/19_*` 以及 `docs/01`–`docs/15` 中尚未由当前代码实现的描述，属于历史方案或未来玩法，不是自动化能力承诺。

发现代码与本规范冲突时，应先关闭有风险的执行入口，再修代码和文档；不能通过把旧方案重新解释为“自动运行”来绕过批准规则。
