## 最小阅读与输入

先读本文件、`AGENTS.md`、文档 22 和 26；只在需要时查目标字段的实现和来源规范。不要加载所有球队历史档案。

玩家应带来：

- 当前 save_id、游戏日期/所处界面，以及 GM 方案使用的 batch_id、数据 commit 和规则版本。
- decision_id、方案版本、完整动作清单、目标球队/球员/员工的可辨认身份。
- 具体字段或交易内容、原值/预期值、Python/SQL 计算结果和必要的规则校验。
- 玩家明确批准的范围；对待定、未批准或方案外项目不执行。
- 可选 CE 表、偏移、当前地址或截图；这些是定位线索，仍需当前进程只读验证。

若批准记录或操作内容不清，只询问缺失项。已经批准且范围明确的动作不重复请求一般确认；若开发后产生批准范围以外的脚本改动或游戏变更，先展示具体差异，再取得对应批准。

## 执行顺序

1. **核对方案和当前状态。** 检查存档、目标身份、依据批次和方案版本。数据库供判断，实际写入前仍要读当前内存原值；已发生交易、读旧档或其他变化导致前提不符时停止，不能凭过期方案覆盖。
2. **核对是否允许。** 普通人物属性修改禁止；交易批准只包含必要名单/合同变更。历史重力属于逐项审批的例外，须有批准后的字段和值。MC 成长故事仍停用，不能用“球员修改”概括授权绕过。
3. **核对实现能力。** 每个写入布局、目标对象及副本都必须可识别、可回读。通用交易/合同执行器、历史新秀注入和历史重力属性执行器尚未完整验收，不能把旧伪代码或通用修改器当成现成能力。缺少实现时先准备必要实现及可审阅变更，按批准范围处理，未验收不试写正式局。
4. **当前进程校准与写前记录。** 核对 PID/模块/签名/对象身份，记录当前原值与可恢复的必要字节。绝不把网页地址或旧 CE 绝对地址当作跨重启有效地址。只记录本次必要范围，不能将完整进程转储当作备份。
5. **仅写批准内容。** 用明确的独立写入入口，目标白名单精确到动作和字段；一项失败停止。涉及多个结构的交易不能只改 team_id 就宣称完成，必须验证需要的名单/槽位/合同引用与一致性。
6. **回读与回执。** 比较实际值和预期值，核验球队名单/身份/合同等关联一致性，记录执行状态及前后值。出现部分成功时标为 `PARTIALLY_APPLIED`，保存已改项目；只在目标仍一致且恢复可验证时回滚，不能承诺不存在的原子事务或无条件回滚。
7. **停止。** 回读是本次执行验收的一部分；完整重采集、数据库更新和上传只有玩家本次也明确要求时才运行。否则交付执行回执，等待玩家另行触发数据更新。无论是否更新数据，都不自动再做一轮 GM 决策。

## 动作边界

| 动作 | 当前规则 |
| --- | --- |
| 交易、签约、裁员、阵容/合同调整 | 玩家批准具体动作；实现、目标和一致性可校验后执行 |
| 球队经营/战术/制服组调整 | 玩家批准具体动作；只使用已验证字段和对应执行入口 |
| 现役人物能力、潜力、倾向、徽章、动作、性格 | 普通方案禁止直接修改；不能夹带到交易里 |
| 历史线人物调整 | 具体历史重力方案获批且受控实现已验证后才能执行；不是通用改值许可 |
| MC 主角成长故事 | 尚未启用，不执行 |
| 历史新秀装载 | 只取已验证新秀模型，缺额保留小人；另验目标槽位并取得批准，不改现役人物能力 |
| 直接修改比赛结果或为剧情保送冠军 | 不属于已授权游戏机制 |

本次文档建立执行流程，不代表上表所有操作已有现成脚本。任何未实现/未验证项目明确报告，不以批准代替技术验收，也不以技术可写代替玩家批准。

## 执行回执

至少记录 decision_id、方案版本、玩家批准范围、save_id、来源批次/commit、执行时进程身份、每项对象及字段、原值/预期值/回读值、成功或失败状态、部分执行/恢复记录，以及是否按本次要求重新采集和发布。游戏原值与方案推测值分别标记，禁止伪造已执行状态。
