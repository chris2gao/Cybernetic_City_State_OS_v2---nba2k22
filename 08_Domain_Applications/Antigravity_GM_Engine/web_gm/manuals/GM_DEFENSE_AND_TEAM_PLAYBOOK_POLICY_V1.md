# GM个人防守优先与每队同名Playbook运营规则 V2

2026-10-20玩家明确区分：**专属的是球队手册容器，战术条目来自共享池**。相同战术可以被多本书引用，另一队可以将其添加或替换到自己的有限槽中；禁止写其它队容器不意味着禁止引用其它手册出现过的战术。查[共享池知识手册](../../docs/GM_SHARED_PLAY_POOL_V1.md)获取类型状态、用途及适配；历史参考池不替代本次已加载全目录和具体写入批准。

**2026-10-19 用户最新业务保证与窗口接力**。上位开发调度见[DEV18](../../docs/development_tasks/DEV_20261019_18_TWO_CODEX_WINDOWS_HANDOFF_AND_BOOK_DEFAULT_V1.md)，M系列实现见[DEV17](../../docs/development_tasks/DEV_20261019_17_CODEX_FIRST_MAINLINE_TEAM_BOOK_COACH_RULES_V1.md)。本规则为GM业务规范，代码实施未自动完成，真实游戏操作仍需玩家批准。

## 一、个人防守优先：GM不设置整体防守

1. 所有30队GM赛前针对**对方具体球员**制定`PERSONAL_DEFENSE`策略，使用既有18项原生个人防守字段；针对一人或多人的不同参数、不同对手球队，支持DEV14稀疏批次批量写。需要设置谁就设置谁，未变化的球员保持HOLD，无需把全联盟18项字段重写一遍。
2. `OVERALL_DEFENSE`整体设置仍可采集、只读解释、保留原版默认，但**日常GM不产生其修改动作**，因为整体设置会覆盖个人防守（用户实机规则）。这一经营规则消除同owner/opponent总体+个人设置的实际覆盖风险；不用再“先整体后个人”的常规执行路径。
3. GM层和DEV14的`stage/validate`需默认阻止普通GM整体防守写入，返回`OVERALL_DEFENSE_GM_DISABLED_USE_PERSONAL`。此前整体设置19/18来源和原生解码保留；非GM特殊维修只有另得玩家特别授权才可调整整体，且需要重新评估已有个人配置。
4. 个人防守只有本次双方名单`native_player_id`和`defender_id`能唯一定位时才可写；遇到不存在条目/身份变更返回`PERSONAL_MATCHUP_UNAVAILABLE`，不能为简便改整体。需要准确区分个人AUTO/继承值和缺失来源。原版ACE临场防守仍ON。
5. 示例：本队对勇士保持原生整体防守原值，对库里单独设置`personal.ScreenDefenseOnBall=GO_OVER`（原生枚举按实际字典），对其他高威胁球员分别设置实际需要的18项个人字段，不改全队整体设置。这个例子是战术策略而非已获批操作。


## 二、球队有固定本队同名Playbook容器（作为当前游戏默认不变量）

**用户确认**：新档30支球队通常使用各自球队同名的战术书，每个球队拥有对应自己的书容器。本外挂经营约束让换帅后立即恢复本队书。**不再把多队共享书导致冲突当成需要解决的常规开发问题，也无需Antigravity先做克隆/新建30个书/全联盟逐本独占验证。**

- 主教练拥有战术体系理念与熟练度，球队保有自己的同名手册。GM不能为改变体系随意修改`coach.PlaybookID`换成其它队书；而是修改**本队68个战术槽**中的必要战术，适配教练体系、阵容和比赛。
- **休赛期换帅示例**：A球队/A教练/A球队书 → A球队签B教练后可能暂时是A球队/B教练/B球队书 → **将A球队现任B教练的`coach.PlaybookID`受控恢复为已存在的A球队同名书** → 回读A书槽位 → GM按B教练体系与A队球员修改A书中的战术。不能去修改B球队的手册内容。
- **换帅次数与时点**：每队每个游戏赛季只允许在**休赛期更换主教练一次**。本次不实现工资/合同到期、教练竞价、自由市场和休赛期操作阶段，只做M3提案约束与已确认换帅事实后的手册恢复接口。
- 仅在新档本名手册初始绑定和已确认换帅后的技术性恢复允许`TEAM_BOOK_REBIND`改变Coach PlaybookID；还需玩家批准和DEV14对象身份/原值检查。成功回读后再独立提案编辑本队槽位；两步骤不能把切书前的旧slot前值带入下一步。
- **正常确定性校验保留**：复用已加载`name/enum_id/index/unique_id`确定本队同名书、当前教练和读写对象；逐批CAS/回读/日志仍执行。实际对象异常时单动作BLOCKED，不暗改别队。**不以假设的跨队共享风险推出大规模新技术任务。**
- Antigravity此前已调通复杂战术槽替换，已有68槽CRC原生功能由DEV14引入；未来CRC真实语义/51倾向/位置训练模板/疲劳是**GM主线完成后的扩展研究**。

## 三、两个Codex模型窗口的衔接

- **窗口① DEV14底层开发，PR#5**：已有Coaching/Book的物理读写、身份、Codec、批准和恢复，实现潜力入库脱敏、Intangibles轮换新写动作，以及仅限新档/换帅场景的安全BookID变更接口；交付`docs/development_reviews/DEV14_TO_M3_HANDOFF.md`。
- **窗口② M系列GM开发，PR#4**：在接收窗口①交接后构建球队与教练的Book目标匹配、休赛期换帅一次GM约束、按当前体系改手册、个人防守战术与训练/轮换分析，生成DEV14期望变更；**不得重新开发执行底层**。
- 两窗口均不能自动合并PR/更改正式游戏/启动GM V4。

## 四、最低验收

1. 日常GM个人防守修改可针对同一对手多名球员，0个OVERALL写动作。
2. 同名Book目标以已加载Native ID而非字符串猜测提交；A队新教练恢复A本名手册后，新槽位重新读取、玩家独立批准，B球队手册内容不改。
3. 休赛期一次换帅准许、常规赛换帅和同季第二次换帅阻止；没有员工签约机制时只是GM规则测试，不假装已经执行了员工签约。
4. 未知战术CRC保留UNKNOWN，但其他GM战术/训练/交易分析能够继续。已登记世界线及Gameplay字段不重复开发。
