## 1. 系统架构：不要让游戏 AI 重新否决外挂 GM

```text
游戏真实状态/比赛成绩 ──[Codex只读采集]──> SQLite、已发布JSON
                                    │
                                    ▼
                               数据分析基线
                                    │
                                    ▼
                         外挂 GM：30队独立利益
                       战绩/战术/阵容/合同/资源/士气
                                    │
                      交易内部议价 / 战术轮换裁决
                                    │
                                    ▼
                           玩家批准明确方案
                                    │
                                    ▼
                         Codex受控实现必要改变
                                    │
                                    ▼
                      NBA2K22赛场模拟 + 数据回读
                                    │
                          下一个玩家触发的GM节点
```

**决策与约束的准确划分：**

| 事项 | 外挂系统裁决 | 游戏本体意义 |
| --- | --- | --- |
| 两队交易是否值得做/是否双方同意 | **完全由两队独立外挂GM议价** | 不需要游戏AI报价、交易难度、CPU交易通过才能形成外部协议 |
| 选秀权与球员谁归谁 | 外挂GM从已验证资产账本选择，双边同意 | 批准后Codex落实相关名单/资产字段并回读，不得只改单一team_id假装完整交易 |
| 薪资与球队财务 | 实测合同/预算是定价信息；是否采用现实CBA限制是另行确认的**外挂规则** | 不将2K原生薪资匹配/交易override/截止日作为默认成交硬门槛 |
| 战术与轮换 | GM依据数据主动决定，估计赢球收益 | 游戏负责真正跑比赛；只有已验收的字段才能安全写入 |
| 球员士气与化学反应 | **次级、非零权重**，只有预计实质影响赢球才改变方案 | 游戏的真实效果需要后续观测；不把士气当否决票 |
| 球员明确交易请求 | GM将真实请求对应球员列入外部交易货架候选 | 不假定游戏有可用读取源或必须点原生交易挂牌开关 |
| 游戏原生交易困难度/CPU是否接受 | **不参与外挂双边一致决策** | 不要求也不建议改变这些设置来使外挂交易“合法” |
| 普通球员能力/潜力编辑 | 禁止 | 游戏自然成长；只有历史重力专项经玩家批准才可能例外 |

- 外部两队GM均接受并不表示游戏已经改变；玩家审批后仍要Codex核对当前对象、精确字段、写入关联、回读名单和存盘，确认执行。
- 完全不要求Codex用游戏原生交易界面达成CPU共识；执行器缺失属于**开发能力缺口**，不是交易博弈被否决。
- “现实NBA交易逻辑”作为合理性原则（双方利益、资产代价、期限、空间、商业价值），**不是把游戏中的CBA检查当自动否决**。若玩家以后希望实行明确的外挂薪资制度，由开发规划基线另拟并待确认。
- 旧 `docs/04_GM_DECISION_ENGINE.md` 的“原生CBA硬性薪资配平”及旧 `docs/15_DATA_FEEDBACK_LOOP_AND_DUAL_SYNC_SYSTEM.md` 的单指针交易示例，属于旧设计思路；不得覆盖以上新决策规则或视为生产级写入方案。

**最新V3内容标准**：除了5轮/8轮深度经营安排，还须使用[六维数据驱动GM决策规范](manuals/GM_DATA_TO_DECISION_STANDARD_V1.md)：先核对全部球员的本季累计与增量/能力/角色，之后独立判断①主教练与制服组是否应留任、②教练打法/攻防能否调整、③阵容与AI轮换能否优化、④是否需要交易/签约、⑤合同/选秀权/成长风险、⑥建队文化和下期反馈。员工身份可读不代表其效果被验证，也不代表可写入任免。历史时代下的人物属性专项从日常GM转至开发规划基线，常规GM优先用合理交易和教练风格回应历史线。

## 2. 第一目标：赢球，长期争冠；第二目标：风险、士气与化学反应

每队内部按**本队赢球目标**排序，不进行主观“士气优先”。争冠队看本赛季/季后赛强度，重建队看未来核心发展、资产累积和长期可持续胜率；不是要求每队无条件追求本月胜场。

建议的排序：
1. 提升本队本赛季合理竞争力，或明确重建队的长期夺冠概率；
2. 保护高价值核心与球队在未来多个赛季的总竞争力；
3. 管理合同、选秀权和角色资产的机会成本；
4. 士气/化学反应作为**仅在其对比赛表现产生影响时加权**的风险项；没有观测就 UNKNOWN，不编造损失概率。

- 士气下降不是交易或减分钟的硬禁止理由；若现实数据支持提高胜率，可以承受不满风险。
- 不可把“士气影响不大”错误等同于“士气完全不存在”。若连续比赛后其与胜率恶化有关，纳入下次实测检验，但不倒推2K隐藏数值公式。
- `NO_CHANGE` 是合理最终结论；不为“每月必须交易”而制造交易。
- 观测不足时可制定小范围试验而非大幅更改；涉及游戏字段仍须具体批准和已验收执行接口。

## 3. 更新后的决策轮次：采用用户批准的V3，最少五轮

**2026-10-18最新玩家指令覆盖本机制旧版“一次定案/最多3轮”的历史规定**。当前权威的详细规则是[GM_MIN_FIVE_ROUNDS_V3](GM_DECISION_ROUNDS_V3.md)和同步修订的[SOP第2节](GM_DECISION_SOP.md)。

- 普通30队经营节点：前3个实质轮各研究10队，须输出每队可追溯的阵容/教练/合同/资产/成长与市场决策档案；全部30队完成之后另有至少2个**独立**回合负责跨联盟资源/双边谈判与终稿执行准备，总计不少于5轮。
- 质量复杂时降为每轮5队，前6个实质轮覆盖30队，仍需至少2轮综合判断，合计不少于8轮；不足时继续延长，绝不为达到轮数而做浅表分析。
- 每个回合结束要保留GitHub档案与完成进度，并等待玩家继续触发。不得在第一轮模拟30队交易达成共识后就请求游戏执行批准。
- `W03/R01`是按旧规则已归档的初步总览；现在只作为待重新论证的候选清单。M02下一阶段从`W03/R02`组A开始，之后R03组B、R04组C、R05整体谈判、R06唯一终稿；若分组改为5队则相应增加轮次。
- 玩家明确批准具体变更仍是独立的执行前提；教练还需离线生成真实批次/摘要并对完整action_ids和batch_digest二次批准，所有最终执行由Codex完成，不能只因GM终稿出炉而默认游戏变更。
- 原有每单项交易最多3次内部报价/反报价是**可调整的市场谈判启发式**，不是限制每节点GM轮次为3，且不改变用户有权将交易延后。

## 4. 交易谈判：两队理性接受同一方案后才交玩家

1. **各自目标**：队A的补强需求/可付最高成本；队B的损失/最低可接受补偿；争冠与重建的时间偏好不同。
2. **真实资产**：最新球队球员唯一身份/位置/55项属性/当前表现/工资合同、选秀权 `asset_id`、原球队、当前持有人和可交易的后三届游戏选秀年份；同名模型/玩家非卖品须拦截。只使用已证实数据；缺少对比时说明UNKNOWN。
3. **内部最多三次报价调整**（是单轮内的模型思考步骤，并非用户三回合）：逐笔添加/移除具体球员或已验证选秀权，分别判断“本队比不交易更好？”。
4. **双方独立接受同一交易标的及完整筹码**，并通过资产冲突/重复转让检查 → `GM_BILATERAL_AGREEMENT_PROPOSED`，交玩家批准；如果没有双方一致 → `NO_DEAL`，本次不提交“已协商完成”的成交案。必要时仅记入待定货架。
5. **双方一致属于外部模拟GM层的判断**，而不是NBA2K内AI同意；不得伪装球员本人/现实球队已同意。
6. 工资差、球队经营压力、真实NBA习惯可用于**评估价格**；不要以游戏原生CPU报价、原生薪资匹配、原生交易开关自动否决两队GM。存在未确认的外挂硬规则（如玩家未来设定资产交换限制）则显式拦截。
7. 只有玩家对特定 `decision_id/version/action_id` 批准才能由Codex进行完整游戏字段更新；技术接口未验收时状态 `APPROVED_BLOCKED_EXECUTOR`，交开发规划基线，不得跳过完整一致性验证。
8. 交易执行之后检查双方当前大名单、合同/归属关系、选秀权、受影响球队阵容、存盘和下一次采集事实；不把文档写入当成交。

**触发挂牌（外部交易候选）：**
- 已验证球员的明确交易请求：自动列 `TRADE_BLOCK_CANDIDATE_REQUESTED` 进入外挂GM询价范围；是否写入游戏内挂牌字段仍需玩家对该字段具体批准。
- 球员不适配战术、发展受阻、合同性价比很差、重建队出售即战力：由所属球队GM主动生成货架候选；仍要权衡卖价，不低价抛售。
- 仅仅低上场时间、某一场发挥差、推测不满不能写成“球员已经申请交易”。

## 5. 轮换时间的决策：证据驱动，胜率优先

决策证据依次为：
1. **已验证球队/球员赛季累计表现与出勤样本**，辅以当前55项能力（不叫OVR）；
2. **尽可能采集当前完整轮换计划、出场角色/分钟和最近比赛实际分钟、球员请求/士气字段**；
3. 球队进攻/防守实际症状，哪一组阵容可能解决、对应替代队友能力与实际产出；
4. 预计增强强项/修复弱点的篮球理由、受影响球员可能的士气变化；胜率收益优先；
5. 变更后通过游戏下一阶段实战数据对照验收。

**可直接提出小调整建议的情形**：同位置两名球员拥有可靠可比样本，某球员在所需特长上明显更合适，调整有明确赢球理由。此时GM可提出“先让X比Y多打几分钟”的有方向方案，精确 `minutes_before/minutes_after` 只有在计划值真实读到后生成。

**不应武断精确修改的情形**：
- 球员只出场1–2场，未观测伤病/出勤原因；
- 只有累计平均分钟，没有当前教练设定轮换和全队分钟分配；
- 仅凭单人场均得分推断其进攻效率或宣称阵容净胜；
- “化学反应70”未见变化就编造某位球员会下降多少士气。

建议以较小时间步试验，用事实决定是否继续加减；具体 ±2/4分钟等是未来可选参数，**不将其视为游戏原生规则或当前已获批准的固定阈值**。已验证的游戏常规时长决定球队总分钟池；缺失则不能构造完整分钟表。

完成后核对游戏写入真实轮换、后续出场分钟是否改变、是否被游戏自动轮换覆盖，以及连贯若干场后的战绩/进攻/防守。士气效应仅做次级记录。

## 6. 30队决策的正式交付格式

- 所有30队均经过内部审查，但对玩家只显示**发生改变、影响最大或风险显著**的球队；稳定队简洁记为 `HOLD / NO_CHANGE`，不必每月输出30×12长文。
- 交付排序：①**可直接批准、已达双方共识的交易**；②**可验证的轮换/战术调整**；③教练/合同/商业动作；④仍未达共识及由于证据不足待延后事项；⑤固定本月不动的核心球队。
- 每项只占一个动作编号，包含球队、真实目标、前值、目标值或可核查的业务效果、数据批次/证据、胜率及长期收益理由、士气风险说明、Codex已实现状态、玩家本次可批准的确切范围。
- 数据不足则不虚构数值，可按方向进入开发规划/分析缺口，不反复提问阻断已有明确动作。
- 不把GM外部“理性接受”误报为现实球员本人表态或原生CPU确认。
- 外挂交易规则中被玩家明确确认的年/轮/原球队/现持有者、最多未来三届和球员属性禁区一直有效。

## 7. 开发规划基线需要补齐的能力（只提交需求，不直接开发）

| 等级 | 需求 | 验收标准 |
|---|---|---|
| P0 | **外部双方GM交易议价/资产锁账模块** | 每队独立估值；相同筹码双向接受才出方案；不能重复出售同一球员/签位；拒价得到NO_DEAL；不受游戏CPU交易难度阻塞 |
| P0 | **交易受控执行器** | 经玩家批准后按真实save/实时对象原值，完整更新双边名单、相关合同归属及选秀权；可回读、幂等、失败留下真实状态；不绕过禁改能力 |
| P1 | **完整轮换计划及球员需求/交易请求只读采集** | 区分计划分钟、实际分钟、缺席原因(可观测则保留)、士气/化学反应、明确交易请求，不可观测就NULL |
| P1 | **受控轮换/角色执行器** | 指定已批准的球员分钟变更，校验球队总时长和计划/实际出场；验证游戏进程是否会自动覆盖 |
| P1 | **赛前赛后变更效果评价** | 按同一save同口径比较相邻数据区间；可解释胜率、效率、伤病/士气影响，不把累计总分直接当月度差值 |
| P2 | **外挂GM对多队交易议价标准化** | 确定性计算与模型主观意愿分离；保存报价/反报价/共识/未成交结果及批准回执，不使用模型自造的证据作为事实 |
| P2 | **经营规则与旧文档治理** | 给旧 docs/04 和 docs/15 相关过时条款标明非现行；把用户明确规则合并到经开发规划审核的config和索引；禁止旧CBA硬门槛反向覆盖 |
 
**请开发规划基线制定任务书，Codex只按玩家单独批准后的开发任务实施。** 本文件绝不宣称上面未验收功能已开发完成。
