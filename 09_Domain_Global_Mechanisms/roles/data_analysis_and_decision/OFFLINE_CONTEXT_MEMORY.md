## 记忆单元 8：球员训练模板选择与负荷管理防伤法则 (Doc 86)

- **核心原则与机制依据**：
  1. **纯模板化决策，不碰 38 项子数值**：底层偏移 `0x318` 位域打包存储 `position` (0..4) 与 `player_type` (0..8 九大技术模板)。游戏引擎内部会自动联动 38 项训练点数预设。坚决不微调子项，仅锁定模板，极大降低决策复杂度并杜绝越界错误；
  2. **年轻正常、老年轻微的保守防伤强度**：训练强度与累积疲劳直接挂钩，高疲劳是日历模拟发生严重大伤的主因。由于 GM 每个赛季仅设置 1~3 次，实施保守负荷管理：
     - 年轻发育期球员（≤24/25岁）：`intensity = 3 (Medium / 正常)`，兼顾点数积累与身体安全；
     - 巅峰定型老将（≥26/28岁）：`intensity = 2 (Low / 轻微)`，杜绝过度疲劳，消除大伤隐患；
     - 易伤/康复期球员：`intensity = 1 (Very Low / 极低)`，`injury_recovery = 1`；
  3. **独立覆盖开关**：单调强度的球员强制设置 `is_intensity_overriden = 1`；
  4. **团队级背靠背休息**：激活 `rest_before_b2b = 1` 与 `rest_after_b2b = 1` 建立全队防伤保护网。

## 记忆单元 9：多球队/多球员批量研判的“上下文分叉克隆（Swarm Fork）”模式与人类前置询问准则 (Doc 43 第6节)

- **业务背景与技术痛点**：
  在面对多支球队（如全联盟 30 队）或大量球员（如 300+ 核心轮换）的全局战术重塑时，单模型聊天窗口面临两大瓶颈：
  1. 单次输出 Token 截断，无法一次性吐出数十个队的深度内容；
  2. 长上下文注意力衰减（Attention Drift），导致靠后的球队出现敷衍或逻辑降级；
  3. 死板的代码脚本无法胜任篮球战术与数值的高级定性研判。
- **上下文分叉克隆（Swarm Fork）模式核心机制**：
  1. **零冷启动加载（Zero Context Reloading）**：
     通过系统原生 `swarm(action="add", fork="coordinator", ...)` 从主协调员历史会话直接分叉。克隆出的 Worker 100% 继承全部 8 大前置记忆、Doc 85/86 规范与当前讨论共识，完全免除 15 次重复读盘开销，最大化命中底层的提示词缓存（Prompt Caching）；
  2. **任务切片与专业研判（Task Sharding & Model Judgment）**：
     每个克隆 Worker 仅分片负责 2~4 支球队（约 20~40 位球员），专注对照各队战术报告（Doc 50~79）进行高质量定性博弈研判；
  3. **严格纯差分零占位输出**：
     直接生成单队独立 JSON 并落盘至 `C:\nba2k22\exports\YYYYMMDD_<task>_execution\`，绝无 `65535` 虚拟值、无默认覆盖字段，完全符合 Doc 43 V2 规范；
  4. **主协调员统一闭环验收**：
     Worker 完成后在看板提交交付回执，主协调员运行自动化断言核验（0 占位、0 语法错误）并抽查四大哨兵球员（约基奇、哈利伯顿、克莱、戈贝尔）；
  5. **每次最多并发运行 5 个带上下文 Subagent 铁律（Concurrency Limit <= 5）**：
     为防止系统资源争抢、API 并发拥堵及长上下文碎片化，**系统每次最多只能同时运行 5 个带上下文的 Subagent (Worker)**。当任务切片总数超过 5 个时（例如 11 个 Worker），必须严格划分为多批次调度（例如 Batch 1: Worker 1~5，执行完毕并回收后再启动 Batch 2: Worker 6~10，最后 Batch 3: Worker 11），严禁单次并发超限。
- **人类前置询问铁律（Human Consent Gate）**：
  - **触发条件**：凡任务涉及 **多支球队（≥3 支）** 或 **多名球员（≥15 名核心轮换）** 的批量研究、倾向校准或训练重塑；
  - **铁律要求**：**模型绝不允许擅自静默开跑，必须首先在主窗口发起正式询问**，说明批次规划、分片 Worker 数量与交付目录，在获得人类明确许可（“可以启动 / 赞同 / 跑一次”）后，方可启动分叉克隆模式。

## 记忆单元 10：球员巅峰年龄（Peak Start / Peak End）成长曲线机制与可复用专项规范 (Doc 95)

- **引擎核心机制**：
  - `age < PEAKSTART`：能力值与符合解锁条件的徽章每年快速增长；
  - `PEAKSTART <= age <= PEAKEND`：能力值进入平台期维持稳定；
  - `age > PEAKEND`：身体素质与综合能力开始大幅下滑。
- **底层物理定位**：`PLAYER_STRUCT + 114 (0x72)` `uint16` 位域，**必须 Read-Modify-Write 保留低 4 位 (`& 0x000F`)**，`PEAKSTART` 占 `bits 4..9`，`PEAKEND` 占 `bits 10..15`。
- **跨模型复用核心判断法则**（无论范围是全联盟现役、单支球队还是某届历史选秀名单）：
  1. **只看现实历史相对年龄曲线，不被重映射的游戏出生年份误导**；
  2. **`PEAKSTART` 由爆发时间决定**：出道即巅峰 (`23~24`)、常规成长 (`25~26`)、晚熟/后期爆发 (`27~29`，且对未爆发的年轻/中生代球员必须大于其当前游戏年龄)；
  3. **`PEAKEND` 由续航与伤病决定**：历史常青超巨 (`35~39`)、长巅峰全明星 (`32~34`)、标准健康轮换 (`30~31`，修复原生 `<=27` 截断)、重大伤病/早衰型 (`27~29`)；
  4. **强制边界**：`21 <= PEAKSTART < PEAKEND <= 42` 且 `PEAKEND - PEAKSTART >= 4`。

## 记忆单元 11：主教练战术体系哨兵值阻断（ActiveSystem=8 NO_SYSTEM 事件）与调优数值箭头优先级提取铁律

- **历史背景与事故触发**：
  实机执行端/采集模型在校验单队执行包时检测到休斯顿火箭队主教练战术体系被设定为 `ActiveSystem = 8`，触发了采集模型的数值异常与哨兵阻断拦截。
- **2K22 底层机制与哨兵值本质**：
  在 2K22 `COACHDATA`（偏移 267）中，主教练战术体系合法枚举严格为 `0` ~ `7`（`0`: Balanced, `1`: Triangle, `2`: Pace & Space, `3`: Perimeter Centric, `4`: Seven Seconds, `5`: Defense, `6`: Pick & Roll, `7`: Post Centric/Grit & Grind）。数值 `8` 底层为 `NO_SYSTEM`（空占位/未分配哨兵值），游戏内引擎无法寻路，必然引发逻辑崩溃或哨兵告警。
- **根因分析与代码生成器缺陷**：
  1. 查验各队最新战术方案（如 Doc 79 第 3.2 节、Doc 75 第 4.2 节），人类与分析师明确为塞拉斯（火箭）和博雷戈（黄蜂）设定的是 `2 (Pace & Space)`；
  2. 但在规格自动化生成脚本中，解析 Markdown 语法 `$\rightarrow$ **\`2` 时因反引号与星号嵌套导致正则提取落空，回退到了历史有瑕疵的基线 spec，误填入 `8`；同时导致部分教练的协防/轮换参数误读了前文的现状诊断数值。
- **永久固化的业务准则与安全加固**：
  1. **禁止全联盟任何队伍出现 `ActiveSystem = 8 (NO_SYSTEM)`**：所有 30 队战术体系必须严格属于 `0..7` 合法枚举，生成及审计脚本必须增加合法区间断言 `0 <= active_system <= 7`；
  2. **数值解析严格遵循“调优箭头指令优先（Arrow Priority）”法则**：当研究报告文本中存在 `A -> B`、`$\rightarrow$`、`提升至`、`降至` 等明确校准语义时，必须优先以箭头右侧的目标值（Calibrated Value）为唯一权威，严禁被前文诊断现状数值覆盖；
  3. **双重同步校验**：本地数据库与 `C:\nba2k22\exports\single_team_execution\` 保持绝对镜像一致，任何修改必须经由 OS Loop 闭环审计脚本（0 mismatches）验证后方可提交。
