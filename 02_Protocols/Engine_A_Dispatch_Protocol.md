# 引擎 A：原生调度总线协议 (Engine A Native Dispatch Protocol)

> **生效域**：本协议仅对**城邦主控大模型（OS Coordinator / 父模型）**生效。在执行任何属于“引擎 A（工业基建代码流）”的任务时，父模型必须像机器一样严格遵守以下原生流转机制，**严禁使用外部 Python 脚本进行自动化编排。**

---

## 阶段 1：架构凝视与白名单确立 (Ring 1: Architect Planning)
在接到基建任务后，主控模型严禁立刻写代码。必须执行以下动作：
1. **生成蓝图 Artifact**：使用原生 `write_to_file` 工具生成一个名为 `[任务名]_Architecture.md` 的工件。
2. **划定沙盒白名单**：在蓝图中，必须明确列出本次施工允许访问和修改的物理目录路径（例如：仅限 `/08_Domain_Applications/App_X/`）。
3. **议长审批**：将该 Artifact 提交议长审批。通过后，进入扇出阶段。

## 阶段 2：沙盒物理隔离与原生发包 (Ring 2: Native Fan-out)
主控模型不再运行多进程代码，而是直接调用 IDE 的原生 `invoke_subagent` 工具。
1. **强制工作区隔离**：调用时，必须设置参数 `Workspace: branch`，使子代理运行在完全隔离的 Git 工作树分支中，防止污染主干。
2. **唤起专属模型**：调用的子代理类型必须是 `TypeName: engine_a_fable_worker`。
3. **传递封闭上下文**：在 `Prompt` 参数中，不得注入整个漫长的对话历史，只允许传入：
   - 之前通过的 `[任务名]_Architecture.md` 蓝图链接。
   - 明确的白名单目录。

## 阶段 3：挂起与异步回收 (Ring 3: Idle & Async Collect)
1. **让出主线程**：发包后，主控模型应当停止调用工具（即结束当前 Turn），让系统陷入安静的挂起状态，将算力全额让渡给底层的子代理沙盒。
2. **消息触发重启**：当子代理完成任务或因物理护栏被熔断时，它会通过 `send_message` 将状态回传给主控模型。主控模型被动唤醒。

## 阶段 4：合并裁决与 MCP 消冲突 (Ring 4: Verdict & Merge)
被子代理唤醒后，主控模型进入最终复盘阶段：
1. **读取子代理分支**：主控模型切换视界至子代理的分支，检查代码 Diff。
2. **熔断处理**：如果收到的是子代理发来的纯文本《系统困境陈述书》（说明沙盒报错已超过 3 次），则判定任务失败，主控模型需生成一份 `Rework_Plan.md` 并再次发包；若重试 2 次均失败，向人类议长（引擎 B）报警求援。
3. **合并冲突解决**：若确认代码无误准备合并回主分支时遇到不可避的并发冲突，禁止强行覆盖。必须调用 MCP 的 `resolve-conflicts` 技能解析双方意图后安全合流。
