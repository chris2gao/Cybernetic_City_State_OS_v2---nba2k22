# 01 OS 开发入口与单窗口任务规范 v1

> 状态：v1；仅当本文件存在于当前 `master` 时为活动规范。
>
> 适用对象：Human、前台审计模型、Claude Code、Codex 及其他被授权执行者。
>
> 目的：让全新窗口以最小材料理解 `01_os`、文件归属、证据、提交与接入门。

本文件只保存 `01_os` 专属增量规则。所有执行者先遵循仓库根部
`AGENT_WORKING_DISCIPLINE.md` 与 `AGENTS.md`；全仓输出控制、证据诚实和不可逆动作纪律
不在这里重复。目录语义、机制定义和机器契约以本文件引用的 canonical 文件为准。

## 1. 新窗口最小加载顺序

仓库根级 router 对每个 working window 启用 repository-wide always-on bootstrap。
一个新窗口只处理一个任务，按以下顺序加载：

1. 读取远端 `master` 的当前精确 40 位 SHA；不要沿用聊天中的旧 SHA。
2. 读取 `AGENT_WORKING_DISCIPLINE.md` 与 `AGENTS.md`。
3. 无条件读取 `01_os/README.md` 与
   `01_os/开发入口与单窗口任务规范_v1.md`（本文件）。
4. 将 `current Human natural-language request` 作为当前有效 task input；不得因尚无
   durable packet 而要求 Human 重新提供固定初始化提示或整套初始化包。
5. 已有 `durable task packet` 时加载它；若尚无 packet 且任务会造成 `material
   repository mutation`，在第一次 business/canonical write 前按第 2、5、7 节建立
   task packet 与 run evidence。
6. 只读取当前任务实际触发的 canonical README、实现文件和对应 registry。
7. 只在当前任务或复验明确要求时读取指定 `01_os/_runs/<run-id>/`；禁止
   default-preload `01_os/_runs/**`。
8. 确认本窗口的发布传输，按 1.1 的传输矩阵执行对应门禁；传输无法确定时停止发布。

Human natural-language task input 与 durable task packet 是两个不同层次：前者足以启动
理解、路由和只读 preflight；后者是 material repository mutation 的耐久边界记录。系统
负责在需要 material write 时形成后者，不能把这项启动工作转嫁为 Human 的固定提示词。

任务包与物理 Git 状态、registry 或 canonical 文件不一致时，以物理 Git 状态为事实，
停止写入并回传冲突。旧聊天、旧分支和旧 receipt 不能覆盖当前 `master`。

### 1.1 发布传输矩阵

受保护发布的门禁按**传输**分支，不按执行者品牌分支。本地 hook 是本地事故守卫，不是远程
授权边界：`git push --no-verify` 和任何不调用 hook 的客户端都绕过它（见
`01_os/05_registry/repository_guards_v1.yml` 的 `known_limit`）。因此没有本地 clone 的
执行者不是"权限不足"，而是需要一组能在该传输上真实执行的等效门。

```yaml
publication_transport:
  local_git:
    hook_guard:
      precondition: 当前 master 已包含并在 registry 登记该 hooks 守卫
      command: git config --get core.hooksPath
      expected: .githooks
      mismatch: blocked
      no_registered_guard: hook_guard = not_applicable

  github_api_connector:
    hook_guard: not_applicable_transport
    replacement_gate:
      - read_remote_master_40_sha
      - bind_exact_expected_branch_head
      - use_non_force_compare_and_swap
      - write_only_allowed_paths
      - compare_remote_base_to_new_head
      - verify_fast_forward_for_master
      - read_back_commit_and_changed_paths
      - report_actual_remote_head

  github_cli_without_verified_hooks:
    hook_guard: not_applicable_transport
    replacement_gate: same_as_github_api_connector

  unknown:
    status: blocked
```

`not_applicable_transport` 不等于无门禁，它只表示本地 hook 在该传输上没有执行机会；替代门
必须实际跑过。两类误报都必须拒绝：在 API 传输上声称 `hook_guard: passed`，以及把
`not_applicable_transport` 当作免检。

未定义的传输产生的不是安全，而是执行者自行裁决：同一次会话里既可以用"传输未定义"自我阻塞
产物，又通过同一传输发布提案。所以 `unknown` 显式 blocked，而不是留白。

普通发布范围、以及哪些 protected action 需要 Human 明确确认，见
`01_os/05_registry/repository_publisher_authority_v1.yml`。

### 1.2 执行环境约定

派单必须在施工前把下面这些定死，否则执行者会在半途撞上它们并把重试算进预算。
每一条都对应已经发生过的返工。

**Git 与路径。** 本仓路径大量是中文，两个 Git 默认值会让路径账本静默出错：

```bash
git config --local core.quotepath false          # 否则中文路径打成 \345\205\250 八进制转义
git config --local status.showUntrackedFiles all # 否则未跟踪目录折叠成一行，漏掉里面的文件
git config --local core.precomposeunicode true
```

*实测（2026-08-09，core 仓）：* 一个 54 文件的提交清单，转义开启时 4,720 字符，
关闭后 3,599 字符；单条全中文路径 113 → 45 字符。省的不多，但是免费的。

不要依赖这些配置来保证正确性。任何生成变更路径集合的程序都必须自己用
`-z`（NUL 分隔，Git 在此格式下永不加引号）并显式 `--untracked-files=all`，
这样仓库配置怎么设都不影响结果。`01_os/06_execution/task_discipline/path_ledger/`
就是按这个约束写的，并有一个故意把配置设成敌对值的真 Git 测试。

**未跟踪缓存目录。** `.pytest_cache/`、`__pycache__/` 若不可读，会让每一次
`git status` 都附带 `Permission denied` 警告。放进 `.git/info/exclude`；
权限本身异常的目录交给 Human 处理，执行者不自行删除。

**Python 包与导入。** 一个目录内的测试与被测模块必须能被统一的测试发现方式收集。
本仓约定：测试文件用 `sys.path.insert(0, Path(__file__).resolve().parent)` 后按模块名
直接 import，不依赖包相对导入，也不要求目录是包。这样
`python -m pytest <dir> -q` 与直接 `python <test file>` 都能跑。

**输出封顶在调用点。** 见 `AGENT_WORKING_DISCIPLINE.md` 第 2 节。
开发期诊断走 `01_os/06_execution/task_discipline/quiet_verify/`：完整日志先落盘，
通过时每个检查一行，失败时才打印尾部。实现验证入口自身时可直接运行测试并完整捕获日志，
但这仍是开发证据，不是候选完成门。

新 material task 的候选验证走
`01_os/06_execution/task_discipline/managed_verification/managed_verify.py`：任务包声明
`verification_plan`，`required_tests` 是该候选内计划的有序检查 ID，所有项必需。
`run` 绑定精确候选、任务包、范围与检查计划，真实执行并保留原始退出码和完整日志；
收尾消费者用同一候选和计划调用 `inspect`，漏执行、错误、脏源或损坏证据不能判通过。
契约见 `03_mechanisms/task_orchestration/受控验证执行契约_v1.yml`。历史任务不追溯改写，
也不能用旧诊断摘要代替新候选的实际执行证据。

这是一条明确调用的执行门，不是远端强制执行边界。通过只允许形成该候选的验证通过声明，
不证明检查语义充分、独立审核完成或 master 发布已获确认；全权限执行者仍可绕过入口。

**开工前一次取全。** 真实 HEAD、祖先关系、hook 守卫、工作区脏度、allowlist、
禁止项、授权门状态用
`01_os/06_execution/task_discipline/preflight/preflight_task_context.py`
一次取出，不要拆成十几次零散读取。它只报告，不授权。

## 2. 一个窗口一个任务

每个窗口必须有一个 `task_id`、一个目标、一个工作分支、一个精确 base SHA、一个明确的
allowed paths 边界、一套验收测试和一个 completion pointer，并且不顺手修复其他问题。

`allowed_changed_paths` 是**任务范围边界**，不是最终 diff 的事前穷举。边界必须无歧义，可用
exact path，也可用 bounded prefix/path-set。开工前列出的已知文件是 forecast，不构成第二条
更紧的边界，也不要求派单者预言确定性依赖图的每一片叶子
（`AGENT_WORKING_DISCIPLINE.md` 第 4 节）。

在边界内部，执行者继续施工，当且仅当同时满足：

1. 路径仍在当前任务范围边界内；
2. 内容属于**本** objective 已经委托的决策空间：可以是从声明 source 按固定规则推导，
   也可以是任务明确授权的局部实现选择或设计裁决；没有新增负载关键的 Human 决策。

逐字节相同是 `T0_mechanical` 推导的判据，不是所有任务继续施工的必要条件。
`T1_standard` 可在已定契约内作局部可逆实现选择；Human 明确委托架构/语义设计的
`T2_semantic` 任务可在该委托范围内作设计决定并落盘理由、边界和可检验条件。
二者不能借此降为 T0，也不能兼任最终独立验收。改变未委托的目标、验收定义、例外或
保护边界才是需要新增 Human 裁决的选择，不得把一般实现选择一概自我阻塞。

两条同时成立即继续，不必为边界内每一个新发现的叶子文件重新请求 Human 逐文件批准；实际
changed paths 仍按第 6、8、10 节以实测值精确呈现。

条件 1 不成立：停止写入，作为 `dispatch boundary defect` 上报——当前 objective 与任务范围
boundary 不自洽——并附建议 boundary。执行者不得自行扩边界。

条件 2 不成立：不修，记录 finding 并请求缺失的 Human 裁决；不得自行扩大委托。

以上只决定**内容**如何施工，不等于已经确认任何 confirmation-bound protected action。受保护的 publication（master 或
其他受保护共享状态）、force、rebase、squash、amend、history rewrite、删除、runtime/scheduler
激活、secret/credential 访问，即使结果完全确定性，也不因本节自动获得 Human 确认，一律按
`AGENT_WORKING_DISCIPLINE.md` 第 6 节、本文件 1.1 与第 9、11 节以及
`01_os/05_registry/repository_publisher_authority_v1.yml` 处理。哪些 publication 属于受保护、
哪些属于第 6 节的正常流程，只在第 11 节第 4 类定义一次，本节不重复。

发现旁支问题时只记录 finding 或后续任务，不扩展当前 diff。需要第二个目标时结束当前
任务并开新窗口。此纪律降低上下文污染和误合并风险，不构成技术访问控制。

## 3. 文件放置规则

| 内容 | canonical 位置 | tracked | registry | 处理 |
|---|---|---:|---:|---|
| 工作流阶段规格与实现 | `01_workflow/<stage>/` | 是 | 是 | 规格/实现分开，显式版本 |
| boot 清单与启动契约 | `02_boot/<name>/` | 是 | 是 | 启动顺序、版本、失败策略 |
| 跨阶段全局机制 | `03_mechanisms/<mechanism>/` | 是 | 是 | protected/versioned |
| 外部 skill 与工具说明 | `04_skills_and_tools/<tool>/` | 是 | 是 | 登记不等于加载 |
| 文件/path-set 注册信息 | `05_registry/*.yml` | 是 | 本身 | 与结构变更同步 |
| loader、wrapper、validator | `06_execution/<area>/<name>/` | 是 | 是 | 不放机制定义正文 |
| 领域内容 | `07_content/` | 是 | 按所属 registry | 不混入机制/运行流量 |
| 活动设计与被取代版本 | `_dev/` | 是 | 是 | supersede，不抹历史 |
| 共享 OS 开发/验证证据 | `_runs/<unique-run-id>/` | 耐久时是 | 否 | core-owned |
| 领域业务/workflow 流量 | `01_os/07_content/_runs/<run-id>/` | 耐久时是 | 否 | domain-owned |
| private/scratch/workspace | 仓库外或 run 内 `_runtime/` | 否 | 否 | 完成后删除 |

仓库级 hooks 只有在文件进入当前 `master`、有明确用途说明、正负例验证和 registry entry
后，才能作为 canonical 守卫引用；其具体路径由对应接入任务决定，本规范不预先声明。

判断：系统定义放 canonical 区；加载/验证放 `06_execution/`；一次开发事实放 `_runs/`；
临时内容放仓库外或 `_runtime/`。不确定时先查 registry 和相邻 README。

## 4. registry 同步规则

新增或移动 canonical 文件/path-set，必须在同一任务中更新对应 registry。entry 至少说明：

```yaml
- path: <exact-path-or-path-set>
  purpose: <what-it-is-for>
  loader: <what-reads-it>
  loader_class: in_repo_program | external_tool_convention | host_application
  discovery: <how-it-is-found>
  evidence: <what-proves-the-loader-claim>
  cache_dirs: []
  failure_surfacing: <when-a-problem-becomes-visible>
  deletion_rule: protected | human_decision_required | free
```

`01_os/_runs/**`、`01_os/07_content/_runs/**`、`_runtime/**` 和角色 private/scratch 不注册；
registry 描述系统结构，不描述运行流量。

## 5. run 与证据目录

新 run 必须使用当前 `master` 未占用的唯一 `run-id`；旧分支编号不能直接复用，创建前搜索
当前 `master` 和待引用历史分支。只创建实际有内容的阶段目录，常用结构：

```text
01_os/_runs/<run-id>/
├── run.yml
├── 01_任务输入/
├── 03_方案设计/
├── 06_执行/
├── 07_测试执行/
└── 08_结论/
```

`run.yml` 至少记录 task、base、branch、ownership、目的、输出、验证和生命周期。状态须与
真实仓库一致，可用：`research_only`、`candidate_pending_validation`、
`candidate_ready_for_independent_review`、`verified_on_demand`、
`integrated_and_verified_on_demand`、`deferred`、`excluded`。

这七个值写在 `lifecycle:` 键下，**必须逐字符落在枚举内**；自由文本状态串禁止，写在
`status:` 下也不算数。收尾时若该 run 已可归档，同时在 `run.yml` 写
`closure_record: <组内相对路径>`，指向一份可读且带
`completion_pointer` / `human_acceptance` / `exclusion_or_deferral` 之一的文件。

*实测 2026-08-28 于 `d9a18b57`：* `01_os/_runs` 下 50 个 run 组写出 **24 种互不相同**
的自由文本状态串，能被机器判为终态的是 **0 个**；communication 归档器早已存在而
`archive/` 至今为空，因为没有任何一条"这个组已完成"的机器判据。归档资格、默认可见性与
引用安全见 `01_os/03_mechanisms/context_management/工作集与归档契约_v1.yml`。

不得用 `passed` 掩盖“只证明安装/可执行/正例”。证据须区分 availability、functional
correctness、security boundary、repeatability 和 integration。

## 6. 分支与发布纪律

`01_os` 的分支与发布遵循根级工作纪律；本区域额外要求：

1. 从当前远端 `master` 精确 SHA 建分支，或使用 Human 明确指定的精确父提交。
2. 修改前确认 branch、HEAD、远端 master 和 worktree；只改 allowed paths。
3. 测试并生成可回放证据，普通 push 工作分支，回传 completion pointer。
4. 由符合第 9 节的新窗口审核；只有当当前 Human 指令或大任务预确认已经明确覆盖这次 `master` 集成时才执行。若尚未覆盖，直接询问 Human；明确答复即足够，不要求授权码、nonce 或额外 authority artifact。
5. 禁止宽泛 `git add -A` 或全量暂存/打包；必须使用精确 publish allowlist。
6. 以上五条与传输无关。本地 push、GitHub CLI、GitHub API/connector 是同一个发布动作的
   三种实现；差别只在 1.1 里跑哪一组物理门，不在于是否需要 base SHA、allowed paths 和证据。
   普通 task/source branch 发布不需要额外 Human 授权；`master` 与不可逆动作只检查是否已有当前
   Human 明确确认或大任务预确认。没有时就在动作边界直接询问，明确答复后继续。

旧分支只作证据源。采用旧内容时从当前 `master` 重建、复测并重生成 registry/run 证据；
禁止把从旧 master 分叉的候选直接并入当前 master。

## 7. 任务包必须包含的字段

```yaml
task_packet:
  task_id: <unique-id>
  repository: chris2gao/Cybernetic_City_State_OS_v2---core
  risk_tier: T0_mechanical | T1_standard | T2_semantic | T3_high_risk
  exact_base_sha: <current-remote-master-or-approved-head>
  branch: <new-or-human-approved-task-branch>
  objective: <one-bounded-goal>
  source_evidence: [<exact-path-or-commit>]
  allowed_changed_paths: [<exact-path-or-prefix>]
  verification_plan: <candidate-tracked-JSON-plan-path>
  required_tests: [<ordered-required-check-id>]
  prohibitions: [modify_master_without_required_Human_confirmation, force_push, rebase, squash]
  required_completion_pointer: <declared-shape>
  big_task: true | false

  publisher:                        # 发布传输与 confirmation 状态，不是身份自述
    principal_binding: trusted_host_injected | connector_authenticated | local_authenticated
    publication_transport: local_git | github_api_connector | github_cli
    source_branch_publication: task_scope_default
    master_integration_confirmation: not_requested | current_Human_confirmed | preconfirmed
    confirmation_ref: <optional-durable-ref-when-another-window-must-replay-it>
    expected_remote_master_head: <fresh-40-char-master-baseline>
    expected_remote_head: <optional-existing-publication-target-head-for-CAS>

  big_task_confirmation_closure:     # 大任务必须在派发前解决已知 confirmation-bound 动作
    enabled: true | false
    known_confirmation_required_actions: [<exact-action>]
    preconfirmed_actions: [<exact-action>]
    confirmation_ref: <optional-durable-simple-confirmation-record>
    uncovered_actions: []

  executor_profile:                 # 运行时本地、只用于本任务路由
    provider: Codex | Gemini | <other-Human-approved-provider>
    model: <runtime-model-name>
    reasoning_effort: low | medium | high | max | <runtime-supported-value>
    # 运行模式，与 reasoning_effort 正交。ultra 是模式不是级别：它并行跑多个子代理，
    # 所以预算和停止条件写在这里而不是 effort 上。见 7.1。
    mode: standard | ultra | <runtime-supported-mode>
    rollout_token_budget: <required-positive-limit-when-mode-is-ultra-or-null>
    routing_basis: <why-this-model-fits-this-task>
    authority: routing_only

  verification_profile:
    reproduce_before_change: required | not_required
    independent_reviewer: Claude | <current-Human-override>
    different_model_family: true | false
    different_measurement_tool: true | false
```

`risk_tier` 是供应商无关的任务语义，其 canonical 定义是：**执行者在"从当前树到 completion
pointer 的整条 objective 路径"上，在任务包所引 Human 内容裁决之后，仍然拥有的决策自由度。**

| 档 | 剩余决策自由度 |
|---|---|
| `T0_mechanical` | 零。每一个输出都由已经陈述的总则算出；两个称职执行者应产生逐字节相同的目标树。 |
| `T1_standard` | 存在实现选择，但局部、可逆，且不改变 contract、interface、semantic、ownership 或 structure。 |
| `T2_semantic` | 仍需决定"什么算对"：contract、semantic、validator behavior、ownership、structure，或据以选择文件与例外的判准本身。 |
| `T3_high_risk` | **按 blast radius 判定，不按剩余自由度判定**：history；master 或其他受保护共享状态的发布影响面；fork 家族的破坏性后果；runtime/scheduler 激活；secrets/credentials；真实学习者或用户数据。 |

**`T3_high_risk` 不因 Human 已经裁定具体内容而降档。** 内容裁决消除的是自由度，`T3` 度量的
是影响面，两者不可互换。

**普通的 source/task branch 发布本身不使任务成为 `T3_high_risk`。** 当前任务包已授权 source
write / task-branch publication，且 `01_os/05_registry/repository_publisher_authority_v1.yml`
已允许该动作（`push_source_branch`、`update_task_branch`）时，这类推送按第 6 节属于正常执行
流程。把任务推入 `T3` 的是 master 或其他受保护共享状态的发布影响面，不是"过程里发生过一次
publication"这件事本身；否则任何以 pushed completion pointer 收尾的实现任务都会被误判为 `T3`。

用先前 Human 内容裁决降低剩余自由度时，必须把**裁决内容**写进当前任务事实；如果后续窗口或
其他 endpoint 需要重放，则再保存一个可检查的 durable decision ref。这个 ref 是语义证据，不是
权限票据。不得为了降 risk tier 而要求授权码、nonce 或 task-authority artifact。必须按整条
objective 衡量，只降低该裁决真正消除的自由度。Human 给出的是一条能算出每一个输出的完整总则，
才可能到 `T0_mechanical`；给出的若仍是需要执行者套用的判准，则保留相应 semantic 层级。

`publisher.confirmation_ref` 只在 confirmation-bound 动作需要跨窗口重放时记录 Human 明确确认；
它不替代内容裁决，也不产生 semantic 降档。普通 task/source branch 发布不需要该字段。

`executor_profile` 只做路由，不能扩大 task scope，也不能替代 confirmation-bound protected action
所需的 Human 明确确认。`publisher` 记录传输和 confirmation 状态；`executor_profile` 记录模型与
运行方式。`provider` 名既不扩大 task scope，也不构成 Human confirmation。`principal_binding`
缺失或不可核验时，发布传输本身仍 fail closed。

### 7.1 模型路由 preflight

本节是“一个窗口一个任务”的稳定入口。正式任务在确定执行者前必须执行 model-routing
preflight：读取 `01_os/03_mechanisms/model_routing/` 的 canonical 契约与活动目录，运行其
boot 清单声明的 validator，再按 task、role、risk tier、task shape、required capabilities
和当前 surface 证据选择 model、product surface 与 parameter profile。

活动型号、参数档位、产品可选项和时效证据只保存在该机制中；本入口与 workflow 不复制目录。
任务时点的个人账户 availability 由 Human override：已登记候选默认 available，Human 明确
unavailable 时排除，明确恢复后重新加入。不得从静态 entitlement 或账户探测推断当前可用性。

选定 route 必须写入当前任务包的 `executor_profile`，至少记录 provider、surface、model、实际
reasoning setting、mode 与 routing basis；对应 receipt 记录机制版本、目录版本、validator
退出码和实际读取路径。模型、思考级别、预算、复现要求和独立审核方式仍须随任务包固定，不能
仅依靠聊天默认。

路由输出的 authority 常量为 `routing_only`：它不改变 allowed paths、risk tier、Human confirmation
coverage、filesystem/security boundary 或任何 protected-action 控制。模型选择也
不能自动降低风险层级。任务仍须定义成功、失败、停止条件和不做什么；测试证据和独立审核按
第 8、9 节执行，停止条件按第 11 节执行。

### 7.2 Human 确认与大任务预确认

默认规则是 **execute by task scope, not authorize per action**。当前 Human 自然语言任务输入加上
material mutation 时的 durable task packet，足以启动并完成普通、可逆、范围内工作；不需要另建
Human task-authority、授权码、nonce 或 delegation chain。跨模型 ordinary handoff 同样如此。

只有 `01_os/05_registry/repository_publisher_authority_v1.yml` 列出的 confirmation-bound actions
需要 Human 明确确认。若当前 Human 指令已经清楚覆盖该 exact action，则视为已确认；否则就在动作
边界直接询问。Human 给出清楚的“继续/执行/同意”等明确答复后即可继续，不再要求第二层授权仪式。
若执行发生在另一个窗口或未来时点，系统可把该答复转写成简单 durable confirmation record，目的
只是让接收方可重放事实，不是创建新的 authority 链。

**大任务必须在派发前做 confirmation closure。** 派单者沿目标 obligation graph 枚举所有已知
confirmation-bound actions，把未覆盖项一次性问完，并在任务包的
`big_task_confirmation_closure` 中记录 covered / uncovered。接收执行者不得对已经 covered 的已知
动作再次索要 Human 微授权。若执行中出现此前不可预见的新 protected action，则立即询问并在 Human
明确答复后继续；这不是拆新任务。若出现的是“什么算对”的新语义选择，则作为 Human decision
问题返回，不得伪装成授权问题。

历史 finding、旧 task-authority、`blocks_freeze`、`authorization_required` 等字段可以保留历史或
技术状态，但**不能单独制造当前 Human permission gate**。当前 canonical policy 决定某动作是否需要
Human confirmation；技术 acceptance 是否满足则由测试、证据和 review 独立判断。

## 8. 测试与证据标准

按根级工作纪律证明声明；`01_os` 任务至少补充：

- 正例、负例、边界例及预期/实际退出码；
- 基线/候选对照和 candidate-caused failures；
- runtime、依赖、隔离状态及适用时的重复运行/输出哈希；
- changed paths 与 allowlist 精确比对、`git diff --check`；
- 无个人绝对路径、secret、临时二进制和进程残留；
- tool crash/不完整结果 fail closed；不可观测指标写 `not_observable`；
- 机器结果、receipt、manifest 与 Human 结论一致，最终环境不得由旧结果代表。

## 9. 独立审核与 Human 决策/确认

实现/执行窗口与最终审核窗口必须是不同会话。审核者验证拓扑、diff scope、关键实现和机器
证据，查声明冲突与 blocking findings，并给出 `ready_for_human_integration`、
`fix_required` 或 `rejected`。

对 `T2_semantic`、`T3_high_risk`、master 接入或经历修正轮次的任务，派单会话不得兼任最终
审核；优先不同模型族。派单者可初核 findings，但不得称为最终独立验收。Human 豁免独立性
时，报告须披露角色重合和未覆盖风险。

派单者或执行者声明了较低的 `risk_tier`，不使该档位自动成为事实：独立审核者可依据任务包所引
裁决 ref、primary evidence 与实际 diff 判定该降档不成立并拒绝接受。这不新增审核流程，它是
本节既有审核的一项检查。

Human 仍决定是否进入 `master`、如何裁决新的架构/语义选择，以及是否执行 confirmation-bound
高影响动作。若这些内容已在当前指令或大任务预确认中明确覆盖，执行者不得重复询问；未覆盖时
直接询问即可，Human 明确答复后继续。独立审核、技术 evidence gate 与 Human confirmation 必须分开，
不得把一个历史 finding 的技术状态解释成新的权限请求。

## 10. completion pointer 最小模板

```yaml
completion_pointer:
  packet_id: <task-id>
  status: ready_for_independent_review | blocked | integrated
  source_branch: <branch>
  source_base: <40-char-sha>
  source_head: <40-char-sha>
  validation:
    tests: <actual>
    candidate_caused_failures: <actual>
    diff_scope: passed | failed
    hook_guard: passed | failed | not_applicable | not_applicable_transport
  repository:
    changed_paths: [<actual>]
    out_of_scope_paths: 0
    binary_artifact_count: <actual>
    worktree_clean: true
  publication:
    transport: local_git | github_api_connector | github_cli
    replacement_gate: passed | failed | not_applicable
    expected_remote_head: <40-char-sha-actually-sent>
    resulting_remote_head: <40-char-sha-actually-read-back>
    compare_and_swap: passed | failed | not_applicable
    fast_forward_verified: true | false | not_applicable
    push_performed: true | false
    master_modified: false | true
    force_push: false
  next_owner: foreground_independent_review | Human
```

所有计数、SHA 和路径来自实际运行或远端读回，不得复制期望值冒充结果。
`resulting_remote_head` 尤其如此：它是发布后从远端读回的值，不是本地 HEAD，也不是
`expected_remote_head` 的复制。两者相等必须由读回证明，不能由假设得出。
`transport: local_git` 与 `hook_guard: not_applicable_transport` 不能同时出现，
非 `local_git` 传输报告 `hook_guard: passed` 同样是无效 pointer。

## 11. 停止条件与修正预算

以下六类任一成立即停止写入并回传。这是既有条目的重排与澄清，不删除任何既有保护；
若某条既有停止条件无法映射进这六类，不得静默删除，须在 completion pointer 中报告。

1. **物理前提不符**：base / branch / master 与任务包不符；worktree 有外来变更；run-id 冲突。
2. **任务范围耗尽**：需要写到 `allowed_changed_paths` 之外。按第 2 节作为
   `dispatch boundary defect` 上报并附建议 boundary；这不是权限申请，执行者不得自行扩边界。
3. **需要新的语义裁决**：出现第 2 节意义上超出当前 Human 委托的选择；
   canonical 语义、例外或门的判准需尚未给出的 Human 裁决。任务已明确委托的
   T1 实现选择或 T2 设计工作不因含有选择而自动触发停止；风险和独立审核要求不变。
4. **遇到尚未覆盖的 confirmation-bound protected action**：包括 `master` 集成、force、
   published-history rewrite、删除 master/repository、repository visibility/credential 变更、
   runtime/scheduler/coordinator 激活，以及 registry 明确列出的其他 action-bound 动作。这里的处理
   不是结束任务或建立新授权链，而是只在动作边界暂停，直接询问 Human；Human 明确答复后继续。
   大任务中所有**已知**此类动作必须在派发前由 7.2 的 confirmation closure 覆盖，因此执行者不得
   对已 covered 项重复询问。若已登记 hooks 未启用、传输门失败或不能普通 fast-forward，那是物理/
   技术 blocker，不是 Human 授权问题。
   **反面：普通 source/task branch push 不是本类条件。** 在 task scope 内、使用认可 transport、
   发布门通过且不触及上述 protected action 时，直接完成发布，不需要 Human 逐次确认。
5. **触及安全边界**：secrets、credentials、`.env`、key store；未授权的网络、sudo、系统安装、
   模型调用或数据外发。
6. **证据不能支撑声明**：测试不能证明声明；机器结果与派单矛盾；或在没有 intervening
   mutation 的情况下，新一轮门既没有缩小 failure/stale 集合，也没有产生新的假设、remedy
   或证据（`AGENT_WORKING_DISCIPLINE.md` 第 2 节）。

初次交付后最多两轮包含**新证据、新假设或新 remedy** 的定点修正。原样重跑、重复声明或
无新证据的改写不算轮次，属于无效重复。第二轮后仍有 blocking finding 时，不得第三轮：
冻结分支和证据，拆根因任务，升级 Human/总架构决定继续、替换、降级或终止。本预算数的是
**交付后**的修正轮次，与第 6 类所指的**一次施工内部**的确定性门收敛是两个不同对象，
互不覆盖，也不因此设置固定轮数上限。

停止不等于失败；正确暴露边界优先于不可审计的“完成”。
