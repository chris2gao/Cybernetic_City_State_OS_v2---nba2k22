# 协作伙伴与接收者设置

本文件只保存稳定的协作角色入口，不保存会随产品更新而变化的 provider、surface、model、
参数档位或账户可用性。动态事实的 canonical 来源是
`../03_mechanisms/model_routing/`，任务时点必须运行其 boot validator 和路由 preflight。

## 稳定协作角色

| collaboration role | 工作函数 | 稳定边界 |
| :--- | :--- | :--- |
| `decision_architecture` | 前台裁决、material 架构与派单 | material 架构需要独立输入或复核 |
| `independent_review` | 隔离验收、证伪与结论 | 不接收 executor private context；独立性是证据要求 |
| `execution` | 在授权分支和路径内实现、验证、发布候选 | 只执行，不自行扩大目标、路径或 protected-action 权限 |
| `auxiliary_mechanical` | 确定性重复、批量与机械工作 | 默认不承担 material 架构或最终独立验收 |

这些角色描述工作函数，不授予 repository、publication、security 或 Human authority。provider、
model、endpoint card 和任务角色标签同样不能授权。

## Human-visible receiver setup

formal cross-endpoint action 若需要选择接收者，必须由 model-routing 产生并验证完整
`receiver_setup`。字段契约位于
`../03_mechanisms/model_routing/协作角色与接收者设置契约_v1.yml`；至少绑定：

- collaboration role 与 provider/product/surface/model/profile；
- session/isolation 与 repository access；
- exact branch 或 SHA、local-file requirement 与 GitHub publication prerequisite；
- communication carrier；
- routing basis 和 availability evidence/assumption ref；
- limitations。

GitHub-only receiver 不得把本地未发布材料视为可读。material independent review 必须使用符合
任务要求的 fresh/isolated setup；产品状态无法机器观测时，只能用绑定到 exact review ID 的
Human setup attestation，且该 attestation 不产生 authority。

## Formal-action boundary

Human relay 仍是手工动作，不启动自动投递、轮询、确认、调度或任务推进。正式跨端动作必须先走
`mechanism_activation` constitution/resolver/gate，再由 communication publisher 产生 durable
artifact 与 v2 pointer。普通 Human 讨论、引用和模板示例在没有跨端 operational intent 时不受阻。
