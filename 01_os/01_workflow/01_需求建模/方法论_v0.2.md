# 需求建模 · 方法论 v0.2

把几句话的需求，通过追问变成结构化建模 A。

**完成条件不是“问够了”，是 schema 填满、跨字段校验通过，且人类确认双方所指相同。**

v0.2 在 v0.1 基础上吸收 `run-006-上下文管理需求建模测试` 的实测结果：

- 从机械“一次一问”改为默认每轮 2–4 个低依赖问题；
- 阶段一的耐久产物改为 `requirement/` 产物包：A + 与版本绑定的人类确认；
- 明确限制追问不能无边界滑入结果方案 B。

---

## 一、核心结构：schema 一物三用

```text
Pydantic / JSON Schema
   ├── 是产物         —— A 本身就是这个对象
   ├── 是停止条件     —— 必填槽位齐全且跨字段校验通过 = 可以进入人类确认
   └── 是提问生成器   —— ValidationError 解析出缺什么，生成下一批问题
```

这是本机制的承重设计。它把“何时继续”和“下一步问什么”连接起来：
校验失败携带缺口，问题生成器只围绕这些缺口工作。

模型可以建议停止，但**无权单独结束循环**。

## 二、阶段一耐久产物

阶段一产出一个 `requirement/` 目录包，而不是只产出一份 A：

```text
requirement/
├─ A_需求建模_vN.yml
└─ 人类确认_vN.yml
```

二者版本必须一致。

- `A_需求建模_vN.yml`：八个 schema 槽位；
- `人类确认_vN.yml`：确认双方所指相同，并绑定 A 的精确版本。

原因：工作流状态必须从磁盘产物推导。人类确认如果只存在于聊天里，阶段一是否完成就无法由产物判定。

A 产生新版本后，旧确认不自动继承；必须对新版本重新确认。

## 三、循环

```text
用户输入
   ↓
模型解析 → 分别更新 schema 槽位
   ↓
程序校验（不是模型判断）
   ↓
校验通过？──是──→ 生成 A 候选 → 人类确认 ──是──→ 写入确认产物 → 完成
   │否                                      │否
   ↓                                        ↓
ValidationError 解析                    指出不一致 → 回到解析
   ↓
按 Impact × Uncertainty 排序
   ↓
选择 2–4 个同层、低依赖问题
   ↓
一次提交一批；答案分别原子写回
   ↑_________________________________________|
```

## 四、四条硬规则

### 一、程序校验，不是模型判断

调研实测出“懒惰延迟”：大模型会单方面把关键模糊点推迟，在非标准路径下甚至不提问直接生成。

所以“是否还有 schema 缺口”由程序判断。每轮之后检查必填槽位与跨字段约束，不管模型是否声称已经理解。

### 二、默认每轮 2–4 个问题，不机械一次一问

v0.1 的“一次一问”降低了单轮认知负担，但 run-006 证明它会产生过多交互轮次、重复回显与 token 消耗。

v0.2 的规则：

1. 每轮 2–4 个问题；
2. 问题必须属于同一抽象层级；
3. 问题之间应低依赖，用户可以分别作答；
4. 每题单独编号、单独给选项、单独给建议与理由；
5. 答案分别写回，不能把一组回答压成一条不可追溯的总结；
6. 一轮结束后统一校验，再生成下一批。

以下情况退回单问题：

- 出现高影响术语冲突；
- 新答案推翻了此前前提；
- 后一个问题必须依赖前一个答案；
- 人类明确表示某处理解不一致。

批量提问的目的不是一次塞满问卷，而是减少无意义的往返。单轮仍不应超过 4 个问题。

### 三、答案立即写回结构化对象

每个答案被接受后，分别更新 A 的对应槽位。对话不是事实来源，结构化对象才是。

第一版可由模型维护草稿，但正式实现应采用 JSON / YAML 对象的原子更新，避免依赖 Markdown 锚点覆盖。

每轮只向人类回显本轮关键变化，不重复输出完整 A；最终确认前再输出完整候选 A。

### 四、建议不是事实

每个问题可以给出建议和理由，帮助人类理解取舍，但必须区分：

- 模型建议；
- 用户确认；
- 尚未确认的推断。

模型推荐的选项在用户明确选择前不得写入 A 为已确认事实。

## 五、提问优先级

缺失槽位不按固定顺序问，按 **Impact × Uncertainty** 排序。

- **Impact**：该槽位空着，是否会实质影响阶段二证据收集、阶段三结果建模或阶段四测试；
- **Uncertainty**：当前信息对它的约束有多弱。

一批问题应优先覆盖同一高影响区域，例如：

- 目标与成功判据；
- 边界与约束；
- 术语与未解歧义；
- 关联领域与假设。

不影响下游的模糊点不问。

## 六、schema 的形状

当前采用 `实现/需求建模schema_v1.md` 的八个槽位：

- 目标；
- 成功判据；
- 边界；
- 约束；
- 术语；
- 关联领域；
- 假设；
- 未解歧义。

槽位按下游需要什么来定，不按需求属于哪个领域来定。

人类确认不是 A 的第九个语义槽位，而是与 A 版本绑定的阶段完成凭证。

## 七、防止需求建模滑入结果建模

追问可以暴露候选方案，但不能未经证据直接把具体实现选型固化成 B。

处理规则：

- 用户明确要求的行为，写入目标、成功判据、边界或约束；
- 当前推理依赖但尚未验证的技术判断，写入假设；
- 必须由证据决定的具体技术路线，写入未解歧义并标记阻塞范围；
- schema 已足以让阶段二直接开工时，停止继续追问实现细节。

判断标准：阶段二能否从 A 的 `关联领域` 与 `假设` 直接开始工作，而无需重新询问需求的基本含义。

## 八、人类同义确认

schema 通过后，模型输出完整 A 候选，请人类核对：

1. 目标是否是要达成的结果；
2. 成功判据是否代表“做成了”；
3. 边界是否排除了不想做的事；
4. 关键术语是否与人类含义相同；
5. 假设与未解歧义是否诚实，没有把未知写成事实。

人类明确确认后，写入 `人类确认_vN.yml`。

确认的是“双方所指同一需求”，不是确认 B、技术方案或实现细节。

## 九、评估

继续借用 ReqElicitBench 的两个离线指标：

- **IRE 隐性需求发掘率**：追问挖出了多少用户最初没有主动说出的关键内容；
- **TKQR 关键问题回合效率**：问到关键点用了多少轮。

run-006 新增一个工程指标：

- **BQR 批次问题效率**：每轮提出的问题中，有多少真正改变了 A 或下游判断；同时记录总轮次与重复回显 token。

BQR 不追求单轮问题越多越好。若批量造成答案互相污染或需要大量返工，应减少批次大小。

## 十、v1/v2 当前明确不做的

- 不追求认识论意义上的完美停止判据；
- 不做本体树或完整信念状态机；
- 不做领域条件必填的大型嵌套 schema；
- 不做 schema 自动迁移；
- 不把所有对话过程长期保存为系统记忆；
- 不在需求阶段完成具体技术方案选择。

先让阶段一稳定产出可由阶段二直接消费、且由人类确认的 A。

## 十一、继承与淘汰

| 继承 | 淘汰或修正 |
| :--- | :--- |
| 状态机 + 必填槽位 | 僵化本体模型 |
| 收集状态与下游执行严格解耦 | 硬编码 NER 字段映射 |
| ValidationError 驱动提问 | 固定逐题话术模板 |
| 答案原子写回 | 对话作为唯一事实来源 |
| Impact × Uncertainty 排序 | 机械一次一问 |
| 人类同义确认 | 模型自行宣布“已经理解” |
