# 01 · 需求建模

把初始需求形成共识A0，经Human确认后，继续形成完整需求结果A并由Human独立确认。

**唯一活动顺序：01a共识A0 → Human确认A0 → 01b完整需求结果A → Human确认A。**
只有A0或旧单层A不能结束阶段01。七阶段身份不变，不提供旧任务兼容器。

## 核心机制

**结构化追问机制。**

- schema 同时是产物、停止条件和问题生成器；
- 默认每轮提出 2–4 个同层、低依赖问题；
- 高影响术语冲突或前提变化时退回单问题澄清；
- 每个答案分别写回结构化 A；
- 人类确认必须形成与 A 版本绑定的耐久记录。

方法：`方法论_v1.md`；结构样例：`实现/需求结果模型模板_v1.yml`。

## 输入 / 输出

- 输入：人类给出的原始需求；
- 输出：`requirement/` 产物包，供下游证据收集与结果建模消费。

当前产物形状：

```text
requirement/
├─ A0_共识_vN.yml + A0_Human确认_vN.yml
└─ A_完整需求结果_vM.yml + A_Human确认_vM.yml
```

统一阶段artifact的payload引用/承载这两个模型和两个独立确认。模型版本或内容改变后，旧确认不自动继承。
结果项列出成品、组成、关系、行为/输入输出、完整性标准，逐项连接SC与未知EVQ。

## 批量提问边界

批量不等于一次发完整问卷。每轮最多 4 个问题，每题必须能够独立回答、独立写回。

以下情况只问一个：

- 新答案可能推翻此前前提；
- 术语含义出现高影响冲突；
- 后一个问题依赖前一个答案；
- 人类指出理解不一致。

每题可以给建议和理由，但建议在用户确认前不是事实。

## 阶段边界

需求追问可以暴露候选方案，但不能未经证据把具体实现技术固化成 B。

- 明确要求写入目标、判据、边界或约束；
- 待验证判断写入假设；
- 需要阶段二证据才能裁决的技术路线写入未解歧义。

当完整A已经可供阶段二逐RES/SC/EVQ查证，且Human已确认其精确版本时，结束需求阶段。
