# 01 · 需求建模

把几句话的需求，通过持续追问，变成立体的需求建模 A。

**完成条件不是“问够了”，是 schema 填满、跨字段校验通过，且人类确认双方陈述同一需求时指的是同一件事。**

## 核心机制

**结构化追问机制。**

- schema 同时是产物、停止条件和问题生成器；
- 默认每轮提出 2–4 个同层、低依赖问题；
- 高影响术语冲突或前提变化时退回单问题澄清；
- 每个答案分别写回结构化 A；
- 人类确认必须形成与 A 版本绑定的耐久记录。

方法：`方法论_v0.2.md`

## 输入 / 输出

- 输入：人类给出的原始需求；
- 输出：`requirement/` 产物包，供下游证据收集与结果建模消费。

第一版产物形状：

```text
requirement/
├─ A_需求建模_vN.yml
└─ 人类确认_vN.yml
```

A 更新版本后，旧确认不自动继承。

## 批量提问边界

批量不等于一次发完整问卷。每轮最多 4 个问题，每题必须能够独立回答、独立写回。

以下情况只问一个：

- 新答案可能推翻此前前提；
- 术语含义出现高影响冲突；
- 后一个问题依赖前一个答案；
- 人类指出理解不一致。

每题可以给建议和理由，但建议在用户确认前不是事实。

## 阶段边界

需求追问可以暴露候选方案，但不能未经证据把具体实现技术固化成 B。

- 明确要求写入目标、判据、边界或约束；
- 待验证判断写入假设；
- 需要阶段二证据才能裁决的技术路线写入未解歧义。

当阶段二能够直接从 `关联领域` 与 `假设` 开始工作时，应停止继续追问实现细节。
