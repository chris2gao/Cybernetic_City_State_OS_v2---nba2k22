# 工作流阶段01：需求共识与需求结果建模 · 方法论 v0.4

**活动来源**：2026-10-23 Human 在 NBA2K22 领域仓库特批直接修订核心工作流，并要求系统 Core 仓库后续检查、测试及接收。仅本仓先行使用；既有 CORE_MANIFEST 的一般同步冻结不因此全面解除。

**关键修正**：原需求追问得到的“共识”不是完整需求。共识形成后必须立即明确任务最终实际交付什么，具体结构和完整性是什么，而不能等到阶段03才第一次发现交付结果。

## 1. 两种需求建模与后续结果建模

| 环节 | 核心问题 | 交付与检查点 |
|---|---|---|
| **01a 需求共识建模** | 为什么做、目标、范围、约束、关键术语、成功方向是否一致？ | A0 目标共识 + Human 版本绑定的同义确认；**不等于正式 A 完成** |
| **01b 需求结果建模（具体需求建模）** | **这个任务最后究竟产出什么真实东西？** 每一部分包含哪些内容、字段/行为、关联、更新、使用场景、验收？ | 预期**最终成果目标模型 A**：逐个交付物及子项的具体内容、已知数据、未知缺口、完整性标准；Human 确认完整 A |
| **02 信息收集与提炼** | A 要求的结果与组成元素，哪些已存在？事实、数据、源码、反证、可行性是什么？ | 按 A 的逐项 ID 与未知缺口收集证据并验证，不泛泛检索 |
| **03 结果建模 B** | 根据 A 与证据，**真正采用怎样的实现结构**，为什么能达成 A？ | 证据支持的可实施设计 B（如最终物理表、完整字段、关联、采集规则及理由） |

所以：**01b 的“需求结果 A”是想要的成品长相和要求；03 的“实现结果 B”是经证据论证的解法。两者都具体，但不相同。**

## 2. 固定七阶段，阶段01内部两个连续检查点

```
Human 意图 → 01a 需求共识(A0) → 01b 需求结果(A) → 02 实证与缺口 → 03 实现结果(B)
                                               → 04 证据驱动测试 → 05 步骤拆分 → 06 执行 → 07 测试执行
```

不增加新 Workflow stage_id；不改旧 v1 runner、文件 hash/receipt 或七阶段完成链。阶段01只有在最终 A 经过 Human 精确版本确认后才可在语义上完成。

## 3. 01b 必须产生的具体内容

对每一个最终结果对象记录稳定 `result_item_id`，并展开：
- **成品形态**：不是“开展调查/做成完整系统”，而是可观察的实际数据库/服务/功能/文件/操作或其组合；
- **组成细目**：已知的所有子对象、字段/属性、行为、选项、输入输出、合法值与操作界面；能列出的必须列，不用笼统“全部”取代；
- **身份与关系**：实体/组件间的多对一、一对多、生命周期、状态变化、时间/历史规则，必要时给候选结构示例；
- **可消费结果**：面向 Human 或下游调用者的具体查询、导出、返回值或操作结果实例；
- **完整性验收**：每个组成项如何逐项核销、怎样判断未遗漏；绑定 `success_criterion_id`；
- **证据状态与未解项**：哪些是 Human 要求、已知工程事实、候选推断或真正未知，未知需要调查范围、来源和关闭条件。不同成熟度不得合并为 DONE。

**不可把 01b 简化成“待收集信息清单”**。应以任务完成时的实际结果为中心，充分填写当下已知的模型；未知的准确列不能捏造，但应明确最终必须怎样证明已经全部覆盖。

## 4. 对数据库类需求的必要结果规格

01b 形成的 A 必须提前说清最终要得到：
1. **原生数据全集**：目标系统的对象、实际页面/选项卡、所有合法文字/数字字段与已知原生来源；含已拿到和未拿到的明确边界；
2. **完整数据实体与字段**：所有需要的逻辑实体、属性/字段范围、单位、枚举、静态/动态/历史、关系、键及业务含义；
3. **物理数据库成品**：最终**确切表数、各表全部字段、字段类型与含义、主外键/索引、数据来源、采集方法、更新时间与设计理由、SQL DDL**；有证据的已知部分尽早在 A 细化，未证的具体物理决定由 02 核实、03 定稿；
4. **页面与库的双向映射**：实际游戏显示字段 → Native/Decoder/采集 → 逻辑实体 → 物理列 → 查询导出，逐项标来源或缺口；
5. **历史、隔离及验收**：至少提供真实值对照、跨表关系验证、长期数据保留、重复采集一致性和访问限制等可观察证明。

用户提议的具体表、字段、结构必须先在需求结果模型里成为**可检视候选成品或明确的交付要求**，不能只因缺少实证就隐藏到 B 阶段。反过来，不能未经实证宣称候选表数是最终事实。

非数据库任务将同一框架映射为功能、UI、服务、API、文档、动作或其他输出，不强制填写 SQL 字段。

## 5. Human 确认与跨阶段返回

- 01a 的 Human 确认仅约束共识 A0，01b 的 **完整 A** 需要独立 Human 同义确认，精确绑定 A 版本。
- A0 与完整 A 之间出现新的产品语义冲突时退回 Human 决定。A 新版本不自动继承旧确认。
- 02/03 发现证据要求改变 A 的产品结果时，退回 01b 与 Human；仅调整不改变 A 的可实施技术方案可由 03 记录论据和变更。
- 第04阶段测试来源为独立证据，不允许只从自身的 B 设计反推出必过的测试。
- 八槽 schema v1（目标、成功判据、边界、约束、术语、关联领域、假设、未解歧义）继续是正式 A 的外壳，`result_items` 为逐项结果规格；可参照 `实现/需求结果模型模板_v1.yml`。

## 6. 生效与兼容边界

本仓从包含此文件且 Boot / Registry 明确引用它的 Git 提交开始，**规划模型及工作窗口必须采用 v0.4 的阶段01语义**；旧 `方法论_v0.2.md` 作为历史来源保留。

**机器约束未声称升级**：当前 `最小运行schema_v1.yml` 与 `run_minimum_operational_loop.py` 仅校验其原有结构和版本绑定，尚无法断言所有 01b 细项已实质齐全；未来 Core 独立审核可引入兼容 v2 机器门，不能追溯使旧 Run 失败。

本次专门授权允许 NBA2K22 仓库 core-owned 文件一次性先行修订，**不扩大本地 DCR、游戏写入、Master 以外其他受保护动作的权限**；后续由 Core 仓库吸收时须按其规范独立复核。
