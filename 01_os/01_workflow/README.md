# 01_workflow

工作流是整个系统的入口。其余六个区域都是它需要什么才建什么。

## 目录结构

**一个阶段一个目录**，阶段的全部内容在自己目录里。

```
01_需求建模/
02_信息收集与提炼/
03_结果建模/
04_测试生成/
05_步骤拆分/
06_执行/
07_测试执行/
```

阶段八（完成）没有机制——全部步骤完成且测试通过即终止，所以不建目录。
**空目录声称一个它还没承担的角色，正是这个系统要避免的东西。**

## 每个阶段目录的内部约定

```
<阶段>/
├── README.md      这个阶段做什么、核心机制是什么、现在什么状态
├── 方法论_vN.md    机制的规格。第一版可以粗，要求是接得上
└── 实现/          实现该机制的文件
```

**规格与实现分开、版本号显式。** 这样第二版重构时，替换的是一个目录内的内容，
不牵动其他阶段——**隔离做好了，升级才便宜。**

## 开发方式

**每个阶段先做出能跑的第一版，再逐个升级。** 不追求一次到位。

七个阶段机制各自独立，某一个换实现不影响其他。所以顺序是：
先让整条链接得上，再回头把每一环做好。

## 最小可运行闭环

跨阶段机器契约位于 `实现/七阶段最小运行契约_v1.yml`；七个阶段分别提供
`实现/最小运行schema_v1.yml`。Boot 位于
`../02_boot/workflow_minimum_operational_loop/`，统一 loader/runner 位于
`../06_execution/workflow/minimum_operational_loop/`。

该闭环只实现确定性控制面：阶段顺序、类型化产物、版本与哈希、协同推演 receipt、冻结测试、
执行 allowlist、重试与上游失效、独立验证和完成。需求、证据、B、测试、步骤及实现内容仍由
模型或 Human 判断产生；runner 不把认知生成伪装成确定性程序。

## 链条

```
需求 → A → 证据 → B → 测试程序 → 步骤拆分 → [执行→验证→循环] → 完成
         ↑______________________________|
                失效可向上退回任意阶段
```

设计依据在 `../_dev/WORKFLOW_BACKBONE_v0.3.md`（四阶段与承重关系）
与 `../_dev/WORKFLOW_MECHANISM_v0.2.md`（连接方式、全局上下文机制、执行循环）。
活动 D2 执行角色裁决位于 `../_dev/决定_谁执行_v0.2.md`。

## 与全局机制的边界

`01_workflow/` 只保存阶段规格和阶段实现。跨阶段复用的上下文加载、角色入口、
workspace partition、访问边界、发布 allowlist、stale 与生命周期由
`../03_mechanisms/context_management/` 统一定义。共享 OS/workflow/mechanism 的
开发与验证证据放 `../_runs/<run-id>/`；领域业务 workflow 的运行流量放
`01_os/07_content/_runs/<run-id>/`。两类 private scratch 均不进入 Git。
