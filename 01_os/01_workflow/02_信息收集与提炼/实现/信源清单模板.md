# 信源清单 · 模板 v1.1

**这是长期资产，不是过程副产品。** 建一次，服务后面所有问题。
每个领域的清单独立存放、独立版本化。

---

## 头部

```yaml
领域: "<领域名>"
建立时间: "<YYYY-MM-DD>"
最后核对: "<YYYY-MM-DD>"
建立者: "<哪个实例 / 人类>"
```

**最后核对**这一项必填。信源会变——平台关停、付费墙上移、索引策略调整。
一份没有核对时间的信源清单，用久了就是另一种“曾经为真的断言”。

## 条目

每个信源一条：

```yaml
- source_id: "<稳定 ID>"
  平台: "<名称>"
  地址: "<URL 或访问方式>"
  类型: "学术 | 权威标准 | 业界官方 | 工程代码 | 民间活跃 | 内部证据 | 基础信息库"

  信源可靠性: "A–E"       # 平台或来源本身的质量
  可靠性理由: "<为什么>"

  发布时间或版本: "<日期、版本或 commit>"
  访问日期: "<YYYY-MM-DD>"

  检索限制:
    索引偏向: "<例：GitHub 权重偏向高星标，单个 prompt 文件不被索引为项目>"
    返回上限: "<例：搜索结果截断在 N 条>"
    付费墙: "<有 / 无 / 部分 / 未知>"
    时间覆盖: "<例：2015 年至今>"
    术语壁垒: "<跨领域同义词、需要人工搭桥的说明>"

  可访问性: "模型可直接访问 | 需人工 | 需订阅"

  基础库专用:
    最后更新: "<YYYY-MM-DD / 未知 / 不适用>"
    已知过期区域: "<哪些部分已知不再有效 / 不适用>"
```

## 两轴分级放在不同对象

- **信源可靠性**记录在本清单：这个平台、论文、官方文档或仓库作为来源有多可靠。
- **信息可信度**记录在具体证据条目：这条信息在当前时间、当前适用范围内有多可信。

不能在平台清单中填写“该平台上信息的一般可信度”来代替证据判断。一个可靠平台上也可能有过期、实验性或仅适用于特定版本的信息；同一平台不同条目的可信度不同。

证据条目格式见 `证据包schema_v1.md`。

## 为什么每条都要记检索限制

**源优先会提高置信度，但不必然提高召回。**

“我检索了该领域的权威信源”听起来比“我搜了互联网”完整得多，而层内漏检一点没少。
不记检索限制，这份多出来的信心就是没挣来的——**而且它会让人停得更早。**

实例：GitHub 是对的信源，但它的搜索权重偏向高星标项目，
个人开发者写在单个 prompt 文件里的实现可能不会被索引成独立项目。
选对了源，尾巴照样漏。

## 为什么“术语壁垒”要单列

不同领域可能在解决同一个问题，却使用完全不同的术语。

例如约束求解与需求追问可能没有共同检索词。若不记录这类壁垒，搜索系统会把“没有共同结果”误读成“两个领域无关”。需要人工提供跨领域同义词时，必须明确记录。

## 为什么“可访问性”要单列

**信源的可访问性不得默默定义证据集的边界。**

模型够不着的东西不会消失，它只是不出现在结果里——
**而这与“不存在”在报告上长得一模一样。**

标为“需人工”的源，要么安排人工挖，要么在边界记录里写明“重要但未覆盖”。
不允许无声脱落。

## 复用

新任务开始时，先查有没有现成清单：

- **有且核对时间近** → 直接用，跳过重新枚举；
- **有但核对时间远** → 先核对再用，核对本身通常比重新枚举便宜；
- **没有** → 建立，并存档。

任务本地的 `信源使用记录` 只记录本次实际用了哪些来源、查询了什么和遇到什么限制；长期信源清单记录平台本身。两者不要混成一份。

这是这套方法论相对于“直接搜索”的核心增益：**直接搜索永远不积累。**
