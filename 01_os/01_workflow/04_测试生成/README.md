# 04 · 测试生成

依据 问题、信息、答案 三者之间的映射，生成有效的测试方法。

## 定义性规则

**测试由证据推导，不由 B 推导。**

从 B 生成的测试检验的是 B 的自洽性；当同一套推理产出 B 和它的测试时，
**测试因构造而通过，什么也证明不了**。

证据是第三方——A 没写它，B 也没写它——**所以基于外部事实的测试能够诚实地失败。**

同一批证据因此干两件事：证明 B 可行，供给测试必须展示的内容。

## 核心机制

**映射 → 测试的生成机制。** 需要强模型。

## 输入 / 输出

- 输入：证据集、A、B
- 输出：测试程序，**每条测试可溯至一条证据**

## 关键性质

**开发之前就能验证结果建模是否可行。** 不考虑作弊的前提下，测试通过即 B 成立。

这些测试随后成为**开发的边界与验证依据**——避免出现没有依据的实现。

## 一条硬约束（来自执行循环）

**测试在循环开始后冻结。** 循环内改测试不是修复，是重新定义什么叫成功。
所以本阶段的产出必须在进入阶段五前定稿。

## 最小运行状态

`实现/最小运行schema_v1.yml` 与统一 runner 已实现冻结测试包、freeze authorization、
证据 claim 绑定和规范化测试摘要。阶段六必须携带同一测试摘要，任何测试内容漂移均 fail closed。

测试的语义设计与可采性判断仍由独立于 B 作者的模型或 Human 完成；runner 只验证冻结与溯源，
不把结构通过等同于测试充分。
