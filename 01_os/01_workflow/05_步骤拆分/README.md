# 05 · 步骤拆分

以 问题、信息、答案、测试 为依据，把问题拆成各个可实现的部分，
每部分可配对应的测试内容。

## 核心机制

**拆分 + 循环停止条件。**

停止条件不是新造的——**它就是阶段四的测试程序**。这是整条链闭合的地方：
信息越准 → 测试越准 → 实现越好，是真的因果，不是修辞。

## 输入 / 输出

- 输入：A、证据、B、测试程序
- 输出：有序步骤，每步可配测试

## 循环的正确形式

**不是"改了再试"，是多次运行、由测试筛出正确的那一次。**

用**采样加过滤**换确定性，而不是指望单次正确。这是模型的实际用法。

## 三个出口，不是两个

| 出口 | 何时 | 动作 |
| :--- | :--- | :--- |
| 通过 | 测试通过 | 下一步骤 |
| 重试 | 像实现缺陷，预算尚有余（三次） | 重跑同一步骤 |
| **失效** | 三次耗尽，或失败表明证据有误 | 向上退回并追加判定 |

**第三个出口让循环诚实。** 一个怎么都过不了的步骤，是关于产出它的那个模型的证据——
最常见是 **B 声称了证据并不支持的东西**，而这正是阶段三的证据依赖标注要暴露的。

三次耗尽后**人类介入**。

## 必须防的失败模式

**通过削弱检查来终止。** 重试压力下，让测试通过最省力的方式是改测试。
**一个除了成功没有别的出口的循环，会找到那个出口。**

所以：测试冻结，且第三个出口必须存在。**这不是警告，是这个循环必须被建造来对抗的东西。**

## Human 共同设计与可执行计划编译（跨领域）

拆分不是把已知业务操作重新展开成几十个 Shell/工具调用。对所有大小任务，先
核对是否已有 Human 审定的可复用 G/R/A/D 原型；有则直接实例化，没有则在首次
设计时向 Human **逐项呈现并讨论**最小 Ready/Done、具体 Action 内部步骤及其
必要性、已有函数/脚本的实际绑定、例外和复用范围。Human 可纠正过度检查、
删并不必要操作，模型给出技术事实依据并据此固定原型版本。

本阶段的交付要能在 06 之前绑定成可执行计划：每个业务叶节点有已审核原型版本、
实际 callable 与固定版本、参数、独立 Done 和需要的实例权限。找不到既有函数时
返回明确的 `CAPABILITY_GAP`，不把临时写胶水脚本当成运行时默认下一步。
不要每个 Loop/每次函数调用都重新要求 Human 审核同一个原型；真正新增的设计
选择才重新讨论。详情见
`../../03_mechanisms/task_orchestration/最小任务原型与执行编译契约_v1.md`。

## Human 裁决：模式归属与执行前冻结

任务原型设计可以进行充分的 Human + AI 逐项讨论，但其输出不能把自由脚本
和临时检查留给阶段 06。已审定的原型直接复用；新能力应作为 Human 授权的
`DEVELOPMENT` 任务设计实现，而不能由既有 `EXECUTION` 任务自行升格。

阶段 05→06 输出须能够绑定为已有 capability 的版本化调用、真实 Ready/Done、
当前实例参数和独立权限。默认执行模式 `EXECUTION`，模型没有自行切换模式权。
当前候选校验入口见 `../../06_execution/task_orchestration/execution_mode_gateway.py`。

## 最小运行状态

`实现/最小运行schema_v1.yml` 与统一 runner 已实现步骤到冻结测试的绑定、1–3 次重试预算、
无环依赖和 `pass / retry / invalidate_upstream` 三出口。上游失效目标必须落在阶段一至四，
不能通过削弱测试或无限重试伪造完成。

步骤内容和拆分质量仍由模型判断；runner 只验证控制边界与可停止性。

金蛋工程候选通过现有runner的 `next-business-action` 显式消费有限业务步骤，
把必要Ready、真实依赖、领域Done和批准业务选择分开表达。决定性且可安全执行的
preflight先于可选准备；PID/worldline变化只使依赖它的事实失效。候选输入及字段见
`../../06_execution/workflow/minimum_operational_loop/README.md`。
这不是新的正式阶段产物schema，不代替冻结测试绑定、三出口或Human签收。
