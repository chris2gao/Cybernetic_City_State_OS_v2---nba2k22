| 研发子窗口（顺序依实际游戏） | 现在能准备/复用 | 仅在Human已进入该窗口且授权时才实际执行 | 必须留下的最小证据 |

## 三、现场实施的现实顺序（规划与开发并非完全分离）

1. **阶段02此刻**：收敛目标UI/容器清单，对照v25现有Reader，列出尚缺的原生字段、场景/身份证据，以及持久化schema增量候选；把现场任务拆成可交Codex的**具体、可中止的子包**。真实游戏尚未进入场景，不以现场证据缺乏阻断所有阶段03建模。
2. **阶段03设计B**：在现有结构上设计能合理吸收后续新增字段/阶段来源的统一逻辑容器、身份和历史接口，并定义`UNKNOWN`分支及真实S7证据验证门。**未证Native细节列可延期实证项，不在现在无证冻结字段编码/地址或伪造新表**。
3. **进入S7现场时**：Human在游戏中推进到对应短时窗口，依据批准的本地只读游戏/Native任务包由Codex进行来源枚举、必要Native探索与Reader/Codec/typed入库/查询实现，随后在同一窗口采最小原始证据（防窗口流失）；真正写游戏内存必须额外由Human明确指定授权范围。
4. **离开窗口前**：审核关键目标容器是否已观察或有证据解释不可观察、原始材料是否足以复核、核心Reader是否能在当场生成真实数据库行并查回、字段与UI是否符合、不可用项是否经Human批准具体非核心延期例外。尚未观察核心来源不能给场景`PASS`，可以把其现场取证包标`PENDING_SCENE`。
5. **S7完成后**：综合S1–S8全域source-to-table差异；只在证据证明具体缺陷时新增工程设计/Reader任务；历史事实不覆盖，一档一库与100年同型Schema仍适用。

## 四、区分三种停止条件（不能混淆）

- **静态研究止步**：无需为了目前尚未产生的真实池无限扫描GitHub；已定位v25可复用结构和未知场景入口，可`STOP_STATIC_PENDING_SCENE`，继续其他研发/设计B调查。
- **阶段02正式完成**：由OS evidence package `可行性判断`和Human/OS阶段门判断是否足以支持B。对于暂不可观测的核心场景，**不能谎称实证通过**；能否在未获得场景前有条件进入后续设计必须明列未决可行性风险，不等于最终原型验收。
- **最终系统验收**：按获批A的RR-01与RES-02，核心S7容器需真实Native读取→身份/字段校验→typed入库→查询的实机证据，或经过证明等价的既有真实证据。真正进入窗口前不能提前给`S7_COMPLETE`，未获Human批准的非核心例外不得默示验收。

**本轮做什么/不做什么**：只更新阶段02规划/来源矩阵；不运行游戏、不操作电脑本地路径、不进行Native新增读写或Codex工程派单、不合并master。原始产品数据来自游戏；不增加自定义选秀模拟、自由球员签约决策、统计累计器。
