# NBA2K22 阶段02 · 九领域×101容器×20 Reader×S1–S8 覆盖差异与开发优先级 v1

**审查目的**：让后续Codex在每一个真实游戏场景能够立即知道**寻找什么食材、使用什么容器、哪些字段和关系尚待证实，以及什么不属于本任务**。基于 Human 2026-10-27 的“容器装食材”解释，按 OS `02 信息收集与实证规划`开展；**不是开发派单、不是S1–S8通过、不是任何新增业务计算需求**。

**固定范围**：PC NBA2K22 offline MyLEAGUE；原始第一任务 Human-approved A v1.9、2026-10-26 Human-approved A-v1-RC01、原型V0.4及ADR01/02；工程只核对 `a3927fb150a213201e404cca043ced4f57409bd1`。Human允许规划模型对已有决策内可逆、证据充分的事项自主判断；遇到**改变批准范围／重大不可逆架构／授权操作／必须Human现场提供场景**等真正承重问题才以阶段协同讨论与追问机制请求精准裁决，不对已决问题重复发问。本轮不需要Human新选择。

## 一、已核对事实与没有得到的结论

- 固定v25 **101个SQLite STRICT表、1789个字段/列、20注册Reader**；按原始九业务领域物理表数：RES-P **16**、RES-G **8**、RES-T **8**、RES-C **19**、RES-M **14**、RES-L **6**、RES-H **12**、RES-S **3**、RES-D **15**。领域名来自第一大任务旧A，不与新A六项RES共享ID命名空间。
- 与旧 `increment37/source-coverage.json` 对比，**74张表**在20个Reader各自“最近一次成功单元”开发者账本中至少有一条**非零行数登记**；另**27张**在这个**有限截面**未登记非零行，**不等于27个没实现的容器或缺陷**。它们含基础实体表、OS来源账本、候选事件、选秀结果、`season_finalizations`等；可能由间接/早期来源写入、仅初始化/接受未来事实、场景尚未生成等，原因仍要分开确认。
- 旧Reader历史成功单元均为 `LIVE_READ/PARTIAL`的**开发归档主张**，本窗口未独立Windows验证，未实际进入S2–S8。不能把“有表”“代码可读”“某次有行”当成“这个场景所有目标UI字段能读、能存、能查”。
- `01_v25_结构与Reader只读盘点_v1.json`中**1394项**真实游戏合法值域仍标 `UNKNOWN`，**305项**来源描述为 `UNKNOWN`；这是**字段元数据的当前分布**，不是1394个字段内容丢失或305个新表必须重建。
- **机器可读源清单**：`08_v25_101表20Reader九领域静态映射_v1.json`，逐表包含领域、物理列数、实际用途、各Reader最近成功单元有没有报告非零行、场景“研究相关性”标签、未实证标识；场景标签绝不作为适用性证据。
- 用户明确限制：**游戏自行计算的累计/场均/排名/奖项及其他业务统计直接读游戏实际结果**；禁止自行重新算篮球业务统计，技术性Native解码和忠实数据对账除外。

## 四、74/27解读：下阶段要核查的是差集，而不是表的存在性

- **74**：至少某个Reader旧归档最新成功unit登记过非零表行。每一项要比对游戏UI字段和真实源语义，避免“有行=字段完备”；一个表可能承载多个场景，不单独复制。
- **27**：旧归档最近各unit未见非零行。这包括`saves`/`players`/`games`等根实体表与`capture_runs`等通用元数据，因此并非“27表未开发”。此外`playoff_series`/`playoff_series_games`、`draft_results`、`season_finalizations`等真实依赖阶段来源的候选表，需要证明为何没有最新来源行、是否早已使用或待新场景形成。
- 下一轮比对按每个`table.column`和PC22 UI目标做三分：**有已证对应与样本、源码候选需指定场景确认、缺少来源/容器需正式差异设计**。不把“字段合法游戏值域UNKNOWN”无依据地改成缺失。
- 当前源目录是**容器完整性研究的结构性候选**，而不是受批准的最终SQL字段全集。各类非核心特殊例外仅Human可批准；核心场景先标`PENDING_SCENE_PROOF`，不能伪造PASS。

## 五、OS阶段02推进和讨论追问触发规则
