## 0 · 两个相反的挖掘目标

**支持 A 可行的信息**：在固定版本的实际仓库/Native证据中，能逐项确认 v25 已提供的 Schema/Reader/来源覆盖及其可信范围；在相应生命周期真实场景中可以把全部关键目标容器映射为确定对象/字段并经 Reader → typed 数据库 → 查询填充；字段组可识别共用写入机制且未来授权实机代表测试和批量清单重采集可行；单档固定逻辑 Schema 能按赛季身份正确容纳长期数据。

**推翻或限制 A 的信息**：核心目标数据源在适用场景确实无法读取，字段/对象身份或 Native 关系在关键环节不可判定，现有 v25 与目标场景/Schema 不兼容，游戏 Native 实际写入或全量新采集对账不能可靠核证复合业务操作，或者真实数据规模使固定 Schema 的 100 季目标无法按现有约束满足。负面证据必须保留且单独报告；若证据要求改动 Human 已批准的产品结果 A，需退回01b重新获 Human 版本确认。

## 3 · 核验优先顺序

1. **02-P0 固定源基线核销（只读 GitHub）**：锁定 v25 SHA及历史/修复候选，整理现有物理DDL、全部表字段、索引关系、20族Reader（数量仅作候选）、42单元等开发声明的原始出处、证据成熟度；标出未核实和冲突。不得修改主线，也不得把代码存在视为真实游戏读取通过。
2. **02-P1 数据容器覆盖矩阵（只读/资料研究）**：以 RES-01/02 的 S1–S8、实际页面/Tab、已知与后生成来源对照 v25；生成每个来源的证据锚点和须Human现场取证的缺口。
3. **02-P2 字段类别/运行时访问与历史事实**：对 RES-03/04 的类型/范围/身份/跨时点/权限和类别共用 Native 机制建立“已证/候选/不明”档案。**不要进行游戏进程写入验证。**
4. **02-P3 写入可靠性与最终验收的可行性证据方案**：对 RES-05/06 的业务一致性单元、完整修改清单、写后新采集、数据库对账、高负载脚本制定需要哪些实证、反证以及授权边界；只编研究计划与验证判据，禁止创建或运行实机写入脚本。
5. **02-P4 独立交叉验证和阶段02停止判断**：形成结构化 evidence 包、可信度/矛盾/边界记录和 feasibility verdict，可为 `supported|partially_supported|refuted|blocked`；不得用“没有搜到”证明“不存在”。不满足阶段02出口证据即保持 OPEN。

**场景时机依赖**：全明星、季后赛、自由市场、选秀等可能尚未生成；在游戏场景出现前，此问题保持 `NOT_YET_GENERATED_WITH_EVIDENCE` 或 `UNKNOWN`，不得凭空建立当前数据；真实 Native 场景操作与样本采集等待 Human 另行许可或提供。
