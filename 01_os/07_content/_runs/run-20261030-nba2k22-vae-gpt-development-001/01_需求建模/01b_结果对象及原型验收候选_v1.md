# VAE Stage01 · 01b式交付对象与首版原型需求候选 v1

**状态：CANDIDATE_PENDING_HUMAN_VERSION_CONFIRMATION。**
本文件借用项目既有01a/01b的交付目标表达方式，但属于Stage01目标规格；不是Core Stage03已从真实Stage02证据推导的B，不是已经实现的工程架构，也不是实机执行授权。

## 一、产品目标与最小交付

在PC22离线MyLEAGUE底层，通过改良原版引擎的可输入条件提升真实竞技环境，而不是外挂决定比赛比分。当前MC存档仅为逐项验证的测试场所，不包含MC独有玩法。Human要求边玩边验证、不断修订；单个被验证的可用能力即可投入后续有权运行，无须等待30队全量或最优滑块。VAE与D1–D5并行，互相引用成果而不互为阶段门。

第一版纵向闭环：**当前配置只读快照 → 异常诊断/竞争解释 → 事前Trial合同 → 单独授权的REA或UI实施 → 技术读回 → 原版自然比赛观察 → 效果评价/失败及经验追加**。本Stage01只形成可验收的需求与合同，不实际执行其中任何游戏写入。

## 四、首个纵向试验的前置门

首个试验由下一阶段实际证据决定，不预设数值。可以优先考虑E1内某个有重复现场观察的3D问题（如弱侧协防滞后、持球速度错配），但必须先确认：
1. **真实Profile**：当前game build、Save、模式、进程/场景与字段USER/CPU侧在只读证据中明确；静态默认、研究推荐不得替代。
2. **问题与竞争解释**：固定异常Game ID和可见表现，不能把偶然AI选择、ACE、动作、帧率或统计Normalize混为单一滑块效果。
3. **试验预注册**：冻结原值、修改范围、主指标、副作用、Human自然游玩观察窗口和回退策略，未获授权只能留在候选。
4. **路径选择**：先询问是否有可验证的REA Getter/Setter或经授权的原生UI；没有就TECH_PATH_BLOCKED，不私下热写、不新增Setter。
5. **技术层级**：Native返回成功、即时Getter读回、UI可见、存盘重载持久化，各自单列并需要其原始证据。
6. **竞技层级**：3D与Calendar分别观察，同save/game/Normalize等可比条件才比较；样本不足返回INCONCLUSIVE，不能伪造改善。
7. **经验与撤回**：不删除失败或负面案例；恢复动作也需其自身授权、技术读回和状态检查。

## 五、Stage01需求验收场景

| 场景 | 验收条件 |
|---|---|
| MC存档不能证明某MyLEAGUE字段同义 | 标MODE_UNVERIFIED；不做该字段写入 |
| 只有旧court.json候选建议值 | 允许用于假设；原始当前值必须UNKNOWN |
| Human未批准实机操作 | 只生成TrialPreflight，ExecutionReceipt保持NOT_RUN |
| Native成功但Getter未变化 | 不得写入TECHNICAL_VERIFIED |
| Getter变化但UI或SaveReload未测 | 只声明限定即时读回，不称持久化成功 |
| 自然比赛出现较差结果或新副作用 | 保留REGRESSED或INCONCLUSIVE，并追加原因及反例 |
| 日历分数与真实Box不符 | 标SCORE_CONFLICT，保留两个证据与Normalize状态 |
| 普通GM试图编辑Badge/Potential | 权限拒绝；移交受控世界维护性需求 |
| D2/D3数据尚缺某个字段 | 生成可追踪的D需求缺口，不等待整体D施工 |
