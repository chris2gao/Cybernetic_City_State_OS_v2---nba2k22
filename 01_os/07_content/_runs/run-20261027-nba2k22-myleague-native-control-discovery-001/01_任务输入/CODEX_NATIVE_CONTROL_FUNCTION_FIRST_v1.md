## 一、最高优先级：Human最新三项指令

1. **功能优先，不做多余研究**。交易已通过原生服务真实执行并由Human在游戏里确认交易记录，认作**当前已取得的成功样例**。不用再追原生返回收据、回调计数、Save/Reload/自动存档、其他交易类型的深度验证、交易全部资产规则、失败原子性。**不要重新跑交易实验**；只复用已定位的交易提案、检查、提交逻辑，纳入控制系统。已知限制可简述，不成为本轮阻塞。
2. **找全能操作的业务行为，恢复使用时真正需要的机制与调用逻辑**。像调整攻防重点、轮换、训练、球员属性/倾向/徽章、签约、选秀、交易一样，从外部模型输入`业务动作+目标实体+具体值`，交给原版游戏Native服务执行。要搞懂**必要的函数入口、参数/对象结构、前提和调用顺序**；不要求先解释玩法策略的深层收益，也不要求重建每个原版AI决定“为什么要做”的算法。
3. **次世代可以大量借鉴**。Human认为次世代与PC终极联盟的管理机制基本相通，差异主要在物理引擎。可直接将次世代MyNBA的玩法菜单、管理业务、功能说明作为寻找PC MyLEAGUE动作的**高价值线索**，避免僵硬平台隔离。唯独真正要提供的本地调用绑定——**PC游戏中的函数定位、ABI、this、输入参数和实际对象**——必须来自PC22本身的证据；次世代说明不能直接当作PC二进制地址或可调用证明。不做单独跨平台对比大课题。
   
**核心路线**：先实现“AI输入数值/业务参数 → 指向原版Native业务函数/共享业务服务 → 游戏自己完成设置或事务”的控制逻辑，后续再研究该行为影响比赛、AI决策好坏等策略知识。已经成功的一对一交易和Coach Gameplan→Coach Apply是模板，而不是需要本轮重做的实验。

## 二、探索目标——以用户操作和原生修改函数双向找全

**从外向内**：参考PC22终极联盟可见菜单与阶段操作，辅以次世代MyNBA可复用玩法资料和现有外部GM/Coach/Player需求，编制`Action Surface Inventory`。不要求重新打开游戏逐菜单实测；可以按现有历史截图、现有项目数据与公开资料标注来源。

**从内向外**：用REA、既有PE静态数据、原生类型/成员/交叉引用、vtable、函数局部代码以及上一轮Code追踪，找`Setter / Mutator / Apply / Validate / Commit / Manager`。从真实函数/数据写入关系还原参数与调用顺序，补出UI目录没有列出的后台AI动作。重点是**可调用的业务行为**，不是把所有只读Getter/算法函数算作控制动作。

所有结果按四档交付：
- `CALL_LOGIC_RECOVERED`：已有静态证据能写出具体对象、函数定位、参数及调用步骤，下一任务可以安排测试；
- `PARTIAL_BINDING`：确定操作候选但缺具体ABI/this/关键参数等；下一步该查哪一处明确；
- `REFERENCE_ONLY`：仅有UI、次世代资料或函数名字，尚无PC22Native定位；
- `NOT_FOUND_WITH_SEARCH_SCOPE`：有边界的检索未发现，不能说游戏不存在该机制。

**已经真实成功**的Coach/Trade另外标`PRIOR_LIVE_SUCCESS`，保留上一轮出处；本轮新登记的函数**不得标为已实测成功**。

## 四、必须写成“以后能接入外挂”的控制系统，而不是静态报告

建议目录：`08_Domain_Applications/Antigravity_GM_Engine/research/rea_native_control/`，具体结构由Codex自主选择。

**必要源代码与数据合同**：
- `NativeActionRegistry`：动作ID、角色、领域、外部AI输入Schema与可见名称、能力状态、Native入口和证据链接。
- `NativeBinding`：PC22构建版本、静态函数定位方法或RVA、调用约定、this/实体对象、关键参数和值域、必要阶段状态。
- `NativeActionPlan`：把模型输入变成`定位对象 → 编码参数 → 必要游戏合法性函数（如存在）→ 原生业务Apply/Commit`的**具体调用顺序**；若缺环节显式`UNKNOWN`。
- `Facade`：为GM/Coach/Player提供统一、类型化、易于后续测试的接口，如`coach.set_defense_focus(team,13)`、`coach.set_rotation(...)`、`player.set_attribute(...)`、`gm.trade(...)`、`gm.sign(...)`、`gm.draft(...)`。例子是期望接口，不得无证据地把全部标为可调用。
- `Coverage Atlas`：每类具体动作的来源、映射状态、现有PC22函数/调用链与缺口。
- `Next-Test Handoff`：列明下一轮要测试哪项动作、需要的场景、预期前后值即可；**不实际执行这些测试**。

可先采用简单实现，不要建立过大的RPC框架、Agent编排平台、完整生产数据库，也不要求写大量形式化schema校验代码。旧内存Writer暂时保留，后续测试证明各Native路径能替换后再迁移；**不因为已证明交易成功就提前删除所有旧路径**。

上一轮已经证实共享原生交易服务能够让两个**游戏内标记为玩家控制的球队**完成一换一交易，Human也确认在游戏交易消息中有记录。因此：

- **应整合已有功能：** 已定位 `FRANCHISE_TRADE` 提案结构、AddPlayerElement/Validate/FullCheck/Process/共享提交Wrapper的原生业务调用顺序；给`gm.trade`提供现有1对1映射声明，留有传入多个资产的以后扩展空间。
