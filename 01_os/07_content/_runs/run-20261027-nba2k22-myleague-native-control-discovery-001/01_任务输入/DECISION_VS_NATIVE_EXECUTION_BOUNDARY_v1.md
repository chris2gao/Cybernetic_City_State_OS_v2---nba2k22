# Human 最新裁决｜决策模型 vs Codex Native 执行层：职责绝对分离

**任务**：`NBA2K22-REA-MYLEAGUE-NATIVE-CONTROL-DISCOVERY-01`。**优先级**：覆盖本Run旧任务书中任何“替游戏/模型寻找满足条件的决策输入”的暗示。**本轮仍然只静态探索、编写调用逻辑，不进行新测试。**

## 核心职责

- **外部 GM / Coach / Player 决策模型决定 WHAT**：交易谁和谁、选择哪几支球队与选秀权、签约谁及合同报价、选哪个新秀、谁首发及分钟数、使用哪种攻防重点、训练方向和强度、具体球员属性或倾向要改成什么值。它负责**主动选择、匹配、比较、估值、权衡和产生业务参数**。不要求Codex当前重新实现决策模型，不为测试去搜“合法/最划算的交易双方”。
- **Codex本任务开发执行层 HOW**：逆向定位原生操作函数/共享业务服务，理解能正确调用它所需的对象、参数、数据格式、调用次序及必要最小前置条件；构建`ActionRegistry`、参数编码与`NativeControlFacade`，**按收到的精确指令原样调用原版游戏处理逻辑**。Codex不帮忙选择球队、球员、交易配对或“最优”数值。
- **游戏自身的原生服务判断 CAN**：原生的校验函数若是业务提交链必要一步，应**保留调用**。如果游戏认为用户提供的某笔交易不合法，则执行层返回`REJECTED_BY_GAME`和已有的拒绝信息／原因（能取得多少取多少）；**不自动替换球员或选秀权、调整工资、发起另一笔交易、重算提案或反复搜索直到通过**。这一判断属于原版游戏机制，不等于让Codex自行做GM决策。

## 最小输入 → 执行语义

| 操作 | 外部模型负责输入 | 执行层应负责的最小功能 | 明确不做 |
|---|---|---|---|
| 交易 | 球队A/B、球员ID或选秀权ID、双方资产集合 | 提案构造、必要原生合法性检查、单次原生提交或返回拒绝 | 搜索薪资匹配的球员、自动调整交易包、GM谈判估值 |
| 签约/续约 | 球队、球员、合同长度/逐年薪资/选项等模型决定的值 | 编码条款、调用原生合同业务入口、返回结果 | 从自由市场搜索“合适的球员”、自动生成最佳报价 |
| 选秀 | 球队、选秀权/顺位、候选球员ID | 原生选秀选择/提交计划，记录可用性 | 推荐新秀、重排名单、进行球队需求打分 |
| 教练设置 | 球队/教练及给定的POE防守或进攻枚举值 | 寻找原生Set/Apply入口，按给定值设置 | 研究“应该保护禁区还是外线”或预测比赛收益 |
| 轮换/阵容 | 指定球员、顺序、位置及分钟数 | 原生轮换/阵容/分钟Setter | 自动优化阵容搭配或计算最佳分钟 |
| 训练/成长 | 具体球员/球队、训练重点及强度或属性目标值 | 原生配置/属性服务绑定，必要范围检查 | 决定谁值得培养，或自动生成球员成长策略 |
| 其他AI操作 | 明确的实体、业务动作、所需参数 | 原生入口与参数映射，报告执行能力/缺口 | 外挂决策逻辑复制或优化 |

## 确定性的执行器合同（未来调用时）

```text
action = ExternalAI.Decision(type, target_ids, explicit_params)
result = NativeControlFacade.dispatch(action)
  -> resolve_native_objects(action.target_ids)
  -> encode_exact_params(action.explicit_params)
  -> call_required_original_game_validation_if_any()
  -> if rejected: return REJECTED_BY_GAME (same requested assets)
  -> else call_original_mutator_or_commit_once()
  -> return available game result / unknown status as appropriate
```

- **不可“帮助”外部模型改变请求**：执行层不会因交易工资不匹配自行换人、因为名额不够自行裁员、因为球员不合适自行重选新秀、因为战术值“可能更优”自行改枚举。
- 编码层可以做**类型/结构转换**与确有证据的格式/必要数值域检查；这是正确调用所需的技术处理，不是另作业务决策。
- 完整交易规则重建、薪资规则模拟器、候选生成器、薪资配平搜索、资产价值模型、AI选秀推荐模型、教练策略优化器均**不属于Codex本任务**；不能花大量时间实现。
- 接口即使把`validate`作为必要Native步骤，也是**“使用游戏的现成判定”**，而不是Codex先自行寻找一组能过验证的输入。
- 仅设计发现与调用代码，**这轮不执行上述函数、不进行新的实机或离线测试**。沿用之前已成功的交易与教练路径作为来源，不补收据/存档持久性研究。
- 次世代MyNBA功能资料可用于寻找可调用动作；PC22实际Native绑定仍须PC22静态证据。
- 保留Codex对函数发现、反编译与接口编码方法的高自由度；**不允许将此自由度扩大为替GM、Coach、Player制定决策**。

## 最小验收

一个控制接口无须证明Codex找到了“合理的交易配对”，只需说明：`gm.trade(teamA, [player_1], teamB, [player_2])`怎样通过原生提案与提交链执行；输入不合法时由游戏机制拒绝，**输入内容保持不变**。其它操作一律类推。

**Human最终定位**：决策模型做选择；Codex开发的原生控制系统做执行；游戏原生业务机制负责它自己的合法性判定。不要混同三者。
