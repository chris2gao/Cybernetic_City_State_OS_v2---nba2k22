## 0. Human业务口径与史料处理

- **MyLEAGUE／MyNBA联赛经营机制按同一业务功能集合进行需求搜集**：不再在新规划/角色功能文档以“次世代与本世代不同”制造默认排除或重复警告。相关攻略的战术、人员、选秀、球探、合同、球队管理目录全部可作为**业务操作候选**。
- **不改写已发布外部原文或历史研究原始证据**。历史论文/指南中关于机型的文字是原作者语境，不再复制成新规划的限制语；只有真正有证据的“某专项功能是否存在于目标游戏构建”仍需要确认。**不同游戏构建的地址、ABI、this指针和函数签名不能直接复用**，这是原生工程绑定要求，不是游戏经营机制差异的研究任务。
- **新范围先从角色需要什么动作建模，再匹配Native实现**。已知业务需求≠已经找到原生函数≠某个实机样例已成功。上一轮61/62个动作属于实现登记而不是需求穷举。
- **GM、Coach、Player做WHAT/WHO/VALUE决策**；Native控制层只做输入→对象解析→参数转换→调用Native业务→回传结果。游戏自己的业务规则可产生拒绝，但执行层不得自动找替代交易、匹配薪资、推荐选秀、优化训练或调整教练数值。
- **区分游戏状态/外挂人格状态**：球员偏好、许诺、谈判、GM协商属于外挂数据库/模型，不要为了“完成游戏操作”随意写入球员原生属性。若确有Human批准的世界编辑能力，需要独立的原生编辑动作合同。

## 4. 本次资料足以指导的执行能力领域

- GM：可查看世界/市场→更改阵容、合同、签权、人员、球探、选秀、发展计划→接收游戏结果。重点需求来自R05A/B/C/D，原Native执行从PR16继承。
- Coach：可读取球队/对手→更改六个POE、体系、战术手册、68槽具体战术、4个Freelance、18项个人防守、轮换/分钟、训练等。旧K04比新REA已验证10字段**宽得多**，必须按旧研究补全需求。
- Player：可读自己的完整资料、球队关系、当前角色、训练/伤病/合同状态；可以通过外挂人格**提出**交易/合同/轮换/训练诉求，但原生游戏操作与模型间通讯是不同接口。需要真实执行的训练设置、角色/属性等必须按能力是否存在标明。
- Shared Read：40组R07内容需分Query family、可见范围、数据时间轴、是否带身份/来源；避免只做写操作。
- World/Simulation：游戏阶段、日历/比赛模式、历史与规则控制是支持三角色参加游戏的**环境能力**，不直接等于每个角色可随意推进赛季。
