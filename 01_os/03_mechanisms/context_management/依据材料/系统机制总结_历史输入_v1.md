## 城邦加载机制初步盘点

本次按当前 `master` 进行核对，最新基线为 `9e2be7801efb4e758a6e383b0032bfbb5eabf9cd`。

先给核心判断：

> **城邦不是把整个 core 仓库加载进上下文，而是采用“固定启动控制面 + 单一角色 Profile + 当前任务引用 + 条件触发协议”的懒加载结构。**

因此，“没有被模型每次读取”不等于“没有用”。测试、Schema、验证器、路由文件和历史证据可能不进入上下文，但仍是运行机制的一部分。

---

# 一、系统实际存在三种“使用”

后续清理必须区分：

| 类型     | 含义                           | 能否仅因未被读取而删除 |
| ------ | ---------------------------- | ----------- |
| 上下文加载  | AI 当前会话实际读取的协议与任务文件          | 否           |
| 机器执行依赖 | 验证器、Schema、脚本、测试和 fixture 使用 | 否           |
| 审计与证据  | 决策、报告、历史执行和裁决记录              | 否           |
| 三者皆非   | 不可达、非证据、且已被新版替代              | 才可能是 Dead   |

启动文件自己也明确说明：它是路由器和懒加载入口，不是全仓库预读清单。

---

# 二、第一层：Bootstrap Receipt 强制加载集

通信合规策略明确规定了 **7 个强制加载文件**：

1. `06_Silicon_Index/AI_Bootstrap_Sequence.md`
2. `AGENTS.md`
3. `.ai/HANDOFF_INIT_PROMPT.md`
4. `.ai/PROTOCOL.md`
5. `.ai/PROTOCOL_ADHERENCE.md`
6. `.ai/HANDOFF_COMMON_CONVENTIONS.md`
7. `.ai/AUTONOMOUS_HANDOFF_COMMUNICATION_v0.1.md`

这是最硬的启动集合，因为首个 C1/C2 事件的 bootstrap receipt 会记录这些文件的具体提交和摘要。

这 **7 个文件不应进入普通清理候选集**。其中任一文件删除或不受控替换，都会影响 release binding、receipt identity 和通信验证。

# 三、第二层：完整上下文边界初始化

新线程、上下文丢失、协议更新或指针冲突时，完整初始化会在上述强制集外再读取：

* `06_Silicon_Index/CONSTITUTION_DIGEST.md`
* `.ai/load_profiles/<selected-profile>.md`
* `.ai/STATE.yml`
* `.ai/INBOX.md`

初始化顺序由 `HANDOFF_INIT_PROMPT.md` 明确规定。

同时，`AGENTS.md` 又要求所有模型尽早读取：

* `AGENT_WORKING_DISCIPLINE.md`
* `.ai/TOKEN_USAGE_PROFILE.md`

所以，**完整初始化的固定控制文件是 13 个**：

```text
7 个 receipt-required 文件
+ CONSTITUTION_DIGEST.md
+ 1 个 selected load profile
+ STATE.yml
+ INBOX.md
+ AGENT_WORKING_DISCIPLINE.md
+ TOKEN_USAGE_PROFILE.md
= 13 个固定文件
```

其中 `.ai/STATE.yml` 和 `.ai/INBOX.md` 要区分 source 上的 neutral baseline 与 review 分支的活动版本，不能把 source 的空状态误认为当前任务状态。

它们并非每回合全部重读。相同上下文中的 fast path 只读取：

* 当前 Human 指令；
* `.ai/STATE.yml`；
* 必要时 `.ai/INBOX.md`；
* signal 中全部非空引用。

这意味着后续优化的正确方向应是：

> 保留协议文件，但减少重复加载和协议内容重叠，而不是因为 fast path 没有读取某个协议就删除它。

* event、STATE、pointer 和 validation artifact 的不可变引用。

**这整个目录不能按“AI 没有读它”判死。** 它是机械验证依赖。

# 八、合作式 Lane 机制

Lane 机制解决多个执行器写同一共享文件的问题，但不是身份或授权系统。

核心组成：

1. `.ai/lanes/index.md`
2. `.ai/lanes/lane_epoch.yml`
3. `.ai/lanes/lane_envelope.schema.json`
4. `.ai/lanes/lane_meta.schema.json`
5. `.ai/lanes/reduce-lanes.ps1`
6. `.ai/lanes/lane-local.ps1`
7. `.ai/lanes/publish-review.ps1`
8. `.ai/lanes/tests/`

运行时还会生成：

```text
.ai/lanes/<lane_instance_id>/events/
```

其中保存事件和 envelope。

Lane 的 reducer 会读取每个 lane 的最大序号事件，并把不可变引用归并到 canonical STATE；local transport 只允许 C0 或 C1 shadow，不进入权威状态。

因此这些 Schema、脚本和测试同样是 Live，即使模型不逐一读取。

* 完整初始化新增的 6 个控制文件；
* 4 个 load profile；
* 5 个 role memory；

  * `DEFAULT_LARGE_TASK_EXECUTION_PROFILE.md`
* 条件 Long-Run 协议；

* communication compliance 的 policy、validator、Schema、fixtures 和 tests；
* lane epoch、Schema、reducer、publication helper 和 tests；
* 当前任务和 signal 实际引用的文件；
* 所有 Evidence 类文件。

## B. 不能仅凭“未加载”删除

* 测试文件；
* fixture 和 proof artifacts；
* Schema；
* validator 和 helper scripts；
* Parliament verdicts；
* execution reports 和 Human Briefs；
* 路由表和 ownership manifest；
* 当前 Profile 没有选中的其他 Profile；
* 其他角色的 role memory。

## C. 值得重点审查的候选区域

这些只是候选方向，不是删除裁决：

1. 被新版完全替代、且没有任何协议、测试或任务引用的旧协议版本；
2. 重复的临时 debug / numbered scripts；
3. 已经失效且不再被 Profile 引用的 routing memory；
4. 可以确定性重新生成、又不承担审计价值的衍生索引；
5. 错放在 core 的领域业务实现，例如待完成 ownership 迁移的 `factory_pipeline`；
6. 既不在加载闭包、也不在执行依赖、又不属于 Evidence 的文件。

## 结论

目前可以把城邦的核心机制理解为：

```text
13 个上下文边界公共控制文件
+ 每个角色 2–6 个固定扩展
+ 当前任务的动态引用
+ 条件宪法/大型任务/领域协议
+ 不进入模型上下文但会被机器执行的 validator、Schema、lanes、fixtures 和 tests
```

真正能够删除的，不是“没被 AI 读到”的文件，而必须同时满足：

```text
不可达
AND 不被任何运行机制执行
AND 不属于证据
AND 已被明确的新版本替代
AND 删除后测试与 release binding 仍然通过
```

这份盘点可以作为独立审核基线，用来检查 Codex 最终的 Live / Evidence / Dead 分类有没有遗漏控制面或把“非上下文文件”错误判成 Dead。


有。上次总结里把它埋在“任务执行协议栈”里了，没有单独突出。

## 大任务执行分两层

### 1. 普通大型任务执行方案

入口是：

```text
.ai/DEFAULT_LARGE_TASK_EXECUTION_PROFILE.md
```

它适合目标稳定、涉及多个文件、测试、修复和发布，但仍由当前 Codex/Claude Code 会话持续执行的任务。

它定义了完整流程：

```text
Human 定义目标
→ 创建任务包
→ 执行器 preflight
→ 连续实现、验证、修复
→ 提交并发布开发/审阅分支
→ exact-head 独立审核
→ 同一 task ID 内继续修正
→ 最后只把真正的保护性决策交给 Human
```

它还明确规定：

* 专用开发分支；
* 精确 source head；
* allowed/forbidden paths；
* completion-preserving；
* 显式路径暂存；
* 测试和 changed-path 验证；
* 非 force push；
* source/master 默认不可推送；
* 独立 exact-head review；
* 审核发现问题后继续原任务，不创建 `finalize`、`closure` 等伪任务。

因此这是一个**成熟的大任务作业方案**，应明确归类为 Live。

---

### 2. 真正的长周期 Program 方案

入口是：

```text
.ai/LONG_RUN_AUTONOMOUS_PROGRAM_PROTOCOL.md
```

这个比普通大型任务更接近你说的“程序方案”。它不是简单长 prompt，而是明确要求预先设计：

* Program ID；
* 完整 stage graph；
* preflight；
* 权限预授予；
* 验证模型；
* checkpoint 链；
* rollback 模型；
* issue ledger；
* 最终交付物；
* post-run repair cohorts。

其执行结构是：

```text
完整设计 Program
→ Human 一次性批准明确范围
→ 本地连续执行
→ 每阶段/每批次 checkpoint
→ 失败回滚到最近安全点
→ 非阻断问题进入 issue log
→ 最终一次性发布审阅包
→ 独立审核与定向修复
```

---

## 它已经定义的程序级机制

### Preflight

执行前必须冻结并检查：

* source branch/head；
* work branch；
  -允许阶段；
* 文件类别；
* forbidden paths；
* 所有协议和证据引用；
* corpus；
* baseline failure；
* 工具依赖；
* rollback base；
* checkpoint 路径；
* publication policy。

### Launch Packet

Program 必须有机器可读的授权结构，例如：

```yaml
program_id: "<stable-id>"
program_ref: "<path>"
source_branch: "<branch>"
source_head: "<immutable-sha>"
work_branch: "<run-branch>"
allowed_stages: [0, 1, 2]
allowed_file_classes: [...]
allowed_paths: [...]
forbidden_paths: [...]
source_push_authorized: false
```

### 本地连续运行

正式启动后：

* 中途不依赖 GitHub；
* 不 fetch、pull、push 或轮询远端；
* 只使用 preflight 固定的不可变引用；
* 所有阶段、测试、日志、commit 和 rollback 在本地完成；
* 最后只进行一次授权范围内的发布。

### Checkpoint 与回滚

每个阶段以及每批最多五项都建立 checkpoint，记录：

* 输入和输出 HEAD；
* changed paths；
* validation evidence；
* issue-log 增量；
* rollback 指令。

出现不安全修改或验证回归时，只回退最近失败 checkpoint，不丢弃其他已接受成果。

### Program 日志

每次运行建立：

```text
.ai/LONG_RUN_LOGS/<program_id>.md
```

记录：

* 数学或语义歧义；
* 跳过的受保护文件；
* 范围扩张候选；
* 延迟阶段；
* manual review；
* post-run repair 候选。

### 状态机

定义了五种最终状态：

```text
completed_clean
completed_with_review_log
completed_with_blockers
blocked_preflight
failed_and_reverted
```

---

## 但目前还缺少什么

需要区分：

> **现在有完整的 Program 协议和执行模型，但还没有一个通用的、独立运行的“大任务编排引擎”。**

现有程序化组件包括：

* 通信 validator；
* receipt 和 transition Schema；
* fixture/test runner；
* lane reducer；
* review publication helper；
* local lane transport。

但这些解决的是通信合规、状态归并和审阅发布，不是通用任务调度器。

当前没有证据表明已经存在这样一个统一程序：

```text
读取 program YAML
→ 自动解析 stage graph
→ 自动加锁
→ 调用各阶段执行器
→ 持久化 checkpoint
→ 断点恢复
→ 自动回滚
→ 自动生成最终 review package
```
