# 阶段协同推演方法论 v1

## 1. 目的与默认状态

本机制解决的不是“如何多问几个问题”，而是如何建立一个有依据、可扩展、可反驳的模型空间，
再根据该空间识别缺口、组织追问与讨论，并形成可执行、可验证、可由 Human 精确确认的结果。

默认状态为 `dormant`。简单事实查找、项目内可直接关闭的缺口、已授权的可逆机械动作、格式化与
无语义复制，不应机械启动完整讨论。无法证明简单路线足够时，不能以休眠作为默认逃逸路径。

## 2. 四层模型空间

### 2.1 通用建模 substrate

通用对象至少覆盖：

- 目标与成功义务；
- schema 字段与缺失项；
- 原子主张与证据；
- 假设与不确定性；
- 术语与范围；
- 选项、评价标准与权衡；
- 风险与失败模式；
- 角色、责任、决定权与授权；
- 产物版本、依赖与确认范围；
- 主要机制、必要细节、局部选择与范围边界。

### 2.2 workflow stage schema

每个阶段 profile 定义该阶段的 `required_model_fields`、start gate、completion gate、
讨论重点、外部行动触发器和重要信息事件触发器。阶段 schema 不能复制全局机制正文。

### 2.3 task-specific schema

当前任务还必须建模 Human 目标、成功条件、下游消费方、风险、不可逆性、权限、allowlist、
版本基线、验收和停止条件。任务包缺失这些承重字段时，不能用通用字段替代。

### 2.4 domain-specific schema

当通用、阶段与任务 schema 的联合表示能力仍不足以表达某一领域承重维度时，必须引入领域专用
schema，或把该缺口记录为 blocking gap。不得因现有字段均有值而假定模型已经充分。

## 3. schema 充分性与缺口判定

承重维度判定：

> 改变该维度，是否可能改变目标、决定、风险、测试结果、授权、依赖、版本有效性或下游验收？

若答案为“是”或未知，该维度必须进入模型。每个承重维度只能有三种合格处置：

1. `represented_with_supported_value`：有可追溯依据的表示；
2. `explicitly_irrelevant_with_reason_and_scope`：说明为什么与哪个范围无关；
3. `unknown_with_blocking_or_deferred_disposition_and_revisit_trigger`：阻断或耐久延期，并设置重访条件。

字段存在但证据不足、字段互相冲突、术语未落地、假设未标注、权限或依赖未知、schema 本身漏掉
承重维度，均属于缺口。schema 充分性未知时 fail closed。

## 4. 追问引擎

### 4.1 缺口类型

- missing field；
- unknown fact；
- unverified assumption；
- terminology ambiguity；
- claim conflict；
- insufficient evidence；
- lack of capability；
- true unknown。

`second-order detail divergence` 不属于 inquiry gap type；它是实现颗粒度分类与激活触发器，
按第 10 节生成耐久事件并进入 Human 范围裁决，不得通过扩充追问类型而静默扩大实现范围。

### 4.2 inquiry item

每个追问或行动至少绑定：

- 目标模型元素；
- 缺口类型；
- 问题或行动；
- 目标 Human、角色或信源；
- 优先级及理由；
- 预期信息价值；
- 获取成本与 Human 打断成本；
- 提问时机；
- 接受条件与证据要求；
- 停止或升级条件；
- 对下游决定、测试或授权的影响。

禁止脱离模型元素和决定影响而提问。开放语义问题默认使用可解释序数判断；只有候选域离散且类型化、
概率有合理校准、行动效用已定义且计算可审计时，才允许数值 EVPI。

### 4.3 排序

追问按依赖顺序和以下优先级排序：

1. 正确性、安全性、可测试性或集成阻塞；
2. 下游决定或权限影响；
3. 风险与不可逆性；
4. 预期信息增益；
5. 阻塞消除能力；
6. 较低的获取成本与 Human 打断成本。

## 5. 讨论引擎

完整协同建模按实际承重缺口覆盖以下检查主题；它们不是轮次配额，可以在同一轮中完成：

1. 目标、成功条件、范围和当前模型；
2. 缺口、信源、Human 行动和未知项；
3. 候选、角色、工具、拓扑和契约；
4. 证据、风险、反例、停止条件和禁止事项；
5. 最终模型、决定、版本绑定和 Human 授权。

普通承重更新检查以下两类内容，不要求拆成两个增量轮次：

1. 新信息、差异理解与影响范围；
2. 决定更新、后继版本和重新确认。

不设置固定轮数下限。是否继续讨论，由尚未关闭的承重缺口、实际证据和必要决定判断，不能用
聊天轮数证明模型就绪。复述、礼貌确认或消息拆分不产生新的就绪证据；高影响冲突仍未关闭时必须
继续处理或明确阻断，即使已经讨论多轮也不能通过。

## 6. 讨论对象与理由化处置

讨论对象包括原子主张、证据、术语、议题、立场或选项、论据、反例、异议、权衡、风险、角色、
决定权、授权、版本和依赖。

必须保持以下区分：

- 事实支持不等于共同理解；
- 共同理解不等于偏好或决定；
- 选项被选择不等于其主张为真；
- 异议被处理不等于异议被采纳；
- 多数票、票数或模型数量不等于理由化处置；
- recommendation 不等于 Human 决定或授权；
- execution complete 不等于 independent verification passed。

允许保留非阻塞分歧，但必须记录理由、残余风险和重访条件。

## 7. 激活与停止

### 7.1 模式

- `dormant`：无承重缺口且无强制触发；
- `full`：新建或结构性改变了承重模型；
- `incremental`：已知影响范围内的普通承重更新。

full 和 incremental 均不设固定讨论轮数。现有全局 active-dormant 激活不变；具体任务按当前任务
范围及 profile 的实质就绪条件执行。普通范围内工作不因模式或阶段变化重新索要已覆盖的 Human
授权；超出已有委托的新承重决定、未覆盖的受保护动作仍须取得当前规则要求的精确确认。测试通过或模型建议不能
替代这些确有要求的 Human 决定，也不能扩展任务范围。

### 7.2 停止条件

满足以下之一才可停止：

- 无 blocking gap 且必需结果完整；
- 剩余问题已耐久标记为非阻塞延期；
- 下一问题不会改变结果、测试或权限范围，且成本高于价值；
- Human 作出有效停止或范围决定；
- 问题被升级为需要 Human 裁决的二阶细节事件。

停止不能抹掉未知项、异议或残余风险。

## 8. 证据与外部行动

承重外部主张使用稳定 source ID、精确位置、访问限制、主张范围和事实/推断分离。
共享来源只计一次；报告一致不能当作独立确认；部分访问必须缩小主张范围。

外部研究、专家、NotebookLM、独立模型或实验环境在派发前必须建立精确行动模型，包含目标、问题、
输入、附件、隔离、输出契约、验收、成本、风险和停止条件，并取得 Human 授权。返回材料先归一化，
再作为重要信息事件决定是否影响既有模型。

## 9. 重要信息事件与版本控制

新证据、执行结果、审核发现或 Human 修正到达时：

1. 归一化事件并绑定精确来源；
2. 加载当前依赖图版本；
3. 分类受影响、明确不受影响和依赖未知的对象；
4. 只使受影响范围失效；
5. 对明确有理由不受影响的范围保留有效性；
6. 未知依赖对受影响进度 fail closed；
7. 创建 append-only 后继版本，并按实际影响确定哪些讨论或确认需要更新；未被实质推翻且仍覆盖当前行动的确认保留有效，不因事件到达或阶段变化一律重问。

禁止静默改写已确认 artifact，也禁止默认全局失效。

## 10. 实现颗粒度

按顺序分类：

1. main mechanism；
2. first-order required detail；
3. ordinary local choice；
4. second-order detail divergence；
5. insufficient information。

普通、局部、可逆且不改变公共契约、权限、生命周期或独立设计分支的选择，由执行模型记录后处理，
不得制造不必要的 Human 微审批。超出当前明确委托的范围、产生新状态机、协议、工具、持久 artifact family、
例外权限系统、生命周期 owner、独立测试体系或与父机制无关的新承重需求时，必须生成二阶细节事件并等待 Human。
当前任务已明确委托的架构或实现范围内，不因产物包含这些类型就再次升级授权；仍须满足既定测试、独立审核和变更边界。

## 11. 审核、执行与验证

本方法各节所称 Human 授权／确认均按当前任务范围政策解释：普通范围内工作可由已有当前 Human
任务输入及持久范围满足，不要求独立 code、nonce、重复阶段答复或新的授权层级。仅在出现未覆盖的
受保护行动、超出委托的新承重决定或范围变化时新增所需确认。该解释不豁免独立审核和验收，也不
使测试、执行者声明或模型建议成为 Human 决定。

执行必须绑定精确 task、branch、40 位 base、allowlist、Human 授权和测试契约。执行者可自检，
但不得宣称独立审核，也不得自行清除 blocker 或 major。独立审核读取 primary diff 和证据。
任何阶段的测试、审核建议或模型一致都不能自动授权机制激活或 master 集成。

## 12. profile 与实例

七个 workflow 阶段各自引用全局 profile。profile 只规定阶段重点、required model fields、
触发器和门，不复制机制正文。实例状态保存在当前 run 的阶段输出区域；canonical 目录不保存实时实例。

本机制已通过 append-only 激活状态记录进入 `active_dormant`：七个 workflow 阶段可发现并加载机制，
但默认仍走 dormant。full 或 incremental 只在命中当前 profile trigger、满足任务级 gate 与权限后启动；
全局激活不授权外部行动、不可逆操作，也不允许在 canonical 目录保存 live instance state。
