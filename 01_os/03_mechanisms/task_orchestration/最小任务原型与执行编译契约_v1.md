# Human 审定的最小任务原型与可执行计划编译 v1

**状态：候选规范；仅在 Human 审定并集成后成为 Core 正式规则。**
**适用范围：所有领域、所有规模的任务及其子任务；不局限于 NBA2K22、WorldData、某个模型或固定工具。**
本机制拓展既有 [原子任务与结果驱动执行模型](原子任务与结果驱动执行模型_v1.md)，不修改七阶段数量，也不新增每次工具调用的审批或正式工作流阶段。

## 1. 要解决的具体失败

2026-11-16 NBA2K22 T15/GE-01 失败：任务有 G/R/A/D 合同，但实际执行中的函数、环境检查、前台控制和临时脚本没有预先收敛；模型在运行中自行增加步骤。测试版 Calendar 工具把“整日全 Pending”当作必要前置，遇到 4 Final + 7 Pending 就停止；规划者又把阶段性“禁止修 Calendar”错误升级成新任务强制阻断，未及时请求 Human 裁决。即使最后发生一次模拟，也不能据此认证执行路径稳定可靠。

**错误模式：** 预先确定“做什么”，没有与 Human 确定“每个可重用动作为什么这样做，最少需要什么，怎样完成”。Loop 于是在执行中反复发明步骤。已实现的技能不复用；工具内部假设被升级为业务规则；模型把安全停止一个 Action 当成终止整个 Goal。

## 2. 对所有层级统一的任务类型

每个 Task（父任务和子任务）仍为 `T=(Goal, Ready_min, Action_bound, Done_min)`，且具有：
- **Goal**：Human 指定、能够独立核验的业务结果；父 Goal 不等于子任务返回码的汇总。
- **Ready_min**：与动作实际发生具有因果必要性的输入、真实依赖、必要环境、权限。每条标明“为何必需”“防止哪种有证据的错误”“由谁/哪个现有工具检查”；不能把可选提升为阻断。
- **Action_bound**：已审定的、版本固定的现有工具/函数/脚本，或为新能力开发而预先讨论的具体操作序列。说明步骤顺序、参数、读写副作用、可复用边界、已内置的检查；不允许执行阶段无授权再发明胶水脚本。
- **Done_min**：与 Goal 对应、下游可使用的最小充分事实和证据。包含每条为何必要、观察来源与未完成状态；不能临时增加额外 Done 条件。
- **Children / dependencies**：仅依据真实依赖进行递归组合；可以是大型研究、一次实验、一次数据采集，也可以是更小的必要操作。已经有稳定业务接口的节点不再无条件拆成几十个工具调用。

**“最小”是 Human 与 AI 经技术证据讨论后的裁决，不是 AI 自称“足够谨慎”，也不是去掉确实必要的安全边界。**

## 3. 一次审设计、多次执行实例

区分三种对象（全部复用现有任务与 Git/PRMS 位置，不新建审批平台）：

| 对象 | 谁决定 | 变更与复用 |
| --- | --- | --- |
| 任务原型（Prototype） | 模型提出每条 Ready/Done/步骤、why/basis 和已有工具绑定；Human **逐项讨论和裁决** | 最终版本以内容摘要和 Human 决策来源固定。可用于相同任务类型的多个实例 |
| 运行实例（Instance） | 领域系统依据当前 Save/日期/目标 ID 等绑定真实参数和新鲜事实 | 在审核范围内复用，不重新审阅不变的原型步骤 |
| 执行计划（Compiled Plan） | 可信 Host 将原型、子节点依赖、函数版本、参数、真实事实和当次权限绑定 | 运行时只能沿编译的 Action / 预定异常路径进行；版本/范围发生负载关键变化必须暂停受影响节点 |

**Human 设计审核不等于自动授权写入、Native 调用、发布 master、删除或其他 protected action。** 后者仍按既有 Human 权限流程就具体实例获取权限，不能因为原型“审核过”就代替。

原型的讨论可以非常细：候选步骤 1 做什么？为什么必要？能否由已有函数自动完成？与上一步重复吗？错误的概率和影响是什么？哪些属于工具内部固定验证而非 Agent 新动作？Human 可删并节点、改 Ready、确定最小 Done 和复用范围；模型需提供技术依据。**审核结论必须反映在固定原型内容里，而不是一次口头提示后下轮重犯。**

## 4. 七阶段 Workflow 的内置衔接（不增加第八阶段）

- **03 结果建模：** 决定父子任务的实际目标和独立的业务 Done；不要把技术准备变成消费者成果。
- **04 测试生成：** 约束结果正确性和必要安全的测试；冻结后执行模型不能为了通过而删改。
- **05 步骤拆分：** 对每个尚无已批准可复用原型的任务建立可讨论的 G/R/A/D、内部操作步骤、必要性与已有能力映射；Human 对首次新原型的最小条件和实际操作逐项裁决；输出已批准原型或精确 `HUMAN_REVIEW_REQUIRED` / `CAPABILITY_GAP`。已批准原型直接按版本复用。
- **05→06 执行计划编译：** 这是**阶段 05 的交付与 06 的接收条件**，不是独立阶段。使用现有已批准原型、可信决策记录和能力目录绑定成具体运行实例。可视化前的候选计划必须列出会调用什么、为何必要、哪项内部自动执行、哪些操作会产生副作用；不鼓励每轮遍历整个仓库。
- **06 执行：** Ready 实际成立便调用绑定函数，不重新决定行动语义、不生成额外开发步骤；由既有工具完成内部检查，观察真实 Done。无法绑定、合同缺陷或新危险状态时，**STOP ACTION ≠ STOP GOAL**：返回 `INCOMPLETE`、原因、证据、具体最小修复与一项 Human 决策请求。
- **07 测试执行：** 既验证结果/真实业务 Done，也核对执行轨迹中的操作是否来自批准计划；不能以测试绿、日志多、工作时长长替代业务成果。
- **内部 Loop：** 在当前已审核计划内迭代真实业务结果与允许的参数；未知环境时读新鲜事实，不为一切日常步骤重新设计。只有能力/任务语义变动才对**受影响节点**重走 Human 设计审阅和编译，未变化节点继续复用。

## 5. 每个原型的最小 Human 设计审核内容

Human 与模型讨论时至少能看见：

1. `goal` 及对上层实际结果的贡献；
2. 每条最小 `ready` 的事实、必要性、来源和是否已由工具内部覆盖；
3. `action` 的有序步骤说明、已存在的具体 callable/CLI 和版本、参数、读写副作用、是否需要人工操作；
4. 每条最小 `done` 的真实事实、来源和独立性；
5. 能力复用适用条件与失效条件、例外处理、当次需要另外取得的权限；
6. 预计的必要操作量 / 哪些动作是 Agent 会独立发起的，与可在工具内部直接自动完成的动作明确分开。

Human 可以要求删除或合并无法证明必要性的检查，但其确认不能替代对真实系统安全和工具行为的技术验证。记录 Human 对“某一步为何必需”的判定；即使模型下次换了岗位或窗口，也应复用这个决策。

## 6. 编译与执行的可检验不变量

- **已批准版本匹配：** 父子节点均有可信 Host 读取的真实 Human 审核引用，内容摘要一致；模型文本自行写 `approved: true` 无效。
- **调用绑定：** 叶节点的每个常规 Action 必须匹配真实存在、明确版本的 callable；缺函数时返回 `CAPABILITY_GAP`，而不是隐式生成新脚本或用自由 Shell 代替。
- **不重复审核：** 同一原型在范围内的参数变化只生成新的 Instance，不生成新原型或逐调用审核。
- **最小条件：** Ready/Done 由可信领域事实计算；模型不能在运行时添加强制门或放宽已批准真安全门。
- **真实 Done：** 每个父任务有独立 Done，Action 成功退出并不意味业务完成。
- **已有保护继续有效：** 写入授权、Native 安全、CAS/Outbox、发布与文件边界在原领域/Host，不由此机制生成授权；UNKNOWN 不重放。
- **工具内固定检查可很丰富：** 不等于 Human 要审核每条机器指令。Human 审核影响业务执行的条件和操作结构，必要内部安全验证由工具实现并给出职责/版本。
- **计划失效反馈：** 未完成 Goal + 真实 blocker + 影响节点 + 可行的最小变更 + Human 选择；只有 Human 终止 Goal 才是任务放弃。不能继续没有价值的准备循环。

## 7. 与现有机制与路线兼容

- PR #23 的 `Atom/Chain/Executor` 负责业务执行节点推进。候选 `reviewed_prototypes.py` 是**审定与绑定桥接**，编译后复用 PR23，不另造第二调度器。
- PR #35 `next_business_action` 是另一种选择策略；单一真实副作用动作必须只有一个执行调度方，不可双重 dispatch。使用哪一种选择器应在真实 Host 明确，选择器无权替代 Human 原型审核。
- 原有七阶段、任务包、PRMS、冻结测试、独立审核、出版及保护门保持有效；不得给每个日历模拟、采集函数调用新增 Git 工单。
- 本候选代码**不能自动接管 Codex/Claude 的任意 Shell 或 GUI 工具**。若 Host 不经过可信编译接口，现有实现只能提供引用规范、审查清单和离线验证；生产级严格限制需要真实宿主侧可执行工具白名单/权限边界。

## 8. 验收场景（跨领域）

1. Human 删除一条过度 Ready 后，原型摘要改变，旧版本不能运行；经真实审核新版后，执行不应再受该条件阻断。
2. 已批准的数据读取型原型，连续百次不同参数实例化，不重写胶水脚本、不重复向 Human 问同一设计问题。
3. 新的临时环境问题不影响已审核业务 Ready，执行模型不能自行附加新阻断条件。
4. 现有工具不支持合法输入：标记 `CAPABILITY_GAP` 并请求 Human 决定是否单独开发/改用实例；不得自行扩大任务。
5. 修改原型 Goal/Done、函数版本或关键步骤后要求审核；仅改普通实例参数时不重审。
6. 抽象父子结构任意嵌套，子节点成功而父业务结果未产生，父任务必须保持 `INCOMPLETE`。
7. 执行中工具返回 UNKNOWN，保持原有 Journal/对账边界，不盲目重放副作用。
8. 已批准原型不自动授予数据库写入、Native、Git master 发布等实例权限。

**候选接入顺序：** 先在纯离线/无副作用的跨领域虚拟案例验证原型编辑→Human 审核→编译→实例执行；确认机制和模型行为后再通过独立 Host 适配真实领域。没有 Human 通过的原型、没有真实宿主边界和运行证据，就不得声明“所有 Agent 已经被强制控制”。

## 9. Human 裁决：执行模式 / 开发模式分离（2026-11-16）

**决定：Core OS 全域任务执行的默认模式为 `EXECUTION`。** 对所有模型、领域、父任务与子任务有效。此项由 Human 明确批准；不等于已批准任何业务原型，也不构成一项 master 合并或真实 Native/文件写入的额外授权。

| 模式 | 准入与可执行操作 | 禁止 |
| --- | --- | --- |
| `EXECUTION`（默认） | 先使用 Human 审定、版本绑定的任务原型，按当次实例参数绑定已存在的能力；Loop 只调整获准的参数、读取实际反馈、推进 Done | 运行中临时发明胶水脚本、添加额外 Ready/Done、调用未注册工具、擅自写代码或自主切换为开发模式 |
| `DEVELOPMENT` | Human 已明确委托的设计/开发任务在其既有 allowed paths、受保护动作边界和测试定义内，可研究、实现新函数或调整既有实现，经独立验证后提出新原型供 Human 审定 | 把“执行中的能力缺口”自行认作开发委托，借开发模式扩权限，自动改写已冻结测试或批准过的任务原型 |

**Human 原有自然语言开发指令本身就是开发委托**；不要求增加授权码、每条命令重复审批或建立新的审批服务。可信 Host 必须从当前 Human 指令/现有任务包中确证任务范围和权限，不能把模型自述的 `mode: DEVELOPMENT` 当作凭证。

**能力缺口时的确定性路径：**

1. 暂停**受影响 Action**，保留父 `Goal=INCOMPLETE`，不要把 BLOCKED 记为 DONE。
2. 报告具体未满足的能力/版本/条件、观测证据与最小可行修复选项；不自动写脚本、不重做无关子任务。
3. Human 若授权开发，则开始具有明确范围的**新的开发会话**，开发、测试、审核相应能力；不在正在执行的实例里“切个模式继续干”。
4. 新能力被 Human 审定为可复用原型后，重新编译受影响实例，从真实已观察状态继续，UNKNOWN 按领域 Journal 对账，禁止盲目重放。

### 可调用边界（首版）

`01_os/06_execution/task_orchestration/execution_mode_gateway.py` 的 `ExecutionModeGateway`：
- 启动时从可信 Host 读取 `ModeState`；默认 `EXECUTION`。开发模式需 Host 给定任务 ID、Human 决策引用、范围引用，逐调用再次由 Host 验证具体开发工具和参数。
- `compile_execution` 只能在执行模式工作，使用 `compile_approved` 和原 PR23 `Executor`；在执行前与真正 callable 的边界再次检查 Host 模式。
- `invoke_development` 只在开发模式开放已注册的 Host 工具，调用前校验当前授权与实例范围；没有向 Shell、系统命令或自由代码生成器的默认回退。
- 会话中的模式/范围变化立即使旧会话失效；**不会**自动变更已有执行计划，恢复同样值也不重新激活已失效的会话。
- 审查用 `review_packet`、任务/模式状态与额外实例写入授权是三个不同概念；谁都不能替代另一个。

**安全边界说明：** 该入口只有在外部 Host 真正将 Agent 的全部相关动作路由到此处并限制其可用工具时，才能作为实际运行约束。它不能拦截已直接暴露给 Codex/Claude 的独立 Shell/GUI/Native 权限，更不能认证模型伪造的 Human 决策。生产“强制”声明必须有可信来源和真实 Host 工具允许/拒绝正反例；当前代码与文档仅构成**全域已批准的规范候选 + 已测 Host 适配器**，正式 master 集成、生产 Host 接管仍另行验收。


## 10. Human 补充裁决：拒绝事件记录与模型—OS 适配性（2026-11-17）

Human 明确认可**执行约束必须可观察**：每次 Host 网关拒绝某个执行请求，要留下结构化记录。如果某模型在同类任务中持续大量触发约束，说明**可能存在模型行为与 OS 原型/执行机制的冲突**，应启动针对性 Human 分析。它不是默认“模型不具备开发能力”的自动判决，也不应为此新增每条检查的人工审批。

### 最小记录边界

`execution_mode_gateway.py` 在实际经过其入口的原型编译、业务 Action 调用和开发工具调用处产生 `ADMITTED`/ `DENIED` 事件。`execution_decision_audit.py` 定义标准事件与轻量汇总。每条事件只记录：
- Host 给出的 `model_ref`、`task_id`、当前 `session_ref`、`mode`；
- `timestamp_utc`、`event_id`、`route`、`operation`（原型/能力 ID，不含敏感参数）；
- `decision`、`reason_code`、`cause`。

正常工具内部几十个检查**不逐个产生日志**；同一个已绑定 Action 的真正调用产生一次准入记录。常规 `Ready=false` 是业务状态，不是模型违规，不能当作“约束拒绝”。审核与安全拒绝不读取、上传原始 Prompt、密码、文件全文或私有 Native 参数。

| cause | 代表情形 | 是否计入模型策略冲突 |
| --- | --- | --- |
| `MODEL_POLICY` | 在 EXECUTION 反复请求开发工具，重复请求未注册/未审定的操作 | **候选冲突信号** |
| `HUMAN_PENDING` | 原型尚未经 Human 审核、开发范围/实例授权缺失 | **不能直接归咎模型** |
| `SYSTEM_GAP` | 原型已批准但既有 callable 不存在或版本不一致 | **能力缺口，不是模型不服从** |
| `HOST_STATE` | Human 撤销、模式/范围/会话发生变化 | **状态变更，不是模型策略冲突** |

### 汇总与 Human 判断

按相同模型、任务类型、原型版本、运行模式、工具访问条件和观测窗口比较；不同任务难度与宿主授权不能混算。统计总请求、准入、拒绝、原因分布、重复拒绝理由与 `MODEL_POLICY` 拒绝率。计算方式：

```text
同口径模型策略拒绝率 =
  MODEL_POLICY 拒绝事件数 ÷ 同口径可观测网关请求数
```

`summarize()` 可按 `model_ref/task_id/route` 过滤、基于 event_id 去重，并在样本足够且所选阈值触发时返回 `REVIEW_MODEL_OS_FIT`。目前函数默认 `min_attempts=10`、比率 30%、同理由重复 3 次，**仅为可测试的预警参数示例，不是 Human 已批准的正式纪律阈值**。未来可以按实际模型任务样本由 Human 裁定。

发现拒绝过高时 Human 先分析：
1. 模型是否持续越过明示计划（真正的适配性或遵循性问题）。
2. 原型是否设定了错误的 Ready/Done 或重复检查（OS 设计问题）。
3. 领域能力是否缺失、Host 目录是否注册错误或授权尚未签收（工程集成问题）。

**预警只用于回看，不自动禁用模型、降低安全要求或重启/终止任务。** 已经被拒绝的操作仍严格拒绝。阈值判断必须有足够分母和同任务对照，避免把单次合法阻断或大量正常内部检查算成“模型冲突”。

### 真正落盘与可观测范围

可信 Host 可通过 `append_jsonl_sink(existing_host_path)` 将事件逐条追加到**由 Host 拥有权限的**本地 JSONL；`load_jsonl`、`summarize` 只读聚合。对于应执行的受控工具调用，Host 若无法写入要求的审计记录，则不得静默继续。文件位置与访问权限由 Host 现有运行空间指定；**不建立新监控平台、不向 GitHub 上传私有全量日志、不进行后台轮询或每轮增加额外检查。**

测试期缺少 Host sink 时仅留有**进程内审计副本**，不算跨窗口持久记录。当前 PR #37 的代码与 Windows 离线测试**不能证明所有 Claude/Codex 调用已被捕获**：若实际 Host 仍向模型直接暴露 Shell/GUI，网关未见的动作就不能计入分母。必须在后续真实 Host 入口接入、验证日志完整性后，才可以进行正式的模型与 OS 适配性比较。


## 11. Human 最新裁决：信任 Agent、如实自报、适度约束（2026-11-17）

**本节优先于第 9–10 节中可能被理解为“必须全面监管 Agent”的表述。**

Human 明确：OS 设计首先信任 Agent 会承认错误、诚实输出、积极配合既定任务原型。双方对执行步骤、Ready/Done、Loop 边界的约定是一种**协作纪律**，不是对模型动机的怀疑。权限与行为纪律是两种不同的问题；权限仍受已有 Human 指令和受保护操作边界约束，但**不得把全面限制/监视模型的所有 Shell、GUI 当作实现任务纪律的先决条件**。

### 最小协作协议

1. **执行前达成共识**：Human 与 Agent 首次共同设计任务原型、最小必要操作、如何自动化、哪些步骤属于过度检查；记录已经达成的裁决，后续复用。
2. **执行中自律**：Agent 按已批准原型和开发/执行模式工作，允许发现事实与主动提出改进；遇到需要改变已审定条件、附加新步骤或改变权限的情况，应暂停相关操作并解释。
3. **发现偏差时主动自报**：Agent 即使在 Host 无法观察的地方发现自己多做了检查、临时编写了胶水、错误升级了前置条件、误判了 Done，仍主动说明：做了什么、为什么、对实际业务结果有何影响、如何纠正、是否需要 Human 决定。**事前发现可先报告而不执行；事后发现应承认并报告，不隐藏也不美化结果。**
4. **保留原生权限边界**：自报不等于有权限执行受保护动作；既有 Native/文件/发布等授权与安全检查独立生效。
5. **不过度监控**：无需增加逐指令监测、全局 Shell 接管、日常行为审计或逐次 Human 审批。正常完成的已审定步骤不产生额外自报；仅在发现有意义的偏差、问题或可重用改进时报告。
6. **建设性复盘**：Human 首先区分模型误解、原型不完善、环境异常与工具缺口。Agent 主动坦诚报告是积极的纠错证据，**不应自动计作拒绝、违规、不服从，也不应自动触发模型禁用或惩罚**。

### 两类记录与指标严禁混淆

| 来源 | 含义 | OS 处理 |
| --- | --- | --- |
| `HOST_OBSERVED` | 网关实际准入/拒绝的工具调用 | 保留事实与原因，按有明确分母的同口径事件分析 |
| `AGENT_SELF_REPORT` | Agent 对自己行为或认识的主动陈述，包括 Host 不可见的偏差 | 独立记录、鼓励自纠、帮助 Human 改进原型；不得伪称为 Host 已验证的事实 |

`agent_self_report.py` 提供独立 `AgentSelfReport`、可选 JSONL 追加与只读统计，**不继承 `GatewayEvent`**。它的统计不与第十节 `MODEL_POLICY` 拒绝率混算。Agent 如实报告的次数增加，可能代表更诚实的自我审查，而非更差的执行能力。没有自报也不能推定“未发生任何偏差”。

报告可以优先写入当前任务的既有聊天、Run/PRMS 或 Git 检查点；使用 JSONL 只是一个可选承载形式。**缺少可写 JSONL 不能成为正常业务执行的新增阻断**。简述事实即可，不记录隐私、密码或完整模型推理，也不建立新独立监控系统。

### 技术边界（不改变信任立场）

当前 callable 网关仍可对接入它的调用施加确定性约束并留有拒绝回执；这是对已承诺执行合同的程序化落实，并非“看守”。对于未经过网关的动作，**Agent 自报可以承担协作记录功能**，但不能被错误宣称为 Host 可验证的全面工具监测。权限保护的技术执行与 Agent 工作纪律的诚信前提不相互替代。

**新版执行验收不以“已接管所有模型工具权限”为单一完成门槛**：可先验证 Human+Agent 共同审阅原型、按已审定步骤执行、真实 Done，以及发现偏差时主动自报。只有在实际风险/授权要求确需技术隔离的具体宿主或操作上，才要求更强的权限实现；这不得自动扩大为全领域通用强制沙箱项目。
