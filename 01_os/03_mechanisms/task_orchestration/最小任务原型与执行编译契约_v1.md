# Human 审定的最小任务原型与可执行计划编译 v1

**状态：候选规范；仅在 Human 审定并集成后成为 Core 正式规则。**
**适用范围：所有领域、所有规模的任务及其子任务；不局限于 NBA2K22、WorldData、某个模型或固定工具。**
本机制拓展既有 [原子任务与结果驱动执行模型](原子任务与结果驱动执行模型_v1.md)，不修改七阶段数量，也不新增每次工具调用的审批或正式工作流阶段。

## 1. 要解决的具体失败

2026-11-16 NBA2K22 T15/GE-01 失败：任务有 G/R/A/D 合同，但实际执行中的函数、环境检查、前台控制和临时脚本没有预先收敛；模型在运行中自行增加步骤。测试版 Calendar 工具把“整日全 Pending”当作必要前置，遇到 4 Final + 7 Pending 就停止；规划者又把阶段性“禁止修 Calendar”错误升级成新任务强制阻断，未及时请求 Human 裁决。即使最后发生一次模拟，也不能据此认证执行路径稳定可靠。

**错误模式：** 预先确定“做什么”，没有与 Human 确定“每个可重用动作为什么这样做，最少需要什么，怎样完成”。Loop 于是在执行中反复发明步骤。已实现的技能不复用；工具内部假设被升级为业务规则；模型把安全停止一个 Action 当成终止整个 Goal。

## 2. 对所有层级统一的任务类型

每个 Task（父任务和子任务）仍为 `T=(Goal, Ready_min, Action_bound, Done_min)`，且具有：
- **Goal**：Human 指定、能够独立核验的业务结果；父 Goal 不等于子任务返回码的汇总。
- **Ready_min**：与动作实际发生具有因果必要性的输入、真实依赖、必要环境、权限。每条标明“为何必需”“防止哪种有证据的错误”“由谁/哪个现有工具检查”；不能把可选提升为阻断。
- **Action_bound**：已审定的、版本固定的现有工具/函数/脚本，或为新能力开发而预先讨论的具体操作序列。说明步骤顺序、参数、读写副作用、可复用边界、已内置的检查；不允许执行阶段无授权再发明胶水脚本。
- **Done_min**：与 Goal 对应、下游可使用的最小充分事实和证据。包含每条为何必要、观察来源与未完成状态；不能临时增加额外 Done 条件。
- **Children / dependencies**：仅依据真实依赖进行递归组合；可以是大型研究、一次实验、一次数据采集，也可以是更小的必要操作。已经有稳定业务接口的节点不再无条件拆成几十个工具调用。

**“最小”是 Human 与 AI 经技术证据讨论后的裁决，不是 AI 自称“足够谨慎”，也不是去掉确实必要的安全边界。**

## 3. 一次审设计、多次执行实例

区分三种对象（全部复用现有任务与 Git/PRMS 位置，不新建审批平台）：

| 对象 | 谁决定 | 变更与复用 |
| --- | --- | --- |
| 任务原型（Prototype） | 模型提出每条 Ready/Done/步骤、why/basis 和已有工具绑定；Human **逐项讨论和裁决** | 最终版本以内容摘要和 Human 决策来源固定。可用于相同任务类型的多个实例 |
| 运行实例（Instance） | 领域系统依据当前 Save/日期/目标 ID 等绑定真实参数和新鲜事实 | 在审核范围内复用，不重新审阅不变的原型步骤 |
| 执行计划（Compiled Plan） | 可信 Host 将原型、子节点依赖、函数版本、参数、真实事实和当次权限绑定 | 运行时只能沿编译的 Action / 预定异常路径进行；版本/范围发生负载关键变化必须暂停受影响节点 |

**Human 设计审核不等于自动授权写入、Native 调用、发布 master、删除或其他 protected action。** 后者仍按既有 Human 权限流程就具体实例获取权限，不能因为原型“审核过”就代替。

原型的讨论可以非常细：候选步骤 1 做什么？为什么必要？能否由已有函数自动完成？与上一步重复吗？错误的概率和影响是什么？哪些属于工具内部固定验证而非 Agent 新动作？Human 可删并节点、改 Ready、确定最小 Done 和复用范围；模型需提供技术依据。**审核结论必须反映在固定原型内容里，而不是一次口头提示后下轮重犯。**

## 4. 七阶段 Workflow 的内置衔接（不增加第八阶段）

- **03 结果建模：** 决定父子任务的实际目标和独立的业务 Done；不要把技术准备变成消费者成果。
- **04 测试生成：** 约束结果正确性和必要安全的测试；冻结后执行模型不能为了通过而删改。
- **05 步骤拆分：** 对每个尚无已批准可复用原型的任务建立可讨论的 G/R/A/D、内部操作步骤、必要性与已有能力映射；Human 对首次新原型的最小条件和实际操作逐项裁决；输出已批准原型或精确 `HUMAN_REVIEW_REQUIRED` / `CAPABILITY_GAP`。已批准原型直接按版本复用。
- **05→06 执行计划编译：** 这是**阶段 05 的交付与 06 的接收条件**，不是独立阶段。使用现有已批准原型、可信决策记录和能力目录绑定成具体运行实例。可视化前的候选计划必须列出会调用什么、为何必要、哪项内部自动执行、哪些操作会产生副作用；不鼓励每轮遍历整个仓库。
- **06 执行：** Ready 实际成立便调用绑定函数，不重新决定行动语义、不生成额外开发步骤；由既有工具完成内部检查，观察真实 Done。无法绑定、合同缺陷或新危险状态时，**STOP ACTION ≠ STOP GOAL**：返回 `INCOMPLETE`、原因、证据、具体最小修复与一项 Human 决策请求。
- **07 测试执行：** 既验证结果/真实业务 Done，也核对执行轨迹中的操作是否来自批准计划；不能以测试绿、日志多、工作时长长替代业务成果。
- **内部 Loop：** 在当前已审核计划内迭代真实业务结果与允许的参数；未知环境时读新鲜事实，不为一切日常步骤重新设计。只有能力/任务语义变动才对**受影响节点**重走 Human 设计审阅和编译，未变化节点继续复用。

## 5. 每个原型的最小 Human 设计审核内容

Human 与模型讨论时至少能看见：

1. `goal` 及对上层实际结果的贡献；
2. 每条最小 `ready` 的事实、必要性、来源和是否已由工具内部覆盖；
3. `action` 的有序步骤说明、已存在的具体 callable/CLI 和版本、参数、读写副作用、是否需要人工操作；
4. 每条最小 `done` 的真实事实、来源和独立性；
5. 能力复用适用条件与失效条件、例外处理、当次需要另外取得的权限；
6. 预计的必要操作量 / 哪些动作是 Agent 会独立发起的，与可在工具内部直接自动完成的动作明确分开。

Human 可以要求删除或合并无法证明必要性的检查，但其确认不能替代对真实系统安全和工具行为的技术验证。记录 Human 对“某一步为何必需”的判定；即使模型下次换了岗位或窗口，也应复用这个决策。

## 6. 编译与执行的可检验不变量

- **已批准版本匹配：** 父子节点均有可信 Host 读取的真实 Human 审核引用，内容摘要一致；模型文本自行写 `approved: true` 无效。
- **调用绑定：** 叶节点的每个常规 Action 必须匹配真实存在、明确版本的 callable；缺函数时返回 `CAPABILITY_GAP`，而不是隐式生成新脚本或用自由 Shell 代替。
- **不重复审核：** 同一原型在范围内的参数变化只生成新的 Instance，不生成新原型或逐调用审核。
- **最小条件：** Ready/Done 由可信领域事实计算；模型不能在运行时添加强制门或放宽已批准真安全门。
- **真实 Done：** 每个父任务有独立 Done，Action 成功退出并不意味业务完成。
- **已有保护继续有效：** 写入授权、Native 安全、CAS/Outbox、发布与文件边界在原领域/Host，不由此机制生成授权；UNKNOWN 不重放。
- **工具内固定检查可很丰富：** 不等于 Human 要审核每条机器指令。Human 审核影响业务执行的条件和操作结构，必要内部安全验证由工具实现并给出职责/版本。
- **计划失效反馈：** 未完成 Goal + 真实 blocker + 影响节点 + 可行的最小变更 + Human 选择；只有 Human 终止 Goal 才是任务放弃。不能继续没有价值的准备循环。

## 7. 与现有机制与路线兼容

- PR #23 的 `Atom/Chain/Executor` 负责业务执行节点推进。候选 `reviewed_prototypes.py` 是**审定与绑定桥接**，编译后复用 PR23，不另造第二调度器。
- PR #35 `next_business_action` 是另一种选择策略；单一真实副作用动作必须只有一个执行调度方，不可双重 dispatch。使用哪一种选择器应在真实 Host 明确，选择器无权替代 Human 原型审核。
- 原有七阶段、任务包、PRMS、冻结测试、独立审核、出版及保护门保持有效；不得给每个日历模拟、采集函数调用新增 Git 工单。
- 本候选代码**不能自动接管 Codex/Claude 的任意 Shell 或 GUI 工具**。若 Host 不经过可信编译接口，现有实现只能提供引用规范、审查清单和离线验证；生产级严格限制需要真实宿主侧可执行工具白名单/权限边界。

## 8. 验收场景（跨领域）

1. Human 删除一条过度 Ready 后，原型摘要改变，旧版本不能运行；经真实审核新版后，执行不应再受该条件阻断。
2. 已批准的数据读取型原型，连续百次不同参数实例化，不重写胶水脚本、不重复向 Human 问同一设计问题。
3. 新的临时环境问题不影响已审核业务 Ready，执行模型不能自行附加新阻断条件。
4. 现有工具不支持合法输入：标记 `CAPABILITY_GAP` 并请求 Human 决定是否单独开发/改用实例；不得自行扩大任务。
5. 修改原型 Goal/Done、函数版本或关键步骤后要求审核；仅改普通实例参数时不重审。
6. 抽象父子结构任意嵌套，子节点成功而父业务结果未产生，父任务必须保持 `INCOMPLETE`。
7. 执行中工具返回 UNKNOWN，保持原有 Journal/对账边界，不盲目重放副作用。
8. 已批准原型不自动授予数据库写入、Native、Git master 发布等实例权限。

**候选接入顺序：** 先在纯离线/无副作用的跨领域虚拟案例验证原型编辑→Human 审核→编译→实例执行；确认机制和模型行为后再通过独立 Host 适配真实领域。没有 Human 通过的原型、没有真实宿主边界和运行证据，就不得声明“所有 Agent 已经被强制控制”。
