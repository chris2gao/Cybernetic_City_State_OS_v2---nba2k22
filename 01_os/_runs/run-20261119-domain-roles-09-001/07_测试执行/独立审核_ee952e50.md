## 5. Findings

### F1（阻断，FIX_REQUIRED）：新规则说“条目怎么写由领域自定，core 不规定”，但 core 的 PRMS 实际强制 `domain_mechanisms.yml` 的条目格式

**位置**：`01_os/05_registry/skills_v1.yml` 中 `os-domain-content.boundaries` 新增的第 3 条（ee952e50 diff 第 316 行附近），以及生成的 `.agents/skills/os-domain-content/SKILL.md`、`.claude/skills/os-domain-content/SKILL.md` 最后一行。原文：

> 在 09 的 domain_mechanisms.yml 找该角色的条目，按条目读取正文；**条目怎么写**、角色规则是什么**由领域自定，core 不规定**

**primary evidence**：`01_os/06_execution/boot/context_management/prms/catalog.py` 的 `discover_g2`（候选第 121–150 行）。它是同一个 skill 的“命令”一节列出的 `prms … domain` G2 发现入口。代码强制的约束有：

- 每个条目必须有 `mechanism_id`（不能缺、不能重复）；
- `domain_id` / `repo` 必须与本领域一致；
- 必须有 `content_path`、`canonical_blob`、`owner`、`publication_status`、`version`、`applicability`、`dependencies`、`evidence_refs`；
- `content_path` 必须位于领域根下。

任何一条不满足都会抛 `PRMSError("REJECTED")`。异常在循环里抛出，所以**一个不合格的条目会让整个领域目录的发现失败**，不只是跳过这一条。

**可复现探针**：`probe_role_entry_ee952e50.py`（与本报告同目录）。它建一个隔离的临时领域 git 仓，对候选中的 PRMS 运行两次：

```text
python -I -B probe_role_entry_ee952e50.py <cand>/01_os/06_execution/boot/context_management/prms
A_free_format: PRMSError REJECTED: missing/duplicate G2 identity
B_g2_envelope: CATALOG_DISCOVERED_NOT_ACTIVATED ['G2:role-teacher']
```

- A：领域按“条目怎么写由领域自定”自选格式，写成 `{role: 数学教学, path: …}`，结果被 core 拒绝。
- B：同一个角色套用现有的 G2 条目字段，可以被发现。

**影响**：

- `role-content-developer` 加载 `os-domain-content` 后，会按这句话去写领域角色条目。照字面执行，写出的条目会让 core 自带的领域目录发现失败。
- Human 第 1 条说“我们只是给他们提供了这个框架”，而 G2 条目字段正是 core 提供的框架。说它“不规定”是一条与代码矛盾的 canonical 陈述。这违反 R4，也违反开发入口 §12 “与 canonical 定义冲突时不得静默选择”的精神。
- 次要问题：G2 条目没有“角色”字段，“找该角色的条目”应该按什么匹配（`mechanism_id`？`applicability`？）没有说明。这本可以合理地留给领域决定，但规则应当明说这一点由领域决定，而不是暗示格式完全自由。

**建议的最小修复**（措辞由执行者定，审核不规定）：把这一句改成类似“条目沿用 `domain_mechanisms.yml` 现有的条目格式（PRMS G2 字段）；哪个条目对应哪个角色、角色规则是什么，由领域自定，core 不规定”。然后运行 `generate_skills.py`，再跑同一套 8 项检查。四个入口文件没有对条目格式作任何断言，不需要改。
