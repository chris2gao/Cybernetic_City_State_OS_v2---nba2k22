## 1. 测试从哪里推导

派单的定义性规则是"测试由 A + evidence 推导，不由 B 推导"。本包据此把每一条检查
绑到 A 的成功判据（A01–A14）与 Stage 02 证据 claim（E-001–E-010 / I01–I10），并在
`04_tests.yml` 中逐条写出。B 只用于识别候选结果面，不作为通过条件。

具体做法：

- **不冻结 B 的命名。** B 提议机制名 `role_window_integration` 与中文文件名
  （`角色契约_v1.yml` 等）。本包的 good-tree overlay 故意使用另一个机制名
  `window_role_binding` 和另一套文件名（`roles_v1.yml` / `windows_v1.yml` /
  `handoff_v1.yml`）。overlay 全绿即证明检查没有编码 B 的命名偏好。
- **冻结的是三件事**：
  1. 三个 document-kind token，取自 A 自己的词汇——A R01 "role contract"、
     A R02 "window/session identity"、A R09 "structured handoff"——放进本仓已有的
     `schema_version` 约定，即 `<mechanism>.role_contract.v*`、
     `<mechanism>.window_contract.v*`、`<mechanism>.handoff_contract.v*`；
  2. 本仓自己的全局机制 pointer 约定（`context_management`、`model_routing`、
     `communication_system` 三次一致印证）：`01_os/03_mechanisms/<m>/`、
     `01_os/02_boot/<m>/`、`01_os/05_registry/<m>_v*.yml`、
     `01_os/06_execution/boot/<m>/`；
  3. A 要求的语义内容，用概念正则匹配，不绑定具体字段名。

机制目录由**内容发现**：扫描 `01_os/03_mechanisms/*/`，取唯一一个同时声明三个 token
的目录。找不到、或找到多于一个，都是失败。

## 3. 词法扫描的假阳性边界

派单要求"任何词法扫描必须区分证据/来源引用与运行期语义，并记录假阳性边界"。这是
T1 在 MR-T25 上真实踩到过的坑（`PRICING` 子串误判）。本包的处理：

- **禁止项一律按 key 位置判定，不按原文子串判定。** `key_positions()` 只看叶子 key
  名是否命中模式，且只在**值为真**时报告。一份写着
  `automatic_task_progression: false` 的文档是合规的，不是违规的；散文正文永远不被
  扫描。
- **"第二份角色表"需要同时满足两个条件**：mapping 的 key 覆盖 ≥3 个角色概念，
  **并且**其条目本身携带 per-role 属性（≥3 个条目各命中 ≥2 个属性概念）。只有第一个
  条件时，一份 model catalog 或 stage profile 集合会被误报。以 stage id 形态开头的
  key（`^\d{2}_`、`workflow_stage`、`stage`、`step`）被排除。
  - 实测的两处**真阴性**：`01_os/02_boot/协作伙伴.md` 的名册表首列是产品名
    （不命中角色概念）；`communication_system/角色与权限边界_v1.yml` 的
    `sender_task_role` 等是消息字段而非角色表（结构化条目不足 3）。
- **provider 名称检查只作用于 role contract 本身**（RW-T19），因为 A 约束的是
  "role architecture 不得写死 provider"。`02_boot/协作伙伴.md` 里的产品名不在此列，
  `开发入口` §7.1 的模型档位表属于 model_routing 的所有权范围（A 的
  explicit_out_of_scope 明确排除 model catalog 重设计），本包不冻结它。

## 5. good tree 与 mutation

good tree = **被测仓库树 + 一份声明式 delta**：

- 新增文件 `fixtures/overlay/**`；
- 对已存在文件的三处编辑 `fixtures/overlay_edits_v1.yml`（X01 working discipline
  角色表变 pointer；X02 context boot 去掉 `_dev` 角色源；X03 机制索引加一行）。

不把 300 行的 `AGENT_WORKING_DISCIPLINE.md` 整份复制进 fixture，是为了避免 fixture
里出现第二份会与真文件漂移的权威副本。

树被复制后重新 `git init/add/commit`：`verify_context_structure.py` 会调用
`git ls-files` 与 `git check-ignore`，没有 index 时它报告的是环境错误而不是机制结论。

42 条 mutation，每条把 good tree 改成"看起来完整但违反一条已接受要求"的树，必须让
目标检查变红。顺带变红的其他检查（collateral）记录但不计失败：一处违规常常同时破坏
多个契约面。特别地，让机制自带 validator 变红的 mutation 会必然让六条 validator 探针
一起红——探针的基线本身已经失败时，它证明不了任何事。

`RW-T37`–`RW-T42` 的 mutation 直接改 fixture validator 的判定逻辑（把某个条件改成
`if False:`），这是唯一能证明"探针不是恒真"的方式。

## 6. 空树与半树探针

- **空树**：只有 `RW-T05`、`RW-T31` 允许为绿——纯禁止性命题在空树上真空成立，这是
  正确语义，它们的非真空性由各自的 mutation 证明。其余任何检查在空树上变绿都属于
  真空存在性断言。
- **半树**（good tree 删掉 boot 目录与 registry）：`RW-T28/T29/T34/T37…T42` 必须红。
  没有 boot 清单就没有声明的加载面，探针无从谈起。
