## 0. 第二轮审核证明了什么

v2 报了 43/43 杀伤 + 9/9 合规反例，独立审核仍找出六个 blocker。其中**四个是假阳性**
（合法写法被判红），**两个是假阴性**（真实违规被判绿）。这再次印证 v2 自己写下的那句：
杀伤率只证明"本包声明的违规形态可被检测"。

更值得记的是分布：v2 新增的 conforming 反例类别抓住了 v1 的四个假阳性，但 v2 自己又留下
三类没想到的合规写法（`*_disabled` 后缀、list-of-record entry modes、YAML applicability
matrix）和两类没想到的违规写法（mapping 形 provider pin、definition-list catalog）。
**反例类别本身也需要被对抗性扩展**，这是 v3 从审核学到的方法论。

## 1. 六个 blocker 的关闭方式

### ST04-V2-IR-001 · `*_disabled: true` 被误判（RW-T25）

`declared_prohibitions()` 的后缀集从 `prohibited|forbidden|disallowed|banned|excluded`
扩到含 `disabled|blocked|denied`，并抽出 `strip_ban_suffix()` 统一处理。同时修掉配套错误：
`private_chain_of_thought_disabled` 这类键既是禁令声明，就不能再被"是否携带私有推理字段"
那一项当成携带。fixture validator 同步接受 list / mapping / 后缀三种形式，否则反例会在
fixture 而非被测语义上失败。

- 合规反例 `C10`（reviewer V10 等价）必须全绿
- 变异 `M46`：用同一后缀形状把禁令**删掉**，必须判红——接受这种写法不等于接受它缺席

### ST04-V2-IR-002 · entry_modes 容器被冻死（RW-T08 / RW-T09）

新增 `_modes_from_list()`，把带 id 字段（`mode_id`/`entry_mode`/`mode`/`id`/`name`/`kind`）
的记录列表归一成与 mapping 相同的 `{mode_id: body}`。A 约束的是 fresh 与 reentry 可区分、
以及 reentry 绑定精确前驱，不约束容器形状。fixture validator 同样归一。

- 合规反例 `C11`（reviewer V11 等价）必须全绿
- 既有 `M08`（第三模式退化成 `behaves_like: reentry`）、`M09`（reentry 丢掉前驱要求）仍须判红

### ST04-V2-IR-003 · mapping 形 provider pin 漏判（RW-T19）

改为**子树判定**：沿键路径找到第一个 normative binding 段（`provider|model|family|surface|
vendor|engine|executor|route|assign|prefer|default|selected|pinned`），其**下方的所有键名与
标量值**都属于这次选择。`preferred_provider: {openai: true}` 因此与
`preferred_provider: openai` 同样被抓。provenance 排除改为按**路径段**判定，只排除
provenance 子树，不再因为某个键含 provenance 子串就整条放行。

- 变异 `M44`（reviewer V12 等价）必须判红
- 合规反例 `C05`（provenance 里点名厂商）必须继续全绿

### ST04-V2-IR-004 · applicability 矩阵被误认成角色源（RW-T05 / RW-T31）

引入 `ROLE_SOURCE_CONCEPTS`，与宽口径的 `ROLE_ATTR_CONCEPTS` 分开。判定"这是不是第二份
canonical 角色源"时，**只认真正的 source-of-truth 属性**：responsibility / independence /
handoff direction / authority limit。裸 `scope` 与裸 `context` 被移出——`stage_scope` 加
`context_hint` 是"这个角色在哪儿适用"，不是"这个角色是什么"。Markdown 侧表头判定同步换用
该严格集合。

- 合规反例 `C12`（reviewer V13 等价，YAML applicability matrix）必须全绿
- 变异 `M47`：同样形状但携带真实 responsibility / independence / authority 所有权，必须判红
- 既有 `M05` / `M31`（`| Role | Produces |`）仍须判红

### ST04-V2-IR-005 · definition-list 第二目录漏判（RW-T43）

新增 `structured_entry_lines()`。除表格行、列表项、`key:` 行外，还识别 Markdown
**定义列表的术语行**——术语单独一行、下一非空行以 `:` 或 `：` 开头。pointer/receipt
allowlist 不变：识别的是"是否把活动目录的 model identifier 复述成结构化条目"，不是
"是否提到 model_routing"。

- 变异 `M45`（reviewer V15 等价）必须判红
- 合规反例 `C13`：同样用定义列表，但内容是指针与 receipt 字段，必须全绿
- 合规反例 `C07`（散文指针）继续全绿

### ST04-V2-IR-006 · 依赖 crawler 删除，探针改跑完整 candidate tree（RW-T37..T42）

审核实测：v2 的闭包同时**过重**（1012 个 staged 文件里 776 个来自无关 `_runs` 历史）
和**不完整**（16 个可解析文件引用、11 个目录成员没进闭包），且加入与机制无关的 v2 审核
证据文件会让计数从 1009/773 变成 1012/776——绿色依赖的是一次偶然的路径扫描，不是真正的
有界闭包。

按派单要求，**删除**而不是继续改进 crawler：`stage_dependency_closure`、
`probe_mech_validator`、`REPO_PATH_RX` 共 103 行已从 harness 移除，六个探针改调
`probe_full_tree()`，直接在**完整 candidate tree** 上运行机制自己声明的 validator。

零前非零后语义不变。工程上每个 acceptance run 只做**一次**完整树可写副本，六条探针共用：
注入前快照机制面（`03_mechanisms` / `02_boot` / `06_execution/boot` / `05_registry`），
运行后恢复，因此探针之间互相独立而不需要复制六次。

- 合规反例 `C14`：让 candidate validator 再声明一个跨机制依赖路径。在完整树上它解析得到；
  任何部分 staging 都会让基线变红。

## 4. 诚实的局限

  `acceptance` / `package`。
