## 1. 六个 blocker 的关闭方式

### ST04-IR-001 · A11 model-catalog thinness

新增 `RW-T43`。判定是 ownership-aware 的：

- **允许**：指向 `01_os/03_mechanisms/model_routing/**` 的 pointer、调用其 boot validator、
  引用 receipt 字段名。这些正是 A11 要求 workflow 做的事。
- **禁止**：把活动目录 `模型与产品面目录_v1.yml` 的 ≥3 个 model identifier 以**结构化条目**
  （表格行、列表项、YAML 键）复述在 `01_os/01_workflow/**` 或稳定入口里；或某文档自称
  `model_routing.catalog.v` schema。
- identifier 从被测树的活动目录读取，不写死型号名——目录变了检查跟着变。
- 反例 `C07`（pointer + receipt 字段引用）必须绿；变异 `M43`（在阶段 README 里加一张
  型号价格表）必须红。

### ST04-IR-002 · 不再强制 `forked_successor`

`RW-T08` 重写。A02 要求的是 `fresh` 与 `reentry` 可区分；E-003 说 lifecycle **可以**建模
forked successor，没有说必须。v2 的判定：

- 必须同时声明 fresh 与 reentry（名称按概念匹配，允许 `re-entry`/`re_entry`）；
- 第三种模式**可有可无**。若存在，才检查它的语义：必须声明自己的 window identity，且必须
  指明它从哪个窗口派生——即不得冒充 reentry；
- 单纯改名不再是缺陷。反例 `C08`（完全没有第三种模式）与 `C09`（第三种模式改名为
  `分叉后继`）必须绿；变异 `M08`（第三种模式退化成 `behaves_like: reentry`、没有自己的
  身份）必须红。

fixture validator 同步放宽，否则 C08/C09 会在 fixture 而不是在被测语义上失败。

### ST04-IR-003 · 去掉 schema-version document-kind 冻结

v1 只认 `<mech>.role_contract.v` / `window_contract.v` / `handoff_contract.v` 三个英文
子串，等于把文档种类的**命名**冻死了。v2 改为两条并行的 naming-neutral 发现路径：

- **路由 (a) 声明式**：boot 清单或 registry 的条目用**描述性字段**（`purpose`、
  `artifact_kind`、`document_kind`、`description`、`用途`…）说明该文档是什么。
- **路由 (b) 内容式**：文档自身的内容说明它是什么——role 契约是"≥5 个角色条目、覆盖 ≥4 个
  角色概念、每条带 per-role 属性"；window 契约是"有 window identity 且同时定义 fresh 与
  reentry"；handoff 契约是"某个键路径同时点名 handoff 与它必须携带的字段"。

**内容证据优先于描述性措辞。** 这条不是风格选择：boot 清单里 "structured cross-window
handoff contract" 这句话同时含 handoff 与 window 两个词，若按措辞先到先得，handoff 文档
会被误当成 window 契约。

同样重要的一个反面教训写在代码里：路由 (a) 的描述性 blob **必须排除 `path` 值**。第一版
修正把整条 entry 的所有字符串拼进 blob，于是目录名 `window_role_binding` 里的 "role" 和
"window" 让每个文件都自称是角色契约和窗口契约，43 条里 15 条无声地绑错了文档。现在
blob 只取描述性键，并丢弃任何含 `/` 的 token。

反例 `C01`（schema_version 改成 `wrb.契约.甲/乙/丙.v1`，同时把 boot purpose 改成不表态的
"canonical document one/two/three"，只剩内容路径可用）与 `C02`（文件改名为
`doc_a/b/c.yml`）必须绿。

fixture validator 也改成按内容分类——否则 C01 会在 fixture 的 token 匹配上失败，而不是在
被测的发现逻辑上通过。

### ST04-IR-004 · polarity / structure / provenance 误伤

三处独立修正：

**极性。** `enabled_positions()` 取代 `key_positions()`。键名自带否定标记
（`_prohibited`、`_disabled`、`_forbidden`、`_denied`、`never`、`no_`、`not_`…）的位置一律
跳过——在那里写 `true` 是**声明禁令成立**，不是打开行为。值也做同样处理：
`prohibited` / `disabled` / `none` / `never` 等一律不算 truthy。反例 `C03` 写满
`automatic_task_progression_prohibited: true`、`quota_probe_prohibited: true`、
`retention_policy_disabled: true` 必须绿；变异 `M26/M34/M35/M36`（真正打开
`automatic_task_progression: true`、`background_processes_started: true`、
`quota_probe_enabled: true`、`retention_policy_active: true`）必须红。

**结构。** `RW-T25` 的禁止字段声明改用 `declared_prohibitions()`，同时接受三种等价写法：
列表项、mapping（`{field: true}`）、以及 `<field>_prohibited: true` 后缀式。A 没有规定
表示法，测试就不该规定。反例 `C04`（mapping 形式）必须绿。

**来源。** `RW-T19` 从"扫描角色文档里所有 scalar"改为"只扫描 normative binding 键"
（`provider|model|family|surface|vendor|engine|executor|route|assign|prefer|default|
selected|pinned`），并显式排除 provenance 类键（`evidence|source|citation|provenance|
note|rationale|basis|comment|example|history|reason|derivation` 以及整段的 `ref`/`refs`）。
反例 `C05`（provenance 里点名 Anthropic / OpenAI / gemini / gpt-5.6 作为对照来源）必须绿；
变异 `M19`（给 independent_review 加 `preferred_provider: Anthropic Claude`）必须红。

这里也踩过一个坑并已修：`ref` 原先是裸子串匹配，于是 `preferred_provider` 因为含有
"**ref**erred" 被当成 provenance 放行，M19 存活。现在 `ref` 只按整段匹配。

### ST04-IR-005 · validator probe 依赖拓扑

v1 只 staging 新机制自身 + boot + loader + registry，于是一个**合法**的 composition
validator——A10 鼓励它引用既有机制而不是复述——会在未变异基线上就失败。v2 用
`stage_dependency_closure()`：

从机制目录、boot 目录、loader 目录与 registry 出发，反复扫描已 staging 的文本文件里出现的
仓库相对路径并把它们拉进来；命中另一个机制内部的依赖时，把那个机制的目录、boot 目录、
loader 目录与 registry 整体带上，直到不动点（上限 6 轮）。

零前非零后的语义不变：未变异闭包必须退出 0，注入缺陷后必须非零。

为了让这条真的被检验，fixture validator 现在**真的会去读** `model_routing/路由契约_v1.yml`
并断言 `authority_constant == routing_only`。实测闭包规模 1004 个文件；如果 staging 少拉了
model_routing，六条探针会在基线就红。

### ST04-IR-006 · Markdown 角色表判定

`markdown_role_table()` 现在与 YAML 侧同样是双条件：首列命中 ≥3 个角色概念，**并且**表头
其余列声明了 normative per-role 属性（responsibility / independence / handoff / authority
概念之一）。只有"哪个角色配哪个档位"这类适用性表格不构成第二份权威角色源。

反例 `C06`（`| 角色 | 推荐档位 |`，三行角色，但表头没有 normative 属性列）必须绿；变异
`M05` / `M31`（`| Role | Produces |`，带 normative 属性列）必须红。
