## 2. 记忆加载行为自检（模拟未来PRMS）

1. **L0固定入口**：按OS Boot加载当前有效规范、任务授权、正式角色身份；全部记录实际文件/版本。
2. **L1岗位CURRENT**：实际运行的PRMS角色CURRENT还未实现；新窗口此时用**规划任务run.yml+RC01候选**作为本任务当前权威记录，不能冒充运行时CURRENT已存在。
3. **L2索引/概要**：读取`00`总包、第1卷起因/时间线、第2卷Q选择、第3卷RES/索引概要模型；获得下一步路线。
4. **L3来源展开**：抽查Human原始裁决，尤其Q22、24、35、36、41、42、44、45、46、47；打开A0与RC01实际文件；核对关键链条。
5. **L4审计/全历史**：若Human问某一轮为何改判或纠正，展开精确旧版A草案与相关commit，不把旧版的GM身份理解误认为最新规则。
6. **检索覆盖报告**：指出读取过哪些文件、未读取哪些、远端SHA和哪些资料尚未核验。被过滤和未展开不等于仓库不存在证据。
7. **正式恢复输出**：至少覆盖RT-01..RT-10，明确接下来需要Human精确批准RC01还是需要先形成RC02候选。

## 3. 快速故障注入问题（新窗口可自检，但不可声称已执行工程测试）

- **索引缺漏**：只读一个概要找不到Q41=C原话时，是否主动查看第6轮Human裁决而非直接得出“未指定”？
- **相反旧版**：在A-v0.3发现GM换队示例时，是否找到后来的Human范围澄清并以之修正适用范围？
- **错误成熟度**：读到“规划升级”后是否拒绝说“PRMS已可运行”？
- **丢失来源**：某段概要没有可核实Git SHA，是否标`unverified`并要求原件？
- **预算不足**：是否优先保留角色、任务、Human权限与来源，再减少无关历史正文？
- **独立审核**：默认审查输入不含开发者观点，是否仍披露Q22=C开放读取的技术风险？
- **半途提交**：GitHub写部分文件失败时，是否查run.yml正式CURRENT指针而非当作已封版？
