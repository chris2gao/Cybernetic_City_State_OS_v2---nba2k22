# OS-PRMS A-v1-RC01 01b终审增量（二）：状态、失败及长期恢复验收 v1

**性质**：规划审查建议，不是新的Human裁决、工程方案B或已通过测试。继承A0 Q1–Q19、01b Q20–Q51、RES-001..020、EVQ/SC-001..020与既有OS机制。完整A继续 CANDIDATE_PENDING_HUMAN。

## 1. 必须分开的五类“状态”

| 对象 | 建议规范的状态维度 | 不能混淆的概念 |
|---|---|---|
| MemoryEvent | candidate、verified、durable；业务结果pending/succeeded/failed/unknown/corrected | “事件已经存档”并不证明其外部操作成功 |
| SummaryCard | candidate/source_verified/published_current；有效性current/stale/contested/superseded/unknown | 读到了旧摘要不等于其结论当前有效 |
| MemoryIndex | candidate/verified_complete/published；覆盖complete/partial/stale/rebuilding/unverified | 已发布索引版本不等于扫描范围覆盖完整 |
| RoleCurrent/Checkpoint | staged/verified/published，包含所依赖事件和索引的有效版本指针 | 已经写入部分文件不等于正式CURRENT生效 |
| RoleSessionOwner | pending/verified/stale/conflict/unverified + owner epoch | GitHub验证所有权不代表关闭外部窗口 |

失败统一至少区分REJECTED、VERSION_CONFLICT、STALE_OWNER、PARTIAL_STAGED、PUBLISH_NOT_CONFIRMED、SOURCE_MISSING、AUTHORITY_UNVERIFIED、EXTERNAL_EFFECT_UNKNOWN、CONTEXT_BUDGET_INSUFFICIENT、INDEX_PARTIAL；不同接口可映射，但不能把unknown自动归为success或failed。

## 2. 操作级前置/结果与不变量

| 操作 | 前置和成功门 | 失败或负例应有的结果 |
|---|---|---|
| record_durable_event | 身份/任务/源版本可解析，event_id和幂等键一致，写入并GitHub读回 | 相同键同内容=ALREADY_APPLIED；同键不同内容=VERSION_CONFLICT；读回不明=UNVERIFIED |
| refresh_summaries | 以changed refs和明确覆盖水位生成只受影响概要、逐项验证源引用 | 源缺失=SOURCE_MISSING；概要仍候选；依赖变更后的旧版stale但原史可查 |
| update_memory_index | 有可验证的索引声明范围与源清单，写入条目和覆盖/遗漏回执 | 未能枚举或缺源=INDEX_PARTIAL/UNVERIFIED；局部空命中不报全域无记录 |
| publish_current/checkpoint | 事件/索引/检查点候选构成闭合引用，版本与owner核验，正式指针读回 | 任何部分提交保留上一published CURRENT并保留失败证据；未知外部操作不盲重放 |
| search_memory | 结构化返回hit+原件ref+状态+来源+分页+coverage | NO_MATCH_WITHIN_SCOPE必须限定范围；过滤时附excluded count与加宽方法 |
| expand_memory | 根据source_ref与expected_sha取原件，核实真实性和来源类别 | 旧SHA或缺源时显式stale/missing，不能用模型猜测原文补洞 |
| build_context | 先固定必要OS Boot/当前任务授权/Role CURRENT，后按任务加载概要和证据 | mandatory_core缺失或预算不足立即BLOCKED；不能丢权限后返回READY |
| create_recovery_package | 标准化task/role/current/checkpoint/证据/待办/源版本和缺口 | 无法验证GitHub时声明未验证；Human转交不授权owner接管 |
| automatic_takeover | 新会话自动申请，GitHub权威owner更新且读回成功后生效 | 并发/断线时不虚构SUCCESS；旧owner写入资格失效，是否可强制阻断原始GitHub客户端保留EVQ-016 |
| copy_all_memory | 来源commit上的全量清单及内容哈希可比对，完成目标副本/风险报告，目标独立CURRENT | 任何缺项=PARTIAL_STAGED；源CURRENT/旧任务授权只能作为历史来源快照，不能覆盖目标CURRENT |

**审查门**：上述结果是产品期望；具体GitHub提交原子性、CAS、owner写入受控路径、watermark实现、索引算法和恢复软件不在01b宣称已实证。

## 4. 指标口径，遵守Q38=B/Q43=B的阶段责任

**01b只规范计量对象和分母，不设无证据数值阈值。**

- 恢复正确性：以预先确定的期望角色ID、任务、Human授权/决定、CURRENT、待办与来源版本为标注集合；逐项输出正确/缺失/错误与引用证据。任何漏mandatory核心必须单独列阻断。
- 历史证据召回：固定样本查询的“应命中且可验证的原始证据集合”为分母；以实际可定位且来源校验成功的记录为分子；同时测误命中与错误归因。样本范围必须明确，不以默认过滤结果作全仓分母。
- 索引覆盖：在可核验的indexed_scope内，以source inventory为分母；无法核验inventory时状态应unknown而非报100%。excluded、unindexed、missing_source分别报告。
- 概要来源准确性：逐条Human决定/确认事实与source/ref比对，记录错误归因、来源失效、遗漏及反证传播；模型观点不得当原始事实。
- 预算成本：分别记录默认Boot/CURRENT、初次索引/概要、按需展开、最终总输入token与工具请求、实际等待时间；估算与观测值分列；不把仓库字节数直接当token。
- 增量成本：源集合规模、实际changed事件、受影响概要/索引条目数、重建次数及漏更新数；没有变更发现证据时不称“完全增量”。
- 完整复制：源commit的规范全量清单项数与可验证目标副本数、逐项哈希一致性、来源血缘、目标CURRENT独立/风险报告；缩减为概要或索引引用属于失败。
- 并发与故障：以owner epoch、GitHub更新/读回结果、旧写入拦截、断连与不明副作用作为观察证据；原生GitHub写权限绕行风险须显式记录。

**02任务**：以实际仓库与多工作台样本采基线、核证GitHub机制；**03任务**：根据证据形成物理与算法方案，并由Human批准具体数量阈值；**04–07**：测试设计、实现及实测。以上用例全部NOT_RUN。
