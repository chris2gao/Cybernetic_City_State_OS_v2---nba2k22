# 步骤 0 · 挖掘目标

**需求 A**：机制 1 第一版——一个能把几句话的需求，通过追问变成结构化建模 A 的机制。

按 T1 选型，三段拼装：`spec-kit` 的 `/clarify` 交互形状 + 类型化 elicitation 的产出形态
+ ReqElicitBench 评测。

---

## 什么样的信息会让我们相信它可以实现

1. `spec-kit` 的 `/clarify` 提示词/流程**可读、可提取**，不深度依赖 spec-kit 自己的运行时
2. 存在一种 schema 格式，既能表达"需求建模 A"，又能被下游（证据收集、结果建模）消费
3. 「schema 在约束下填满」这个停止条件**有可实现的判定方式**——
   即能机械判断"还缺哪些槽位"
4. ReqElicitBench 的评测能在我们的环境跑起来，或至少它的评分维度可以手工套用

## 什么样的信息会让我们相信它不能实现

1. `/clarify` 与 spec-kit 的 spec 格式、命令体系**深度耦合**，剥离后不成立
2. 没有任何 schema 形态能同时满足"人类可读的需求建模"与"机器可消费的结构化输入"——
   两个目标冲突
3. 槽位是否填满**无法机械判定**，只能靠模型主观判断——
   那第一版的停止条件就退化成"模型说够了"，与现有方案无差别
4. ReqElicitBench 需要我们没有的基础设施（特定数据集、评测服务、算力）

---

## 这两组的作用

第二组不是形式。**它决定了这次挖掘要主动去找什么。**

具体地说：不能只去搜"spec-kit clarify 怎么用"，还要搜
"有没有人试过把 clarify 从 spec-kit 里剥出来"、"剥离时遇到什么问题"。
**只找支持证据，就是确认偏误开始的地方。**

## 停止判据将怎么算

EIG：再挖一轮，能否改变"三段拼装可行/不可行"这个判断？
不能就停。**不追求覆盖率。**
