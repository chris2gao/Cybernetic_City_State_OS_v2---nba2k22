# 成熟模式对照 v1

本文件只记录用于约束架构的成熟模式，不把外部产品实现直接升级为本仓要求。

## 1. Open Policy Agent — decision 与 enforcement 分离

官方资料：
- https://www.openpolicyagent.org/docs
- https://www.openpolicyagent.org/docs/deploy

关键模式：OPA 作为 Policy Decision Point，应用/网关等 Policy Enforcement Point 提供结构化输入并执行决策。对本任务的约束是：`resolve_required_mechanisms` 应保持决策纯度，不直接执行机制或授予 authority；pre-action gate 才负责阻断/放行。

## 2. Kubernetes Admission — 动作落地前拦截

官方资料：
- https://kubernetes.io/docs/concepts/policy/
- https://kubernetes.io/docs/reference/access-authn-authz/admission-controllers/

关键模式：匹配的 admission validation 在请求真正被接受之前执行，拒绝即使整个动作失败。对本任务的约束是：formal action 的 mandatory mechanism 缺失不能只产生 warning；该动作不得被系统承认为有效 formal dispatch/publication。

## 3. in-toto — 预期步骤与实际执行证据分离

官方资料：
- https://in-toto.io/docs/getting-started/
- https://in-toto.io/docs/specs/

关键模式：layout 定义预期步骤/执行者，link/attestation 类证据记录实际命令、材料、产物，再进行验证。对本任务的约束是：compliance receipt 不能只写“我遵守了机制”，而应绑定 action、expected mechanism、observed execution/evidence 和物理 repository ref。

## 4. 本仓采用方式

采用模式：

```text
structured action
→ policy decision / mechanism resolution
→ pre-action enforcement
→ mechanism execution
→ observed compliance evidence
→ independent validation
```

不采用：
- 引入 OPA 作为新依赖，仅因为模式相似；
- 引入 Kubernetes admission 组件；
- 在 v1 强制引入 in-toto 签名/密钥体系。

理由：本任务需要的是经验证的职责分离模式，不是新的基础设施依赖。首先用仓库现有 Python/YAML/validator 体系实现最小工作 vertical slice；只有未来出现具体需求才评估外部依赖。
