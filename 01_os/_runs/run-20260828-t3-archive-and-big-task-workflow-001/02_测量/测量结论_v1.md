# T3 累计工作集成本测量结论 v1

测量对象：`d9a18b57749a0608a06ab546fd179b63e696e7f1`（当前 master，也是本任务 exact base）。
工具：`02_测量/measure_working_set.py`、`02_测量/survey_run_lifecycle.py`，
均从 Git 对象库读取，不依赖文件系统遍历。原始输出为同目录的
`baseline_measurement_v1.json` 与 `run_lifecycle_survey_v1.json`。

派单给出的 baseline（1126 / 9,709,564、360 / 883,096、17 / 71,005）**逐字节复现成立**，
本任务不沿用该数字，而是独立重算后确认一致。

## 1. 三个量必须分开，混同它们会得出相反结论

| 量 | 定义 | 实测 |
|---|---|---|
| `repository_bytes` | 树里有多少内容 | 12,676,439 B / 1,781 tracked files |
| `listing_bytes` | 一次完整 tracked 路径枚举返回多少 | **209,761 B** |
| `default_load_bytes` | 启动 bootstrap 无条件读多少 | **61,534 B / 1,068 行 / 5 个文件** |

`default_load_bytes` 是**固定的**：`CLAUDE.md` + `AGENTS.md` +
`AGENT_WORKING_DISCIPLINE.md` + `01_os/README.md` +
`01_os/开发入口与单窗口任务规范_v1.md`。它不随 `_runs` 增长而增长，
因为 `AGENTS.md` 第 9 条已经禁止 default-preload `01_os/_runs/**`，且该禁令**实际生效**。

**因此"仓库变大所以每次加载变贵"这个假设不成立，本任务拒绝以它为依据。**
物理搬移历史文件对 `default_load_bytes` 的收益是 **0**。

## 2. 成本真正发生在枚举与检索，不在加载

| surface | files | content_B | listing_B | 占枚举 |
|---|---:|---:|---:|---:|
| `01_os/_runs` | 1126 | 9,709,564 | 128,363 | **61.2%** |
| `01_os/_communication` | 360 | 883,096 | 60,808 | **29.0%** |
| `01_os/_dev` | 17 | 71,005 | 701 | 0.3% |
| 全部 canonical 活动面（01/02/03/04/05/06/07） | 260 | 1,842,619 | 19,509 | 9.3% |
| 仓库根 + 其他 | 18 | 170,155 | 380 | 0.2% |

累计面合计 **189,872 B = 枚举字节的 90.52%**。
一次 `git ls-files` / `rg --files` 里，每 10 个字符有 9 个属于历史证据。

内容检索的噪声比更高。对八个"路由一个任务时真的会搜的词"做无过滤全树检索：

| 词 | 命中行 | 历史面命中 | 历史占比 |
|---|---:|---:|---:|
| `registry` | 3584 | 3330 | 92.9% |
| `lifecycle` | 299 | 281 | 94.0% |
| `risk_tier` | 102 | 95 | 93.1% |
| `allowed_changed_paths` | 125 | 114 | 91.2% |
| `completion_pointer` | 237 | 210 | 88.6% |
| `archive` | 576 | 476 | 82.6% |
| `hook_guard` | 50 | 36 | 72.0% |
| `task_authority` | 336 | 233 | 69.3% |

区间 **69.3%–94.0%**。也就是说一次无过滤检索的代价是"答案所需"的 3–15 倍。
这与 `AGENT_WORKING_DISCIPLINE.md` 第 2 节记录的事故同源：那里的教训是
"在调用点封顶"，这里补上的是**为什么不封顶会这么贵**——因为默认可见面里 90% 是历史。

## 3. 根因不是文件多，是仓库分不清"完成的 run"和"在跑的 run"

这是本次测量最关键的一条，它决定了机制形状。

| 事实 | 实测 |
|---|---|
| `_runs` 顶层 run 组 | 50 |
| 其中带 `run.yml` | 32（18 个没有） |
| 其中带 `08_*` 结论目录 | 27 |
| `run.yml` 里出现的**互不相同**的生命周期字符串 | **24** |
| 能被机器判定为终态、因而可归档的 run | **0** |
| communication `active/` 任务组 | 9 |
| communication `archive/` 任务组 | **0** |

`01_os/开发入口与单窗口任务规范_v1.md` 第 5 节已经声明了七个合法状态
（`research_only`、`candidate_pending_validation`、
`candidate_ready_for_independent_review`、`verified_on_demand`、
`integrated_and_verified_on_demand`、`deferred`、`excluded`）。
实测**没有一个 run 使用这个枚举**：绝大多数写在 `status:` 键下，是自由文本，
例如 `complete_awaiting_Human_fast_forward_authorization`、
`IMPLEMENTATION_AUTHORIZED_NO_MASTER_PUBLICATION`、
`architecture_v3_fresh_independent_rereview_dispatched`。

communication 侧更直接：`导航与归档契约_v1.yml` 与 `archive_task.py` 早就存在且
`default_load.active_current_task_only: true` 已写明，但 `archive/` 是空的——
**机制存在，一次都没被用过**。原因不是没人愿意归档，是没有任何一条机器可判的
"这个任务已经完成"的判据；`archive_task.py` 要求
`completion_pointer_ref` / `material_residuals_ref` / `private_runtime_policy_ref`
三个文件物理可读，而现存任务根里没有按这个形状写的文件。

**结论：先让生命周期可判，归档才可能发生。反过来做——先搬文件——就是 Human 明确
警告的"大扫除"，而且会在没有判据的情况下破坏 durable ref。**

## 4. 由测量直接推出的设计约束

1. 不以 `default_load_bytes` 为由做任何物理搬移：收益实测为 0。
2. 优先做**枚举/检索面的默认隔离**，这是 90.52% 与 69–94% 两个数字指向的地方。
3. 隔离必须是**显式工具 + 显式加宽开关**，不能是全局静默排除。全局静默排除会
   把"历史里确实有这条证据"变成假阴性，而本仓已经为假阴性付过学费
   （`AGENT_WORKING_DISCIPLINE.md` 第 3 节）。
4. 生命周期状态必须先变成**机器可读且被校验**，否则归档没有前置判据。
5. 物理迁移能力要实现、要测试，但在本任务中**只在合成 fixture 上运行**；
   对真实历史的迁移属于后续运营动作，需要逐个 run 的引用安全证明。

## 5. 本次测量不能证明什么

- 不能证明 token 账单会下降多少：本仓没有可回放的按调用 token 计量，
  上述都是**返回字节**，不是计费 token。字节是 token 的上界代理，不是 token。
- 不能证明 `rg` / `git grep` 的**墙钟时间**是瓶颈：未测时间，本轮只测返回量。
- 不能证明 50 个 run 里哪些"应该"归档：那需要逐个读结论，属于运营判断，不在本任务。
- 未测未跟踪文件与 `.gitignore` 外的本机残留；本轮全部基于 tracked 集合。
