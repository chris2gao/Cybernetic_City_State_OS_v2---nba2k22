# T3 设计决策 v1 —— 采纳什么、否决什么、为什么

依据：`02_测量/测量结论_v1.md`。本文件记录**被否决的方案**与理由，
按 `AGENT_WORKING_DISCIPLINE.md`「什么让积累的材料有价值」一节，
否决记录与采纳记录同等重要。

## A. 累计工作集与归档

### A-1 否决：物理批量搬移 `_runs` / `_dev` 历史

实测 `default_load_bytes` = 61,534 B 且**不含任何累计面**，所以搬移对默认加载
收益为 0。同时 50 个 run 中能被机器判为终态的是 **0** 个，没有任何一个 run 具备
搬移的前置判据。在无判据下搬移会：破坏 durable ref（`_runs/<run-id>/...` 被大量
completion pointer、审核裁决和 `important_refs` 直接引用）、且无法回答"为什么是这
50 个里的这 27 个"。派单 `conditional_archive_pilot` 的四个条件一个都不成立。
**否决。**

### A-2 否决：全局静默排除（`.ignore` / `.gitattributes` 把 `_runs` 排除出检索）

这一条最诱人：加一行就能把 90.52% 的枚举噪声去掉。否决理由是它把噪声换成了
**假阴性**——搜索"历史里有没有这条证据"会静默返回空，而调用者不知道自己被过滤了。
本仓已经为假阴性付过学费（`AGENT_WORKING_DISCIPLINE.md` 第 3 节：一个被误判成
学习者标识的路径片段；以及 CLAUDE.md 记录的 cp936 编码假阴性）。
**否决静默排除，采纳显式工具 + 显式加宽开关。**

### A-3 否决：新建一个与 communication 并列的第二套归档机制

`01_os/03_mechanisms/communication_system/导航与归档契约_v1.yml` 已经定义了正确形状：
`discovery{active_task_roots, archived_task_roots}` +
`default_load{active_current_task_only: true, archive_requires:[exact_archive_pointer,
Human_explicit_request]}` + `archive{prerequisite_evidence, preconditions, action_order}` +
`secure_erasure_claim: false`。重造第二套会产生两个都要维护的真值来源。
**否决重造，采纳把该形状上升为跨累计面的通用契约，communication 成为它的一个实例。**

### A-4 采纳：先让生命周期可判，再让归档可能发生

顺序由测量决定，不是偏好：`archive/` 至今为空，不是因为缺搬移代码
（`archive_task.py` 234 行，早就在），而是因为缺"这个组已完成"的机器判据。
所以本任务的第一交付物是**生命周期状态机 + 校验器**，第二交付物才是搬移能力。

落点（均在 `allowed_changed_paths` 内）：

| 交付物 | 路径 | 性质 |
|---|---|---|
| 通用工作集与归档契约 | `01_os/03_mechanisms/context_management/工作集与归档契约_v1.yml` | canonical 机器契约 |
| 说明与理由 | `01_os/03_mechanisms/context_management/工作集与归档_v1.md` | canonical 文档 |
| 生命周期模型与解析 | `01_os/06_execution/boot/context_management/working_set/lifecycle.py` | loader/validator |
| 工作集索引与默认可见集 | `.../working_set/working_set.py` | loader |
| 引用安全扫描 | `.../working_set/reference_safety.py` | validator |
| 通用归档搬移 | `.../working_set/archive_group.py` | 执行入口 |
| 静态校验器 | `.../working_set/validate_working_set.py` | registry 声明的 loader |

选择 `context_management` 而不是新建机制目录：该机制已经拥有
`文件隔离与产物生命周期_v1.md` 与 `实现/文件布局契约_v1.yml`，"哪些内容属于哪个
生命周期类"本来就是它的职责。新建 `03_mechanisms/archive/` 会把同一职责劈成两半。

### A-5 采纳：默认不搬真实历史，只在合成 fixture 上证明搬移能力

派单 `conditional_archive_pilot.otherwise` 明确允许这一条。搬移代码必须存在且被测，
否则"机制"只是提案；但对真实 `_runs` 的迁移是运营动作，需要逐 run 的引用安全证明，
不在本任务的 objective 内。本任务交付**能力 + 判据 + 测试**，不交付迁移结果。

### A-6 采纳：`retain` 而非 `delete` 作为归档语义

契约显式写 `secure_erasure_claim: false` 并继承 communication 的
`public_history_categories_preserved`。归档不是删除，Git 历史仍完整可达。

## B. 默认大任务与长时执行

### B-1 否决：把"大任务"写成新的 workflow 阶段或改动七阶段语义

派单 `explicit_non_goals` 明确禁止"仅为表达任务纪律而改动七阶段领域语义"。
大任务是**编排**属性，不是阶段。**否决改阶段，采纳新建
`03_mechanisms/task_orchestration/`。**

### B-2 否决：用"轮次上限"或"最少文件数"之类的量化门定义大任务

`AGENT_WORKING_DISCIPLINE.md` 第 4 节的教训正是"派单不要钉死执行者能测的数字"，
且第 2 节明确"收敛由 failure set 收缩证明，不由固定轮数上限证明"。
**否决量化阈值，采纳按"停止条件是否成立"定义边界**：不成立就继续，
成立就停——大小由 objective 的连贯性决定，不由计数决定。

### B-3 采纳：把「什么是内部 continuation、什么是真停止」变成可执行判定

这是第 4 项唯一真正需要机制的地方。派单把两个集合都列全了：

- 内部 continuation（**不产生新的 Human 门**）：确定性施工、验证、修复、证据更新、
  清理、task-branch commit/push、completion closure。
- 真停止：新的语义选择、scope escape、未覆盖的 protected action、
  安全/隐私/secret、破坏性 Git/history rewrite、runtime 激活、
  需要另一个独立模型时的 Human relay。

落点：

| 交付物 | 路径 |
|---|---|
| 大任务与长时执行契约 | `01_os/03_mechanisms/task_orchestration/大任务与长时执行契约_v1.yml` |
| 机制说明 | `01_os/03_mechanisms/task_orchestration/README.md` |
| 闭合前检查 + 停止分类 | `01_os/06_execution/task_orchestration/big_task/closure_preflight.py` |

### B-4 记录为边界，不越界

`01_os/02_boot/**` **不在** `allowed_changed_paths` 内，因此本任务
**不为 `task_orchestration` 建 boot 启动清单**。该机制通过
`05_registry/task_orchestration_v1.yml` 注册、并由 `AGENTS.md` 与开发入口引用。
"是否需要 boot manifest"留作后续任务的 finding，不在本窗口自行扩边界
（`01_os/开发入口与单窗口任务规范_v1.md` 第 2 节条件 1）。

## C. 两个交付物之间的关系

它们不是两件无关的事。测量给出的根因是"仓库分不清完成与未完成"，而
`Human/current.yml` 与 `run.yml` 的状态之所以是 24 种自由文本，正是因为过去每个
小任务各自即兴写一个状态词——碎片化的任务产生碎片化的状态。
B 的 closure preflight 要求任务在派单时就声明终态与 completion pointer 形状，
A 的生命周期校验器则在收尾时验证它确实被写成了枚举值。
**B 保证状态被产生，A 保证状态能被消费。**
