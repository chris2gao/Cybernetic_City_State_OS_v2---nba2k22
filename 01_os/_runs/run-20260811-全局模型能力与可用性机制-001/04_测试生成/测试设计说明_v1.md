## 1. 这套测试测什么，判据从哪来

`01_os/01_workflow/04_测试生成/实现/测试schema_v1.md` 把合法性拆成两个锚点：

| | 来自 |
| :--- | :--- |
| 测什么（被测主体） | B 的 result claim |
| 什么算通过（判据来源） | Stage 02 证据 |

本包严格照此执行。每条测试的 `subject_result_claim_ids` 指向 `B_结果模型_v1.yml`
的 claim key；每条测试的 `evidence_claim_ids` 只指向
`证据对齐与冲突消解_v1.yml` 的 `accepted_claims` / `rejected_or_downgraded_claims` /
`source_registry` / `conflicts_resolved` 的 ID，**一个都不指向 B**。
`实现/verify_stage04_acceptance.py package` 会机械地拒绝任何指向 B 的判据来源。

`success_criterion_index` 指向 `A_需求建模_v3.yml` 的 `成功判据` 序号（1–12）。
两个锚点都绕开 B，这是"测试由证据推导"在结构上的落实。

### 三类的区别

- **positive**：断言某个结构必须存在且取特定值。空树上必红。
- **negative**：断言某个东西**不得**出现。空树上真空为真——这是"不得包含"的正确语义，
  不是缺陷。它们的非真空性由自己的 mutation 证明（M21→MR-T02、M14→MR-T23、M26→MR-T25）。
- **boundary**：在边界条件上断言 fail-closed 行为——重复键、缺新鲜度字段、
  未登记文件、非 formal 证据越级、unknown 被留空。

## 4. 为什么这些测试能失败

`可失败: true` 不是一句声明。三份实测证据：

1. **positive fixture 全绿。** `fixtures/good_tree/` 是一棵手写的、满足全部契约的树；
   28/28 通过。检查本身不是恒假的。
2. **27 条 mutation 全部被杀。** `fixtures/mutations_v1.yml` 每条把 good_tree 改成
   "看起来完整但违反某一条已接受证据"的树，并声明它应该杀死哪一条检查。kill rate 27/27。
   这就是 `method_qualification.known_error_rate` 的量化来源——它度量的是对**已声明**
   违规形态的杀伤率，不是对未预期形态的覆盖率，两者不可互换。
3. **当前仓库 5/28 通过。** 机制尚未实现，23 条红。测试在冻结时点就是红的，
   这正是 Stage 05/06 的工作面。

collateral（一条 mutation 顺带杀死其他检查）被记录但不算失败：一处违规常常
同时破坏多个契约面。已记录三处显著 collateral：M01（删机制 README）连带 MR-T03/T21，
M04（塞入 cost 决策步）连带 MR-T25，M14（重复键）使整份目录不可解析、连带 8 条。

## 6. 发现（findings）

### F1 — A_需求建模_v3.yml 不是合法 YAML（upstream，未修）

`A_需求建模_v3.yml` 声明 `schema_version: citystate.requirement_model.A.v1`，
但第 56 行以反引号开头的纯量使整份文件无法被 YAML 解析：

```
    - `01_workflow/**` 只负责阶段顺序、输入输出、失效回退和机制调用时点。
```

YAML 的反引号是保留指示符，不能作为纯量首字符（第 55 行的反引号在句中，因此无碍）。
一个声明了机器 schema 却不能被机器读取的需求文件，属于 Stage 01 缺陷。

**处置**：不修。修复 A 超出本阶段唯一允许写入路径。
`package` 子命令每次运行都会打印 `UPSTREAM_DEFECT`，并以确定性的结构化计数
（`成功判据` 块内 `- 描述:` 行数 = 12）继续校验，不因此静默通过也不因此阻塞。
本包对 A 的绑定是 sha256 字节绑定，不依赖可解析性。
建议由 Stage 01 拥有者在单独窗口以最小改动修复（加引号即可），修复后本包的
`input_refs[0].sha256` 必须同步更新——那是一次需要重新冻结的变更。

### F2 — B13 未映射到任何 A 成功判据（B 内部，不阻塞）

`B.requirement_satisfaction` 覆盖 criterion_01…criterion_12，但 `B13_failure_surfacing`
不出现在任何一条映射里。B 的其余 12 条 claim 都被映射。

**处置**：不作为 Stage 3 blocker。B13 与 A 的成功判据 1（机制作为独立全局机制存在）
和 `03_mechanisms/README.md` 的"每个机制必须声明失效何时显现"一致，没有与 A 冲突，
只是漏了映射。本包把 B13 相关的六条检查绑到判据 1。建议 Stage 05 顺带补映射。

### F3 — A 成功判据 9 无实现测试（明确不覆盖）

判据 9（至少一轮 blind independent deep research + 逐 claim reconciliation）是
Stage 02 的过程事实，`Stage02_证据结论_v2.yml` 已记录 `independent_pass:
complete_with_source_cleaning` 与 `reconciliation: complete`。为它编造一条静态检查
只会产生一条不可能失败的测试。本包在 `not_covered_by_this_package` 显式声明不覆盖。

### F4 — 运行期行为降级为契约声明检查（明确不覆盖）

A 判据 2 说"每次路由输出…"。Stage 06 之前不存在可执行路由器，运行期断言在冻结时点
无法诚实地失败。已降级为对 contract 的静态检查（MR-T04/T05/T06），并在
`not_covered_by_this_package` 说明。Stage 07 若产出可执行路由器，应补运行期用例——
那是新增测试，不是修改本包。

### 没有发现 B blocker

B v1 与 A v3 / Stage02 v2 无实质冲突。F2 是映射遗漏，F1 属于 Stage 01，
均不构成"B 与 A/evidence 冲突"意义上的 Stage 3 blocker。

## 7. 冻结之后

`01_os/01_workflow/04_测试生成/README.md`：测试在循环开始后冻结，循环内改测试不是修复，
是重新定义什么叫成功。因此：

- Stage 05 只能把 `test_ids` 绑进 step，不得增删改本包任何一条测试；
- Stage 06 必须携带同一 `test_package_sha256`，任何漂移 fail closed；
- 若 Stage 06 发现某条测试本身写错，正确做法是停止并升级 Human，
  由 Human 决定是否重开一轮 Stage 04 并重新冻结，而不是就地改绿。
