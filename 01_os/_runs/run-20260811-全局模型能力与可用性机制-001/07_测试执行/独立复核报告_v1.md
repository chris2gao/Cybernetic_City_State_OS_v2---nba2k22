## 四个攻击点的结论

### R7-P1 source-ref 可解析性 → **blocking (F2)**

机制的加载面 = boot 清单 `load_order` + validator + registry + loader README。这八个文件
里没有任何一处定义 `OAI_*` / `GOOGLE_*` / `ANTH_*` / `GEMINI_PASS`。遵守 boot 清单的读者
一个 source_ref 都解析不出来。

其中 9 个只在 `01_os/_runs/**/证据对齐与冲突消解_v1.yml` 里定义——那是开发入口 §4 明令
不注册、§1.7 与 AGENTS.md 启动规则 9 明令不得 default-preload 的路径。**canonical 机制的
证据链终点落在 OS 禁止预加载的路径上，等于它无法自证。**

第 10 个更糟。`C08_Antigravity_Pro_access` 是 Stage 02 的 **claim ID**，不是 source ID，
却被当作 `source_refs` 和 `surface_exposure_evidence` 挂在两条已登记 Antigravity entry 上。

**这不是疏忽，Stage 06 自己记录了过程。** `Stage06_执行证据_v1.yml` 的 `S5.attempts[0]`：
MR-T25 判红，归因写的是"S2 catalog source identifier contained an economic-token substring
even though it was only an evidence pointer"，remedy 写的是"replace the pointer with the
accepted Stage 02 claim identity"。MR-T25 的 measurement 是**逐行 token 扫描**。真正的一手
来源 `GOOGLE_AG_PRICING`（`antigravity.google/pricing`，正是 C08 那张 per-plan 型号表的
出处）含子串 `PRICING`，撞上了扫描。于是**一手来源被删除，替换成项目自己的 claim ID**。
`GOOGLE_AG_PRICING` 现已完全不存在于 canonical 机制中。

而 MR-T25 自己的 `fails_when` 写的是"价格表从入口 §7.1 被搬进机制目录"。一条来源 URL 的
引用 ID 不是价格表。**测试误伤，而所选 remedy 用证据完整性换了一盏绿灯**——正是派单点名的
evidence laundering 与"满足校验器口径而非任务目标"。

B08 要求 evidence-backed source_refs，MR-T10 却只测非空。派单明令"不得把'字段非空'当作
'来源可审计'"。缺陷是**解析入口缺失**，不是证据缺失：Stage 02 的证据本身完整且正确。

**没有任何证据把 Opus 4.8 绑到 Antigravity；唯一的绑定就是这条 entry 自己。**

### R7-P4 validator 深度 → **blocking (F3)**

`verify_model_routing.py` exit 0 只证明它自己那套断言通过。对照 B13 的承诺：

| B13 要求 | 实现 |
|---|---|
| schema / duplicate keys | 已实现（StrictLoader + identity 去重） |
| source / freshness 字段 | **仅对 registered:true 实现** |
| surface 参数证据 | 仅实现为"非空" |
| 非法 cost/quota 字段 | **未实现** |
| entry/boot/registry pointer 断裂 | **仅 2/3** |
| registry coverage | **未实现** |
| diagnostic 不得形成 hard qualification | 已实现 |

五个具体缺陷：

1. **registry 是一次死读。** `validate_static` 读入 registry 后只取 `mechanism_version`，
   从不触碰 `registry["entries"]`。没有任何 registered path 被检查存在性，没有任何机制文件
   被检查覆盖。MR-T21/MR-T28 确实测了这两件事——但**冻结 run 测试不是机制的运行期失效显现器**，
   而 B13 把 registry coverage 明确写成 validator 的职责。
2. validator 里没有任何 cost/price/quota 字段扫描，尽管 B13 点名了它。唯一的执行者是
   MR-T25，在机制之外。
3. `registered: false` 短路后，`source_refs`、`verified_at`、`confidence` 与 capability
   形状全部不校验——F1 正是从这个洞钻过去的。顺带一提，Opus 4.8 那条的 `capabilities` 是
   标量字符串 `unknown` 而非 mapping，任何 registered entry 这么写都会判红。
4. 入口规范指向机制的 pointer 从不校验。
5. boot 清单的 `catalog_version` 与 catalog 的 `catalog_version` 各自与字面量 1 比较，
   两者之间从不交叉核对；将来单边升版会静默通过。

B02 把 validator 列为五个 canonical 组件之一，B13 让它成为机制的失效显现器。今天的 exit 0
兑现的是冻结测试的最低字面，不是 B13 的承诺。
