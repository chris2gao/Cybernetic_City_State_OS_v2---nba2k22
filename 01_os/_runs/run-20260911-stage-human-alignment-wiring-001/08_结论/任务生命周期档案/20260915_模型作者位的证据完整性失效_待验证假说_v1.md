# 模型作者位的证据完整性失效

收尾归档位置：既有 W6 run 的任务证据；2026-10-22 按 Human 指示迁入，不建立根目录档案面。

**类别：待验证假说。不是 OS 规则，不构成对任何执行者的约束。**

日期 2026-09-15 ｜ 来源：W6 阶段验收发布闸任务（run-20260911-stage-human-alignment-wiring-001）
四轮 executor(Claude) × secondary co-auditor(Codex) × Human(GPT 协同分析) 的实测与讨论。

---

## 0. 为什么记下来

W6 本身是在修一个产品层问题：系统容易把"字段、validator、流程节点都做完整"误当成
"Human 和模型真的理解并接受了主要方案"。

在实现这个修复的过程中，执行者反复犯了**同构的错误**：validator 存在当成保证存在、
测试全绿当成语义闭合、引用形状相同当成指称相同。

**同一个认知倾向从产品层递归到了实现层。** 这件事的普遍性可能高于 W6 本身，所以单独留档。

---

## 1. 假说

> 生成模型在长期承担作者角色时，会同时受到情境依赖检索、缓存习语、指称漂移与共享假设
> 自证的影响。可靠系统不能主要依赖模型记住抽象原则，而必须在**写作、验证、终态、独立
> 复核**四个位置主动破坏这些错误闭环。

总类命名：**Epistemic Integrity Failure（证据—语义完整性失效）**。

---

## 2. 三个根因家族

三者表面不同，底层操作不同，**对策也不同**——这是分家族的唯一理由。

### A. Proxy-Evidence Collapse（代理证据坍缩）

证明对象没变，但拿了不充分的代理当证据。

| 实际产出 | 被当成 |
| --- | --- |
| 一行长得像守卫的代码 | 存在保护 |
| `int(x,16)` 不报错 | 语法已校验 |
| 注册项写着"可被挑战" | commitment 已校验 |
| 测试点数在涨 | 回归跑完了 |
| 套件全绿 | 没有死检查 |
| 引用在声明的 blob 上存在 | 对象符合契约 |
| verification 文件在声明位置 | 验证通过了 |

**危险的不是单次替换，是闭合。** implementation、fixture、test、interpretation、report
全部由同一个假设派生，于是必然互相一致。此时"全绿"的信息量是零——它只证明
"后来写的东西与最初的假设一致"，没有证明那个假设来自 canonical truth。这就是
correlated error。

**对策：mutation falsification。** 把守卫拿掉/短路/改成恒真，对应测试必须变红。

### B. Referent Drift（指称漂移）

论证过程中**证明对象本身**悄悄换了。经典 equivocation。

- `repo_root`：一会儿指被审判的仓库，一会儿指运行中的安装
  → 产出了本轮唯一的**安全**缺陷：发布闸从被审判的仓库加载校验器，
  构造过的仓库可以自带宽松校验器并被执行。
- `backup`：一会儿指原生产文件，一会儿指上一轮写入的桩
  → 产出了本轮唯一的**破坏性**缺陷：测试把 646 行生产网关"还原"成 3 行桩。
- `ref` 形状相同 → 默认 referent 相同（receipt ref 被默认在 M 读取，仅因为它长得像
  `current_model_ref`；而后者拿到 M 是有 `accepted_model_commit` 这个真实契约字段支撑的，
  receipt 没有对应物）。

危险性高于 A：它不只产生假证明，还会让程序**读错仓库、改错对象、恢复错文件**。

**对策：world-explicit naming（写作时）+ referent perturbation（测试时）**，顺序不能反。
见第 4 节。

### C. Cached-Idiom Substitution（缓存习语替换）

模型从训练/工程习惯里直接取一个熟悉实现，没有重新验证它在**当前精确定义**下是否成立。

`int(x,16)` 主要属于 C 而非 A：它**事后**表现为一个不充分代理，但**产生机制**是熟悉习语
自动补全，不是先编了一个错误的证明故事。区分有用，因为 C 最适合静态反模式/lint，而
A 最适合 mutation。

已实证的习语清单（触发物字面在场，适合机械化）：

```
int(x, 16)                   ≠ 十六进制语法校验（吃 +、-、_）
re.match(r'[0-9a-f]+', x)    ≠ 同上（无锚定、无长度）
except Exception             ≠ 预期失败（吞掉真错误）
in / 字符串包含               ≠ 结构匹配
grep/Select-String 命中       ≠ 代码确实做了这件事（会命中注释与 docstring，本轮两次）
rmtree(ignore_errors=True)   ≠ 删除成功（Windows 只读位，累计 246 个残留仓库）
"进程存在"                    ≠ 任务完成
"文件存在"                    ≠ 内容正确
"ref 解析成功"                ≠ 对象语义正确
```

## 3. 为什么"知道了还会再犯"

这是最值得注意的现象，也是"把教训写进提示词"为何不足的原因。

本轮有一个干净的实例：执行者**记录了** GD-1（`_chain_stages` 自己和自己比较），
**十分钟后**在另一个名字下造出了 `declared_accepted_output`——同样是两边同源的恒真检查。

不是没理解。理解了，并且能准确复述。

**机制是检索时的描述错配。** 写那行代码的当下，自我表述不是"我正在比较两个值"，
而是"**我正在补一个能抓住撒谎 control 的安全检查**"。元规则"比较前追 provenance"索引在
前一个描述上，认知状态处在后一个描述里。规则没触发不是因为它软，是因为**它挂错了钩子**。

由此得到一个关于"什么值得写下来"的判据（**概率判断，非可判定**）：

> 规则越能由当前代码/操作中直接可观测的 lexical 或 structural cue 触发，越适合成为稳定的
> 局部纪律；越需要模型先重新解释"我现在实际上在做什么"才能命中，越不能依赖文字本身。

因此 C 类（`int(x,16)` 等）应优先进 lint/static check；而"比较前追 provenance""注意不要
混淆语义"只能作为思维辅助，**不得计入保证**。

**注意**：字面在场也不保证一定检索到，长上下文中尤其不保证。所以最佳落点是机械检查，
不是文档。

## 4. 防线（Epistemic Integrity Assurance Stack）

前四层可机械执行，第五层是组织隔离层——**可靠性不同，不应混为一谈**。

| # | 层 | 证明什么 | 依赖模型记得？ |
| --- | --- | --- | --- |
| 1 | Anti-idiom check | 已实证危险的习语没有被使用 | 否（lint） |
| 2 | Referent-explicit naming | 跨世界对象的名字编码 world/role | 是（写作纪律） |
| 3 | Citation-at-authoring | 新引入的 load-bearing 语义关系说得出来源 | 是（写作纪律） |
| 4a | Terminal-state gate | **此刻**即将交付的真实产物满足硬条件 | 否 |
| 4b | Mutation falsification | 这个守卫**有因果作用** | 否 |
| 4c | Referent perturbation | 程序读的**确实是**它声称的那个对象 | 否 |
| 5 | Independent falsification | 打断 correlated error | 是（依赖另一模型的认知质量） |

### 1. Anti-idiom check

**陷阱：禁 token 会变成位移而不是纠正。** 禁掉 `int(x,16)`，模型会写
`re.match(r'[0-9a-f]+', x)`——没有锚定、没有长度，照样错。

所以规则必须挂在**性质**上而不是**写法**上：不是"别用 `int(x,16)`"，而是
"十六进制语法校验必须附带一个能让它对 `+`、`_`、大写、超长、空串各失败一次的测试"。
前者可位移，后者不能。

### 2. Referent-explicit naming

`repo_root` → `judged_repo_root` / `installation_root`；`backup` → `backup_of_original_gate`。
跨世界对象的名字应编码 world/role，必要时编码 time/version。

它不能证明正确，但能让 equivocation 在**调用点**刺眼。**必须排在 4c 之前**：
differential testing 只能攻击"我们已经想到可能混淆的两个世界"，而本轮栽的两次恰好是
当时根本没意识到那里有两个世界——没看见这一对**正是错误本身**。命名纪律作用在写的时候，
覆盖未枚举的情况。

### 3. Citation-at-authoring

引入新的 load-bearing 语义关系时，当场必须能指出它来自哪条**现行** canonical /
Human decision / physical fact。

本轮反例：写"receipt 从 M 读"的那一刻若被要求回答"哪条有效契约定义
`receipt_ref → M`"，就会当场卡住。实际发生的是没人问，于是一个发明被当成推导写了进去，
并被 fixture 固定下来。

**限定（重要）**：citation 的产出**不是通过标记，而是一个待验证命题**。
"有引用所以语义正确"本身就是 A 类代理。现成反例：co-auditor 曾引用
`映射契约 v1:198-205` 作为现行依据，而那几行位于 v1 part_3，已被 v2 全量替换。
所以写下来源之后仍须验证该来源 current、applicable、未被 superseded、且真的蕴含该关系。

### 4a. Terminal-state gate

不可逆动作（提交/发布）之前，从**当前产物**重新测量终态，并在检查与动作之间放硬闸。

本轮实测：这是命中率最高的一层。提交守卫两次拒绝了执行者（YAML 语法错、
正则匹配到 docstring 散文），blob 哈希比对本可抓住桩事故。

**它自己的特征失效模式：守卫断言过期。** 本轮出现过 registry 断言还在找旧函数名、
正则匹配到散文。配套纪律：**守卫的断言必须在守卫运行时从产物/canonical 重新推导，
不得凭记忆写死。**

### 4b / 4c 为什么必须是两种

- **mutation** 证明守卫有因果作用 → 抓 dead guard、tautology、verdict 未被消费、parser 超集。
- **referent perturbation** 证明程序读的是所声称的对象 → 让可能混淆的世界产生不同值
  （candidate / worktree、judged repo / installation、original / stub、base / current），
  再看系统用了谁。

**mutation 单独解决不了 B 类**：若 fixture 本身也按错误的世界布置，mutant 仍可能全绿。

### 5. Independent falsification

不是因为 reviewer 一定更聪明，而是**它没有参与生成作者的 latent hypothesis**。
它会自然问"为什么是 M？"，而作者会问"M 上的 receipt 有没有被正确读取？"——差距巨大。

## 5. 换 executor 的信号：发现权漂移

不看错误总数，看**新的 load-bearing 缺陷主要由谁发现**。

作者仍能在交付前自我反证、自己发现 principal 问题 → 系统健康，继续执行是合理的。
连续几轮变成"作者形成闭合 claim → 外部 reviewer 构造最小反例"，而作者的
self-falsification 越来越少 → **epistemic coupling 已经形成**。

本轮可以看到这个相变：早期执行者自己发现了生产网关被桩覆盖、校验器从错误仓库加载；
后期 dead guard、receipt mapping、profile completeness、OID grammar 越来越依赖冷读发现。

换 executor 是**重置相关性，不是惩罚犯错**。

## 6. 验证方案（尚未执行）

### 三档 benchmark，测的是 transfer gap

| 档 | 输入 | 问什么 |
| --- | --- | --- |
| diagnostic | 已有错误代码 | 能不能识别 |
| **self-audit** | **模型自己的实现 + 物理复核指令** | **切换姿态后能不能发现** |
| author | 只给正常工程目标 | 一开始会不会造出来 |

有价值的不是 diagnostic 分数，是 `diagnostic → self-audit → author` **三档之间掉多少**。

**self-audit 这一档决定补救措施要多贵**：本轮执行者确实自己抓到了那条恒真检查——
就在主动切到审计姿态做物理核验的时候。所以"知道→施工时用不上"不是二值断崖，
中间存在一个可达且便宜的状态。若 self-audit recovery 高，只需在交付前**强制一次姿态切换**；
若也低，则每次改动都得外部证伪，成本完全不同。只测两档答不出这个问题。

### 领域轮换，防 benchmark 自己变成新的缓存习语

固定认知形状，轮换表面领域：

| 形状 | 领域 A | 领域 B | 领域 C |
| --- | --- | --- | --- |
| parser 超集冒充语法 | Git OID | ISO-8601 UTC | 货币金额 / UUID |
| 两边同源当独立一致 | commit 派生 | 缓存派生 | 配置/快照派生 |
| 过程信号当终态 | 测试点数 | 上传字节 | 队列长度 |

主要指标 = **未见领域族上的 author-mode 表现**。

### 证伪标准（预先规定）

> 措施上线后，**held-out 领域族上的 author-mode load-bearing 错误率**没有实质下降，
> 就不得升格为 OS 规则。

**测量陷阱必须预先堵上。** load-bearing 错误是低频事件，现场样本量不足以判断"有没有下降"，
于是会自然发生一件事：用 benchmark 上的提升去代替现场错误率的下降——**那就是又一次代理
替换，发生在专门治理代理替换的项目的验收环节里。**

所以写死：

- 指标 = held-out 领域族上的 author-mode 错误率，**预注册** n 与最小可检测效应量；
- 现场错误率**只用于证伪，不用于证实**：现场再出同类事故可直接判措施无效；
  现场没出事故**不算**措施有效（样本不足）。

这是"代理只能用于已被证明有效的方向"这条原则在验收环节的应用。

## 7. 操作口令

> **未经证明具有充分性的代理，只能用于它已被证明有效的方向；默认不得由代理 PASS 推导
> 目标 PASS。**

实用形式（对当前遇到的大量 heuristic proxy 成立）：

| 代理 | 失败时 | 通过时 |
| --- | --- | --- |
| `int(x,16)` | 可排除候选 | 不能证明是 Git SHA |
| 进度增长 / 停止 | 停止可说明异常 | 增长不能证明完成 |
| ref 解析 | 失败可证明绑定有问题 | 成功只证明"可解析" |
| validator 文件存在 | — | 不能证明它被生产路径调用 |
| commitment 字段存在 | — | 不能证明 challenge 发生过 |

配套：

> **Names suggest; contracts define. Shapes do not imply semantics.**
>
> 字段名、数据形状、相邻字段、类似机制、fixture 惯例——都不能生成语义。
> 只有现行 canonical、物理状态或 Human decision 可以建立语义。

以及：**未知不是一个等待模型填补的槽位。未知本身可以是正确的系统状态。**
本轮执行者做得最好的一件事，是最后能够说 `NO_REFERENT_DEFINED`，不再猜。

## 8. 后续任务（W6 principal closure 之后再启动）

不要把这条讨论插进正在进行的 W6，否则两个目标会纠缠在同一个执行窗口里。

问题陈述：**如何检测并打破模型作者形成的 self-consistent but false proof loop？**

只做三个最小产物，**不新造大型 schema，不再写"模型应当谨慎"的宣言**：

1. situated、跨领域轮换的 diagnostic / self-audit / author benchmark，测 transfer gap；
2. load-bearing validator 的 mutation + referent-perturbation harness pattern；
3. 一组从真实事故提炼的、具有字面/状态触发条件的 anti-idiom 与 terminal-gate candidates。

**验收要求这三个产物本身可被证伪**——要说得出"哪几条上线后 author-mode 错误率没动"。
否则它就变成新一版"提醒模型小心"的文档，只是穿了工程的外衣。

## 9. 本文件的地位

**这是假说，不是结论。** 它来自一个任务、一个执行者、四轮审计，样本量为一。

其中已被实测的部分：第 2 节的全部案例、第 3 节的 GD-1 复犯实例、第 4 节 4a 的命中记录、
第 5 节的相变观察。**未被实测的部分：整套防线是否真能降低错误率。** 那正是第 6 节要做的事。

在第 6 节的实验给出结果之前，不得把本文件任何一条升格为 `AGENT_WORKING_DISCIPLINE.md`
或 `01_os/**` 中的规则。把一份未经验证的分析写进 OS 并当成保证已经成立——那恰好是本文件
第 2 节 A 类的定义。
