这两份针对“Agent 确定性工作流”的开源生态调研报告，虽然目标都是考察 17 项核心操作的可用工具，但在检索深度、架构认知和部分长尾工具的发现上呈现出明显的互补性。

以下是两份报告的重复结论与核心差异对比：

### 🤝 重复的结论 (Overlaps)

1. **生态整体成熟度与“重灾区”共识**
   * **成熟领域**：两份报告都认为在 Schema校验、RDF图约束校验 (SHACL)、约束求解 (CSP)、测试溯源、变异测试以及 Prompt 评测等领域，开源生态非常成熟，可直接集成。
   * **循环报道剥离（完全缺失）**：对于“纯文本的循环报道剥离”这一需求，两份报告得出了一致的**否定结论**。现存工具要么是针对富媒体文件的数字溯源（如 C2PA），要么是需要重度人工审查的重量级平台，**不存在**开箱即用的自动化确定性工具。
   * **原子事实支撑度（属于混合范式）**：双方都锁定了 `FActScore`，并同时指出它的**坑点**：它不是纯粹的离线确定性计算，而是强依赖外部大模型（LLM）或 API 来拆解原子事实，违背了“纯确定性”的初衷。

2. **工具选型的高度重合**
   基于独立的检索，两份报告在多个领域推举了完全相同的标杆工具：
   * **Schema 校验**：均推荐 `check-jsonschema`。
   * **测试溯源校验**：均推荐 `OpenFastTrace`。
   * **RDF SHACL 校验**：均推荐 `pySHACL`。
   * **变异测试**：均推荐 Python 生态的 `mutmut`。
   * **约束求解**：均推荐微软开源的 `Z3-solver`。
   * **Prompt/Skill 评测**：均强烈推荐 `promptfoo`，并都认可其与 Agent 流程（特别是 MCP）的原生契合度。

3. **集成的底层逻辑：轻量级 Wrapper 优于庞大的 MCP Server**
   两份报告都洞察到：不应该执着于寻找“原生支持 MCP”的领域专用服务器，而是应该**用 Python API 或 CLI 命令行工具作为基础，再将其包装给 Agent**。因为大部分成熟的科研/工程工具只提供 CLI 和主流语言 API。

---

### ⚖️ 主要的差异与互补 (Differences)

1. **“竞争性假设分析 (ACH)” 的结论截然相反**
   * **ChatGPT 报告**：认为 ACH 工具生态很差，只找到了老旧的 PHP Web 应用（Burton）和极其庞大的本地情报平台（ArkhamMirror），没有轻量级现代 Python 库，建议自己手写。
   * **Gemini 报告**：**成功找到了现代方案**。发现了一个专门针对 LLM 工作流设计的 Python 评估框架 `EMR-ACH`，其纯矩阵代数运算逻辑非常适合抽离成 Agent 技能。

2. **“形态交叉一致性剔除” 的实现路径分歧**
   * **ChatGPT 报告**：检索失败（甚至搜到了毫不相关的电视剧），结论是“没有现代开源库”，建议直接把条件转化为 SAT/CP 约束，丢给 `Z3` 或 `OR-Tools` 求解。
   * **Gemini 报告**：挖到了一个专用的独立 Python 脚本工具 `zwicky-morphological-analysis`，可以直接调用，但指出了其底层依赖简单 DFS（深度优先搜索）算法，可能面临组合爆炸的风险。

3. **“重合度与规模估计 (Capture-Recapture)” 的工具栈偏好**
   * **ChatGPT 报告**：偏向于数据科学领域的实体匹配（`splink`, `recordlinkage`）结合 R 语言的经典包 `Rcapture`。
   * **Gemini 报告**：找到的是更轻量且无需引入 R 环境的纯 Python 库 `recapturedocs`，并从统计学角度提示了小样本情况下的 Lincoln-Petersen 公式偏差陷阱，强调必须使用 Chapman 修正算式。

4. **架构深度剖析：关于 MCP “上下文膨胀”的警告**
   * **ChatGPT 报告**：只是平铺直叙地提及“MCP 服务器相对稀缺，主要作为 Wrapper 存在”。
   * **Gemini 报告**：深入指出了 MCP 协议的**致命缺陷**——“工具定义上下文膨胀”。几十个工具的 Schema 注入会让 Agent 分心且耗尽 Token。Gemini 报告强烈建议采用按需读取的“Agent Skills”（渐进式技能包）范式来替代全量 MCP 挂载。

5. **技术踩坑预警的具体程度不同**
   Gemini 报告在已知限制和“坑点”上深入到了代码和框架兼容性级别：
   * 在提及 `mutmut` 时，Gemini 警告它不仅不支持 Python 3.14，其 AST 引擎还会**忽略带装饰器的 FastAPI 路由函数**，导致覆盖率假死。而 ChatGPT 只是泛泛提及了它需要 WSL 和计算资源大。
   * 在讨论 `check-jsonschema` 时，Gemini 报告警告了 MCP 中使用 `anyOf`（如 Union 类型）会导致主流编辑器客户端直接拦截阻断。
   * 在讨论原子事实评估时，Gemini 额外对比了 `AlignScore`，并指出了其极高显存占用和官方训练集充满噪声的问题。

**总结**：ChatGPT 的报告更像是一次广泛的组件筛查（Broad Sweep），为整体架构确定了哪些方向可走；而 Gemini 的报告在部分高难节点上挖掘得更深，并在大模型集成的微观架构（如上下文控制、代码级兼容报错）上提供了更致命的避坑指南。
