### 我上一轮口头给出的 74% 是错的

那个数字是**只读了 NotebookLM 摘要**时算的（n₁≈14、n₂≈12、m=6）。
摘要只列了它认为值得对比的工具，不是完整清单。
读完两份报告后按完整清单重算：**64%，不是 74%**。

**这正是本项目反复出现的那类错误**——拿一份被裁剪过的材料当全集。
与"截断的结果只支持'至少有这些'"是同一个形状。

### 64% 是上界，不是点估计

Chapman 假设两路**等可捕获**，而本轮明显不成立：
ChatGPT 广扫十七项，Gemini 深挖六项。
重合集中在"好找的那批"，会抬高 m、压低 N̂。真实剩余量应比 36% 更大。

## 2. 两路分歧：谁推翻了谁

**这是并行派单唯一不可替代的产出。** 三处分歧全部是单路会漏掉的。

### ACH——Gemini 推翻了 ChatGPT

ChatGPT：生态很差，只有老旧 PHP 的 `Burton`（10 次提交）和重型平台 `ArkhamMirror`，**建议自己手写**。

Gemini：找到 **`EMR-ACH`**（ApartsinProjects/EMR-ACH）——2024 年后的 Python 框架，**专为把 LLM 预测转成结构化矩阵分析而设计**。核心是纯矩阵代数：证据矩阵 × 影响矩阵 → 诊断性权重 → 假设得分，可整段剥离封成 skill。

**采信 Gemini。** ChatGPT 的"没有"是检索失败，不是生态不存在。

### 形态交叉一致性——两路互补，都不完整

ChatGPT：检索失败（返回里混进了电视剧 *Cross*），结论"无现代 OSS"，建议把互斥条件编成 SAT/CP 约束丢给 Z3 / OR-Tools。

Gemini：找到 `zwicky-morphological-analysis`（JohannesBuchner），纯 Python、离线、GPL-3.0，**但只有 10 次提交，底层是带提前截断的 DFS**——高维或弱约束下会组合爆炸。

**两条都要留**：小矩阵直接用 zwicky，规模上来了转 Z3。**ChatGPT 的退路是 Gemini 那条路的兜底**。

### 孤立主张检测——两路给了不同层次

ChatGPT：`argdown` / `arguebuf` / `AIFdb`——论证图表示层，**没有专做"标出无证据主张"的成品**，要自己写图查询。

Gemini：`PyArg`——直接提供入度为零节点的图遍历。

**采信 Gemini**，`PyArg` 是更短的路径。

## 3. 两路一致的否定结论

**只有一项被两路同时判死：循环报道剥离（操作 4）。**

- ChatGPT：找到的是 `mediacloud` 这类**上游语料平台**和通用去重组件，**没有**任何工具的文档契约是"追溯首发、折叠循环链"。去重容易，溯源是 provenance 问题不是相似度问题。
- Gemini：`pyc2pa` 只处理**富媒体的密码学签名**，管不了文本改写；`Civic Table` 架构文档明写 **"Entity merges require human review"**，从设计上就堵死了闭环自动化。

**两路都独立撞到同一堵墙，这个"没有"可以采信。** 归入自建。

另有两项**一致确认为陷阱**：

- **操作 13 内部要调模型**（见 `00_确定性操作清单.md` 的更正段）
- **操作 2 无通用工具**，两路都说要自己写包装脚本——但这件事本来就只有几十行

## 4. 只有一路给出的踩坑预警

Gemini 深到了代码与框架兼容级，**其中一条直接改变我们的选型**：

| 工具 | 坑 | 对我们的影响 |
| :--- | :--- | :--- |
| **`mutmut`** | 不兼容 **Python 3.14**（Pony ORM pickle 失败）；AST 引擎**跳过所有带装饰器的函数与类** | **本机实测 Python 3.14.6，装上直接不能用**；且即便降版本，带装饰器的代码会静默报"捕获率为零" |
| `check-jsonschema` | MCP 客户端对 `anyOf`（Union 类型）有实现缺陷，**合法输入会被编辑器端直接拦截**，请求根本不下发 | 接口参数要用宽泛类型，细校验下沉到 Python 内部 |
| `AlignScore` | 显存消耗巨大；官方 470 万训练集含大量噪声，清洗后用 10% 反而更准 | 不采用 |

ChatGPT 对 mutmut 只说了"需要 fork 支持、Windows 上要 WSL、算力贵"——**没提版本断裂**。

## 5. 架构结论：不要全量挂 MCP

**两路一致**：不要追求"原生 MCP 的领域服务器"，成熟工具基本只出 CLI 和语言 API，**拿 CLI/API 做基础再包装**才是现实路径。

**Gemini 多给一条，且带测量**：MCP 的**工具定义上下文膨胀**——所有工具 schema 必须在会话初期全量注入；数十个工具的 schema 就消耗数万 token，**工具数破二十后 agent 选择准确率断崖下跌**。

由此定分层：

| 形态 | 用于 | 理由 |
| :--- | :--- | :--- |
| **Agent Skill**（渐进式披露） | 纯离线数学/逻辑：形态分析、ACH、孤立主张、约束求解、集合覆盖 | 初期只占约 100 token 的名称与描述，命中才读全文；无常驻服务 |
| **MCP server** | 重环境：promptfoo、OpenFastTrace | 跨进程隔离，各自吃自己的运行时 |
| **内联脚本** | 校验错误转追问、集合运算 | 几十行，外部化反而是净损失 |

中间件 `mcp-skill-server` 可把任何带 `--help` 的 CLI 脚本零改造转成 MCP 接口——**留作后备，不预先引入**。
