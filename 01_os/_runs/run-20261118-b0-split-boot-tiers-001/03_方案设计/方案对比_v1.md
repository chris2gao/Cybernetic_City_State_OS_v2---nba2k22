## 1. 原有实现与问题（实测）

**读取量。** B0 五个文件共 127,786 字节：`AGENT_WORKING_DISCIPLINE.md` 40,290、`AGENTS.md` 20,074、
`01_os/README.md` 5,931、`01_os/开发入口与单窗口任务规范_v1.md` 48,676、`CORE_MANIFEST.yml` 12,815。
生成的目录（`.claude/skills/citystate-os/SKILL.md`）给出的角色启动读取量：规划约 174 KB、开发 177、审核 167、
特色内容开发 177、特色内容教学或使用 152。其中 B0 都是 124 KB，非 B0 部分只有 28–53 KB。

**B0 里有什么。** 按段落粗分：

| 文件 | 规则 | 事故经过 / 实测数字 / 设计理由 | 说明 |
|---|---:|---:|---|
| AGENT_WORKING_DISCIPLINE.md | ≈31 KB | ≈9 KB | 每节的 *Paid for* 段、§2 的 2026-07-26 实测数字、§8 的 d9a18b57 实测、“What is not worth optimising”、“What makes the accumulated material worth anything” |
| AGENTS.md | ≈19 KB | ≈1 KB | 几乎全是规则；但约 6 KB 是 DISCIPLINE §0.1–0.4、§8 的重述 |
| 开发入口 | ≈46 KB | ≈2–3 KB | §1.2、§5 的实测、§8.1 的历史参考、§1.1 的“未定义传输”理由 |
| 01_os/README.md | ≈5.5 KB | ≈0.4 KB | “Two rules” 里的历史事故句 |
| CORE_MANIFEST.yml | ≈5.8 KB（YAML 键值） | ≈7 KB（109 行注释） | 机器文件，由 validator 读 |

**结论：只把“事故经过、实测数字与设计理由”移走，B0 只能从 124 KB 降到约 107 KB。** 任务目标的“60–80 KB”
做不到，除非 B0 自身也分层（规则按“启动必读 / 按动作读取 / 程序读取”放）。这是派单内部的冲突：
“规则留在启动层”与“降到 60–80 KB”不能同时成立。按纪律 §4，我照实测报告，由 Human 选。

**读什么写在两处。** 三层只登记在 `01_os/05_registry/skills_v1.yml`（每个 unit 的 `startup` / `on_action` /
`reads`）；各机制 `01_os/02_boot/*/启动清单_v1.yml` 的 `load_order` 仍平铺。`generate_skills.py` 把 boot 与
`reads` 合并，再用 `is_program_path()` 按文件名猜哪些属程序读取。14 个 unit 里有 6 个没有 boot：
`citystate-os`、`os-task-continuity`、`os-task-discipline`、`os-publication`、`os-tools`、`os-domain-content`。

**不能动的接口（实测）。**

- `load_order` 的形状被多处消费：通讯与机制激活 validator 要求字符串列表；MWU validator 要求顺序逐项相等；
  阶段协同推演 boot 按 blob SHA 钉住被加载文件；PRMS `catalog.py` / `context.py` 把 `load_order` 当强制依赖。
  所以分层**不能**改 `load_order` 本身，只能另加一个键。
- B0 文本里被 validator 检查的词：`01_os/README.md` 的 `01_os/_runs/`、`core-owned`、
  `08_Domain_Applications/_runs/`、`domain-owned`（CM033）与 `minimum_work_unit_output`（MWU）；
  `AGENTS.md` 的 `Formal Action Constitution` 与 `mechanism_activation`（机制激活 static）；
  `CORE_MANIFEST.yml` 的 `core_owned_paths` / `domain_owned_paths`。PRMS `catalog.py` 的 `B0_PATHS`
  用于 core/domain 版本比对。
- 全仓大量引用“开发入口 §1.1 / §5 / §7.2 / §11”等节号（AGENTS、DISCIPLINE、skills、lifecycle.py 等），
  节号必须保持可解析。
- 没有任何 registry 钉住 boot 清单自身的 blob，给 boot 加键不会连带改其他钉值。

## 2. 两个方案

两个方案的 boot 三层部分完全相同（第 3 节）；差别只在 B0 怎么拆。

### 方案 A：严格按派单——只移出依据，规则全部留在启动层

- 新增 `01_os/入口依据与事故记录_v1.md`：把 B0 里的事故经过、实测数字、设计理由**原文移入**，
  按“源文件 § 节”分节。源文件每处被移走的地方留一行 `依据：入口依据与事故记录_v1.md §…`。
- `CORE_MANIFEST.yml`：109 行注释里的历史与理由移入依据文件；YAML 键值不动，保留“机器消费者”说明。
- 规则文字一字不改，节号不变。
- **预计 B0 ≈ 107 KB；各角色启动 ≈ 135–160 KB（降约 10%）。不达 60–80 KB。**

### 方案 B（推荐）：A 加上 B0 自身分层

在 A 的基础上：

1. **开发入口拆为“启动核心 + 按动作细则”。** 新增 `01_os/开发入口_按动作细则_v1.md`，把只在特定动作时才用到的节
   **原文、原节号**移过去：§1.1 传输矩阵、§1.2 执行环境、§3 文件放置、§4 registry 同步、§6 分支与发布、
   §7（含 7.1、7.2）任务包与 Human 确认、§8（含 8.1）测试与证据、§9（含 9.1–9.3）独立审核、§10 completion pointer、
   §12 权威参考、§13 经验回流。开发入口保留 §1 加载顺序、§2 任务边界、§5 run 与 lifecycle 枚举、§11 停止条件，
   每个被移走的节留下原标题和一行“何时读、在哪里”，所以“开发入口 §7.2”这类引用仍能找到。
   开发入口启动部分约 13 KB。
2. **`CORE_MANIFEST.yml` 改为程序读取。** 它是机器文件，validator 读；`AGENTS.md` / `CLAUDE.md` 的启动顺序本来就
   没有点名它，只有 `skills_v1.yml` 把它放进了 B0。文件本身不改。
3. **`AGENTS.md` 去重。** “Reusable task prototypes”“Execution-mode routing”“Denial receipts”“Trust-first”
   “Default Task Orchestration” 五节是 DISCIPLINE §0.1–0.4、§8 与开发入口 §11 的重述，各改为一行指向原节；
   逐句核对，AGENTS 独有的句子保留在原处（例如 `reviewed_prototypes.py`、`execution_mode_gateway.py`、
   closure_preflight 指针）。Startup Rules、Backend Executor、Formal Handoffs、Formal Action Constitution、
   Engineering Design Principles、Safety、Git 七节不动。约 20 → 13 KB。
4. DISCIPLINE 与 README 同方案 A。

- **预计 B0 启动 ≈ 62 KB（降约一半），落在 60–80 KB；各角色启动 ≈ 90–115 KB（降约 35%）。**
- 若“60–80 KB”指的是**每个角色的启动合计**，还需要再把非 B0 的启动必读调层（如 `os-publication` 的
  `repository_publisher_authority_v1.yml` 是 registry 文件、按定义属程序读取；`TASK_CONTINUITY.md` 9.8 KB、
  `task_orchestration/README.md` 11.2 KB 可部分改为按动作读取）。这超出本派单的 B0 范围，建议另立后续任务，不在本任务做。

## 3. boot 三层（两个方案相同）

**目标：每个 unit 的“读什么”只写在它的 boot 清单里；`skills_v1.yml` 只保留 skill 元数据与角色矩阵。**

1. 8 个现有 boot 各加一个顶层键 `read_tiers`，`load_order` 与其他键原样不动：

   ```yaml
   read_tiers:            # 读取分层（Human 决定 2026-11-18）；generate_skills.py 读取；authority_effect: none
     startup: [<path>]
     on_action:
       - when: <何时读>
         reads: [<path>]
     program: [<path>]    # validator / runner 读；明确列出，不再按文件名猜
     optional: [<path>]   # 有则必读（目前只有领域 08）
   ```

   `.py` 路径仍视为入口程序，不分层。原来只写在 `skills_v1.yml` `reads` 里、boot 没列的路径（例如通讯的
   `接收方bootstrap_v1.md`、模型路由的 `协作伙伴.md`、上下文管理的 `方法论_v1.md`、workflow 各阶段 README）
   一并移入对应 boot 的 `read_tiers`。
2. 为 6 个没有 boot 的 unit 新建 boot 清单：`01_os/02_boot/os_entry/`（citystate-os，即 B0 分层本身）、
   `task_continuity/`（PRMS）、`task_discipline/`、`publication/`、`skills_and_tools/`、`domain_content/`，
   各只含 `启动清单_v1.yml`。注册到 `skills_v1.yml` entries，使 PRMS catalog 的 BOOT 条目保持 registered。
3. `skills_v1.yml`：删除各 unit 的 `reads` / `startup` / `on_action` / `optional_reads`，每个 unit 必须有 `boot`；
   保留 name、title、description、when、commands、boundaries、mechanism_id 与 roles。
4. `generate_skills.py`：从 boot 的 `read_tiers` 读分层；去掉 `is_program_path()` 猜测与 `B0_PATHS` 常量
   （B0 = `os_entry` boot 的 startup）。生成的 SKILL.md 结构不变。
5. `validate_skills.py`（经 `generate_skills.py --check`）新增 fail：unit 无 boot 或 boot 无 `read_tiers`；
   boot 点名的路径未进任何层；同一路径进了两层；`skills_v1.yml` 仍带读取键（第二来源）。原有的漂移、缺文件、
   未知 unit、未登记机制、输出根非 core-owned 检查保留。`test_skills.py` 补对应正例与负例。
6. 重新生成 `.agents/skills/` 与 `.claude/skills/`；更新 `01_os/02_boot/README.md`、`01_os/06_execution/skills/README.md`
   的说明。`CLAUDE.md` / `AGENTS.md` / `GEMINI.md` 的启动顺序文字（“Always read 01_os/README.md 与开发入口”）
   在两个方案下都仍然成立，不需要改；方案 B 只在开发入口里加细则指针。

这样直接从 `AGENTS.md` 进入 boot 清单的模型（Codex、Antigravity）也能在同一个文件里看到分层，R4 关闭。

## 4. 差异与边界

- **保留**：全部规则原文与节号；`load_order` 形状与内容；被 validator 检查的词；角色矩阵、命令、边界；
  PRMS `B0_PATHS`（只用于 core/domain 版本比对，不是加载清单，不改）。
- **修改**：B0 各文件（移出依据、方案 B 再移出细则与去重）；8 个 boot 加 `read_tiers`；6 个新 boot；
  `skills_v1.yml`；生成器、校验器与测试；生成的 skill 文件；两份 README。
- **不在范围**：改任何规则的语义；非 B0 机制文档调层（见 §2 方案 B 末段，建议后续任务）；领域仓库；hooks；
  master 集成（需 Human 在审核后另行确认）。
- **跨供应商影响**：Codex / Antigravity 仍从 `AGENTS.md` 进入，读取顺序不变；方案 B 下它们读到的开发入口更短，
  由节标题下的指针在动作点读细则。
