### 请求正文（整段发送）

我们在建一个人机协作工作流。链条是：
需求 A → 收集外部证据 → 由证据推出结果建模 B → **由证据生成测试** → 拆分步骤 → 执行。

本次要解决的是**测试生成**这一环，它有一条不寻常的规则：

> **测试由证据推导，不由 B 推导。**

理由是：从 B 生成的测试检验的是 B 的自洽性；当同一套推理产出 B 和它的测试时，
测试因构造而通过，什么也证明不了。证据是第三方——A 没写它，B 也没写它——
所以基于外部事实的测试**能够诚实地失败**。

请回答以下六个问题。**这是实现层调研，不是选型。**

#### 先说明我们认为相关的领域

请把检索覆盖到下面六个，但**不要局限于此**；你认为还有别的相关领域，请一并搜索并说明理由。

| 领域 | 我们认为它为什么相关 |
| :--- | :--- |
| 软件测试生成 | 属性测试、规格驱动测试、变异测试 |
| 验收测试驱动开发 / BDD | "先写验收标准再实现"与我们"测试先于步骤"同构 |
| **科学方法论 / 可证伪性** | "什么观察会推翻这个结论"——**这正是从证据推测试的原始形态** |
| 计量与评估方法论 | 指标效度、构念效度——一个测试有没有测到它声称测的东西 |
| 司法证据与鉴定标准 | Daubert / Mohan / Kelly-Frye 判"证据可采性"，借来判"测试可采性" |
| 事实核查自动化 | FactScore 之类原子级事实精确度，可能是"证据支撑度"的现成量法 |

**第三个领域是我们的赌注**，理由见第 1 问。

**若你认为其中某个领域其实不相关，请说明**——那也是有用信息。

**1. 现有的测试生成方法，是不是全都从"规格"生成？**

我们担心：属性测试、规格驱动测试、BDD 等等，其输入都是**规格**——
而在我们的链条里规格就是 B。若如此，"测试由证据推导"这条规则就无法落地。

**有没有从"证据 / 观察 / 事实"直接生成检验的既有做法？** 不限软件领域。
科学方法论里"什么观察会推翻这个假设"、
流行病学的"预先注册的检验"、
法庭的"什么证词会证伪这个说法"——这类都算。

**这是本轮最重要的一问。**

**2. 描述性的证据，如何转成规定性的测试？**

证据说"世界是这样"，测试说"应当如此"。这中间有没有可操作的转换方法？
还是说必然要引入一次人的判断？如果必然，那个判断具体是什么？

**3. 怎样让"每条测试可溯至一条证据"成为结构约束而非纪律？**

我们已在别处用 schema 校验强制"每条主张挂依据"。测试侧有类似做法吗？
需求可追溯性矩阵（RTM）、测试溯源、来源溯源（provenance）等方向都算。

**4. 判断"一条测试够不够格当验收依据"，有哪些标准？**

Daubert 的五要素（可测试性、同行评审、已知错误率、操作标准、普遍接受度）
原本判的是证据在法庭上的可采性。
**借来判测试的资格，是有效类比还是误用？** 有没有人做过这个类比？
其他领域（计量效度、构念效度）有没有更贴切的标准？

**5. "实现之前就能验证 B 的可行性"，在什么意义上成立？**

我们希望测试能在开发前就验证结果建模是否可行，而不只是在实现后验证正确性。
没有实现物时，测试测什么？
形式化验证、模型检验、可满足性检查、思想实验——哪些真的能在实现前给出信息？

**6. FactScore 一类的原子级事实精确度度量，怎么用？**

它衡量长文本中各原子声明被外部知识源支持的百分比。
**能否用来量化"B 的每条主张被证据支撑的程度"？** 需要什么前提？有什么已知失效？
